### Explanation — how the banner and version are produced

- **Banner assembly** *(inferred from source; the resulting banner is the observed
  capture above)*. The banner text is built in `the_banner` [`scapy/main.py:L628-L639`],
  a list of lines that includes the literal `"   | Welcome to Scapy"`
  [`scapy/main.py:L632`], the version line `"   | Version %s" % conf.version`
  [`scapy/main.py:L633`], the project URL [`scapy/main.py:L635`], and `"   | Have fun!"`
  [`scapy/main.py:L637`]; a randomly chosen quote is appended after that. The value
  substituted into the version line is `conf.version`, which is bound to Scapy's
  `VERSION` string: `config.py` imports it with `from scapy import VERSION`
  [`scapy/config.py:L22`] and exposes it as the read-only attribute
  `version = ReadOnlyAttribute("version", VERSION)` [`scapy/config.py:L726`].
- **Launcher chain** *(inferred from source; the launch itself was observed)*.
  `./run_scapy` sets `PYTHON` to `python3` when unset [`run_scapy:L5`] and then execs
  the module with the repo on the path:
  `PYTHONPATH=$DIR exec "$PYTHON" -m scapy` [`run_scapy:L13`]. Running the `scapy`
  package as a module executes `scapy/__main__.py`, which does
  `from scapy.main import interact` [`scapy/__main__.py:L13`] and then calls
  `interact()` [`scapy/__main__.py:L15`] (defined at [`scapy/main.py:L503`]). The same
  console entry point is declared for installed use as
  `scapy = "scapy.main:interact"` [`pyproject.toml:L47`].
- **Why the standard shell (not IPython).** IPython is an *optional* dependency —
  `cli = ["ipython"]` [`pyproject.toml:L50`] — and it is not installed here, so Scapy
  emits `WARNING: IPython not available. Using standard Python shell instead.` and
  falls back to the plain Python console (which is also why `AutoCompletion, History
  are disabled.`).
- **Startup notices actually observed.** `INFO: Can't import PyX.` (PyX is optional
  and absent), `INFO: No IPv6 support in kernel` (this container's kernel), and — with
  cryptography 43.0.0 present — two `CryptographyDeprecationWarning: TripleDES ...`
  lines. Those two warnings originate from the IPsec layer, which references the

  `TripleDES` but marks it deprecated (its removal is announced for cryptography
  `48.0.0`, as the warning text itself states). They are reproduced verbatim in the
  banner capture above and reported exactly as observed — not abbreviated or omitted.

### Explanation — WHY the version is `2026.07.14` (the crux)

The version is **not stored statically** — the packaging marks it `dynamic`
(`dynamic = ["version", "readme"]` [`pyproject.toml:L7`], resolved from
`attr="scapy.VERSION"` [`pyproject.toml:L78`]). It is **computed at import time** by
`_version()` [`scapy/__init__.py:L122-L166`] and bound as
`VERSION = __version__ = _version()` [`scapy/__init__.py:L169`]. `_version()` tries
four sources in order and, if all fail, falls back to the file's modification date
**(inferred from reading the function, then each branch proven below)**:

- **Method 0** — `os.environ['SCAPY_VERSION']` [`scapy/__init__.py:L131`]. Unset here:

  ```
  $ echo "SCAPY_VERSION=[${SCAPY_VERSION:-<unset>}]"
  SCAPY_VERSION=[<unset>]
  ```

- **Method 1** — read the packaged `scapy/VERSION` file [`scapy/__init__.py:L135-L143`].
  Absent in a git checkout (raises `FileNotFoundError`):

  ```
  $ ls scapy/VERSION
  ls: cannot access 'scapy/VERSION': No such file or directory
  ```

- **Method 2** — a git-archive substitution tag via `_version_from_git_archive()`
  (called at [`scapy/__init__.py:L147`], defined at [`scapy/__init__.py:L38-L56`]). In a
  live checkout the `$Format:...$` placeholder is left unsubstituted, so the function's
  guard `if "Format" in tstamp: raise ValueError('not a git archive')`
  [`scapy/__init__.py:L55-L56`] fires and the method raises `ValueError` **(inferred)**.

- **Method 3** — `_version_from_git_describe()` (called at [`scapy/__init__.py:L153`],
  defined at [`scapy/__init__.py:L72-L119`]). It does **not** run a bare
  `git describe --tags`. Its actual command chain begins with
  `git describe --tags --always --long` [`scapy/__init__.py:L114`]; because `--always`
  is passed, git falls back to the **abbreviated commit hash** instead of failing when
  no tags exist, so this command *succeeds* (exit 0):

  ```
  $ git describe --tags --always --long
  <current-HEAD-short-hash>
  ```

  *(Per transformation #3 in the Methodology, the value printed here is shown as a
  **marked placeholder**, not a literal: the real output is this checkout's current
  abbreviated `HEAD` commit hash, which differs per checkout — and, being the hash of the
  very commit that records this file, cannot be hard-coded because a commit cannot embed
  its own hash inside a file it commits (the same reason O6 avoids naming a commit). The
  stable, reproducible fact — independent of the exact hash — is that the command returns
  a bare commit hash with **no** `v` prefix.)*

  That result does not start with `"v"` [`scapy/__init__.py:L115`], so the function
  next runs `git rev-list --tags --max-count=1` [`scapy/__init__.py:L117`] and then
  describes once more [`scapy/__init__.py:L118`]. That `rev-list` command produces **no
  output** — there are no tags in this checkout — which is shown below as an
  immediately-returning shell prompt (Methodology transformation #2):

  ```
  $ git rev-list --tags --max-count=1
  $
  ```

  Finally the resulting tag is passed to `_parse_tag(tag)` [`scapy/__init__.py:L119`],
  whose regex `^v?(.+?)-(\d+)-g[a-f0-9]+$` [`scapy/__init__.py:L30`] does not match a
  bare commit hash, so `_parse_tag` **raises `ValueError('tag has invalid format')`**
  [`scapy/__init__.py:L35`]. Confirmed by invoking the resolver directly:

  ```
  $ PYTHONPATH=. python3 -c "import scapy; scapy._version_from_git_describe()"
  Traceback (most recent call last):
    File "<string>", line 1, in <module>
      import scapy; scapy._version_from_git_describe()
                    ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~^^
    File "/tmp/blitzy/scapy/blitzy-37139374-2987-4b74-83fd-7a234a49bd85_dbd14b/scapy/__init__.py", line 119, in _version_from_git_describe
      return _parse_tag(tag)
    File "/tmp/blitzy/scapy/blitzy-37139374-2987-4b74-83fd-7a234a49bd85_dbd14b/scapy/__init__.py", line 35, in _parse_tag
      raise ValueError('tag has invalid format')
  ValueError: tag has invalid format
  ```

  `_version()` catches that exception with a broad `except Exception` at
  [`scapy/__init__.py:L154`] and proceeds to the fallback. (So the earlier document's
  claim of a bare `git describe --tags` → `fatal: No names found` was inaccurate: with
  `--always`, git returns the commit hash and the real failure is the `ValueError`
  above.)

- **Fallback** — the modification time of `scapy/__init__.py`, formatted `%Y.%m.%d`:
  `datetime...utcfromtimestamp(os.path.getmtime(__file__))` [`scapy/__init__.py:L160`]
  then `.strftime('%Y.%m.%d')` [`scapy/__init__.py:L161`]. Proven to equal the reported
  version:

  ```
  $ PYTHONPATH=. python3 -c "import os,datetime; print(datetime.datetime.utcfromtimestamp(os.path.getmtime('scapy/__init__.py')).strftime('%Y.%m.%d'))" 2>/dev/null
  2026.07.14
  ```

  *(The trailing `2>/dev/null` is shown in the command itself: replicating
  `scapy/__init__.py:L160`'s `datetime.datetime.utcfromtimestamp(...)` **directly in
  `__main__`** surfaces a Python 3.13 `DeprecationWarning` on stderr for that call —
  whereas Scapy's own invocation of the same line does **not** print it, because
  Python's default warning filter shows `DeprecationWarning` only for code triggered in
  `__main__`. Discarding stderr here isolates the stdout value; the value is unaffected
  and matches the reported version.)*

So **`2026.07.14` is the modification-date fallback — a date-shaped string, not a
semantic release tag.** (Corroborating outside context, used only as background and
**not** as the basis for any claim above: this commit post-dates the Scapy **2.5.0**
release — published 25 December 2022 per the project's release page,
`https://github.com/secdev/scapy/releases/tag/v2.5.0` — and pre-dates **2.6.0**
(released 2024, `https://github.com/secdev/scapy/releases/tag/v2.6.0`). A tag-derived
version at this commit would therefore look like a `2.5.0.dev*` development string,
never a calendar date, which is consistent with the mtime fallback being taken. The
runtime observations above remain the authoritative basis.)

### What `show()` shows, and why `show2()` differs

`.show()` prints the packet **as authored** — it renders the fields with their
current in-memory values via `show` [`scapy/packet.py:L1459`], which returns
`_show_or_dump(...)` at [`scapy/packet.py:L1471`]; that helper is itself defined at
[`scapy/packet.py:L1383`].
Because the auto-computed fields have not been serialized yet, `ihl`, `len`, and the
two `chksum` fields display **`None`**.

`.show2()` instead renders an **assembled** copy: it re-dissects the serialized bytes
via `self.__class__(raw(self)).show(...)` — `show2` is defined at
[`scapy/packet.py:L1473`] and the re-dissection expression is at
[`scapy/packet.py:L1486`]. Serialization runs the build pipeline (see O4), so the same
view now shows the **computed** values: `ihl = 5`, `len = 28`, IP `chksum = 0x7cde`,
and ICMP `chksum = 0xf7ff`. These exactly match the serialized bytes in
`raw(p).hex()` above: `45` = version 4 / IHL 5, `00 1c` = total length 28,
`40` = TTL 64, `01` = protocol 1 (ICMP), `7cde` = IP checksum, `7f 00 00 01` twice =
source and destination `127.0.0.1`, then `08` = ICMP type 8 (echo-request), `00` = code,
`f7ff` = ICMP checksum.

A useful nuance visible above: `src` already shows `127.0.0.1` in **`.show()`** (the
`SourceIPField` resolves it from the routing table at display time — see O4), whereas
`ihl` / `len` / `chksum` remain `None` until serialization. So not every field behaves
the same at display time.

### ICMP defaults (for completeness)

The ICMP layer's defaults come from `ICMP.fields_desc` [`scapy/layers/inet.py:L954-L977`]:
`type` is `ByteEnumField("type", 8, icmptypes)` [`scapy/layers/inet.py:L954`] — value
`8` renders as `echo-request` — and `code` is a `MultiEnumField` defaulting to `0`
[`scapy/layers/inet.py:L955`]. The `id` and `seq` entries **are** `ConditionalField`s
[`scapy/layers/inet.py:L957`, `scapy/layers/inet.py:L958`], each displayed only when
`pkt.type in icmp_id_seq_types` (which includes the echo type `8`), so both appear here
as `0x0`. The `unused` entry, however, is **not** a `ConditionalField`: it is a
**`MultipleTypeField`** [`scapy/layers/inet.py:L968-L976`] that selects a `ShortField`
when `pkt.type in [11, 12]` or an `IntField` for a set of other types, and otherwise
uses the **fallback** `StrFixedLenField("unused", "", length=0)`
[`scapy/layers/inet.py:L976`]. For an echo-request (`type=8`) neither typed variant
applies, so the zero-length fallback is chosen — which is precisely why `unused`
renders as the empty string `''` above. ICMP `chksum` is declared
`XShortField("chksum", None)` [`scapy/layers/inet.py:L956`] and is computed in
`ICMP.post_build` [`scapy/layers/inet.py:L979-L984`] (the `checksum(p)` call at
[`scapy/layers/inet.py:L981-L983`]): `None` in `.show()` and `0xf7ff` in `.show2()`,
exactly like the IP checksum. *(The field-type facts here are inferred from reading
`ICMP.fields_desc`; the rendered values `id=0x0`, `seq=0x0`, `unused=''` are observed
in the capture above.)*

### What happens at the network layer, step by step

1. **Route resolution.** `conf.route.route("127.0.0.1")` returns
   `('lo', '127.0.0.1', '0.0.0.0')` — destination `127.0.0.1` routes over the loopback
   interface `lo` with source address `127.0.0.1` and no gateway. The routing table is
   the `Route` class [`scapy/route.py:L31`] and this lookup is its `route()` method
   [`scapy/route.py:L146`].
2. **Socket selection.** `sr1()` [`scapy/sendrecv.py:L656`] delegates to `sr()`
   [`scapy/sendrecv.py:L635`], which opens the Layer-3 socket from the configured
   factory `conf.L3socket(...)` [`scapy/sendrecv.py:L648`] and hands the send/receive +
   answer-matching to `sndrcv` [`scapy/sendrecv.py:L650`]. `sr1` returns only the first
   matched answer — `ans[0][1]` [`scapy/sendrecv.py:L663`] — or `None`
   [`scapy/sendrecv.py:L664`]. The "`Received … got … answers …`" line is printed
   because the default verbosity is `conf.verb = 2` [`scapy/config.py:L759`].
3. **Transmit → wait → match.** For each socket the sequence observed is: build the
   packet → route over `lo` → open the L3 socket → transmit 1 packet
   ("Finished sending 1 packets.") → wait up to the timeout → match replies to the
   request.

### The crux (Observed): default socket gets no matched answer; raw socket gets one

- With the **default** `conf.L3socket = L3PacketSocket` — set for Linux at
  [`scapy/config.py:L647`] and defined at [`scapy/arch/linux.py:L587`] as a subclass of
  `L2Socket` [`scapy/arch/linux.py:L475`] that "read/write packets at layer 3 using
  Linux PF_PACKET sockets" [`scapy/arch/linux.py:L588`] — the packet is transmitted but
  **0 answers are matched** on `lo` ("Received 1 packets, got 0 answers, remaining 1
  packets"), so `sr1(...)` returns **`None`**.
- Switching to `conf.L3socket = L3RawSocket` (the class is defined at
  [`scapy/supersocket.py:L283`]) yields **1 matched answer** — an ICMP **`echo-reply`**
  (`type=echo-reply`, i.e. type `0`) from `127.0.0.1`, whose `summary()` is
  `IP / ICMP 127.0.0.1 > 127.0.0.1 echo-reply 0`.

**Why the two sockets differ (inferred from the socket definitions).** `L3RawSocket`
**transmits** through a `PF_INET`/`SOCK_RAW` socket with `IP_HDRINCL` set
(`self.outs = socket(AF_INET, SOCK_RAW, IPPROTO_RAW)` [`scapy/supersocket.py:L294`], the
`IP_HDRINCL` option at [`scapy/supersocket.py:L295`]) and **receives** through a
`PF_PACKET`/`SOCK_RAW` socket (`self.ins = socket(AF_PACKET, SOCK_RAW, ...)`
[`scapy/supersocket.py:L296`]); its class description is literally
`"Layer 3 using Raw sockets (PF_INET/SOCK_RAW)"` [`scapy/supersocket.py:L284`].
`L3PacketSocket`, by contrast, sends and receives through Linux `PF_PACKET` sockets
(it inherits the `PF_PACKET`/`SOCK_RAW` `ins` from `L2Socket` [class at
`scapy/arch/linux.py:L475`; the `ins` socket is created at
`scapy/arch/linux.py:L490-L491`]). On loopback, transmitting via the `PF_INET`/`SOCK_RAW`
path is what lets Scapy **match** the kernel's echo-reply to the request, whereas the
default `PF_PACKET` transmit path yields **no matched answer** here.

**Scope of the claim (per Rule 3).** The precise, observed difference is in Scapy's
**answer matching**: the default `L3PacketSocket` produced **0 matched answers**
(`sr1` → `None`) while `L3RawSocket` produced **1 matched answer** (the `echo-reply`).
This is stated exactly as the "got 0 answers" vs "got 1 answers" counts captured above;
it is **not** a claim that the kernel never loops the packet back on `lo`.

**Note on `scapy/config.py:L672`.** That line sets `conf.L3socket = L3RawSocket` only
in the **non-Linux `else` branch** [`scapy/config.py:L669-L673`]; it is **not** the
Linux default (Linux uses `L3PacketSocket` at [`scapy/config.py:L647`]) and it is not
where `L3RawSocket` is defined (that is [`scapy/supersocket.py:L283`]). On this Linux
host the raw socket was selected only because the observation script explicitly assigned
`conf.L3socket = L3RawSocket`. To avoid leaving that global mutated, the script saves the
original factory (`original = conf.L3socket`), performs the raw-socket send inside a
`try`/`finally`, and restores it in the `finally` block; the final
`restored conf.L3socket = L3PacketSocket` line in the capture confirms the default was
put back (this matters only because `conf` is process-global state — the script itself
runs in an ephemeral subprocess, so nothing leaks into the repository or a later run
regardless).

**Outside context (authoritative attribution; background only).** This commit predates
Scapy **2.6.0**, whose release notes introduce automatic use of a raw socket on the
loopback interface on Linux (release page:
`https://github.com/secdev/scapy/releases/tag/v2.6.0`; and the Scapy troubleshooting
guide, `https://scapy.readthedocs.io/en/latest/troubleshooting.html`, documents using a
`PF_INET/SOCK_RAW` socket instead of `PF_PACKET/SOCK_RAW` to reach local IPv4
applications on loopback). That automation is **absent** at this pre-2.6.0 commit, which
is consistent with the observed need to switch sockets manually. The runtime capture
above remains the authoritative basis; Scapy's request/reply pairing internals
(`answers`/`hashret`) are **(inferred)** from the design and were not separately
instrumented.

### 1. Field defaults are declared on the `IP` class

`IP.fields_desc` [`scapy/layers/inet.py:L524-L537`] declares the header fields with
literal defaults — `version=4` [`scapy/layers/inet.py:L524`], `tos=0`
[`scapy/layers/inet.py:L526`], `id=1` [`scapy/layers/inet.py:L528`], `ttl=64`
[`scapy/layers/inet.py:L531`], `proto=0` [`scapy/layers/inet.py:L532`] — and leaves
`ihl` [`scapy/layers/inet.py:L525`], `len` [`scapy/layers/inet.py:L527`], and `chksum`
[`scapy/layers/inet.py:L533`] as **`None`**, which act as "compute-me-later" sentinels.
`src` is a `SourceIPField` [`scapy/layers/inet.py:L535`] and `dst` a `DestIPField` with
literal default `127.0.0.1` [`scapy/layers/inet.py:L536`]. *(Field declarations
inferred from reading `IP.fields_desc`.)* **Observed** that the three sentinels are
`None` before serialization: `pre-build ihl/len/chksum: None None None` (capture above).

### 2. The generic build pipeline

Serialization is a fixed pipeline **(inferred from reading the call chain)**:
`build()` [`scapy/packet.py:L746`] calls `do_build()` (invoked at
[`scapy/packet.py:L753`]; defined at [`scapy/packet.py:L724`]), which calls
`self_build()` to serialize the declared fields (invoked at [`scapy/packet.py:L733`];
defined at [`scapy/packet.py:L678`]) and then invokes `post_build(pkt, pay)` (at
[`scapy/packet.py:L738`]). The **base** `post_build` [`scapy/packet.py:L758-L767`]
simply returns `pkt + pay` unchanged [`scapy/packet.py:L767`] — so, by default, a layer
performs **no** auto-computation.

### 3. `IP` overrides `post_build` to fill the sentinels

`IP.post_build` [`scapy/layers/inet.py:L539-L551`] is where the `None` placeholders
become real values at serialization time: `ihl = len(p) // 4` when `ihl is None`
[`scapy/layers/inet.py:L542-L544`]; `len = len(p) + len(pay)` when `len is None`
[`scapy/layers/inet.py:L545-L547`]; and `chksum = checksum(p)` when `chksum is None`
[`scapy/layers/inet.py:L548-L550`]. **This is exactly why** `.show()` shows `None`
while `.show2()` / `raw()` show `ihl=5`, `len=28`, `chksum=0x7cde` (tie back to the O2
captures). *(Mechanism inferred from reading `IP.post_build`; the resulting values are
observed in the O2 captures.)*

### 4. Protocol number comes from a layer binding, not a hard-coded IP default

The IP `proto` default is literally `0` [`scapy/layers/inet.py:L532`], **Observed** as
`IP().proto = 0`. The value `1` (ICMP) is supplied by a *binding*:
`bind_layers(IP, ICMP, frag=0, proto=1)` [`scapy/layers/inet.py:L1112`] registers the
overload `{IP: {'frag': 0, 'proto': 1}}` on the ICMP class, **Observed** as
`ICMP().overload_fields = {<class 'scapy.layers.inet.IP'>: {'frag': 0, 'proto': 1}}`.
When `IP()/ICMP()` stacks the layers, `add_payload` [`scapy/packet.py:L360-L377`] walks
the underlayer's alias types [`scapy/packet.py:L370`] and, finding the IP entry in the
payload's `overload_fields` [`scapy/packet.py:L371`], copies it into the IP layer's
`overloaded_fields` [`scapy/packet.py:L372`]. The net effect is that IP `proto` becomes
`1`, **Observed** as `(IP()/ICMP()).proto = 1` (rendered `icmp`). So the transition from
`0` to `1` is caused by stacking ICMP onto IP, not by any IP default.

### 5. Source address is resolved from the routing table

`src` is a `SourceIPField` [`scapy/fields.py:L854`]. When it is left unset, it resolves
to the source address the routing table associates with the destination:
`return conf.route.route(dst)[1]` [`scapy/fields.py:L877`]. For the default destination
`dst = "127.0.0.1"` (the `DestIPField` default [`scapy/layers/inet.py:L503`, used at
`L536`]) — **Observed** `IP().dst = 127.0.0.1` — this yields `127.0.0.1`, **Observed**
as `route(127.0.0.1)[1] = 127.0.0.1`. That is why `src` already displays `127.0.0.1`
even in `.show()`, before serialization.

**Summary of cause → effect.** Declaring the class fixes literal defaults and marks
`ihl`/`len`/`chksum` as `None`; stacking a bound payload rewrites `proto` (and `frag`)
via the overload mechanism; leaving `src` unset triggers a routing lookup at access
time; and serialization runs `IP.post_build`, which turns the three `None` sentinels
into the computed `ihl`, `len`, and `chksum` seen in `.show2()` and the raw bytes.

### Why "193" `.uts` files but only "190" campaigns

There are **193** `.uts` files on disk, but the canonical config runs **190**:

```
$ find test -name '*.uts' | wc -l
193
```

The reconciliation is deterministic and follows the config's globbing rules:

- The `testfiles` globs [`test/configs/linux.utsc:L2-L14`] match **192** unique files.
  The only on-disk `.uts` **not** matched is `test/scapy/automaton.uts`, because the
  config globs `test/scapy/layers/*.uts` [`test/configs/linux.utsc:L4`] but **not**
  `test/scapy/*.uts`  →  −1.
- `remove_testfiles` [`test/configs/linux.utsc:L16-L19`] then drops `test/windows.uts`
  and `test/bpf.uts`  →  −2.
- 192 − 2 = **190 campaigns**, confirmed by the runner loading exactly 190 `━ Loading:`
  markers and by replicating the glob in Python:

```
$ python3 - <<'PY'
import glob, json
cfg = json.load(open("test/configs/linux.utsc"))
matched = sorted({f for pat in cfg["testfiles"] for f in glob.glob(pat)})
final = [f for f in matched if f not in set(cfg["remove_testfiles"])]
allu = sorted(glob.glob("test/**/*.uts", recursive=True))
print("on disk:", len(allu), "| matched:", len(matched), "| final campaigns:", len(final))
print("on disk but NOT matched:", sorted(set(allu) - set(matched)))
PY
on disk: 193 | matched: 192 | final campaigns: 190
on disk but NOT matched: ['test/scapy/automaton.uts']
```
