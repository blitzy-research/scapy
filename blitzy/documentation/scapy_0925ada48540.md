# How Scapy Matches a Returning ICMP *Destination-Unreachable* Error to the Original ICMP *Echo-Request*

**Repository:** Scapy checkout at branch `scapy_0925ada48540` (HEAD `0925ada4`)
**Task type:** Read-only, runtime-grounded investigation. The only persistent artifact is this document; no source file was modified.

## Summary (one-paragraph answer)

When Scapy sends an ICMP echo-request to an unreachable host and an ICMP *destination-unreachable* error comes back, it does **not** compare the two packets by eye or by a single field. Instead it **re-dissects the returning error from its wire bytes**, auto-decoding the copy of the original datagram carried in the ICMP payload into dedicated `IPerror`/`ICMPerror` (and, for transport payloads, `TCPerror`/`UDPerror`) sub-layers, and then confirms the match through a **two-stage `hashret()` → `answers()` path**. Stage one is a fast hash-bucket pre-filter: the receive loop computes `r.hashret()` and looks it up in the dictionary of hashes registered for sent packets. For an ICMP error, `IP.hashret()` delegates to the *embedded original* (`self.payload.payload.hashret()`), so the error hashes to the **same bytes** as the request that elicited it. Stage two is the authoritative field comparison: `IP.answers()` delegates into the embedded `IPerror.answers()`, which compares source, destination, IP-id, and protocol (and recurses into the transport `*error` layer). A candidate is accepted as an answer only if it passes **both** stages. Because neither stage inspects TTL or checksum, ordinary in-flight mutation of those fields cannot break matching; several comparisons are gated by `conf` toggles (`checkIPsrc`, `checkIPID`, `check_TCPerror_seqack`) that trade strictness against tolerance of real-world network variation; and RFC 4884 extension parsing (loaded on demand via `load_contrib('icmp_extensions')`) changes the *dissected structure* of an oversized error without changing whether it is considered a valid match.

- The embedded original is auto-decoded because `ICMP.guess_payload_class` returns `IPerror` for `type in [3, 4, 5, 11, 12]` [`scapy/layers/inet.py:1000-1006`; `return IPerror` at `:1002`].

- Base delegation: `Packet.answers` recurses into payloads only when `other.__class__ == self.__class__` [`scapy/packet.py:1221-1226`].

**(f) Cause → effect.** The error packet, once re-dissected from wire bytes, carries the original datagram as decoded `IPerror`/`ICMPerror` layers. The driver first buckets the candidate by `hashret()` (cheap), and only for candidates in an occupied bucket does it run the authoritative `answers()` field comparison. Because both the request's and the error's hash reduce to the *embedded original's* hash, the error lands in the request's bucket; `answers()` then walks the embedded citation and confirms the field-level match — so the returned error is recorded as the answer to the echo-request.

- **The mechanism is not a general-purpose digest** — it is a purpose-built byte string assembled by `IP.hashret` and `ICMP.hashret`, designed so a request and its answer produce the same value (`Packet.hashret` docstring: *"returns a string that has the same value for a request and its answer"* [`scapy/packet.py:1215-1219`]).
- **Request (non-error) path:** `IP.hashret` returns `strxor(inet_pton(socket.AF_INET, self.src), inet_pton(socket.AF_INET, self.dst)) + struct.pack("B", self.proto) + self.payload.hashret()` [`scapy/layers/inet.py:577-580`], gated by `if conf.checkIPsrc and conf.checkIPaddr:` [`:577`].
- **ICMP-error path:** `IP.hashret` short-circuits to `return self.payload.payload.hashret()` when `self.proto == socket.IPPROTO_ICMP` and `self.payload.type in [3, 4, 5, 11, 12]` [`scapy/layers/inet.py:568-572`] — i.e. it hashes the **embedded original**.
- **Trailing 4 bytes:** `ICMP.hashret` returns `struct.pack("HH", self.id, self.seq) + self.payload.hashret()` when `self.type in icmp_id_seq_types` [`scapy/layers/inet.py:986-989`; `icmp_id_seq_types = [0, 8, 13, 14, 15, 16, 17, 18, 37, 38]` at `:949`]. For the echo-request here `id = 0, seq = 0` → `\x00\x00\x00\x00`.
- **Base delegation:** `Packet.hashret` returns `self.payload.hashret()` [`scapy/packet.py:1215-1219`].

**(f) Cause → effect.** The exact value observed is `02e40ebd0100000000`, decomposing as `strxor(src, dst)` = `02e40ebd` (the 4-byte term `0x0AEC06B5 ^ 0x08080808`), then `proto` = `01` (ICMP), then `ICMP.hashret()` = `00000000` (`id=0, seq=0`). Two properties make request and error hash identically:
  1. The `src ⊕ dst` term is **order-independent** (XOR is symmetric), so a packet and its reversed-address reply produce the same 4 bytes.
  2. For the ICMP error, `IP.hashret` does not hash the *error's* own addresses at all — it delegates to the embedded original, which reconstructs the request's exact bytes.
  Hence the error is deposited into the same hash bucket as the request. **The IP `id` (`0x1234`) does not appear in the hash** — only `src ⊕ dst`, `proto`, and the ICMP `id`/`seq` do.

**(g) Observed vs inferred.**
- **Observed:** `orig.hashret()` and `err.hashret()` are byte-identical (`b'\x02\xe4\x0e\xbd\x01\x00\x00\x00\x00'`, hex `02e40ebd0100000000`); the decode script reassembles that exact value from `strxor(src,dst)[4B] + proto[1B] + ICMP.hashret()[4B]`; the IP id is absent from the bytes.
- **Inferred (from code):** the *reason* the two hashes coincide — the order-independence of `strxor` and the error path's delegation to the embedded original — is read from `IP.hashret` [`scapy/layers/inet.py:568-581`]. The byte-identity itself is observed.
- **Environment note:** the first four bytes (`02e40ebd`) depend on the routed source IP; on another host they differ (the Docker cross-check produced `a419080a0100000000`). The invariant — request hash equals error hash — is what holds universally.

**(f) Cause → effect.** Loading the extension parser **changes the dissected packet structure** — the identical oversized wire dissects to `IP / ICMP / IPerror / ICMPerror / Padding` before loading (the RFC-4884 tail is unparsed padding) and to `… / Padding / ICMPExtensionHeader / ICMPExtensionMPLS` after loading (the tail is now parsed into extension layers). It does **not** change whether the response is a valid match: `err.answers(orig) = 1` **both before and after**. The reason is that `ICMPExtension_post_dissection` only re-splits the trailing **padding**; it never touches the `IPerror`/`ICMPerror` citation fields that `answers()` compares. The checksum nuance explains why a *correct* RFC-4884 packet is required to trigger the parser: scapy's own multi-object builder emits `2000dfff…` (checksum computed over the header alone), whose whole-structure checksum is `65274` (non-zero) and is therefore **rejected** at `:94`; the RFC-correct whole-structure checksum `2000defa…` verifies to `0` and is **accepted**, so the extension attaches.

**Background (external corroboration, not a runtime observation).** RFC 4884 ("Extended ICMP to Support Multi-Part Messages", April 2007) appends the Extension Structure to ICMP types 3/11/12, requires the "original datagram" field to be at least 128 octets zero-padded to a 32-bit boundary, and records the original length in a formerly-reserved octet (in 32-bit words).

**Precise length semantics in Scapy's parser (avoid conflating three distinct lengths).** The implementation does **not** key on "the ICMP length being 144." It gates on the **outer IPv4 total-length** field — `pkt.len > 144` [`scapy/contrib/icmp_extensions.py:78`], where `pkt` is the whole IP packet — and only then slices the extension from **offset 136 of the *built ICMP message*** — `bytes = pkt[ICMP].build()[136:]` [`:79`], i.e. 8-byte ICMP header + 128-byte citation. In the exercised packet the three lengths are all different and all observed above:

  - **outer IPv4 total length** `IP.len = 164` — this is the value compared against `144` at `:78`;
  - **ICMP message byte-length** `= 144` (8-byte ICMP header + 128-byte citation + 8-byte extension), which is what the byte-136 slice indexes into;
  - **RFC 4884 minimum citation** `= 128` octets — the "original datagram" field length the RFC mandates, which fixes the 136 slice offset (8 + 128).

So the `144` in the code is an **outer-IP-length gate**, not the ICMP length; the `136` is an **offset inside the built ICMP message**; and the `128` is the **RFC-mandated citation minimum**. (The in-source comment at `:67-68` loosely calls `pkt.len` "the ICMP packet length" and says "byte 137," but the executed code uses the outer IP `len` field and offset `136`.)
