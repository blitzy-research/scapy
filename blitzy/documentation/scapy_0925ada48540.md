# Scapy Ethernet framing: minimum-frame padding & EtherType next-layer selection

> **A runtime-observed Q&A** answering, from **executed evidence**, two closely-related Scapy behaviors:
>
> 1. **Whether and *where* Ethernet minimum-frame padding is applied.**
> 2. **How the *next protocol layer* is selected from the Ethernet `type` (EtherType) field, including handling of *unrecognized* EtherTypes.**
>
> Every behavioral claim below is paired with the **actual, complete, unedited runtime output** that produced it (the command **and** its output) plus a precise `file:line` citation naming the specific function/method. This is a **read-only investigation** — no Scapy source file was modified; the only file created is this document.

---

## TL;DR — direct answers

| # | Question | Direct answer |
|---|----------|---------------|
| **Q1** | Build 3 packets in memory and capture `.show()`, `hexdump()`, `len(raw(pkt))`. | Built via the `/` operator; they serialize to fixed, **un-padded** lengths: `Ether()/IP()/TCP()` → **54 B**, `…/Raw(10 B)` → **64 B**, `Ether(type=0x9000)/Raw("HELLOPAYLOAD")` → **26 B**. |
| **Q2** | Does Scapy auto-pad a short frame during in-memory serialization? | **No.** `raw(pkt)` / `bytes(pkt)` never pad to the Ethernet minimum. Even the "normal" `Ether()/IP()/TCP()` is only **54 B** (< 60) and is left un-padded. |
| **Q3** | What happens to padding on round-trip `Ether(raw(pkt))`? | A clean short packet round-trips **byte-for-byte with NO `Padding`/`Raw` layer**. Padding only appears when the wire frame actually carries trailing bytes (e.g., a NIC-padded frame), which re-dissect into a **`Padding`** layer. |
| **Q4** | What does Scapy display after Ethernet for an unrecognized EtherType? | A single **`###[ Raw ]###`** layer — **no error, no guess**. `type` prints numerically (`0x9000`). |
| **Q5** | At what payload size does padding behavior change? | **None** — a payload sweep of `{0,1,2,4,6,10,20}` shows serialized length grows **one-for-one** with payload, with **no floor** at 60. The threshold constant `conf.min_pkt_size = 60` is *never* consulted during build. (Sweep **stable across 2 identical runs**.) |
| **Q6** | *Where* is the padding decision made, and *how* is the next protocol resolved? | Padding lives **only in the OS send path** (`scapy/arch/linux.py`), **not** the build path — **INFERRED-FROM-CODE** (needs a raw socket + kernel `EINVAL`, not reproducible here). Next-protocol resolution is driven by the `bind_layers()` table consulted by `guess_payload_class()`. |
| **Q7** | What is the fallback for an unrecognized EtherType? | `guess_payload_class()` finds no binding → `default_payload_class()` returns `conf.raw_layer` (i.e., **`Raw`**). |

> **⭐ KEY FINDING (answers the user's "0x9000 or something random"):** `0x9000` is **NOT random** — it is Scapy's own **DEFAULT** EtherType value, hard-coded at `scapy/layers/l2.py:248` as `XShortEnumField("type", 0x9000, ETHER_TYPES)`. It is a *legitimate-but-unregistered* value (absent from the `ETHER_TYPES` table), which is exactly why it falls through to `Raw`.

## Section 2 — The three built packets (Q1)

**Direct answer:** all three packets are built **in memory** via the `/` operator and serialize to fixed, **un-padded** lengths — **54**, **64**, and **26** bytes respectively.

**How the `/` composition and serialization work (cited):**
- The `/` operator is `Packet.__div__` at `scapy/packet.py:596`, aliased for Python 3 as `__truediv__ = __div__` at `scapy/packet.py:607` (Python 3's `a / b` dispatches to `__truediv__`). It stacks the right-hand layer as the payload of the left-hand layer.
- The `Ether` class is defined at `scapy/layers/l2.py:244` (`class Ether(Packet):`).
- `raw(pkt)` is `scapy/compat.py:112` (`def raw(x):`), whose body is simply `return bytes(x)` at `scapy/compat.py:118` — i.e. `raw()` == `bytes()`, which drives `Packet.build()`.

**On the `type` rendering:** `Ether.type` is an `XShortEnumField` (`scapy/layers/l2.py:248`). `.show()` renders it as the **name** when the value is present in `ETHER_TYPES` (so `p1` shows `type = IPv4` for `0x0800`) and **numerically** when it is absent (so `p3` shows `type = 0x9000`). This matches the banner check `0x0800 in? True` / `0x9000 in ETHER_TYPES? False`.

## Section 3 — Are short frames auto-padded during build? (Q2) + payload-size sweep (Q5)

**Direct answer to Q2: NO.** `raw(pkt)` / `bytes(pkt)` do **not** pad a short frame up to the Ethernet minimum during in-memory serialization. Even the "normal" `Ether()/IP()/TCP()` is only **54 bytes** — already below the 60-byte `conf.min_pkt_size` — and Scapy leaves it un-padded.

Observed (from `obs_scapy.py`):

```text
=== Q1b/Q2: short 10-byte payload ===
len(raw)= 64
no-payload Ether/IP/TCP len(raw)= 54 (< 60 => True )
```

The `Ether()/IP()/TCP()` frame is 54 bytes and `54 < 60` is `True`, yet `len(raw(...))` is exactly 54 — no floor is applied.

### 3.1 Q5 — payload-size sweep (proves there is no in-memory padding floor)

**Direct answer to Q5: there is no size at which build-time padding "kicks in."** Sweeping payload sizes `{0, 1, 2, 4, 6, 10, 20}`, the total serialized length grows **one-for-one** with the payload — no jump, no floor at 60.

Observed sweep (`obs_scapy.py`):

```text
=== Q5: payload-size sweep ===
  raw payload=  0 -> total raw bytes = 54
  raw payload=  1 -> total raw bytes = 55
  raw payload=  2 -> total raw bytes = 56
  raw payload=  4 -> total raw bytes = 58
  raw payload=  6 -> total raw bytes = 60
  raw payload= 10 -> total raw bytes = 64
  raw payload= 20 -> total raw bytes = 74
```

Every step is `54 + payload` exactly (`0→54`, `6→60`, `10→64`, `20→74`). Crucially, the `6→60` and `10→64` rows straddle the 60-byte threshold with **no discontinuity**: if `raw()` padded to `conf.min_pkt_size`, every row below 6 would floor at 60 — it does not.

**Stability (magnitude rigor):** the sweep was run **twice** with the canonical invocation and the two outputs are **byte-for-byte identical** (`diff run1.txt run2.txt` is empty; both files are 1307 bytes). The swept sizes were `{0,1,2,4,6,10,20}`. It was additionally reproduced identically on native Python 3.13.7 (§1.3).

### 3.2 Why there is no build-time padding (mechanism, cited)

The build path simply serializes each layer and appends only **stored** trailing padding — there is **no minimum-frame logic** anywhere in it:

- `Packet.build()` at `scapy/packet.py:746-758` does `p = self.do_build()` then `p += self.build_padding()` then `p = self.build_done(p)` and returns `p`.
- `Packet.build_padding()` at `scapy/packet.py:742-744` is `return self.payload.build_padding()` — it recursively collects only whatever padding the payload layers already *hold*; a freshly-built packet holds none. There is no reference to `conf.min_pkt_size` here.

The threshold constant `conf.min_pkt_size = 60` (`scapy/config.py:778`) is therefore **never consulted during build** — its only consumers are on the OS send path (see §7), which is why in-memory serialization tracks the payload one-for-one.

## Section 4 — Round-trip `Raw`-vs-`Padding` state transition (Q3)

**Direct answer:** a clean short packet round-tripped through `Ether(raw(pkt))` is preserved **byte-for-byte with NO `Padding` and NO `Raw` layer**. Padding only appears when the wire bytes *actually carry* trailing bytes beyond what the upper layer declares (e.g., a NIC-padded frame) — and those residual bytes re-dissect into a **`Padding`** layer, not `Raw`.

This is a stateful behavior, so it is observed **before** (clean round-trip) and **after** (wire-padded frame).

### 4.1 BEFORE — clean round-trip preserves bytes, no extra layer

Observed (`obs_scapy.py`), `rt = Ether(raw(Ether()/IP()/TCP()))`:

```text
=== Q3: round-trip clean short packet ===
round-trip len = 54
round-trip layers: ['Ether', 'IP', 'TCP']
has Padding layer?  0
has Raw layer?  0
```

54 bytes in, 54 bytes out, identical layer stack `['Ether','IP','TCP']`, and neither `haslayer(Padding)` nor `haslayer(Raw)` is set. Because the IP total-length field exactly accounts for all bytes after the IP header, there are **no residual bytes**, so nothing is wrapped.

### 4.2 AFTER — a wire-padded 60-byte frame re-dissects into a `Padding` layer

To simulate what a NIC emits on the wire (padding a runt frame up to the minimum), 6 zero bytes are appended to the 54-byte clean frame (`wire = raw(clean) + b"\x00"*6`, total 60) and re-dissected:

```text
=== Q3 contrast: simulate NIC-padded 60-byte wire frame ===
re-dissected layers: ['Ether', 'IP', 'TCP', 'Padding']
haslayer(Padding)= True
Padding.load = b'\x00\x00\x00\x00\x00\x00' (len 6)
```

Now the stack gains a trailing **`Padding`** layer whose `load` is exactly the 6 zero bytes. The transition `NO Padding` → `Padding` is driven entirely by whether trailing bytes are present.

### 4.3 Why the residual bytes become `Padding` (mechanism, cited)

The split between "payload" and "trailing padding" is decided by each layer's `extract_padding()` hook during dissection:

- **`IP.extract_padding()`** at `scapy/layers/inet.py:553-557` computes `tmp_len = self.len - (self.ihl << 2)` (`scapy/layers/inet.py:554`). For a default `IP()/TCP()` frame `self.len = 40` and `self.ihl = 5`, so `tmp_len = 40 - (5<<2) = 40 - 20 = 20`. It then returns `s[:tmp_len]` (the first 20 bytes — the TCP segment) as the *payload* and `s[tmp_len:]` (`scapy/layers/inet.py:557`) as the *padding*. For the clean 54-byte frame the input `s` after IP is exactly 20 bytes, so the padding slice is empty; for the 60-byte wire frame it is the 6 trailing zero bytes.
- The generic base hook is `Packet.extract_padding()` at `scapy/packet.py:982-990`, which by default returns `(s, None)` (no padding) — layers like `IP` override it.
- `Packet.dissect()` at `scapy/packet.py:1049-1060` performs the wrapping: `payl, pad = self.extract_padding(s)` (`scapy/packet.py:1057`), then `if pad and conf.padding:` (`scapy/packet.py:1059`) → `self.add_payload(conf.padding_layer(pad))` (`scapy/packet.py:1060`). The guard `conf.padding` is the `= 1` default from §1.2, and `conf.padding_layer` is `Padding`.
- The `conf.padding_layer = Padding` / `conf.raw_layer = Raw` assignments are at `scapy/packet.py:1922` and `scapy/packet.py:1921` (class `Padding(Raw)` at `scapy/packet.py:1906`, class `Raw` at `scapy/packet.py:1877`).

**Causal summary:** trailing bytes that a layer's `extract_padding()` carves off are wrapped in `conf.padding_layer` (`Padding`) by `dissect()`. A clean build has no such bytes, so a clean round-trip yields no `Padding`; a wire-padded frame does, so it yields a `Padding` layer.

### 5.1 ⭐ KEY FINDING — `0x9000` is Scapy's *default* EtherType, not a random value

The user's phrasing ("try an EtherType of 0x9000 or something random") contains a subtle misconception worth surfacing directly:

> **`0x9000` is NOT random.** It is Scapy's **own default value** for the `Ether.type` field.

Cited at `scapy/layers/l2.py:248`:

```python
XShortEnumField("type", 0x9000, ETHER_TYPES)
```

The second positional argument to `XShortEnumField` is the field's **default**, so any `Ether()` created without an explicit `type=` starts life with `type == 0x9000`. It is a *legitimate-but-unregistered* value: legitimate because Scapy itself uses it as the default, unregistered because it is absent from the `ETHER_TYPES` name/dispatch table. This is corroborated at runtime by the banner line:

```text
0x9000 in ETHER_TYPES? False | 0x0800 in? True | 0x86dd in? True
```

`ETHER_TYPES` is populated by `load_ethertypes()` at `scapy/data.py:355` (parsing `/etc/ethertypes` or Scapy's bundled backup table), assigned via `ETHER_TYPES = load_ethertypes(None)` at `scapy/data.py:526`. Because `0x9000` is not a key in that table and no `bind_layers()` registration targets it (§7b), it both (a) prints numerically and (b) falls through to `Raw`.

## Section 6 — `dispatch_hook` length/type divergence: `Dot3` vs `Ether` (Q6 edge)

**Direct answer:** the 2-byte type/length field is interpreted per the Ethernet II vs. IEEE 802.3 rule — a value **`<= 1500`** is treated as an **802.3 length** and the frame re-dissects as **`Dot3`**; a value **`> 1500`** is a true **EtherType** and the frame stays **`Ether`**.

Observed (`obs_scapy.py`):

```text
=== Q6 edge: dispatch_hook length/type divergence ===
type=100 re-dissect first layer: Dot3
type=0x9000 re-dissect first layer: Ether
```

## Section 7 — Code-level mechanism (Q6 *where* padding + Q7 *how* next protocol)

### 7a. *Where* the padding decision lives — the OS send path, NOT the build path

> **⚠️ INFERRED-FROM-CODE (not runtime-observed).** The send-time minimum-frame padding fallback requires a **real raw socket** *and* a kernel **`EINVAL` (`errno == 22`)** response, which is **not reproducible in this sandbox** (no privileged raw-socket send). The following is established by **reading the code**, not by executing it. Everything else in this document is runtime-observed.

The **only** places Scapy applies Ethernet minimum-frame padding are on the Linux OS send path, and both do so **reactively** — only *after* the kernel rejects an undersized frame with `EINVAL`:

- **`L2Socket.send()`** — class `L2Socket` at `scapy/arch/linux.py:475`, method `send()` at `scapy/arch/linux.py:565-576`. It first attempts `SuperSocket.send(self, x)` (`scapy/arch/linux.py:568`); on `socket.error as msg` it checks `if msg.errno == 22 and len(x) < conf.min_pkt_size:` (`scapy/arch/linux.py:570`), builds `padding = b"\x00" * (conf.min_pkt_size - len(x))` (`scapy/arch/linux.py:571`), and resends `SuperSocket.send(self, x / Padding(load=padding))` (`scapy/arch/linux.py:573`), otherwise `raise` (`scapy/arch/linux.py:576`).

  ```python
  def send(self, x):                                              # l.565
      # type: (Packet) -> int
      try:
          return SuperSocket.send(self, x)                        # l.568
      except socket.error as msg:
          if msg.errno == 22 and len(x) < conf.min_pkt_size:      # l.570
              padding = b"\x00" * (conf.min_pkt_size - len(x))    # l.571
              if isinstance(x, Packet):
                  return SuperSocket.send(self, x / Padding(load=padding))  # l.573
              else:
                  return SuperSocket.send(self, raw(x) + padding)
          raise                                                   # l.576
  ```

- **`L3PacketSocket.send()`** — class `L3PacketSocket(L2Socket)` at `scapy/arch/linux.py:587`, method `send()` at `scapy/arch/linux.py:598`; the identical reactive padding block is at `scapy/arch/linux.py:621-623`: `if msg.errno == 22 and len(sx) < conf.min_pkt_size:` (`scapy/arch/linux.py:621`) then resend `sx + b"\x00" * (conf.min_pkt_size - len(sx))` (`scapy/arch/linux.py:623`).

**Causal point:** this is precisely *why* build-time serialization never pads (§3) — padding is a **send-time / on-the-wire** concern, delegated to the OS-specific socket layer and only triggered by a kernel `EINVAL`. `conf.min_pkt_size` (`scapy/config.py:778`) is consumed *only* here.

### 7b. *How* the next protocol is resolved — `bind_layers` → `guess_payload_class` → `Raw` (Q7)

**Direct answer (Q7):** the next layer is chosen by matching the current layer's fields against the `bind_layers()` registration table in `Packet.guess_payload_class()`; when **no** binding matches, `Packet.default_payload_class()` returns `conf.raw_layer` (i.e., `Raw`). That is the fallback that turns an unknown EtherType into a `Raw` layer.

- **`Packet.guess_payload_class()`** at `scapy/packet.py:1062-1079` iterates `self.aliastypes` and each `t.payload_guess` `(fval, cls)` pair; if `all(v == self.getfieldval(k) for k, v in fval.items())` it returns `cls`. With no match it executes `return self.default_payload_class(payload)` at `scapy/packet.py:1079`.
- **`Packet.default_payload_class()`** at `scapy/packet.py:1081-1090` is simply `return conf.raw_layer` (`scapy/packet.py:1090`).
- **`conf.raw_layer = Raw`** at `scapy/packet.py:1921` (class `Raw` at `scapy/packet.py:1877`). This is the **Q7 fallback** and the reason §5's `0x9000` frame yields `['Ether', 'Raw']`.

The `payload_guess` table is populated by `bind_layers()` calls at import time. The registrations relevant to `Ether.type` are:

- `bind_layers(Ether, IP, type=2048)` at `scapy/layers/inet.py:1101` (`2048` = `0x0800`, IPv4).
- `bind_layers(Ether, IPv6, type=0x86dd)` at `scapy/layers/inet6.py:4083`.
- `Ether`'s own bindings — LLC (`type=122`), `Dot1Q` (`type=33024`), `Dot1AD` (`type=0x88a8`), ARP (`type=2054`), etc. — at `scapy/layers/l2.py:687-716`.

Crucially, **none** of these binds `type=0x9000`, so a `0x9000` frame matches nothing in `guess_payload_class()` and falls through to `default_payload_class()` → `conf.raw_layer` → `Raw`. This chain is corroborated at runtime by §5's `dissected layers: ['Ether', 'Raw']` (no error, no guess).

## Section 8 — IEEE 802.3 reconciliation (why 60, and the `<= 1500` rule)

This section provides standards background to explain *why* Scapy uses the specific constants observed above. The load-bearing content remains the observed Scapy behavior and citations; the standards facts are context.

### 8.1 Why `conf.min_pkt_size = 60` and not the well-known `64`

IEEE 802.3 mandates a **minimum Ethernet frame of 64 bytes** — but that figure **includes the 4-byte Frame Check Sequence (FCS/CRC)**, which the **NIC** computes and appends. Scapy builds frames **without** the FCS, so its software minimum is:

```
conf.min_pkt_size = 60 = 64 (standard minimum) − 4 (FCS added by the NIC)
```

Padding to 60 bytes in software therefore yields a **64-byte frame on the wire** once the NIC appends the 4-byte FCS. This reconciles the observed `conf.min_pkt_size = 60` (`scapy/config.py:778`, §1.2) with the familiar "64-byte minimum." (Equivalently, the 46-byte minimum *payload* = 60 − 14-byte Ethernet header.)

### 8.2 Why the `dispatch_hook` threshold is `<= 1500`

In Ethernet, the same 2-byte field is overloaded as either a **length** (IEEE 802.3, followed by an 802.2/LLC header) or an **EtherType** (Ethernet II). The disambiguation rule is:

- value **`<= 1500`** → it is a **length** → an 802.3/LLC frame → Scapy dissects as **`Dot3`**;
- value **`> 1500`** → it is an **EtherType** → Ethernet II → Scapy keeps it as **`Ether`**.

(1500 is the standard MTU / maximum 802.3 payload length; EtherType values are assigned at `0x0600` = 1536 and above.) This is exactly the branch observed in §6 and coded at `scapy/layers/l2.py:270`. `0x9000` (= 36864) is comfortably `> 1500`, so it remains an `Ether` frame and then falls through to `Raw` for lack of a binding.
