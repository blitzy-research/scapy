Scapy is "a powerful Python-based interactive packet manipulation program and library" (`README.md:12-13`). By its own description it "is able to forge or decode packets of a wide number of protocols, send them on the wire, capture them, store or read them using pcap files, match requests and replies, and much more" (`README.md:15-18`). This document answers, with evidence, a four‑part question about **what Scapy displays and reports at runtime** as one packet travels through its full lifecycle — **build → send → sniff → summarize** — using the user's exact example stack:

Each behavioral claim below is paired with the **verbatim** console output that produced it, and each source‑grounded claim carries an exact `file:line` reference. The five sections are: (1) Building, (2) Sending, (3) Sniffing, (4) Summary, and (5) a Coverage confirmation.

## Section 1 — Building the packet (what Scapy displays as each layer is added)

### 1.1 The `/` operator stacks layers

Scapy composes protocol layers with the division operator `/`. This is implemented by `Packet.__div__` at `scapy/packet.py:596`, which clones both operands and calls `add_payload()` (`scapy/packet.py:360`) so that in `A/B` the layer **`B` becomes the payload of `A`**. Stacking `Ether()/IP()/TCP()` therefore nests **TCP inside IP inside Ethernet**. The three layers named in the question are distinct classes:

- **Ethernet** — `class Ether(Packet)` at `scapy/layers/l2.py:244`.
- **IP** — `class IP(Packet, IPTools)` at `scapy/layers/inet.py:521`.
- **TCP** — `class TCP(Packet)` at `scapy/layers/inet.py:753`.

### 1.2 Building incrementally — the `repr` changes as each layer is attached

Every time a layer is added, the object's textual representation (from `Packet.__repr__` at `scapy/packet.py:552`) reflects the new nested structure. Adding one layer at a time produced exactly this, verbatim:

```text
>>> Ether()
<Ether  |>
>>> Ether()/IP(dst="127.0.0.1")
<Ether  type=IPv4 |<IP  dst=127.0.0.1 |>>
>>> Ether()/IP(dst="127.0.0.1")/TCP(dport=80)
<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http |>>>
```

**Auto‑populated linkage fields (observed).** Notice what appears *without being set*:

- `Ether` gains **`type=IPv4`** the moment an `IP` layer is attached — evidence: the bare `<Ether  |>` becomes `<Ether  type=IPv4 |...>`. The Ethernet header advertises the next protocol so the receiver can dissect it.
- `IP` gains **`proto=tcp`** the moment a `TCP` layer is attached — evidence: `<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP ...>>`. The IP header advertises its L4 payload type.

These linkage values are computed at build time (see §1.5), which is why they show up in the `repr` only once the *next* layer exists to imply them.

**Human‑readable field renderings (observed).** Scapy prints well‑known port numbers as service names, not integers:

- TCP destination port **80** renders as **`dport=http`** — evidence: `<TCP  dport=http |>`.
- The default TCP source port renders as **`sport=ftp_data`** (port 20) — shown in the `.show()` tree in §1.3.

### 1.4 Contrast — `.show2()` rebuilds so automatic fields are calculated

`.show2()` (`scapy/packet.py:1473`) differs from `.show()` by first assembling the packet. Its docstring says it prints "an assembled version of the packet, so that automatic fields are calculated (checksums, etc.)" (`scapy/packet.py:1476-1478`), and it is implemented as `return self.__class__(raw(self)).show(...)` at `scapy/packet.py:1486` — i.e. it serializes the packet to bytes with `raw(self)` and re‑parses them. ### 1.5 Why (rationale): the build chain fills the computed fields

The difference between §1.3 and §1.4 is *assembly*. Serializing a packet runs the build chain: `self_build()` (`scapy/packet.py:678`) → `do_build()` (`scapy/packet.py:724`) → `post_build()` (`scapy/packet.py:758`, where lengths and checksums are filled in) → `build()` (`scapy/packet.py:746`). Therefore:

- `.show()` reflects fields **as currently stored** — an unset auto field is `None` (evidence: the `None` lines in §1.3).
- `.show2()` reflects fields **after assembly**, because it rebuilds via `self.__class__(raw(self))` (`scapy/packet.py:1486`) — so `ihl`, `len`, `chksum`, and `dataofs` acquire concrete values (evidence: the resolved lines in §1.4).

## Section 2 — Sending the packet (what Scapy reports during transmission)

### 2.1 Two send functions: layer 3 vs layer 2

Scapy offers two "usual" ways to transmit, differing by the layer at which they operate:

- **`send()`** transmits at **layer 3** (`scapy/sendrecv.py:422`). You hand it an `IP(...)` packet; Scapy builds the L2 header for you and **resolves the egress interface from the routing table** (§2.2).
- **`sendp()`** transmits at **layer 2** (`scapy/sendrecv.py:452`). You supply the explicit `Ether(...)` header, and Scapy sends the frame on the interface you name.

(The send‑and‑receive family is analogous: `sr` (`scapy/sendrecv.py:635`) and `sr1` (`scapy/sendrecv.py:656`) at L3, `srp` (`scapy/sendrecv.py:668`) and `srp1` (`scapy/sendrecv.py:693`) at L2. They are not needed to answer the question but are the reply‑collecting counterparts.)

### 2.2 Routing information (the "routing" sub‑question)

Because `send()` works at L3, it must decide *which interface* and *which source IP* to use. That decision comes from `Route.route()` at `scapy/route.py:146`, whose docstring states it "returns: (iface, output_ip, gateway_ip)" (`scapy/route.py:152`). Resolving the example destination produced verbatim:

```text
>>> conf.route.route("127.0.0.1")
('lo', '127.0.0.1', '0.0.0.0')
```

Reading the triple against the documented order (`iface, output_ip, gateway_ip`):

- egress interface **`iface = 'lo'`** — the loopback, matching `conf.loopback_name` (`scapy/config.py:911`);
- outgoing address **`output_ip = '127.0.0.1'`**;
- **`gateway_ip = '0.0.0.0'`** — meaning the destination is directly reachable (no gateway hop).

The whole routing table is rendered by `Route.__repr__` at `scapy/route.py:47`, whose six‑column header tuple is defined at `scapy/route.py:60` as `("Network", "Netmask", "Gateway", "Iface", "Output IP", "Metric")`. The six columns, named exactly, are **Network / Netmask / Gateway / Iface / Output IP / Metric**. The loopback route that governs our send is the deterministic row:

### 2.4 The transmission report (what Scapy prints while sending)

The console output during transmission is written by the internal send loop `__gen_send()` at `scapy/sendrecv.py:332`. It emits a **per‑packet progress dot** via `os.write(1, b".")` at `scapy/sendrecv.py:380`, and after the loop prints the summary line `print("\nSent %i packets." % n)` at `scapy/sendrecv.py:392`. This prints **by default** because verbosity defaults to `conf.verb = 2` (`scapy/config.py:759`).

Sending the example at **layer 3** produced verbatim (the leading `.` is the progress dot; captured with unbuffered output to preserve the true console ordering):

```text
>>> send(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"))
.
Sent 1 packets.
```

Sending the equivalent frame at **layer 2** produced the identical report:

```text
>>> sendp(Ether()/IP(dst="127.0.0.1")/TCP(dport=80, flags="S"), iface="lo")
.
Sent 1 packets.
```

The literal summary string is exactly `Sent 1 packets.` (from the format `"\nSent %i packets."` at `scapy/sendrecv.py:392`, with `n = 1`).

> **Observed ordering nuance (reported truthfully).** The dot is written straight to file descriptor 1 with `os.write(1, b".")` (`scapy/sendrecv.py:380`), bypassing Python's buffered `sys.stdout`, whereas `Sent 1 packets.` goes through buffered `print()` (`scapy/sendrecv.py:392`). When output is piped rather than shown on a TTY, the buffered `print()` can flush *after* the raw dot; running the interpreter unbuffered (`python -u`) restores the natural `.` ‑then‑ `Sent 1 packets.` order shown above.

When the stack is sent at **layer 3** over loopback, Scapy synthesizes the Ethernet header itself. The concrete bytes that go out are captured and shown in Section 3: a frame whose Ethernet header is `dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4` (the same all‑broadcast destination / all‑zero source already visible in the pre‑send `.show()` tree of §1.3).

## Section 3 — Sniffing the packet (how Scapy presents, interprets, and reconstructs the bytes)

### 3.1 Capturing with `AsyncSniffer` on `lo`

Capture was done with **`AsyncSniffer`** (`scapy/sendrecv.py:981`) on interface `lo`, while a matching packet was sent so the capture is self‑contained. The blocking equivalent is **`sniff()`** (`scapy/sendrecv.py:1308`). The exact pattern used was:

```python
t = AsyncSniffer(iface="lo", count=1,
                 lfilter=lambda p: TCP in p and p[TCP].dport == 80 and p[TCP].flags == "S")
t.start()
time.sleep(0.5)
send(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"), verbose=0)
t.join(timeout=5)
pkt = t.results[0]
```

A Python `lfilter` callback (`lambda p: TCP in p and ...`) is used to select exactly the SYN we send; it runs in‑process and needs no external library.

**BPF filter behavior in this container (reported truthfully).** A capture‑layer BPF string filter (e.g. `filter="tcp and dst port 80"`) *also works here*, and was verified to capture the packet — summary `Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S`. This is because **libpcap is present** on this host: Scapy reports its version as `b'libpcap version 1.10.5 (with TPACKET_V3)'`, so BPF compilation succeeds even though `conf.use_pcap = False` (native `PF_PACKET` sockets are still used for the actual capture). No "libpcap is not available" error was observed in this environment, so none is quoted here. On a host that genuinely lacks libpcap, a BPF `filter=` would fail to compile while an `lfilter=` callback would keep working — that is why the `lfilter` approach is used above as the portable default.

### 3.2 How the received bytes are presented — dissection into layers

The captured object is not raw bytes to the user: Scapy has already **interpreted** the bytes into a layered packet. Its `repr` (`scapy/packet.py:552`) was, verbatim:

```text
<Ether  dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4 |<IP  version=4 ihl=5 tos=0x0 len=40 id=1 flags= frag=0 ttl=64 proto=tcp chksum=0x7ccd src=127.0.0.1 dst=127.0.0.1 |<TCP  sport=ftp_data dport=http seq=0 ack=0 dataofs=5 reserved=0 flags=S window=8192 chksum=0x917c urgptr=0 |>>>
```

Two things to note from this exact line:

- The **synthetic Ethernet header** created for the L3 send is now visible on the wire: `dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4` (confirming §2.5).
- The IP/TCP fields that were `None` before sending are **fully populated on receipt** — `ihl=5`, `len=40`, `chksum=0x7ccd`, `dataofs=5`, `chksum=0x917c` — identical to the assembled `.show2()` values from §1.4, because what was captured is the assembled bytes re‑parsed. (No trailing `Raw`/`Padding` layer appeared on this loopback frame; the packet dissected cleanly to `Ether/IP/TCP`.)

### 3.4 Layer reconstruction (the "layer reconstruction" sub‑question), by name

Turning raw bytes back into `Ether/IP/TCP` is **dissection**, driven by `dissect()` at `scapy/packet.py:1049` (which runs `pre_dissect → do_dissect → post_dissect → extract_padding → do_dissect_payload`) and `guess_payload_class()` at `scapy/packet.py:1062`, which chooses the *next* layer's class from the registered layer bindings. This is the inverse of the build chain from §1.5, and it is why the linkage fields matter: `Ether.type=IPv4` tells the dissector the next layer is `IP`, and `IP.proto=tcp` tells it the layer after that is `TCP`.

**Round‑trip demonstration (observed).** Serializing the built stack to bytes and re‑parsing them recovers the same three layers:

```text
>>> raw(Ether()/IP(dst="127.0.0.1")/TCP(dport=80, flags="S"))   # -> 54 bytes
>>> Ether(<those 54 bytes>)
<Ether  dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4 |<IP  version=4 ihl=5 tos=0x0 len=40 id=1 flags= frag=0 ttl=64 proto=tcp chksum=0x7ccd src=127.0.0.1 dst=127.0.0.1 |<TCP  sport=ftp_data dport=http seq=0 ack=0 dataofs=5 reserved=0 flags=S window=8192 chksum=0x917c urgptr=0 |>>>
>>> [layer.__name__ for layer in _.layers()]
['Ether', 'IP', 'TCP']
```

The recovered layer list `['Ether', 'IP', 'TCP']` is the concrete evidence that dissection rebuilt every layer from bytes alone.

**`Raw` fallback (observed).** When `guess_payload_class()` (`scapy/packet.py:1062`) cannot identify the next layer, the remaining bytes are kept as a `Raw` layer rather than being discarded. Attaching bytes that match no binding demonstrates this verbatim:

```text
>>> Ether()/IP(dst="127.0.0.1")/b"UNKNOWN_PAYLOAD_1234"
<Ether  type=IPv4 |<IP  dst=127.0.0.1 |<Raw  load='UNKNOWN_PAYLOAD_1234' |>>>
```

Here the trailing bytes became `<Raw  load='UNKNOWN_PAYLOAD_1234'>` (and `Raw in pkt` returns `True`), whereas the well‑known IP‑proto/port bindings caused the SYN above to reconstruct all the way to `TCP`.

## Section 4 — Summary (what the observations reveal)

Running the exact stack `Ether()/IP(dst="127.0.0.1")/TCP(dport=80)` through its full lifecycle revealed a consistent story — *forge → send → capture* — end to end. One claim, one line of evidence:

- **Build.** The `/` operator (`scapy/packet.py:596`) stacks the layers Ethernet → IP → TCP, and building incrementally shows Scapy auto‑populating the **linkage fields** so each layer advertises the next: `Ether` acquires `type=IPv4` and `IP` acquires `proto=tcp` (evidence: `<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http |>>>`). The **computed fields** (`ihl`, `len`, `chksum`, `dataofs`) are unset — printed as `None` by `.show()` (evidence: `ihl       = None`) — until the packet is assembled, at which point `.show2()` resolves them (evidence: `ihl       = 5`, `len       = 40`, `chksum    = 0x7ccd`). The reason is the build chain `self_build → do_build → post_build → build` (`scapy/packet.py:678,724,758,746`).

- **Send.** The layer‑3 `send()` (`scapy/sendrecv.py:422`) consults the **routing table** to choose an egress path — `conf.route.route("127.0.0.1")` returned `('lo', '127.0.0.1', '0.0.0.0')` (evidence: that triple) — whereas layer‑2 `sendp()` (`scapy/sendrecv.py:452`) uses the explicit `Ether` header instead. Both report transmission the same way under the default `conf.verb = 2` (`scapy/config.py:759`): a progress dot then `Sent 1 packets.` (evidence: the `.` and `Sent 1 packets.` lines from `scapy/sendrecv.py:380,392`).

- **Sniff.** The captured bytes are **dissected** straight back into `Ether/IP/TCP` (evidence: the captured `repr` in §3.2), tagged with the capturing interface `sniffed_on = 'lo'` (evidence: `'lo'`), and reconstructed field‑by‑field by `dissect()`/`guess_payload_class()` (`scapy/packet.py:1049,1062`) — recovering the layer list `['Ether', 'IP', 'TCP']` — with a `Raw` fallback for bytes that match no binding (evidence: `<Raw  load='UNKNOWN_PAYLOAD_1234' |>`). The whole packet collapses to a one‑line `.summary()` (`scapy/packet.py:1642`): `Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S`.

Taken together, the runtime behavior is exactly the lifecycle Scapy advertises for itself — it can "forge or decode packets ... send them on the wire, capture them" (`README.md:15-18`): the build stage *forges* the layers (filling linkage and computed fields at assembly), the send stage *puts them on the wire* (resolving a route and reporting the count), and the sniff stage *captures and decodes* them back into the same layered structure.

## Section 5 — Coverage confirmation

Every concrete item named in the question is addressed **by name**, with runtime evidence and a `file:line` citation:

- **Ethernet** — ✔ Section 1 (built `repr`/`.show()` show the `Ether` layer; `class Ether(Packet)` at `scapy/layers/l2.py:244`) and Section 3 (the synthetic `dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4` header on the captured frame).
- **IP** — ✔ Section 1 (`IP` layer, `proto=tcp`, `chksum` resolution; `class IP(Packet, IPTools)` at `scapy/layers/inet.py:521`).
