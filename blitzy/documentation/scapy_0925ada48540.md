# What Scapy Displays and Reports Across a Packet's Lifecycle — Building, Sending, and Sniffing

## The question being answered

> Start Scapy normally and build a simple multi-layer packet such as an Ethernet/IP/TCP stack. Observe what Scapy displays about the packet as each layer is added and how the final structure looks before it is sent.
> Send the packet using Scapy's usual sending mechanism; watch what Scapy reports during transmission — the routing information it prints, what it shows about the packet as it leaves the system, and any other output emitted during the send.
> Sniff for the same traffic; observe how Scapy presents received bytes — what it displays as it interprets the data and how it reconstructs the layers when the packet is shown.
> Summarize what Scapy revealed during building, sending, and sniffing.

This document answers the question **from directly observed runtime output**. Every claim below is paired with the exact command that produced it, the actual (complete, unedited) output, and a `file:line` reference naming the specific function or method in the Scapy source that performs the work. The same `Ether()/IP()/TCP()` packet is carried through all three stages, so the sniffed frame is demonstrably the counterpart of the built frame.

## Section 2 — Building the `Ether()/IP()/TCP()` packet

**Plain answer:** Layers are stacked with the `/` operator. As each layer is added, `__repr__` shows the growing nested structure and reveals **binding-derived fields** (`type=IPv4` appears once IP is added; `proto=tcp` appears once TCP is added). The "final structure before sending" has a crucial property: **auto-computed fields (`ihl`, `len`, `chksum`, `dataofs`) display as `None`** — `show()` dumps this unresolved template, while `show2()` (and `raw()`) trigger the build and show the **computed** wire values.

### 2.1 The `/` operator stacks layers

Stacking is `Packet.__div__` at `scapy/packet.py:L596`, aliased as `__truediv__ = __div__` at `scapy/packet.py:L607`; it attaches the right operand as the payload of the left via `add_payload` at `scapy/packet.py:L360`. So `Ether()/IP()/TCP()` yields an `Ether` whose payload is `IP` whose payload is `TCP`.

Command:
```
PYTHONPATH=<repo-root> python3 -c 'from scapy.all import *; conf.color_theme=NoTheme(); \
ei=Ether()/IP(); \
print("Ether()             repr:", repr(Ether())); \
print("Ether()/IP()        repr:", repr(ei)); \
print("Ether()/IP()/TCP()  repr:", repr(Ether()/IP()/TCP())); \
print("type(Ether()/IP()) =", type(ei).__name__, "| .payload =", type(ei.payload).__name__); \
print("layer chain:", [c.__name__ for c in (Ether()/IP()/TCP()).layers()])'
```

Actual output (deterministic across runs):
```
Ether()             repr: <Ether  |>
Ether()/IP()        repr: <Ether  type=IPv4 |<IP  |>>
Ether()/IP()/TCP()  repr: <Ether  type=IPv4 |<IP  frag=0 proto=tcp |<TCP  |>>>
type(Ether()/IP()) = Ether | .payload = IP
layer chain: ['Ether', 'IP', 'TCP']
```

**What this reveals as each layer is added** (via `__repr__`, `scapy/packet.py:L552`): a bare `Ether()` prints `<Ether  |>` with no fields (all defaults, nothing to show). Adding IP makes `Ether` display **`type=IPv4`** — this is not a user-set value; it is derived from the layer binding `bind_layers(Ether, IP, type=2048)` at `scapy/layers/inet.py:L1101` (2048 = `0x0800`). Adding TCP makes `IP` display **`proto=tcp`** (plus `frag=0`), derived from `bind_layers(IP, TCP, frag=0, proto=6)` at `scapy/layers/inet.py:L1113`. The binding registrar itself is `bind_layers` (`scapy/packet.py:L1975`), which populates the guessing tables used later by `dissect` (Section 4); the bottom-up half is `bind_bottom_up` (`scapy/packet.py:L1931`).

### 2.6 The crux — why the fields change (proved, not inferred)

`show()` dumps the **live template**, whereas `show2()` dumps a **rebuilt copy**. Crucially, calling `raw()`/`build()` does **not** mutate the original object's field attributes — it computes values into the output byte string. This was verified directly: after calling `raw(p_fresh)`, a subsequent `p_fresh.show()` **still prints `None`** for the auto fields:

Command:
```
PYTHONPATH=<repo-root> python3 -c 'from scapy.all import *; conf.color_theme=NoTheme(); \
p=Ether()/IP()/TCP(); _=raw(p); \
print("IP.ihl after raw():", p[IP].ihl, "| IP.chksum:", p[IP].chksum, "| TCP.chksum:", p[TCP].chksum)'
```
Actual output:
```
IP.ihl after raw(): None | IP.chksum: None | TCP.chksum: None
```

So the `None → value` transition is not a state change on the object; it is what serialization computes. `show()` = the unresolved template; `show2()` = the finalized wire form. Summarizing the quartet: **`__repr__`** = terse nested template; **`summary()`** = one-line description; **`show()`** = full unresolved template (auto fields `None`); **`show2()`** = full finalized wire form (auto fields computed). Auto-field defaulting behavior lives in the field layer (`scapy/fields.py`); the packet-level orchestration is `build`/`do_build`/`post_build` (`scapy/packet.py:L746,L724,L758`).

**Nuance on the Ethernet source MAC (labeled host-specific):** in the dumps above `src = 00:00:00:00:00:00`. That is because `IP.dst` defaults to `127.0.0.1`, which routes over `lo` (whose MAC is all-zero). A **bare** `Ether()` with no IP payload instead resolves its `src` from `conf.iface` (eth0). That MAC is **host-specific** (stable across runs in this container, but not portable):

```
The canonical `Ether()/IP()/TCP()` used throughout this document targets `127.0.0.1`, so its `src` is the deterministic `00:00:00:00:00:00`.

## Section 3 — Sending the packet

**Plain answer:** Under the default verbosity `conf.verb = 2`, `send()` (layer 3) prints an intentionally **terse** two lines — a single `.` progress marker followed by `Sent 1 packets.` — and nothing else. In particular, **`send()` does not print the routing table**; it resolves the outgoing interface/source/gateway internally via `conf.route.route()`. The send-and-receive family (`sr`/`sr1`/`srp`/`srp1`) is distinct and prints a multi-line emission/reception report.

### 3.1 `send()` — layer 3 (the "usual sending mechanism")

`send` is defined at `scapy/sendrecv.py:L422` ("Send packets at layer 3"); its `verbose` defaults to `conf.verb`. It funnels into the shared engine `__gen_send` at `scapy/sendrecv.py:L332`.

Command:
```
PYTHONPATH=<repo-root> python3 -c 'from scapy.all import *; conf.color_theme=NoTheme(); send(IP(dst="127.0.0.1")/TCP())'
```

Actual, complete output (stdout):
```
.
Sent 1 packets.
```

- The **`.`** is the per-packet progress marker, written **unbuffered** to file descriptor 1 by `os.write(1, b".")` at `scapy/sendrecv.py:L380` (inside `__gen_send`, guarded by `if verbose:`).
- The **`Sent 1 packets.`** line is `print("\nSent %i packets." % n)` at `scapy/sendrecv.py:L392` (also guarded by `if verbose:`). The leading `\n` in that `print` is why the total appears on its own line after the `.`.
- Because the `.` is written unbuffered (bypassing Python's buffered `stdout`) while other prints are buffered, the `.` can interleave ahead of buffered text; the output above is exactly as observed. No routing table, and nothing "about the packet", is printed by `send()` at the default verbosity.

There was **no send-time output on stderr** (the only stderr content was the import-time `CryptographyDeprecationWarning` from Section 1).

### 3.2 `sendp()` — layer 2 (same terse output)

`sendp` is defined at `scapy/sendrecv.py:L452` ("Send packets at layer 2"); it also uses `__gen_send`, so it prints the same two lines.

Command:
```
PYTHONPATH=<repo-root> python3 -c 'from scapy.all import *; conf.color_theme=NoTheme(); \
sendp(Ether()/IP(dst="127.0.0.1")/TCP(), iface="lo")'
```

Actual output:
```
.
Sent 1 packets.
```

The difference between `send` and `sendp` is the layer at which the packet enters the stack (L3 vs L2), not the console output. `send` builds the L2 header itself (resolving it from the route), whereas `sendp` transmits the exact frame given, including the Ethernet header.

### 3.3 The send-and-receive family — `sr`/`sr1`/`srp`/`srp1` (distinct output)

These variants send and then wait for replies, so they print a different, multi-line report produced by `SndRcvHandler` (`scapy/sendrecv.py:L100`): `"Begin emission:"` (`scapy/sendrecv.py:L239`), `"Finished sending %i packets."` (`scapy/sendrecv.py:L250`), and the summary `"Received %i packets, got %i answers, remaining %i packets"` (`scapy/sendrecv.py:L218`). `sr` is at `scapy/sendrecv.py:L635`, `sr1` at `L656`, `srp` (L2) at `L668`, `srp1` (L2) at `L693`.

Command (a `timeout` is used to avoid hanging while waiting for replies):
```

ans = sr1(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"), timeout=2, verbose=2); \
print("sr1 return value:", repr(ans))'
```

Actual, complete output:
```
.Begin emission:

```

Command:

## Section 4 — Sniffing the same traffic

**Plain answer:** Scapy captures raw bytes and **reconstructs the layers by dissection**: it guesses the next layer from binding tables (EtherType `0x0800` → IP, IP protocol `6` → TCP), rebuilding an `Ether/IP/TCP` stack. The received frame's `show()` displays the **computed** fields (because the bytes on the wire already carry them), and the captured frame is byte-for-byte identical to the built frame (`raw(received) == raw(built)` → `True`).

### 4.1 A BPF `filter=` fails here (libpcap absent) — reported truthfully

The classic way to capture one flow is a BPF filter such as `filter="tcp and port 80"`. In this canonical build **libpcap is absent**, so BPF compilation fails and the filter is rejected:

```

So the BPF-filter path is **unavailable under the default build**. The working, canonical substitute is a **Python-level `lfilter=`** callable (evaluated per packet, requiring no libpcap).

### 4.2 Capturing with `AsyncSniffer` + `lfilter`

`sniff` is at `scapy/sendrecv.py:L1308` and `AsyncSniffer` (its threaded form) at `scapy/sendrecv.py:L981`. The sniffer is started on `lo`, then the **same** `Ether()/IP()/TCP()` packet is transmitted; the `lfilter` matches the default ports so the captured frame equals the built frame.

### 4.3 How the received bytes are interpreted (dissection = build in reverse)

- **Layer reconstruction:** `r.layers()` → `['Ether', 'IP', 'TCP']`. The received buffer is a flat byte string; Scapy rebuilds the layer stack in `Packet.dissect` at `scapy/packet.py:L1049`. Starting from `Ether` (the link-layer type for the capture), it reads the Ethernet header, sees `type == 0x0800`, and consults the **same binding tables** used at build time to choose `IP` (`bind_layers(Ether, IP, type=2048)`, `scapy/layers/inet.py:L1101`); then it reads `proto == 6` and chooses `TCP` (`bind_layers(IP, TCP, frag=0, proto=6)`, `scapy/layers/inet.py:L1113`). These bindings are stored via `bind_layers`/`bind_bottom_up` (`scapy/packet.py:L1975`/`L1931`).
- **Interpreting the fields:** because `r` was created from wire bytes, its auto fields are **already the computed values** — `r.show()` prints `ihl=5, len=40, chksum=0x7ccd` (IP) and `dataofs=5, chksum=0x917c` (TCP). Contrast with Section 2.3, where the freshly-built (not-yet-serialized) template printed those as `None`. `summary()` gives the same one-liner as the built packet.
- **Consistency proof:** `raw(r) == raw(Ether()/IP(dst="127.0.0.1")/TCP())` → **`True`**, and `hexdump(r)` is byte-identical to Section 2.5. The sniffed frame is provably the exact counterpart of the built frame.

## Section 5 — Summary: what Scapy revealed at each stage

Carrying one `Ether()/IP()/TCP()` packet through the lifecycle exposes three complementary faces of the same object:

- **Building assembles a layer stack and *defers* computation.** The `/` operator (`Packet.__div__`/`__truediv__`, `scapy/packet.py:L596,L607`, via `add_payload` `L360`) nests layers, and the binding tables immediately surface derived fields (`type=IPv4`, `proto=tcp`) in `__repr__` (`scapy/packet.py:L552`). The display quartet shows increasing detail — `__repr__` (terse), `summary()` (`L1642`, one-liner), `show()` (`L1459`, full template), `show2()` (`L1473`, full wire form). The headline finding is the **before→after transition**: length/offset/checksum fields (IP `ihl`/`len`/`chksum`, TCP `dataofs`/`chksum`) read **`None`** in `show()` and become **computed** (`ihl=5, len=40, chksum=0x7ccd`; `dataofs=5, chksum=0x917c`) in `show2()`, because `show2()` rebuilds via `raw()` → `build`/`post_build` (`scapy/packet.py:L746,L758`; per-layer computation in `IP.post_build` `scapy/layers/inet.py:L539` and `TCP.post_build` `scapy/layers/inet.py:L767`). Building does not mutate those attributes — serialization computes them.

- **Sending serializes, routes, and reports tersely.** `send()` (L3, `scapy/sendrecv.py:L422`) and `sendp()` (L2, `L452`) both emit only `.` (`os.write(1, b".")`, `scapy/sendrecv.py:L380`) then `Sent 1 packets.` (`print`, `L392`) under `conf.verb=2`. The routing decision is **resolved internally, not printed**: `conf.route.route()` (`scapy/route.py:L146`) returns the `(iface, src, gateway)` triple — deterministically `('lo', '127.0.0.1', '0.0.0.0')` for loopback and the host-specific `('eth0', '10.236.0.35', '10.236.0.1')` for a public destination. The send-and-receive family (`sr`/`sr1`/`srp`/`srp1`, `scapy/sendrecv.py:L635/L656/L668/L693`) is distinct, printing `Begin emission:` / `Finished sending N packets.` / `Received … got … answers` via `SndRcvHandler` (`L100`).

- **Sniffing reverses building.** `sniff`/`AsyncSniffer` (`scapy/sendrecv.py:L1308`/`L981`) capture raw bytes; `Packet.dissect` (`scapy/packet.py:L1049`) walks the **same** binding tables (`bind_layers`, `scapy/packet.py:L1975`) in the bottom-up direction to rebuild `Ether/IP/TCP`. Because the captured bytes already carry the computed fields, the received packet's `show()` shows them populated — no `None`s.

**The unifying insight:** *build* and *dissect* are inverses over the same binding tables — build stacks layers and computes the deferred fields on serialization; dissect reads the bytes and re-guesses the layers. Sending is the byte-emission step in between, deliberately quiet at the default verbosity, with routing handled behind the scenes. The end-to-end consistency is proven: the sniffed frame satisfies `raw(received) == raw(built)` → `True`, so the three stages are demonstrably operating on one and the same packet.
