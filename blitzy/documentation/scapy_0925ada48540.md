## 1. The question and the built‑in‑only reproduction strategy

**Question.** When an application‑layer payload is split across multiple TCP segments and **at
least one segment overlaps (retransmits) a sequence range that a previous segment already
delivered**, how does Scapy's **offline** `TCPSession` reconstruct the single byte stream? For two
overlap variants, what is the exact reconstructed‑bytes `repr`, the integer byte length, and
**which bytes win** in the overlap region? Where in the source is that decision made, and why does
it produce exactly those bytes?

- **User Variant 1 (V1)** — the overlapping/retransmitted segment carries **identical** bytes for
  the overlapping sequence range.
- **User Variant 2 (V2)** — the overlapping/retransmitted segment carries **different** bytes for
  the **same** sequence range.

**Why the reproduction must ride on HTTP, not a bare `Raw` payload. [Inferred / code‑explained]**
`TCPSession` only reconstructs a stream for a payload class that exposes a `tcp_reassemble`
class‑function. Its engine, `TCPSession._process_packet`, gates reassembly on
`if hasattr(pay_class, "tcp_reassemble"):` at `scapy/sessions.py:325`; when the attribute is absent
the `else:` branch at `scapy/sessions.py:327` returns the packet **unreassembled**
(`return pkt`, `scapy/sessions.py:330`). A bare `Raw` payload has **no** such method
(`hasattr(Raw, "tcp_reassemble")` is `False` — **[Observed]**, see §3.2), so it is never
reassembled. The canonical **built‑in** layer that ships a compatible
`tcp_reassemble(cls, data, metadata, _)` is `HTTP` (`scapy/layers/http.py:580`). The built‑in
`http` layer is **not** loaded by default — `scapy/config.py:847` states
`# can, tls, http and a few others are not loaded by default` directly above the
`load_layers = [` list at `scapy/config.py:848`, and `'http'` is absent from it. Loading it with the
shipped loader `load_layer("http")` registers the shipped `TCP:80 ↔ HTTP` bindings
(`scapy/layers/http.py:748`) and exposes `HTTP.tcp_reassemble`.

**Constraints honoured.** Built‑in layers only (`IP`, `TCP`, `Raw`, `HTTP`) plus the shipped
`load_layer("http")`; **no** new `Packet` subclass; **no** `bind_layers` / `bind_bottom_up` call;
**no** import or instantiation of `StringBuffer` (or any internal buffer helper). The real offline
path is exercised end‑to‑end via `sniff(offline="<file>.pcap", session=TCPSession)` — no bypass, no
private helper, no fallback, no synthetic stand‑in. No Scapy source file is modified; the only file
this task adds to the repository is **this** document.

## 3. Reproduction — commands and complete, unedited output

### 3.1 Main harness (HTTP loaded) — V1, V2 and a reverse‑order control

The harness lives **outside** the repository at `/tmp/scapy_probe/probe.py`. It builds three
built‑in `IP()/TCP()/Raw()` segments carrying a 38‑byte HTTP response header (`Content-Length: 8`)
followed by an 8‑byte body split so that **segment 2 overlaps exactly the 4‑byte first body chunk
already delivered by segment 1**, writes them to a `.pcap` with `wrpcap(...)`, and reads them back
through the real offline path `sniff(offline=..., session=TCPSession)`. A third, non‑requested
**reverse‑order control (REV)** swaps which bytes segment 1 vs segment 2 carry over the identical
range, to isolate whether the winner is decided by processing order or by sequence‑number
magnitude. Each variant is run **twice** (`RUN 1`, `RUN 2`) to check determinism.

**Harness source (`/tmp/scapy_probe/probe.py`), verbatim:**

```python

warnings.filterwarnings("ignore")          # hide the harmless mtime-fallback DeprecationWarning
import sys
import scapy                               # for provenance proof
from scapy.all import IP, TCP, Raw, wrpcap, sniff, load_layer, conf
from scapy.sessions import TCPSession

load_layer("http")                          # PIVOTAL: engages built-in HTTP.tcp_reassemble via shipped TCP:80 bindings

HDR = b"HTTP/1.1 200 OK\r\nContent-Length: 8\r\n\r\n"   # len == 38; declares an 8-byte body

def build(first_chunk, overlap_chunk):
    seg1 = IP()/TCP(sport=1234, dport=80, seq=1000, flags="A")/Raw(HDR + first_chunk)  # buffer 0-41 (38+4)
    seg2 = IP()/TCP(sport=1234, dport=80, seq=1038, flags="A")/Raw(overlap_chunk)      # OVERLAP -> buffer 38-41
    seg3 = IP()/TCP(sport=1234, dport=80, seq=1042, flags="FA")/Raw(b"BBBB")           # FIN -> buffer 42-45
    return [seg1, seg2, seg3]

def run(first_chunk, overlap_chunk, path):
    wrpcap(path, build(first_chunk, overlap_chunk))
    pkts = sniff(offline=path, session=TCPSession)
    return [bytes(p[TCP].payload) for p in pkts if TCP in p]

print("scapy.__file__:", scapy.__file__)
print("conf.version:", repr(conf.version))
print("python:", sys.version.split()[0])
print("HDR len:", len(HDR))
for run_no in (1, 2):                        # >= 2 runs to prove determinism
    print("==== RUN", run_no, "====")
    for label, fc, oc, fn in [("V1", b"AAAA", b"AAAA", "v1.pcap"),
                              ("V2", b"AAAA", b"ZZZZ", "v2.pcap"),
                              ("REV", b"ZZZZ", b"AAAA", "rev.pcap")]:
        o = run(fc, oc, "/tmp/scapy_probe/" + fn)
        print(label, "count=", len(o), "repr=", repr(o[0]), "len=", len(o[0]))
```

**Reading the result.**

- The reconstructed stream for the reassembled variants is always a **single** packet whose payload
  is `HDR(38 bytes)` + `4‑byte body chunk` + `BBBB(4 bytes)` = **46 bytes**; the 8‑byte body matches
  the advertised `Content-Length: 8`.
- **Which bytes win in the overlap region:** V2 yields `ZZZZ`, REV yields `AAAA`. In **both** cases the
  winner is the bytes carried by **segment 2**, i.e. the segment processed **last** over that range —
  regardless of whether those bytes are the "original" or the "retransmission", and regardless of
  sequence‑number magnitude (V2 and REV use the identical sequence numbers; only the byte contents
  and their processing order differ). See §6.6 for the cause→effect trace.
- **Length is unchanged (46) on the same‑range overlap:** an overlap that lands entirely within
  already‑covered bytes does not grow the buffer.

### 6.1 Offline entry path — [Inferred / code‑explained]

docstring even gives the example `--Ex: session=TCPSession` at `scapy/sendrecv.py:992`. The offline
files are opened by the enclosing block `if offline is not None:` at `scapy/sendrecv.py:1107`:

```python

            flt = karg.get('filter')

            if isinstance(offline, str):

            if isinstance(offline, list) and \
                    all(isinstance(elt, str) for elt in offline):

                    fname if flt is None else
```

i.e. reading is delegated to `PcapReader` — defined as `class PcapReader(RawPcapReader):` at
`scapy/utils.py:1367`. The pcaps themselves are written by `wrpcap(...)` (`def wrpcap(` at

calls the engine `TCPSession._process_packet` (`scapy/sessions.py:286`).

### 6.2 The reassembly gate — why `Raw` is never reassembled — [Inferred / code‑explained]

Inside `_process_packet`, the enclosing condition that selects the reassembly function — `if "pay_class" not in metadata:` at `scapy/sessions.py:323`, with the `hasattr(pay_class, "tcp_reassemble")` gate at `scapy/sessions.py:325` — is:

```python
        if "pay_class" not in metadata:
            pay_class = pay.__class__
            if hasattr(pay_class, "tcp_reassemble"):
                tcp_reassemble = pay_class.tcp_reassemble
            else:
                # We can't know for sure when a packet ends.
                # Ignore.
                return pkt
            metadata["pay_class"] = pay_class
            metadata["tcp_reassemble"] = tcp_reassemble
```

This is exactly why the **no‑HTTP control** returns three separate packets: for a bare `Raw`
payload, `hasattr(pay_class, "tcp_reassemble")` is `False` (**[Observed]** in §3.2), the `else:`
branch at `:327` fires, and `return pkt` at `:330` hands the segment back unreassembled. With the
HTTP layer loaded the payload class is `HTTP`, which does expose `tcp_reassemble`
(`scapy/layers/http.py:580`), so reassembly proceeds.

### 6.3 Relative‑sequence baseline and the accumulation call — [Inferred / code‑explained]

Before buffering, the engine converts the absolute TCP sequence number into a relative offset — read at `scapy/sessions.py:338`, applied at `scapy/sessions.py:341`, then buffered by the accumulation call `data.append(new_data, seq)` at `scapy/sessions.py:344`:

```python
        # Get a relative sequence number for a storage purpose
        relative_seq = metadata.get("relative_seq", None)
        if relative_seq is None:
            relative_seq = metadata["relative_seq"] = seq - 1
        seq = seq - relative_seq
        # Add the data to the buffer
        # Note that this take care of retransmission packets.
        data.append(new_data, seq)
```

The first segment sets the baseline `relative_seq = seq - 1` (`:340`); every subsequent segment's
offset is `seq - relative_seq` (`:341`). The comment at `:343`
(`# Note that this take care of retransmission packets.`) sits directly above the accumulation call
`data.append(new_data, seq)` at `:344` — the single call that funnels **every** segment, original or
retransmitted, into the same buffer.

### 6.4 The decisive overwrite in `StringBuffer.append` — the crux — [Inferred / code‑explained]

`data` is a `StringBuffer` (`class StringBuffer(object):` at `scapy/sessions.py:161`). Its entire
`append` method — `def append(self, data, seq):` at `scapy/sessions.py:179`, quoted
verbatim through `scapy/sessions.py:193` — is:

```python
    def append(self, data, seq):
        # type: (bytes, int) -> None
        data_len = len(data)
        seq = seq - 1
        if seq + data_len > self.content_len:
            self.content += b"\x00" * (seq - self.content_len + data_len)
            # If data was missing, mark it.
            self.incomplete.append((self.content_len, seq))
            self.content_len = seq + data_len
            assert len(self.content) == self.content_len
        # XXX removes empty space marker.
        # for ifrag in self.incomplete:
        #     if [???]:
        #         self.incomplete.remove([???])
        memoryview(self.content)[seq:seq + data_len] = data
```

Two facts about this method decide the entire answer:

1. **The overwrite at `scapy/sessions.py:193` is outside/after the `if` block**, so
   `memoryview(self.content)[seq:seq + data_len] = data` executes on **every** call, regardless of
   whether that range was already populated. The **last** write to a given range therefore wins.
2. **The growth guard `if seq + data_len > self.content_len:` at `scapy/sessions.py:183`** only
   enlarges the buffer when the incoming range extends past the current end. An overlap that lands
   entirely within already‑covered bytes does **not** satisfy this condition, so the buffer is
   **not** grown and its total length is unchanged.

### 6.5 When the stream is considered complete — [Inferred / code‑explained]

`StringBuffer.full` (`def full(self):` at `scapy/sessions.py:195`) unconditionally
`return True  # XXX` (`scapy/sessions.py:199`), so the assembly branch — `if data.full():` at

### 6.6 Cause → effect — [Observed + code‑explained]

Putting §6.3–§6.5 together with the sequence arithmetic (baseline `relative_seq = 1000 - 1 = 999` at
`:340`, then `seq -= relative_seq` at `:341`, then `seq -= 1` at `:182`, so the net buffer offset is
`seq_wire - 1000`):

| segment | wire `seq` | buffer offset | length | buffer positions | grows? |
|---|---|---|---|---|---|
| seg1 (`HDR`+chunk) | 1000 | 0 | 42 | 0–41 | yes → `content_len = 42` |
| seg2 (**overlap**) | 1038 | 38 | 4 | 38–41 | **no** (`38+4=42 > 42` is false) |
| seg3 (`BBBB`, FIN) | 1042 | 42 | 4 | 42–45 | yes → `content_len = 46` |

- seg2 lands at offset 38 — exactly the 4 body bytes seg1 wrote at 38–41 (the 38‑byte header occupies
  0–37). Because the overwrite at `scapy/sessions.py:193` runs unconditionally, **seg2's bytes
  replace seg1's over 38–41**. seg2 is processed **after** seg1 in pcap order, so **seg2 wins**. That
  is precisely why **V2 → `ZZZZ`** and the **reverse control → `AAAA`** over the *identical* sequence
  range: the winner is decided by **processing order**, **not** by sequence‑number magnitude and
  **not** by original‑vs‑retransmission status. **[Observed + code‑explained]**
- Because seg2's range (38–41) is already covered, the growth guard at `scapy/sessions.py:183` is not
  satisfied, so the buffer does not grow and the final length stays **46**. **[Observed +
  code‑explained]**
- For **V1** the two segments carry identical bytes (`AAAA`), so although the same last‑write‑wins
  overwrite still occurs, the result is indistinguishable — `AAAA` either way. **[Observed]**

In short: **offline `TCPSession` resolves an overlap by last‑write‑wins in pcap/processing order,
via the unconditional `memoryview` assignment at `scapy/sessions.py:193`, and preserves the stream
length when the overlap falls within an already‑covered range because the growth guard at
`scapy/sessions.py:183` is skipped.**
