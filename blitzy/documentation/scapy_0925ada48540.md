# Scapy `Ether()/IP()/TCP()` — Build, Send, Sniff, and Dissect: An Observed Runtime Walkthrough

This document answers, **from verbatim observed runtime output**, exactly what Scapy reveals when you start it normally, build a layered `Ether()/IP()/TCP()` packet, send it on the wire (including the routing it consults), and sniff it back (including how it dissects the raw bytes). It closes with a synthesis and the environment caveats needed to reproduce the results.

Scapy is described by the project itself as a Python-based interactive packet-manipulation program and library able to forge/decode packets, send them on the wire, and capture them (`README.md:L13-L17`). The subject packet studied throughout is the user's exact packet: **`Ether()/IP()/TCP()`**.

## How this investigation was run (run-first methodology)

Every value below was produced by actually running the code path and capturing the output — not from reading source alone. Two kinds of invocation were used:

- **Canonical console startup** (Section 1) via the repository wrapper:
  ```bash
  echo 'exit()' | ./run_scapy
  ```
  `run_scapy:L13` is `PYTHONPATH=$DIR exec "$PYTHON" -m scapy $@` (with `PYTHON` defaulting to `python3`), which runs the package via `scapy/__main__.py` (`from scapy.main import interact` → `interact()`) and reaches `scapy.main.interact()` (`scapy/main.py:L503`).
- **Scripted probes** run from the repository root as:
  ```bash
  PYTHONPATH=. python3 /tmp/scapy_probe/<probe>.py
  ```
  The probe scripts live **outside** the repository (under `/tmp/scapy_probe/`) and are deleted afterward, leaving the Scapy source tree unchanged.

Repository state at capture time: branch `scapy_0925ada48540`, HEAD `0925ada485406684174d6f068dbd85c4154657b3`, **zero git tags**, running as `uid=0(root)`, interfaces `lo`/`eth0`/`docker0`. Stable values below were confirmed identical across at least two runs; environment-specific values (the `eth0` rows of the routing table) are explicitly labeled as such.

**CRITICAL — `2026.07.02` is a NON-CANONICAL file-mtime fallback, not a released Scapy version.** A normally released Scapy line is `2.x`. The value `2026.07.02` arises because this repository has **zero git tags**, so the canonical VCS-stamped version path is unavailable. The observed cause chain:

```text

git describe --tags --always --long -> 0925ada4
git rev-list --tags --max-count=1 -> ''
mtime(scapy/__init__.py) UTC -> 2026.07.02
```

Cause → effect, step by step:

1. `git describe --tags --always --long` returns the bare commit abbreviation `0925ada4` (it does **not** start with `v` and has no `TAG-N-gHASH` shape), so `_version_from_git_describe()` (`scapy/__init__.py:L72-L119`, whose `git describe` call is at `scapy/__init__.py:L114`) yields no parseable release version and raises.
2. `git rev-list --tags --max-count=1` returns empty (no tagged revision exists).
3. `_version()` (`scapy/__init__.py:L122`) therefore falls through Methods 0–3 to the **Fallback** block at `scapy/__init__.py:L157-L162`, which computes the file modification time: `d = datetime.datetime.utcfromtimestamp(os.path.getmtime(__file__))` (`scapy/__init__.py:L160`) and `return d.strftime('%Y.%m.%d')` (`scapy/__init__.py:L161`).
4. The mtime of `scapy/__init__.py` is `2026-07-02`, so the fallback yields `2026.07.02`.

The value `2026.07.02` is therefore reported **verbatim** but is explicitly a **file-modification-time fallback**; the canonical `git describe` path is unavailable in this tagless checkout.

## 2. Building & displaying `Ether()/IP()/TCP()`

### The `/` operator stacks layers

The `/` (division) operator is how Scapy stacks protocol layers. It is implemented by `Packet.__div__` (`scapy/packet.py:L596`), aliased as `__truediv__ = __div__` (`scapy/packet.py:L607`). It clones both operands and calls `cloneA.add_payload(cloneB)`, which is what applies the underlayer's binding/overload fields onto the layer beneath it.

### `repr` progression (`Packet.__repr__`, `scapy/packet.py:L552`)

Watching the `repr` grow as each layer is added shows the bindings being applied:

- `repr(Ether())`:
  ```python
  <Ether  |>
  ```
  A bare Ethernet header with no bound payload yet.

- `repr(Ether()/IP())`:
  ```python
  <Ether  type=IPv4 |<IP  |>>
  ```
  Cause → effect: dividing by `IP()` binds `IP` as the payload of `Ether`, and the binding sets the Ethernet **`type=IPv4`** field automatically (the underlayer's overload field).

- `repr(Ether()/IP()/TCP())`:
  ```python
  <Ether  type=IPv4 |<IP  frag=0 proto=tcp |<TCP  |>>>
  ```
  Cause → effect: dividing the `IP` layer by `TCP()` binds `TCP` beneath `IP`, and the binding sets the IP **`proto=tcp`** field. (`frag=0` is also shown on the IP layer.)

### `summary()` (`scapy/packet.py:L1642`)

```python
Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S
```

`summary()` returns `self._do_summary()[1]` (`scapy/packet.py:L1642`). Each default is named here:

- source port **`ftp_data`** (= 20) — the TCP `sport` default rendered by its enum field.
- destination port **`http`** (= 80) — the TCP `dport` default.
- TCP flag **`S`** — the SYN flag, the default `flags` value.
- both IP addresses default to **`127.0.0.1`** (the `src`/`dst` defaults for a locally-constructed `IP()`).

### `command()` (`scapy/packet.py:L1662`)

```python

```

`command()` (`scapy/packet.py:L1662`) reconstructs the exact constructor expression that would rebuild the packet — here identical to what was typed, because every field is still at its default.

## 3. Sending & routing

### `sendp()` (Layer 2) vs `send()` (Layer 3)

Because the subject packet is rooted at `Ether()`, the correct "usual sending mechanism" is the **Layer-2** sender `sendp()` (`scapy/sendrecv.py:L452`). The **Layer-3** sender `send()` (`scapy/sendrecv.py:L422`) is for an `IP()`-rooted packet. Both dispatch to the common emitter `__gen_send()` (`scapy/sendrecv.py:L332`).

Cause → effect: `sendp()` opens a Layer-2 socket and puts the raw Ethernet frame on the wire exactly as built; `send()` opens a Layer-3 socket and lets the operating system build the Layer-2 (Ethernet) header. The socket send itself flows through `SuperSocket.send()` (`scapy/supersocket.py:L97`); the L3 path uses `L3RawSocket` (`scapy/supersocket.py:L283`).

### Verbose emitter output (default `conf.verb = 2`)

With the default verbosity, `__gen_send()` writes one `.` per packet via `os.write(1, b".")` (`scapy/sendrecv.py:L379-L380`) and then prints the summary line `print("\nSent %i packets." % n)` (`scapy/sendrecv.py:L391-L392`). Observed:

- `sendp(p, iface="lo", count=1)`:
  ```console
  .
  Sent 1 packets.
  ```

- `sendp(p, iface="lo", count=3)`:
  ```console
  ...
  Sent 3 packets.
  ```

- `send(IP(dst="127.0.0.1")/TCP(), count=1)` (the Layer-3 sender):
  ```console
  .
  Sent 1 packets.
  ```

Aside on output ordering (observed): when this output is captured **through a pipe**, the unbuffered dots (written directly to fd 1 via `os.write`) are flushed immediately and can appear coalesced ahead of the buffered `print` lines — e.g. all five dots from the three sends above rendered together as `.....` at the very start of the piped capture. In an interactive REPL the dots render inline immediately before each `\nSent N packets.` line. This is a stdout-buffering artifact, not a Scapy behavior change.

### KEY CONTRAST — why the sniffed packet is fully populated

Cause → effect: the pre-send packet held Python defaults with computed fields unresolved (`None`), but the sniffed packet is instantiated **from raw wire bytes**, so Scapy *parses* every field out of the bytes. The parse path is `dissect()` (`scapy/packet.py:L1049`) → `do_dissect()` (`scapy/packet.py:L1002`) → `guess_payload_class()` (`scapy/packet.py:L1062`), which walks the `bind_layers` table to choose the next layer class:

- Ether → IP because the EtherType is `0x0800`.
- IP → TCP because the IP `proto` is `6`.
- When no binding matches, it falls back to `conf.raw_layer` (`Raw`) via `default_payload_class` (`scapy/packet.py:L1090`).

That reconstruction from bytes is exactly why a received packet shows fully-resolved layers and computed fields, while the in-memory pre-send packet does not.

### CHECKSUM PAIRING — each checksum paired with the packet that produced it

The checksums must not be mixed between packets:

- **Marked** packet (`dport=12345`): TCP `chksum = 0x6193`.
  ```python
  ... dport=12345 ... chksum=0x6193 ...
  ```
- **Default** packet (`dport=http`, i.e. 80) from Section 2: TCP `chksum = 0x917c`.
  ```python
  chksum    = 0x917c
  ```
  Cause → effect: the TCP checksum covers the destination port (among other fields), so changing `dport` from `80` to `12345` changes the TCP checksum from `0x917c` to `0x6193`.
- IP `chksum = 0x7ccd` is **identical** in both packets, because the IP header fields (version, ihl, tos, len, id, flags, frag, ttl, proto, src, dst) are the same in both — the differing port lives in the TCP header, which the IP checksum does not cover.

### Session / reassembly classes

Scapy's sniffing can run through a session object that reassembles traffic. The default is `DefaultSession` (`scapy/sessions.py:L32`); `IPSession` (`scapy/sessions.py:L114`) defragments IP on the fly, and `TCPSession` (`scapy/sessions.py:L223`) reassembles certain TCP streams. **(inferred)** Their internal defragmentation/reassembly behavior is described from reading these classes; the round-trip above used the default single-packet capture and did not exercise IP defragmentation or TCP stream reassembly.

## 5. Summary

Tracing the exact packet `Ether()/IP()/TCP()` from construction to capture, Scapy reveals a consistent build → send → sniff story, each step backed by the observed output above:

- **Build/display.** The `/` operator (`__div__`, `scapy/packet.py:L596`) stacks layers and applies bindings, visible in the `repr` progression as `type=IPv4` on Ether and `proto=tcp` on IP. `summary()` names the defaults (`ftp_data`→`http`, flag `S`), and `command()` echoes the reconstructable `Ether()/IP()/TCP()`.
- **Computed fields are deferred.** The in-memory packet leaves length/checksum fields unresolved (`show()` shows IP `ihl/len/chksum` and TCP `dataofs/chksum` as `None`) until `build()`/`post_build()` (`scapy/packet.py:L758`) fills them — which is why `show2()`, `hexdump()`, and `bytes()` reveal IP `ihl=5 len=40 chksum=0x7ccd`, TCP `dataofs=5 chksum=0x917c`, and a total length of `54` bytes.
- **Send/route.** `sendp()` (`scapy/sendrecv.py:L452`) puts the 54-byte Layer-2 frame on the interface chosen from `conf.route` (for `127.0.0.1` that resolves to `('lo', '127.0.0.1', '0.0.0.0')`), while the common emitter `__gen_send` (`scapy/sendrecv.py:L332`) prints one `.` per packet and then `Sent N packets.`. `send()` (`scapy/sendrecv.py:L422`) is the Layer-3 counterpart.
- **Sniff/dissect.** Capturing with `sniff`/`AsyncSniffer` recovers the frame, and `dissect()`/`guess_payload_class()` (`scapy/packet.py:L1049`, `L1062`) reconstruct Ether/IP/TCP from raw bytes — so the received packet is fully populated (e.g. the marked packet's TCP `chksum=0x6193`), in direct contrast to the unresolved pre-send packet.

In short: Scapy defers computed fields in memory and resolves them at build time; routing is consulted from `conf.route` before transmission; and dissection rebuilds a complete, fully-typed packet from the raw bytes seen on the wire.
