## The question (verbatim)

## TL;DR — the root cause in one paragraph

The mis-pairing is **not** a race, a timing artifact, a TCP-flags subtlety, a `Raw`-payload fallthrough, or a `multi_recv` duplication bug. It is a **structural** consequence of two design decisions in the matching algorithm acting together. (1) Scapy buckets every sent packet by the byte string returned from `hashret()` — `self.hsent.setdefault(p.hashret(), []).append(p)` at `scapy/sendrecv.py:244` — and (2) for each received packet it walks that one bucket **in insertion order** and pairs with the **first** sent packet for which `answers()` is truthy, then `break`s (`scapy/sendrecv.py:279-292`). When you set `conf.checkIPsrc`/`conf.checkIPaddr = False`, `IP.hashret()` stops folding the addresses into the key — control falls through to `return struct.pack("B", self.proto) + self.payload.hashret()` at `scapy/layers/inet.py:581` — so two probes addressed to **different** gateways collapse into the **same** bucket. Simultaneously, `IP.answers()` skips its address check (the `if conf.checkIPaddr:` gate at `scapy/layers/inet.py:595`), so an echo-reply that genuinely came from gateway G2 returns truthy for the G1 probe as well. The G1 probe is listed first in the shared bucket, so it "wins" and absorbs G2's reply. The distinct destination IPs that `tcpdump`/Wireshark see on the wire never enter the match key, so the mistake is entirely internal to Scapy's key construction and first-match-wins selection.

## How Scapy matches requests to answers (the pipeline)

Matching is a **two-step, structural** procedure implemented in `SndRcvHandler` (`scapy/sendrecv.py:100`). It never consults wall-clock time, send timestamps, or inter-send delays when *deciding a match* — but it **does** depend on the insertion (send) order of packets within a colliding `hashret()` bucket, because that bucket is walked in insertion order at `scapy/sendrecv.py:279`.

**Step 1 — bucket every sent packet by its `hashret()` key.** `self.hsent` is a `Dict[bytes, List[Packet]]` (declared at `scapy/sendrecv.py:168`). As each stimulus is sent, it is appended to the list for its key:

```python
# scapy/sendrecv.py:244
self.hsent.setdefault(p.hashret(), []).append(p)
```

**Step 2 — for each received packet, pick the first answering sender in its bucket.** In `_process_packet` (`scapy/sendrecv.py`), the received packet's key is computed, the matching bucket is looked up, and the bucket is iterated **in insertion order**; the first sender for which `answers()` is truthy wins, and the loop `break`s:

```python
# scapy/sendrecv.py:276-292
h = r.hashret()                         # :276
if h in self.hsent:                     # :277
    hlst = self.hsent[h]                # :278
    for i, sentpkt in enumerate(hlst):  # :279  (insertion order)
        if r.answers(sentpkt):          # :280
            self.ans.append(QueryAnswer(sentpkt, r))
            ...
            if not self.multi:
                del hlst[i]              # :286
                self.noans += 1
            else:
                ...
                sentpkt._answered = 1
            break                       # :292  (FIRST MATCH WINS)
```

`sr()` (`scapy/sendrecv.py:635`) wraps `sndrcv()` (`scapy/sendrecv.py:322`); `sr1()` (`scapy/sendrecv.py:656`) returns the *first* answer of the first answered couple:

```python
# scapy/sendrecv.py:663
return cast(Packet, ans[0][1])
```

The base class delegates both operations down the layer stack: `Packet.hashret()` returns `self.payload.hashret()` (`scapy/packet.py:1215-1219`), and `Packet.answers()` requires class equality then delegates to the payload (`scapy/packet.py:1221-1226`):

```python
# scapy/packet.py:1221-1226
def answers(self, other):
    if other.__class__ == self.__class__:
        return self.payload.answers(other.payload)
    return 0
```

**Therefore a mis-pairing requires BOTH conditions to hold at once:**

1. a **`hashret()` bucket collision** — two probes produce the same key and land in the same list, and
2. **`answers()` returning truthy for an earlier-listed, non-originating probe** — so the first-match-wins loop stops on the wrong sender.

The remainder of this document shows, with captured output, exactly when both conditions arise.

## R1 — the exact scenario that mis-pairs a received packet with the wrong sent packet

**Claim.** Send two ICMP echo-request probes to two different gateways, G1 = `10.0.0.1` and G2 = `10.0.0.2`, with `conf.checkIPaddr = False` (and/or `conf.checkIPsrc = False`). Both probes hash to the *same* bucket key `0100000000`. An echo-reply that genuinely came from G2 is then paired with `SENT[0]` — the **G1** probe — because it is first in the shared bucket and `answers()` no longer discriminates on address.

**Captured output (the mis-pairing, reproduced):**

```text
########################################################################
# FINDING 2 - mis-pairing reproduced + control run (R1,R7)
########################################################################
--- conf.checkIPaddr=False conf.checkIPsrc=False ---
  SENT[0] IP / ICMP 10.0.0.254 > 10.0.0.1 echo-request 0 hashret=0100000000
  SENT[1] IP / ICMP 10.0.0.254 > 10.0.0.2 echo-request 0 hashret=0100000000
  RECV    IP / ICMP 10.0.0.2 > 10.0.0.254 echo-reply 0 hashret=0100000000
  buckets: {'0100000000': ['10.0.0.1', '10.0.0.2']}
  RECV.answers(SENT[0]->10.0.0.1)=1  RECV.answers(SENT[1]->10.0.0.2)=1
  >>> sndrcv pairs RECV with SENT[0] (dst=10.0.0.1)  ==> MISPAIR (reply from 10.0.0.2 paired to 10.0.0.1 probe)
```

**Why.** Both probes share bucket `0100000000` (`scapy/sendrecv.py:244`). The reply's key is also `0100000000`, so the lookup at `scapy/sendrecv.py:277-278` selects that one bucket, and the loop at `scapy/sendrecv.py:279` iterates `['10.0.0.1', '10.0.0.2']` in insertion order. `RECV.answers(SENT[0]) = 1` because with `checkIPaddr = False`, `IP.answers()` skips the address gate (`scapy/layers/inet.py:595`); the loop stops at index 0 and `break`s (`scapy/sendrecv.py:292`). The genuinely-from-G2 reply is therefore attributed to the **G1** probe.

## R2 — distinct destination IPs are on the wire, yet the packets are mis-paired *inside* Scapy

**Claim.** `tcpdump`/Wireshark are correct: the two probes really do carry different destination IPs on the wire. The mis-pairing is purely internal to Scapy's `hashret()` **key construction**. With defaults, the addresses are folded into the key and the two gateways differ; with `checkIPaddr = False`, the addresses are **omitted** from the key and the two gateways become indistinguishable.

**Captured output (bucket-collision proof):**

```text
########################################################################
# FINDING 1 - disabling address checks collapses gateways into one bucket (R2,R4)
########################################################################
checkIPaddr=True : hashret(dst=10.0.0.1)=000000ff0134120700   hashret(dst=10.0.0.2)=000000fc0134120700   equal=False
checkIPaddr=False: hashret(dst=10.0.0.1)=0134120700           hashret(dst=10.0.0.2)=0134120700           equal=True
```

**Why, at the byte level.** `IP.hashret()` chooses between two branches:

```python
# scapy/layers/inet.py:577-581
if conf.checkIPsrc and conf.checkIPaddr:
    return (strxor(inet_pton(socket.AF_INET, self.src),
                   inet_pton(socket.AF_INET, self.dst)) +
            struct.pack("B", self.proto) + self.payload.hashret())
return struct.pack("B", self.proto) + self.payload.hashret()
```

- With **both flags `True`** (`scapy/layers/inet.py:577`), the key begins with `strxor(src, dst)` (`scapy/layers/inet.py:578-580`). For src `10.0.0.254`: `254 ^ 1 = 0xFF` and `254 ^ 2 = 0xFC`, so the leading four bytes are `000000ff` for G1 and `000000fc` for G2 — the keys differ in exactly that trailing byte (`ff` vs `fc`).
- With **either flag `False`**, control falls through to the address-omitting return at `scapy/layers/inet.py:581`, which emits only `struct.pack("B", self.proto)` (`01` for `socket.IPPROTO_ICMP`) followed by `self.payload.hashret()`. No address bytes appear, so both gateways yield the identical key `0134120700`.

The full-key decomposition (verified independently): `000000ff` (strxor) + `01` (proto) + `34120700` (`struct.pack("HH", 0x1234, 7)`, native little-endian) = `000000ff0134120700`. Dropping the strxor prefix leaves `0134120700`. The gateway-distinguishing information lives *entirely* in the `000000ff`/`000000fc` prefix that vanishes at `scapy/layers/inet.py:581`. This is why the wire being correct is irrelevant to the internal match: the destination address is simply not part of the key anymore.

This symmetry is intentional and is asserted by the in-repo tests — a request `IP(src=a1,dst=a2)/ICMP(type=8)` and its swapped-address reply `IP(src=a2,dst=a1)/ICMP(type=0)` hash **equal** (`test/regression.uts:1215-1219`), so a legitimate reply collapses onto its own request's bucket. The defect appears only when the addresses are removed and *two different requests* consequently collapse together.

## R3 — it is not a timing/race condition; sequential sends and delays cannot help

**Claim.** The selection depends only on bucket membership and position within the bucket, never on wall-clock time, send timestamps, or inter-send delays. It **does** depend on insertion (send) order within a colliding `hashret()` bucket — the bucket is iterated in insertion order at `scapy/sendrecv.py:279` — so the packet that occupies index 0 of the shared bucket is the one that wins. Adding inter-send delays cannot change a structural collision: a delay changes only *when* a packet is appended, not the relative order of the two colliding probes within the bucket.

**Captured output:**

```text
########################################################################
# R3 - STRUCTURAL, not temporal
########################################################################
  _process_packet references 'time'=False 'sent_time'=False ; IP.answers references time/sleep=False
  order [G1,G2] -> pairs 10.0.0.1 ;  order [G2,G1] -> pairs 10.0.0.2  (position decides, not delay)
```

**Why.** Inspecting the source of `SndRcvHandler._process_packet` shows it references neither `time` nor `sent_time`, and `IP.answers` references neither `time` nor `sleep` — the matching decision is computed purely from packet structure. The second line is decisive: with the identical reply, sending order `[G1, G2]` pairs it to `10.0.0.1`, while order `[G2, G1]` pairs it to `10.0.0.2`. **Position in the bucket decides, not elapsed time.** A delay merely changes *when* packets are appended, not *which* one is first in a colliding bucket, so it cannot fix the mismatch. (Timestamps are recorded elsewhere for latency reporting, but they are not consulted by `answers()` or by the selection loop at `scapy/sendrecv.py:279-292`.)

## R4 — why `conf.checkIPsrc = False` / `conf.checkIPaddr = False` do not help (they are the trigger), and exactly how they change `hashret()` and `answers()`

**Claim.** These two flags are precisely what *causes* the mis-pairing; disabling them removes the only gateway discrimination Scapy had. They change behavior in two places.

**(a) In `hashret()` — they control whether addresses enter the key.**

- Both `True` → the address-folding branch runs (`scapy/layers/inet.py:577-580`); addresses are **included**, so distinct gateways get distinct buckets.
- Either `False` → the fallthrough runs (`scapy/layers/inet.py:581`); addresses are **omitted**, so distinct gateways **collide** in one bucket.

This is the exact transition captured under R2 (`000000ff…`/`000000fc…` when `True`; both `0134120700` when `False`).

**(b) In `answers()` — `checkIPaddr` gates the address correspondence check.**

```python
# scapy/layers/inet.py:595-599
if conf.checkIPaddr:
    if other.dst == "224.0.0.251" and self.dst == "224.0.0.251":  # mDNS
        return self.payload.answers(other.payload)
    elif (self.dst != other.src):
        return 0
```

```python
# scapy/layers/inet.py:607-610
if ((conf.checkIPaddr and (self.src != other.dst)) or
        (self.proto != other.proto)):
    return 0
return self.payload.answers(other.payload)
```

With `checkIPaddr = False`, the `elif (self.dst != other.src)` reject at `scapy/layers/inet.py:598-599` is skipped, and the `self.src != other.dst` clause at `scapy/layers/inet.py:607-608` is short-circuited away. The reply therefore "answers" **both** probes.

**Control run proves the flags are the trigger** — with the *default* `checkIPaddr = True`/`checkIPsrc = True`, the same reply pairs *correctly*:

```text
--- conf.checkIPaddr=True conf.checkIPsrc=True ---
  SENT[0] IP / ICMP 10.0.0.254 > 10.0.0.1 echo-request 0 hashret=000000ff0100000000
  SENT[1] IP / ICMP 10.0.0.254 > 10.0.0.2 echo-request 0 hashret=000000fc0100000000
  RECV    IP / ICMP 10.0.0.2 > 10.0.0.254 echo-reply 0 hashret=000000fc0100000000
  buckets: {'000000ff0100000000': ['10.0.0.1'], '000000fc0100000000': ['10.0.0.2']}
  RECV.answers(SENT[0]->10.0.0.1)=0  RECV.answers(SENT[1]->10.0.0.2)=1
  >>> sndrcv pairs RECV with SENT[1] (dst=10.0.0.2)  ==> CORRECT (paired to 10.0.0.2 probe)
```

Here the buckets are distinct (`000000ff0100000000` vs `000000fc0100000000`), the reply's key equals G2's bucket (because `strxor` is symmetric: `src ^ dst` is identical for the request `10.0.0.254→10.0.0.2` and the reply `10.0.0.2→10.0.0.254`), and `RECV.answers(SENT[0]) = 0` because `self.dst (10.0.0.254) != other.src (10.0.0.254)` is false but `self.src (10.0.0.2) != other.dst (10.0.0.1)` triggers the reject at `scapy/layers/inet.py:607-608`. So disabling the flags does not merely fail to help — it is the direct and only cause.

## R5 — why a unique ICMP sequence number does not always differentiate the probes (tunneled IP-in-IP)

**Claim.** For a tunneled (IP-in-IP) probe, the inner ICMP `seq` *does* enter the **sent** packet's `hashret()` — so the two probes' sent keys differ. But a real ICMP error (e.g. time-exceeded) quotes only the outer IP header plus the **first 8 bytes** of the offending packet, so the inner ICMP id/seq are physically absent from the quote. The received error therefore re-derives a truncated key that matches **no** bucket, and the response is silently dropped (counted as unanswered). The unique sequence number cannot discriminate because it has been truncated away before matching runs.

**Captured output:**

```text
########################################################################
# FINDING 3 - tunneled unique seq truncated out of ICMP-error quote (R5)
########################################################################
full tunneled probe = 48 bytes (outer IP 20 + inner IP 20 + ICMP 8)
  SENT[0] IP / IP / ICMP 10.0.0.254 > 192.168.1.100 echo-request 0 hashret=040134120100
  SENT[1] IP / IP / ICMP 10.0.0.254 > 192.168.1.100 echo-request 0 hashret=040134120200
  RECV    IP / ICMP 10.0.0.2 > 10.0.0.254 time-exceeded ttl-zero-during-transit / IPerror / IPerror hashret=0400
  >>> dropped (hashret 0400 in no bucket)
  quote-length sweep:
    N=28  recv.hashret=0400           DROP
    N=30  recv.hashret=0401           DROP
    N=32  recv.hashret=0401           DROP
    N=34  recv.hashret=04             DROP
    N=36  recv.hashret=0401           DROP
    N=38  recv.hashret=04             DROP
    N=40  recv.hashret=0401           DROP
    N=42  recv.hashret=040100000000   DROP
    N=44  recv.hashret=040100000000   DROP
    N=46  recv.hashret=040134120000   DROP
    N=48  recv.hashret=040134120100   match->SENT0
    N=46  recv.hashret=040134120000   DROP
    N=47  recv.hashret=0401           DROP
    N=48  recv.hashret=040134120100   match->SENT0
```

**Why.** The two sent probes hash to `040134120100` (seq=1) and `040134120200` (seq=2): the leading `04` is the outer proto (IP-in-IP, `struct.pack("B", 4)`), `01` is the inner proto (ICMP), and the trailing `34120100`/`34120200` come from `struct.pack("HH", self.id, self.seq)` in `ICMP.hashret()`:

```python
# scapy/layers/inet.py:986-989
def hashret(self):
    if self.type in icmp_id_seq_types:
        return struct.pack("HH", self.id, self.seq) + self.payload.hashret()
    return self.payload.hashret()
```

(`icmp_id_seq_types = [0, 8, 13, 14, 15, 16, 17, 18, 37, 38]` at `scapy/layers/inet.py:949`; echo-request type 8 is included, so id/seq are hashed.) The unique sequence is genuinely present in the *sent* key.

The received error, however, re-derives its key from the **quoted** copy of the original packet. The quote-length sweep is the proof: for every quote length from 28 up to 46 bytes the re-derived key is a truncated prefix (`0400`, `0401`, `04`, `040100000000`, `040134120000`, …) that appears in **no** bucket → `DROP`. Only at the full **48-byte** quote — which is the first length that includes the inner ICMP sequence bytes — does the key become `040134120100` and match `SENT0`. A standards-minimal ICMP error carries far fewer than 48 bytes of the original datagram, so the inner id/seq never survive; the sequence number cannot differentiate the probes because it is not in the data the matcher sees.

## R6 — confirming the non-causes (Raw payload, TCP flags, `multi_recv`)

**Claim.** The three mechanisms already investigated are genuinely *not* the cause. Captured output:

```text
########################################################################
# R6 - NON-CAUSES
########################################################################
(a) Raw: Raw(b'A').answers(Raw(b'B'))=1 (packet.py:1891-1893); echo pkts haslayer(Raw)=0/0; r.answers(s)=1 via ICMP.answers
(b) TCP-flags: echo pkts haslayer(TCP)=0/0; TCPerror.answers guarded by isinstance(other,TCP) inet.py:1044 -> unreached
(c) multi=False -> first-pick sequence for 2 duplicate replies: ['10.0.0.1', '10.0.0.2']
(c) multi=True  -> first-pick sequence for 2 duplicate replies: ['10.0.0.1', '10.0.0.1']
```

**(a) Not a `Raw`-payload-vs-parsed-layer issue.** `Raw.answers()` does return `1` unconditionally:

```python
# scapy/packet.py:1891-1893
def answers(self, other):
    return 1
```

…but that path is only reached if matching *descends to a `Raw` layer*. The ICMP echo probes have **no** `Raw` layer (`haslayer(Raw) = 0/0` for both sent and received), so matching resolves through the typed `ICMP.answers()` (`scapy/layers/inet.py:991-998`) and never reaches `Raw.answers()`. The observed `r.answers(s) = 1` here comes from `ICMP.answers` (the `(other.type, self.type)` pair `(8, 0)` with equal id/seq at `scapy/layers/inet.py:994-997`), not from `Raw`.

**(b) Not a TCP-flags strictness issue.** The probes are ICMP with **no** TCP layer (`haslayer(TCP) = 0/0`). `TCPerror.answers()` begins with a type guard:

```python
# scapy/layers/inet.py:1043-1045
def answers(self, other):
    if not isinstance(other, TCP):
        return 0
```

Because `other` is never a `TCP` instance in this scenario, `TCPerror.answers()` returns `0` immediately and none of the TCP-flag / seq-ack logic (which is itself gated by `conf.check_TCPerror_seqack = False` at `scapy/config.py:758`) ever runs. No TCP-flag strictness participates in the mis-pairing.

**(c) Not a `multi_recv` duplicate-processing issue.** `multi` controls only whether a matched sender is removed from its bucket for subsequent duplicates (the `del hlst[i]` at `scapy/sendrecv.py:286` in the `if not self.multi:` branch vs. the `_answered` marking in the `else:` branch at `scapy/sendrecv.py:288`). It does **not** change *which* candidate is selected first. The output confirms it: for two duplicate replies, `multi=False` first-picks `['10.0.0.1', '10.0.0.2']` (the first match is removed, so the second duplicate falls through to the next sender) while `multi=True` first-picks `['10.0.0.1', '10.0.0.1']` (nothing removed, so both duplicates pick the same first sender) — but in **both** cases the *first* pick is `10.0.0.1`. Toggling `multi` cannot rescue the very first mis-pairing, which is exactly what the user observed.

## R7 — end-to-end: bucketing + first-match-wins → the mis-pairing

Tying R1, R2, and R4 together through the pipeline of "How Scapy matches":

1. Both probes are sent, so both are appended to bucket `0100000000` (`scapy/sendrecv.py:244`), in the order `['10.0.0.1', '10.0.0.2']`. The addresses are absent from the key because `checkIPaddr = False` routed `IP.hashret()` to `scapy/layers/inet.py:581`.
2. The reply from G2 arrives; its key is also `0100000000`, so the lookup at `scapy/sendrecv.py:277-278` selects the shared bucket.
3. The loop at `scapy/sendrecv.py:279` iterates in insertion order. At index 0 (`SENT[0]`, the G1 probe), `RECV.answers(SENT[0]) = 1` because `IP.answers` skips the address gate (`scapy/layers/inet.py:595`) and `ICMP.answers` sees the `(8, 0)` type pair with equal id/seq (`scapy/layers/inet.py:994-997`).
4. The couple `(SENT[0], RECV)` is recorded and the loop `break`s at `scapy/sendrecv.py:292`. `SENT[1]` (the true originator) is never examined.
5. `sr1()` then returns `ans[0][1]` (`scapy/sendrecv.py:663`) — the "answer" attributed to the **G1** probe, though the packet physically came from **G2**.

This is the complete causal chain: **`hashret()` bucket collision** (addresses dropped at `scapy/layers/inet.py:581`) **+ `answers()` first-match-wins** (`scapy/sendrecv.py:279-292`). Once two probes share a bucket, the first-listed one absorbs the other's reply.

## The critical asymmetry: echo-replies are mis-pairable, ICMP-errors are protected

A cohesive picture must distinguish the two response shapes, because they behave **oppositely** under `checkIPaddr = False`. Captured output:

```text
########################################################################
# ASYMMETRY - echo-reply skips addr check, but IPerror.answers test_IPdst is UNCONDITIONAL
########################################################################
checkIPaddr=False:
  echo-reply(from 10.0.0.2).answers(G1 probe)=1  .answers(G2 probe)=1  -> answers BOTH => mis-pairable
  ICMP-error(quotes G1).answers(G1 probe)=1  .answers(G2 probe)=0  -> answers ONLY correct => protected
  reason: IP.answers checkIPaddr gate skipped (inet.py:595) for echo-reply;
          IPerror.answers test_IPdst=self.dst==other.dst is UNCONDITIONAL (inet.py:1022)
```

- **Echo-replies are mis-pairable.** A direct echo-reply is matched by the *outer* `IP.answers()`, whose address check is entirely behind the `if conf.checkIPaddr:` gate at `scapy/layers/inet.py:595`. Disable the flag and the reply answers **both** probes.
- **ICMP-errors are protected.** An ICMP error is matched by `IPerror.answers()` (the quoted inner IP header; `class IPerror(IP):` is declared at `scapy/layers/inet.py:1013`, with the class name `name = "IP in ICMP"` at `scapy/layers/inet.py:1014`). There, the source test is flag-gated but the **destination test is unconditional**:

```python
# scapy/layers/inet.py:1021-1022
test_IPsrc = not conf.checkIPsrc or self.src == other.src   # flag-gated
test_IPdst = self.dst == other.dst                          # UNCONDITIONAL — no flag gate
```

Because `test_IPdst` at `scapy/layers/inet.py:1022` compares the quoted original destination to each sent packet's destination **regardless of any `conf` flag**, an ICMP error can only match the sender it actually quotes. So errors never cross-pair between gateways: they either match the correct probe (when the quote is long enough — R5) or drop (when the inner discriminator is truncated). The user's cross-gateway symptom is therefore fundamentally an **echo-reply** phenomenon; tunneled ICMP-errors fail differently, by dropping.

## Web-search corroboration (the behavior is by-design matching semantics)

The in-repo semantics match Scapy's published contract; the observed behavior is documented, not a crash or environmental anomaly.

- **`sr`/`sr1` matching contract.** Scapy's published behavior — `sr()` returns request/answer couples plus the list of unanswered packets, and `sr1()` returns only the first answering packet — is exactly what the in-repo engine implements: `sndrcv()` at `scapy/sendrecv.py:322` and `sr1()` returning `ans[0][1]` at `scapy/sendrecv.py:663`. The `SndRcvHandler` docstring describes its own job as the code that "matches the requests and answers" (`scapy/sendrecv.py:105`), and the in-repo usage guide documents the return value as "a list of couples (packet sent, answer)" (`doc/scapy/usage.rst:362`).
- **`conf.checkIPaddr` purpose.** Scapy's documented default is to verify that a reply's source address corresponds to the destination the stimulus was sent to; the usage guide describes disabling that check with `conf.checkIPaddr = False` for broadcast/multicast, where a reply's source legitimately differs from the request's destination (rationale at `doc/scapy/usage.rst:1667`, with the `>>> conf.checkIPaddr = False` example at `doc/scapy/usage.rst:1639`). This confirms the flag governs source/destination correspondence — so disabling it removes address discrimination, which is precisely the bucket collapse demonstrated in R2/R4.
- **`conf.checkIPinIP` purpose.** The `checkIPinIP` flag (default `True`) controls whether Scapy verifies that encapsulated IP-in-IP layers correspond during matching (comment and default at `scapy/config.py:753,755`); that `True` default is what keeps the tunnel handling active at `scapy/layers/inet.py:573-574`.
- **Independent real-world corroboration.** A practitioner report describes `srp1` refusing to accept a reply that Wireshark confirmed was received, and explains that a qualifying answer requires that "IP source and destination are swapped from the packet sent to the answer received" (klauselk.com), fixed by `conf.checkIPaddr = False`. This independently confirms the matching is **structural** (the `self.dst != other.src` swap test at `scapy/layers/inet.py:598`), not timing-based, and that `checkIPaddr` is the address-discrimination switch.

**Conclusion of corroboration:** the mis-pairing is by-design matching semantics; the user's `checkIPsrc`/`checkIPaddr = False` settings are the trigger that removes gateway discrimination.
