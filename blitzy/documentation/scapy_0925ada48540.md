# Scapy Runtime Behavior — Building, Displaying, Sending, and Sniffing a Multi-Layer Packet

This document answers a single practical question empirically: **what does the in-repository
Scapy library actually do, and actually print, across the full lifecycle of one packet** — when
you build a multi-layer `Ether()/IP()/TCP()` stack, display it, route it, send it, and then sniff
the very same traffic back off the wire?

Every behavioral claim below is backed by **two** independent sources of truth:

1. an exact **`file:line` citation** into the Scapy source tree (so the *why* is grounded in code), and
2. **genuine runtime output** captured by actually building and running the in-repo library on this
   branch (`scapy_0925ada48540`) — never memorized or assumed API behavior.

Wherever the output looks surprising, the document explains the underlying mechanism rather than
just recording the result.

## Central thesis (TL;DR)

The investigation reduces to two findings that recur in every section:

- **The same packet displays differently before and after serialization.** A freshly *built* packet
  shows its auto-computed fields (IP `ihl`/`len`/`chksum`, TCP `dataofs`/`chksum`) as `None`, because
  those fields are filled in *lazily, at serialization time*, inside each layer's `post_build`. A
  packet that has gone over the wire and been *dissected* (or merely re-assembled by `show2()`) shows
  those exact fields populated with concrete values.
- **Routing is resolved silently.** `send()` consults the routing table to pick an egress interface
  and source address, but there is **no per-send routing printout**. The only send-time output is a
  progress glyph plus a short count/banner, governed by `conf.verb`.

## How this document was produced (methodology)

Scapy is run directly from the in-repository source (it is *never* `pip install`-ed). The repository
root is placed on `PYTHONPATH` and the public-API umbrella `scapy/all.py` is imported, which is what
the repo-root launcher `run_scapy` does as well — `PYTHONPATH=$DIR exec "$PYTHON" -m scapy`
[`run_scapy`:L1-L13] — before handing off to the interactive console via `interact()`
[`scapy/main.py`:L503] (which falls back to the plain Python REPL here because IPython is not
installed).

```text
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=<repo_root> python3 <script>
```

All probe scripts were kept outside the repository (under `/tmp`) and deleted afterward, so the
working tree stays clean. Importing through `from scapy.all import *` matters: it triggers interface
detection so that `conf.iface` resolves to a real interface. A bare `from scapy.config import conf`
leaves `conf.iface` at its declared default of `None` [`scapy/config.py`:L734].

| Setting | Value | Meaning / why it matters |
|---------|-------|--------------------------|
| `scapy.VERSION` | `2026.06.26` | Version string reported at runtime |
| `conf.verb` | `2` | Default verbosity (0=mute … 3=verbose); `send`/`sr*` are verbose by default [`scapy/config.py`:L759] |
| `conf.iface` | `eth0` | Default egress interface; resolves only after `from scapy.all import *` |
| `conf.use_pcap` | `False` | Use **native** OS sockets, not libpcap [`scapy/config.py`:L832] |
| `conf.use_bpf` | `False` | No BPF backend (not BSD) [`scapy/config.py`:L837] |
| `conf.loopback_name` | `lo` | Loopback interface name on Linux [`scapy/config.py`:L911] |
| `conf.L3socket` | `L3PacketSocket` | Concrete native L3 socket class selected because `use_pcap=False` |

**Rationale — why the version string is `2026.06.26`.** `scapy.VERSION` is produced by `_version()`
[`scapy/__init__.py`:L131-L172], which tries, in order: the `SCAPY_VERSION` environment variable, a
bundled `scapy/VERSION` file, a git-archive tag, and `git describe`. In this checkout there is no
`scapy/VERSION` file and the git-based methods do not yield a tag, so the function reaches its final
fallback — the modification date of `__init__.py` formatted as `%Y.%m.%d`. That is why the "version"
reads like a date.

**Rationale — why native sockets.** Because `conf.use_pcap` and `conf.use_bpf` are both `False`,
Scapy talks to the kernel through native `AF_PACKET`/raw sockets (`L3PacketSocket`). This is also why
**raw-socket operations require root**; the process here runs as `uid 0`, satisfying that
requirement.

**Constraint — no `libpcap`.** This environment has no `libpcap` installed. Any Berkeley Packet
Filter (BPF) `filter=` expression therefore cannot be compiled. Importantly, on a native Linux
socket this does **not** raise — it is logged as an error and the capture proceeds *without* the
filter. Attempting `sniff(iface="lo", count=1, timeout=1, filter="tcp port 9100")` emits:

```text
ERROR: Cannot set filter: libpcap is not available. Cannot compile filter !
```

The message originates in `compile_filter()`, which raises
`ImportError("libpcap is not available. Cannot compile filter !")` [`scapy/arch/common.py`:L74-L76];
the native Linux socket catches that and logs it via `log_runtime.error("Cannot set filter: %s", ex)`
[`scapy/arch/linux.py`:L500-L503]. The practical consequence: in this environment we filter captures
with `count`/`timeout`/`lfilter` and an explicit `iface="lo"`, never a BPF `filter=` argument
[`scapy/sendrecv.py`:L1308].

**Benign import warning.** Importing Scapy emits a `CryptographyDeprecationWarning` about TripleDES,
raised when the IPsec layer references the algorithm [`scapy/layers/ipsec.py`:L573, L577]. It is
harmless and unrelated to the build/send/sniff behavior documented here.

> Note on Python version: the AAP cites Python 3.12.3 for the reference capture; this offline
> environment provides Python **3.13.7**, and **every output shown in this document was captured in
> that documented environment (Python 3.13.7)**. The behavior itself is a *library-level design
> property* rather than an interpreter feature — the auto-computed fields are filled lazily inside
> each layer's `post_build`, and routing is a plain table lookup — so it is not expected to vary with
> the Python minor version (the project supports a range: `tox.ini` envlist and CI
> `python-version: "3.11"` at [`.github/workflows/unittests.yml`:L57]; `pyproject.toml` declares
> `requires-python = ">=3.7, <4"`). A multi-version reproduction matrix was **not** run, so this
> document makes no cross-version byte-for-byte reproduction claim.

## 2. Building & displaying an `Ether()/IP(dst)/TCP(dport)` stack (R1)

**Question:** *How do you construct a simple multi-layer packet, and what does Scapy display about it
as the structure is assembled and just before it is sent?*

### Building with the `/` operator

```python
pkt = Ether()/IP(dst="127.0.0.1")/TCP(dport=80, flags="S")
```

The `/` operator is overloaded on the `Packet` base class as `__div__` (with
`__truediv__ = __div__` so it also works on Python 3) [`scapy/packet.py`:L596]. It does not concatenate
bytes — it **stacks layers**: it clones both operands and calls `add_payload` to attach the
right-hand layer as the payload of the left-hand layer [`scapy/packet.py`:L360]. Reading the operator
left-to-right, `Ether` becomes the lowest layer, `IP` its payload, and `TCP` the payload of `IP`.

### `repr` — the interactive view

Simply evaluating the packet (its `__repr__` [`scapy/packet.py`:L552]) prints a compact, nested view:

```text
<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http flags=S |>>>
```

**Rationale — why `repr` is terse.** `__repr__` deliberately shows **only the fields that differ from
their defaults** (plus a few "always show" fields). That is why most of the dozens of header fields
are hidden here, and why `type=IPv4` appears even though we never set it (see below).

**Rationale — why `Ether.type` is already `IPv4`.** We never assigned the EtherType, yet it shows
`IPv4`. This is the *overload* mechanism. The binding `bind_layers(Ether, IP, type=2048)`
[`scapy/layers/inet.py`:L1101] registers, via `bind_top_down` [`scapy/packet.py`:L1953], an entry
`IP._overload_fields[Ether] = {'type': 2048}`. When `IP` is attached as the payload of `Ether`,
`add_payload` copies that overload into the `Ether` instance's `overloaded_fields`
[`scapy/packet.py`:L360-L372], so `Ether.type` resolves to `2048` (`0x0800` = IPv4) during display and
build. The `bind_top_down` docstring demonstrates exactly this behavior with `Ether()/SNAP()`.

### `summary()` — one line

```python
pkt.summary()
```

```text
Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S
```

`summary()` returns a single-line description [`scapy/packet.py`:L1642]. The port "names"
(`ftp_data` for TCP source port 20, `http` for destination port 80) come from Scapy's enum fields,
which render well-known port numbers as their service names.

### `show()` — the built packet, *as it is*

```python
pkt.show()
```

```text
###[ Ethernet ]###
  dst       = ff:ff:ff:ff:ff:ff
  src       = 00:00:00:00:00:00
  type      = IPv4
###[ IP ]###
     version   = 4
     ihl       = None
     tos       = 0x0
     len       = None
     id        = 1
     flags     =
     frag      = 0
     ttl       = 64
     proto     = tcp
     chksum    = None
     src       = 127.0.0.1
     dst       = 127.0.0.1
     \options   \
###[ TCP ]###
        sport     = ftp_data
        dport     = http
        seq       = 0
        ack       = 0
        dataofs   = None
        reserved  = 0
        flags     = S
        window    = 8192
        chksum    = None
        urgptr    = 0
        options   = ''
```

This is the crux of the whole investigation. `show()` renders a hierarchical view of the packet
**exactly as it currently is**, listing *every* field — including the ones that are still `None`
[`scapy/packet.py`:L1459]. Note the un-filled, auto-computed fields:

- IP `ihl = None`, `len = None`, `chksum = None`
- TCP `dataofs = None`, `chksum = None`

Reading the same fields back directly confirms they really are `None`, not merely hidden:

```python
pkt[IP].ihl, pkt[IP].len, pkt[IP].chksum      # -> (None, None, None)
pkt[TCP].dataofs, pkt[TCP].chksum             # -> (None, None)
```

**Rationale — why these fields are `None` before sending.** The base `Packet.post_build` does no
computation at all; it simply returns `pkt + pay` [`scapy/packet.py`:L767]. The values only get
computed because `IP` and `TCP` **override** `post_build`:

- `IP.post_build` computes `ihl`, `len`, and `chksum` *only when they are `None`*
  [`scapy/layers/inet.py`:L539].
- `TCP.post_build` computes `dataofs` and the `chksum` (the latter via the IP pseudo-header) *only
  when they are `None`* [`scapy/layers/inet.py`:L767].

Crucially, `post_build` runs at **serialization** time — inside `build()`/`do_build()`
[`scapy/packet.py`:L746, L724], driven by `self_build()` [`scapy/packet.py`:L678] — which `show()`
never triggers. A freshly built packet has therefore not been serialized, so the overrides have not
run, so the fields are still their placeholder `None`.

### `show2()` — the *assembled* packet

```python
pkt.show2()
```

```text
###[ Ethernet ]###
  dst       = ff:ff:ff:ff:ff:ff
  src       = 00:00:00:00:00:00
  type      = IPv4
###[ IP ]###
     version   = 4
     ihl       = 5
     tos       = 0x0
     len       = 40
     id        = 1
     flags     =
     frag      = 0
     ttl       = 64
     proto     = tcp
     chksum    = 0x7ccd
     src       = 127.0.0.1
     dst       = 127.0.0.1
     \options   \
###[ TCP ]###
        sport     = ftp_data
        dport     = http
        seq       = 0
        ack       = 0
        dataofs   = 5
        reserved  = 0
        flags     = S
        window    = 8192
        chksum    = 0x917c
        urgptr    = 0
        options   = ''
```

The previously-`None` fields are now concrete: IP `ihl=5`, `len=40`, `chksum=0x7ccd`; TCP
`dataofs=5`, `chksum=0x917c`.

**Rationale — why `show2()` fills them in.** `show2()` is implemented as
`return self.__class__(raw(self)).show(...)` [`scapy/packet.py`:L1486]. That single line does two
things: `raw(self)` **serializes** the packet (running the `post_build` overrides, which compute the
fields), and `self.__class__(...)` **re-dissects** the resulting bytes back into a fresh packet
object. `show2()` then displays that rebuilt object — so every automatic field appears with its
real, computed value. Its docstring says exactly this: it shows "an assembled version of the packet,
so that automatic fields are calculated (checksums, etc.)".

## 3. Routing resolution (R2, part 1)

**Question:** *When you send the packet, how does Scapy decide which interface it leaves on — and
what does it report about that decision?*

The answer to the second half is: **nothing is printed**. Routing is a silent table lookup. To
*observe* the decision the prompt asks about, we inspect the table and the resolved tuple directly.

### The routing table

```python
conf.route
```

```text
Network            Netmask          Gateway            Iface    Output IP           Metric
0.0.0.0            0.0.0.0          <default-gateway>  eth0     <container-ip>      0
<container-net>    255.255.255.0    <default-gateway>  eth0     <container-ip>      0
<default-gateway>  255.255.255.255  0.0.0.0            eth0     <container-ip>      0
127.0.0.0          255.0.0.0        0.0.0.0            lo       127.0.0.1           1
<docker-net>       255.255.0.0      0.0.0.0            docker0  <docker-bridge-ip>  0
```

> **Redaction note.** Every non-loopback row above carries an environment-specific private/container
> address (the container's `eth0` output IP and its default gateway, plus the Docker bridge network),
> none of which is relevant to this loopback-only investigation. Those addresses have been generalized
> to placeholders — `<default-gateway>`, `<container-ip>`, `<container-net>`, `<docker-bridge-ip>`,
> `<docker-net>` — so the document leaks no environment-specific addressing. Only the **loopback row**
> (`127.0.0.0/8 → lo`, output IP `127.0.0.1`), which is the one that actually governs our `127.0.0.1`
> destination, is reproduced verbatim. The interface names (`eth0`, `lo`, `docker0`) and the standard
> netmasks are retained because they are generic and reveal nothing environment-specific.

`conf.route` is an instance of `Route` [`scapy/route.py`:L31]; printing it renders the
`Network / Netmask / Gateway / Iface / Output IP / Metric` table. The row that matters for our
destination is `127.0.0.0/8 → lo` with output IP `127.0.0.1`.

### Resolving the egress for a destination

```python
IP(dst="127.0.0.1").route()
```

```text
('lo', '127.0.0.1', '0.0.0.0')      # (interface, source_ip, gateway)
```

`IP.route()` is a thin wrapper: `return conf.route.route(dst)` [`scapy/layers/inet.py`:L566]. The real
work is in `Route.route(self, dst=None, verbose=conf.verb)` [`scapy/route.py`:L146], whose docstring
defines the return value as the 3-tuple `(iface, output_ip, gateway_ip)`. For `127.0.0.1` it returns
`('lo', '127.0.0.1', '0.0.0.0')`: leave via `lo`, source from `127.0.0.1`, no gateway (direct).

**Rationale — why routing is silent.** Read `Route.route()` carefully: it selects the most specific
matching route and **returns** the tuple. The *only* time it prints anything is the failure path —
`if verbose: warning("No route found (no default route?)")` — taken when no route matches at all
[`scapy/route.py`:L188-L189]. On the success path it prints nothing. So when `send()` calls into
this machinery to choose an interface and source address, the decision is made without any
routing-specific output. This is verifiable directly in the send path: `send()`
[`scapy/sendrecv.py`:L422] resolves its egress interface through `_interface_selection()`
[`scapy/sendrecv.py`:L616], whose body is `iff = next(packet.__iter__()).route()[0]`
[`scapy/sendrecv.py`:L626] — it calls the packet's own `route()` (for an `IP` packet that is
`IP.route()` → `conf.route.route()`) and keeps element `[0]`, the interface. That lookup returns its
tuple silently; nothing about the chosen interface or source IP is printed during the send.

## 4. Sending the packet (R2, part 2)

**Question:** *What does Scapy report while it transmits the packet?*

### `send()` — fire-and-forget at layer 3

```python
send(IP(dst="127.0.0.1")/TCP(dport=9100, flags="S"), iface="lo")
```

```text
.
Sent 1 packets.
```

`send()` transmits at layer 3 [`scapy/sendrecv.py`:L422]; its docstring is literally "Send packets at
layer 3". With `conf.verb == 2`, it prints a single progress glyph `.` (one per packet, written
directly to the output stream) followed by the count banner `Sent 1 packets.`
[`scapy/sendrecv.py`:L392]. Note what is **absent**: there is no line telling you which interface was
chosen or which source IP was used — confirming the silent-routing finding from §3. (The `iface="lo"`
argument here simply pins the interface explicitly; without it, `send()` would consult the routing
table and pick `lo` for `127.0.0.1` anyway.)

### `sr1()` — send and receive the first answer

```python
sr1(IP(dst="127.0.0.1")/TCP(dport=9101, flags="S"), timeout=2, iface="lo")
```

```text
Begin emission:
Finished sending 1 packets.
.
Received 1 packets, got 0 answers, remaining 1 packets
```

`sr1()` [`scapy/sendrecv.py`:L656] is the send-and-receive-first-answer variant built on the
`SndRcvHandler` engine [`scapy/sendrecv.py`:L100] and `sndrcv()` [`scapy/sendrecv.py`:L322]. With the
default verbosity it prints the full emission/reception banner sequence. Each line is a literal in
`scapy/sendrecv.py`:

- `Begin emission:` — [`scapy/sendrecv.py`:L239]
- `Finished sending %i packets.` — [`scapy/sendrecv.py`:L250]
- `Received %i packets, got %i answers, remaining %i packets` — [`scapy/sendrecv.py`:L218]

between which Scapy writes per-packet progress glyphs (`*` for received, `.` for sending ticks)
directly to the file descriptor; the `.` above the final banner is the receive-side tick.

**Rationale — "got 0 answers" on a loopback SYN.** We sent a TCP SYN to `127.0.0.1:9101`, where
nothing listens. Scapy's L3 socket captured `1` packet on the way through, but it was not matched as
an *answer* to our stimulus (the reply did not satisfy the request/answer correlation, so it counts
as `0 answers` with the request `remaining`). `sr1()` therefore returned `None`. This is expected and
correct behavior for an unanswered probe; it is reported, not hidden.

**Rationale — what governs send-time output.** Everything printed by `send()`/`sr1()` is gated by
`conf.verb` (default `2`) [`scapy/config.py`:L759], or the per-call `verbose=` argument. Set
`verbose=0` (or `conf.verb = 0`) and the glyphs and banners disappear entirely. The output is purely
*progress reporting* — it is not, and never includes, a routing decision.

## 5. Sniffing & dissection (R3)

**Question:** *If we sniff for the same traffic, how does Scapy present the received bytes, and how
does it reconstruct the layered structure?*

Because there is no `libpcap` (so no BPF `filter=`), we capture with an `AsyncSniffer` on `lo`, using
a Python `lfilter` predicate and `count=1`, then send the matching packet and collect the result:

```python
import time
t = AsyncSniffer(iface="lo", count=1,
                 lfilter=lambda p: p.haslayer(TCP) and p[TCP].dport == 9100)
t.start()
time.sleep(0.5)                                   # let the sniffer attach
send(IP(dst="127.0.0.1")/TCP(dport=9100, flags="S"), iface="lo")
t.join(timeout=5)
received = t.results[0]
```

`AsyncSniffer` [`scapy/sendrecv.py`:L981] is the threaded capture engine that backs the synchronous
`sniff()` [`scapy/sendrecv.py`:L1308]. The `lfilter` is a pure-Python predicate applied to each
dissected packet — the in-environment replacement for a BPF `filter=` string. The capture succeeded
with exactly one packet:

```text
captured count: 1
received.sniffed_on -> 'lo'
```

`received.sniffed_on` records the interface the packet was captured on (`lo`), confirming the
round-trip went over loopback.

```text
        flags     = S
        window    = 8192
        chksum    = 0x6e40
        urgptr    = 0
        options   = ''
```

Compare this with the **built** packet from §2. The difference is the heart of the whole exercise:

- On the built packet, `repr` was terse and `show()` printed IP `ihl=None len=None chksum=None` and
  TCP `dataofs=None chksum=None`.
- On the sniffed packet, **every field is explicit and concrete** — including IP `ihl=5`, `len=40`,
  `chksum=0x7ccd` and TCP `dataofs=5`, `chksum=0x6e40`. There is no `None` anywhere.

**Rationale — why dissected fields are always concrete.** A sniffed packet does not arrive as a
Python object; it arrives as **bytes**. Scapy turns those bytes back into a layered packet through
`dissect()` [`scapy/packet.py`:L1049] and `do_dissect()` [`scapy/packet.py`:L1002], the inverse of the
build pipeline. Dissection reads each field's value straight out of the wire bytes, so `ihl`, `len`,
and the checksums are whatever the bytes actually contain — never the `None` placeholder, which only
exists on a not-yet-serialized object. The layered structure is reconstructed by guessing each
payload type from the `bind_layers` table (the same bindings that drove `Ether.type` during build in
§2): EtherType `0x0800` → `IP`, IP `proto=6` → `TCP`.

**Rationale — why the sniffed TCP checksum (`0x6e40`) differs from `show2()`'s (`0x917c`).** Both are
*concrete* computed checksums; they differ only because the destination port differs — `9100` for the
sniffed packet versus `80` in the `show2()` example of §2. The TCP checksum covers the header
(including `dport`) and the IP pseudo-header, so changing the port necessarily changes the checksum.
The point that matters is qualitative, not the specific hex: a checksum that was `None` at build time
is a real value once the packet has been serialized and dissected.

**Rationale — same mechanism as `show2()`.** Note that `show2()` (§2) and sniffing produce concrete
fields by the *identical* route: serialize to bytes, then dissect back. `show2()` does it in-process
(`self.__class__(raw(self))` [`scapy/packet.py`:L1486]); sniffing does it across the kernel — the
packet is serialized by `send()`, traverses `lo`, and is dissected on capture. The display code is
the same; only the source of the bytes differs.

## 6. Summary / conclusions (R4)

Synthesizing what Scapy revealed at each stage of the packet's life:

### The build-vs-sniff contrast (the central finding)

The *same* packet — same source object, same protocols — presents differently before and after it is
serialized to bytes. The auto-computed header fields are the tell:

| Field | Built packet — `show()` | After serialize+dissect — `show2()` / sniffed |
|-------|-------------------------|-----------------------------------------------|
| IP `ihl` | `None` | `5` |
| IP `len` | `None` | `40` |
| IP `chksum` | `None` | `0x7ccd` |
| TCP `dataofs` | `None` | `5` |
| TCP `chksum` | `None` | `0x917c` (dport 80) / `0x6e40` (dport 9100) |

The reason is a single design choice: these fields are computed **lazily, at serialization time**,
inside each layer's overridden `post_build` — `IP.post_build` [`scapy/layers/inet.py`:L539] and
`TCP.post_build` [`scapy/layers/inet.py`:L767] — whereas the base `Packet.post_build` does nothing but
`return pkt + pay` [`scapy/packet.py`:L767]. Consequently:

- `show()` displays the packet **as-is**, *before* serialization, so the fields are `None`
  [`scapy/packet.py`:L1459].
- `show2()` displays an **assembled** copy: it serializes with `raw()` and re-dissects via the class
  constructor [`scapy/packet.py`:L1473], so the fields are concrete.
- A **sniffed** packet is bytes off the wire run through `dissect()`/`do_dissect()`
  [`scapy/packet.py`:L1049, L1002], so its fields are likewise concrete.

In short: **`show()` is pre-serialization (`None`); `show2()` and sniffing are post-serialization
(concrete).**

### Routing is resolved silently

Across the entire send path there is **no routing printout**. `send()` [`scapy/sendrecv.py`:L422]
consults `IP.route()` → `conf.route.route()` [`scapy/layers/inet.py`:L559; `scapy/route.py`:L146],
which simply *returns* the `(iface, output_ip, gateway)` tuple and only prints on the no-route failure
path. The routing decision for `127.0.0.1` is `('lo', '127.0.0.1', '0.0.0.0')`. To *see* the egress
decision, you must ask for it (`conf.route`, `IP(dst).route()`); Scapy will not volunteer it during a
send.

### Transmission output is just progress reporting

What `send()`/`sr1()` print — the `.`/`*` glyphs and the `Begin emission:` /
`Finished sending N packets.` / `Received X packets, got Y answers, remaining Z packets` banners
[`scapy/sendrecv.py`:L239, L250, L218, L392] — is purely progress/result reporting, gated by
`conf.verb` (default `2`) [`scapy/config.py`:L759]. It conveys *how many* packets went out and came
back, not *where* they were routed.

### The packet lifecycle in one sentence

Building stacks layers via `/` and `add_payload` and leaves computed fields unset; displaying with
`show()` shows that unfinished state; sending serializes the packet (computing the fields), selects an
egress silently via the routing table, and reports only progress; sniffing captures the resulting
bytes and dissects them back into a fully-populated layered packet — which is why the round-tripped
packet finally shows every computed field as a concrete value.

(`pyproject.toml` declares the supported range as `requires-python = ">=3.7, <4"`).
