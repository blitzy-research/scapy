**Question.** Construct (1) a normal `Ether()/IP()/TCP()` stack, (2) a frame carrying a
deliberately short payload ("~10 bytes"), and (3) a frame with an unrecognized/weird EtherType
("0x9000 or random"). No packets are transmitted; everything happens in memory.

**Command.**

```bash
cd /tmp/blitzy/scapy/blitzy-cf45a59e-fb94-46e5-a801-76610266538c_164580 && PYTHONPATH=$PWD .venv/bin/python /tmp/scapy_obs.py
```

**Observed output — R1-relevant excerpt** (the complete, unedited `stdout`+`stderr` transcript for this command is reproduced verbatim in **Appendix A.1**):

```
    p2 Ether()/IP()/TCP()/Raw(b'X'*10) -> ['Ether', 'IP', 'TCP', 'Raw'], 64
    p2b Ether()/Raw(b'A'*10) -> ['Ether', 'Raw'], 24

```

**What each packet is, and its serialized length:**

- **(1) Normal stack** — `Ether()/IP()/TCP()` → layers `['Ether', 'IP', 'TCP']`, **54 bytes**.
  This is the baseline: 14 (Ethernet header) + 20 (default IP header, `ihl=5`) + 20 (default TCP
  header, `dataofs=5`) = 54.
- **(2) Short-payload frames (user example "~10 bytes")** —
  `Ether()/IP()/TCP()/Raw(b"X"*10)` → `['Ether', 'IP', 'TCP', 'Raw']`, **64 bytes** (54 + 10); and
  a bare Layer-2 frame `Ether()/Raw(b"A"*10)` → `['Ether', 'Raw']`, **24 bytes** (14 + 10). Neither
  is padded up to the 60-byte Ethernet minimum — see R2.
- **(3) Unrecognized-EtherType frame (user example "0x9000 or random")** —
  `Ether(type=0x9000)/Raw(b"payload!")` → `['Ether', 'Raw']`, **22 bytes** (14 + 8). `0x9000`
  happens to be Scapy's own default `Ether.type`, and it is not bound to any protocol — see R4.

**Causal code explanation.** Packets are stacked with the `/` operator and serialized to bytes via
`raw()` (equivalently `bytes()`); no packet is transmitted anywhere in this investigation. The
serialization entry point is `raw()` in `scapy/compat.py:112`, whose body is simply:

```python
def raw(x):
    # type: (Packet) -> bytes
    """
    Builds a packet and returns its bytes representation.
    This function is and will always be cross-version compatible
    """
    return bytes(x)                    # scapy/compat.py:118
```

The `Ether` layer's field layout is defined in `scapy/layers/l2.py:244-248`:

```python
class Ether(Packet):
    name = "Ethernet"
    fields_desc = [DestMACField("dst"),                       # l2.py:246
                   SourceMACField("src"),                     # l2.py:247
                   XShortEnumField("type", 0x9000, ETHER_TYPES)]  # l2.py:248
```

The `type` field defaults to `0x9000` (`XShortEnumField`, `scapy/layers/l2.py:248`), which is why
packet (3)'s default EtherType is `0x9000` unless overridden. `DestMACField`/`SourceMACField`
supply the destination and source MACs (the destination defaults to broadcast when no route
resolves — the origin of the benign L2 warnings noted in §0.4).

## R2 — Does Scapy auto-pad to the Ethernet minimum on build? → NO. The frame stays small.

**Question.** For a short payload, does Scapy auto-pad the frame up to the Ethernet minimum size on
build, or does the frame "stay small"?

**Answer.** It **stays small**. A default `Ether()/IP()/TCP()` serializes to exactly **54 bytes**
with **no** padding added; the 64-byte and 24-byte short frames from R1 are likewise **not** padded
to the 60-byte on-wire minimum.

**Command.** (same script as R1)

```bash
cd /tmp/blitzy/scapy/blitzy-cf45a59e-fb94-46e5-a801-76610266538c_164580 && PYTHONPATH=$PWD .venv/bin/python /tmp/scapy_obs.py
```

**Observed output — R2-relevant excerpt, including the hexdump of the 54-byte default frame** (complete, unedited `stdout`+`stderr` transcript in **Appendix A.1**):

```
R2: raw(Ether()/IP()/TCP()) = 54 bytes (STAYS SMALL, no pad-to-60)
hexdump of the 54-byte default frame:
0000  FF FF FF FF FF FF 00 00 00 00 00 00 08 00 45 00  ..............E.
0010  00 28 00 01 00 00 40 06 7C CD 7F 00 00 01 7F 00  .(....@.|.......
0020  00 01 00 14 00 50 00 00 00 00 00 00 00 00 50 02  .....P........P.
0030  20 00 91 7C 00 00                                 ..|..
    short frame p2 = 64 bytes; bare L2 p2b = 24 bytes (NOT padded to 60)
```

The hexdump is exactly 54 bytes (rows `0000`–`0030`, last row ending at offset `0x35`). Reading it:
`FF FF FF FF FF FF` (broadcast dst) · `00 00 00 00 00 00` (src) · `08 00` (EtherType = IPv4) ·
`45 00 …` (IP header, `45` = version 4, ihl 5) · then the TCP header. There are **no trailing zero
padding bytes** appended after the TCP header — the frame ends where the protocol data ends.

**Root cause — the build path contains no pad-to-60 logic.** `Packet.build`
(`scapy/packet.py:746-756`) composes a layer as *do-build* + *build-padding* + *build-done*:

```python
def build(self):                       # scapy/packet.py:746
    p = self.do_build()
    p += self.build_padding()
    p = self.build_done(p)
    return p
```

`Packet.build_padding` (`scapy/packet.py:742-744`) only recurses into the payload — it adds nothing
of its own:

```python
def build_padding(self):               # scapy/packet.py:742
    return self.payload.build_padding()
```

and `Packet.post_build` (`scapy/packet.py:758-767`) simply concatenates this layer's bytes with the
payload's bytes, with **no** minimum-frame / pad-to-60 logic anywhere:

```python
def post_build(self, pkt, pay):        # scapy/packet.py:758
    ...
    return pkt + pay                   # scapy/packet.py:767
```

There is no `+= b"\x00" * (60 - len(...))` anywhere in this path. The only way `build_padding`
contributes bytes is if an explicit `Padding` layer is present (see the padding-provenance section).

**`Ether` adds no build/dispatch overrides — proven at runtime.** The single most important
structural fact tying R2, R4, R5, and R6 together is that the `Ether` class
(`scapy/layers/l2.py:244-272`) overrides **neither** `post_build` **nor** `guess_payload_class`
**nor** `build`/`build_padding`/`extract_padding`. Its entire build and dispatch behavior therefore
derives from the base `Packet` class in `scapy/packet.py`. This was verified by runtime identity
(`is`) checks:

**Command.**

```bash
cd /tmp/blitzy/scapy/blitzy-cf45a59e-fb94-46e5-a801-76610266538c_164580 && PYTHONPATH=$PWD .venv/bin/python /tmp/scapy_obs3.py
```

**Observed output — identity-check excerpt** (the complete, unedited `obs3.py` transcript — this block, the dispatch evidence, the full sweep, and `stderr` — is in **Appendix A.3**):

```
=== R2 root-cause: Ether inherits build/dispatch from base Packet (identity checks) ===
Ether.post_build is Packet.post_build                  -> True
Ether.guess_payload_class is Packet.guess_payload_class -> True
Ether.build is Packet.build                            -> True
Ether.build_padding is Packet.build_padding            -> True
Ether.extract_padding is Packet.extract_padding        -> True
'post_build' in Ether.__dict__                         -> False
'guess_payload_class' in Ether.__dict__                -> False
```

All five methods are the *same function object* as `Packet`'s, and neither `post_build` nor
`guess_payload_class` appears in `Ether.__dict__`. **Conclusion:** there is no pad-to-60 logic
anywhere in the Ethernet build path, so Scapy does not auto-pad on build.

## R3 — Does padding "stick around or disappear" across an `Ether(raw(packet))` round-trip?

**Question.** Convert a packet to raw bytes and re-dissect via `Ether(raw(packet))`. Does any
padding stick around or disappear?

**Answer.** For a normal `Ether()/IP()/TCP()`, the round-trip **preserves the length (54 bytes) and
introduces no `Padding` layer** — because none was there to begin with (R2). The re-dissection
re-dispatches the payload strictly by the EtherType field. Padding is a **dissection-time**
artifact, and it only appears when the serialized bytes actually carry trailing data past a
length-delimited layer (demonstrated in the padding-provenance section).

**Command.** (same script as R1)

```bash
cd /tmp/blitzy/scapy/blitzy-cf45a59e-fb94-46e5-a801-76610266538c_164580 && PYTHONPATH=$PWD .venv/bin/python /tmp/scapy_obs.py
```

**Observed output — R3-relevant excerpt** (complete, unedited `stdout`+`stderr` transcript in **Appendix A.1**):

```
R3: Ether(raw(Ether()/IP()/TCP())) -> ['Ether', 'IP', 'TCP'], 54 preserved, no Padding.
    Re-dispatch: Ether(type=0x0800)/Raw(b'A'*10) round-trips ['Ether','Raw'] -> ['Ether', 'IP']
    .show(): type=IPv4; IP version=4 ihl=1 tos=0x41 len=16705 id=16705 flags=DF frag=321 ttl=65 proto=65 src=127.0.0.1 dst=127.0.0.1
```

**Interpretation.**

- **Round-trip of the normal frame:** `Ether(raw(Ether()/IP()/TCP()))` yields layers
  `['Ether', 'IP', 'TCP']`, length still **54 bytes**, and **no `Padding` layer**. Nothing was
  added and nothing was lost — the padding neither appears nor disappears, because there never was
  any.
- **Re-dispatch demonstration (teaching contrast):** `Ether(type=0x0800)/Raw(b"A"*10)` is built
  with an opaque 10-byte `Raw` payload (`['Ether', 'Raw']`), but after
  `Ether(raw(...))` it re-dissects to `['Ether', 'IP']`. The ten `0x41` (`'A'`) bytes are
  **reinterpreted as an IP header** because the EtherType `0x0800` is bound to `IP`. The `.show()`
  reveals the bytes forced into IP fields: `version=4` (high nibble of `0x41`), `ihl=1` (low
  nibble), `tos=0x41`, `len=16705` (`0x4141`), `id=16705`, `flags=DF`/`frag=321`, `ttl=65`
  (`0x41`), `proto=65`. This shows dissection is driven purely by the EtherType, not by what the
  bytes "meant" at build time.

**Causal code explanation — padding arises only on DISSECTION.** The dissection core is
`Packet.dissect` (`scapy/packet.py:1049-1060`):

```python
def dissect(self, s):                              # scapy/packet.py:1049
    s = self.pre_dissect(s)
    s = self.do_dissect(s)
    s = self.post_dissect(s)
    payl, pad = self.extract_padding(s)            # scapy/packet.py:1057
    self.do_dissect_payload(payl)
    if pad and conf.padding:                       # scapy/packet.py:1059
        self.add_payload(conf.padding_layer(pad))  # scapy/packet.py:1060
```

A `Padding` layer is appended **only if** `extract_padding` returns a non-empty `pad` **and**
`conf.padding` is truthy (it is `1` by default). The base `Packet.extract_padding`
(`scapy/packet.py:982-990`) returns *no* padding:

```python
def extract_padding(self, s):          # scapy/packet.py:982
    ...
    return s, None                     # scapy/packet.py:990
```

Only **length-bearing layers** override `extract_padding` to split off trailing bytes: `IP` and
`TCP` (via their length fields) and `Dot3` (802.3) at `scapy/layers/l2.py:281-284`:

```python
def extract_padding(self, s):          # scapy/layers/l2.py:281  (Dot3)
    tmp_len = self.len
    return s[:tmp_len], s[tmp_len:]
```

Because a plain `Ether()/IP()/TCP()` frame has no trailing bytes beyond what the TCP layer
consumes, `extract_padding` yields an empty `pad`, the `if pad and conf.padding` guard is false, and
**no `Padding` layer is added** on the round-trip. This is why the round-trip length is preserved at
54 bytes.

## R4 — What does Scapy show after Ethernet for an unrecognized EtherType? → the payload becomes `Raw` (no error, no guess)

**Question.** With an unknown EtherType (user example "0x9000 or random"), what does Scapy show
after the Ethernet layer — a raw dump, an error, or a guess?

**Answer.** The payload becomes a **`Raw`** layer. There is **no error** and **no guessing**. This
generalizes across unknown values: `0x9000`, `0x1234`, and `0x88b5` all dissect their payload as
`Raw`. In `.show()`, the numeric `type` is printed as **hex** (`0x9000` / `0x1234` / `0x88b5`)
because `ETHER_TYPES` has no name for it — contrast `0x0800`, which shows as the name `IPv4`.

**Causal code explanation.** Two independent concerns are at work here, and it is important not to
conflate them:

1. **Dispatch (which payload class):** an unbound EtherType falls through to `Raw` via
   `guess_payload_class` → `default_payload_class` → `conf.raw_layer` (detailed in R6c below). This
   is *why* the payload is `Raw` and why there is no error and no guess.
2. **Display (hex vs. name):** whether the numeric `type` prints as `0x9000` or as `IPv4` is purely

   `scapy/data.py:530`). If the numeric value has an entry (e.g. `0x0800` → `IPv4`), the enum field
   prints the name; otherwise it prints the raw hex. Since `ETHER_TYPES` has no name for `0x9000`,
   `0x1234`, or `0x88b5`, they display as hex.

### R6(a) — Where Scapy decides to add padding

Padding is **not** decided on build; it is decided on **dissect**. On build, `Packet.build`
(`scapy/packet.py:746-756`) = `do_build()` + `build_padding()` + `build_done()`; `post_build`
(`scapy/packet.py:758-767`) returns `pkt + pay`; `build_padding` (`scapy/packet.py:742-744`)
recurses into the payload and only an explicit `Padding` layer emits bytes. There is no pad-to-60
step. (Code quoted in full in R2.)

On dissect, the decision is the guard in `Packet.dissect` (`scapy/packet.py:1057-1060`):

```python
payl, pad = self.extract_padding(s)            # scapy/packet.py:1057
self.do_dissect_payload(payl)
if pad and conf.padding:                       # scapy/packet.py:1059
    self.add_payload(conf.padding_layer(pad))  # scapy/packet.py:1060
```

The trailing bytes come from a length-bearing layer's `extract_padding` override (base returns
`(s, None)` at `scapy/packet.py:982-990`; `Dot3` splits on `self.len` at
`scapy/layers/l2.py:281-284`). So "where padding is decided" is `Packet.dissect`, gated by
`conf.padding`, fed by `extract_padding`.

### R6(b) — How an EtherType maps to the next protocol

The mapping is performed by `Packet.guess_payload_class` (`scapy/packet.py:1062-1079`):

```python
def guess_payload_class(self, payload):        # scapy/packet.py:1062
    ...
    for t in self.aliastypes:
        for fval, cls in t.payload_guess:
            try:
                if all(v == self.getfieldval(k)
                       for k, v in fval.items()):
                    return cls  # type: ignore
            except AttributeError:
                pass
    return self.default_payload_class(payload)  # scapy/packet.py:1079
```

It iterates `self.aliastypes` and, for each class, its `payload_guess` list of
`(field-values, class)` pairs; it returns the bound `cls` as soon as **all** field values in a pair
match the current layer's fields (here, the `type` field). `aliastypes` is set per class in
`scapy/base_classes.py:358-360`:

```python
newcls.aliastypes = (                          # scapy/base_classes.py:358
    [newcls] + getattr(newcls, "aliastypes", [])
)
```

The `payload_guess` entries are populated by `bind_layers(...)` calls. The relevant Ethernet
bindings are:

- `bind_layers(Ether, IP, type=2048)` — EtherType `0x0800` → `IP` (`scapy/layers/inet.py:1101`).
- `bind_layers(Ether, IPv6, type=0x86dd)` — EtherType `0x86dd` → `IPv6` (`scapy/layers/inet6.py:4083`).
- `bind_layers(Ether, ARP, type=2054)` — EtherType `0x0806` → `ARP` (`scapy/layers/l2.py:695`),
  alongside the LLC/`Dot1Q`/`Dot1AD` bindings (`scapy/layers/l2.py:687-694`).

So `0x0800` matches the `IP` binding and dissects as `IP` (confirmed by the runtime evidence in R4:
`type=0x0800 -> guess_payload_class=IP`).

### R6(c) — The unrecognized-number fallback

When no `payload_guess` pair matches (an unbound EtherType such as `0x9000`),
`guess_payload_class` returns `self.default_payload_class(payload)`
(`scapy/packet.py:1079`), and `Packet.default_payload_class` (`scapy/packet.py:1081-1090`) returns
`conf.raw_layer`:

```python
def default_payload_class(self, payload):      # scapy/packet.py:1081
    ...
    return conf.raw_layer                       # scapy/packet.py:1090
```

`conf.raw_layer` is assigned to the `Raw` class at `scapy/packet.py:1921`
(`conf.raw_layer = Raw`; `Raw` is defined at `scapy/packet.py:1877`). This is exactly why an unknown
EtherType yields a `Raw` payload with **no error and no guessing** — it is a deterministic fallback,
not a heuristic. (The runtime evidence in R4 shows `default_payload_class=Raw` for every type,
including `0x0800`.)

There is also a **safety net** for the case where a *bound* class is found but fails to parse the
bytes. `Packet.do_dissect_payload` (`scapy/packet.py:1023-1047`) wraps the guessed class'
construction in a `try/except`; on any non-`KeyboardInterrupt` exception it falls back to
`conf.raw_layer` (`scapy/packet.py:1046`):

```python
p = conf.raw_layer(s, _internal=1, _underlayer=self)   # scapy/packet.py:1046
```

So even a matched-but-unparseable payload degrades gracefully to `Raw` rather than raising.

### R6 note — `Ether.dispatch_hook` (class selection at construction, distinct from payload dispatch)

Separately from payload dispatch, `Ether.dispatch_hook` (`scapy/layers/l2.py:267-272`) chooses which
*Layer-2 class* to instantiate from raw bytes:

```python
@classmethod
def dispatch_hook(cls, _pkt=None, *args, **kargs):     # scapy/layers/l2.py:267
    if _pkt and len(_pkt) >= 14:
        if struct.unpack("!H", _pkt[12:14])[0] <= 1500:
            return Dot3
    return cls
```

When the `type/len` field (bytes 12–13) is ≤ 1500, the frame is treated as IEEE 802.3 (`Dot3`)
rather than Ethernet II; otherwise it stays `Ether`. This is a class-selection hook at construction
time — orthogonal to the payload `guess_payload_class` dispatch in R6(b)/(c). It matters here
because `Dot3` is one of the length-bearing layers whose `extract_padding`
(`scapy/layers/l2.py:281-284`) can produce padding on dissection.

```python
            bytes_encode(self.load) if self.raw_packet_cache is None
```

one place the `Padding` load re-enters the serialized output. That is precisely why the appended
padding survives the round-trip and the re-serialized frame is 60 bytes.

## External context — WHY Scapy does not pad (framing R2/R5)

The observed non-padding is not a Scapy quirk; it follows from where Ethernet padding and the FCS
are conventionally produced. The relevant networking facts, each grounded in an authoritative
public reference (primary standard first, then corroborating documentation), are:

- The **minimum Ethernet frame is 64 octets including the 4-byte FCS**; the minimum payload is
  46 octets (42 when an 802.1Q tag is present), and zero-padding is added when the payload is
  shorter than that minimum. This is defined by the IEEE 802.3 standard itself and restated by
  well-referenced secondary sources:
    - IEEE Std 802.3-2018, *IEEE Standard for Ethernet*, §3.1.1 "Packet format"
      (doi:[10.1109/IEEESTD.2018.8457469](https://doi.org/10.1109/IEEESTD.2018.8457469)) — the
      primary normative source for the 64-octet minimum and the frame layout.
    - Wikipedia, "Ethernet frame" — <https://en.wikipedia.org/wiki/Ethernet_frame> — "Its minimum
      size is governed by a requirement for a minimum frame transmission of 64 octets"; the payload
      "can be 42 octets if an 802.1Q tag is present[;] Minimum is 46 octets without" (this article
      cites IEEE Std 802.3-2018 directly).
    - Wireshark wiki, "Ethernet" — <https://wiki.wireshark.org/Ethernet> — "Ethernet packets with
      less than the minimum 64 bytes for an Ethernet packet (header + user data + FCS) are padded
      to 64 bytes, which means that if there's less than 64-(14+4) = 46 bytes of user data, extra
      padding data is added."
- The **preamble/SFD (and frequently the FCS) are handled at OSI Layer 1 by the NIC** and stripped
  before Layer 2 — which is where packet sniffers and user-space tools collect their data — so
  those fields are typically not visible to such tools:
    - Wireshark wiki, "Ethernet" — <https://wiki.wireshark.org/Ethernet> — the minimum size "is
      commonly mentioned at 64 bytes, which is including the FCS[.] This can be confusing as the FCS
      is often not shown by Wireshark, simply because the underlying mechanisms simply don't supply
      it", and "the Ethernet hardware filters the preamble, it is not given to Wireshark or any
      other application."
    - Wikipedia, "Ethernet frame" — <https://en.wikipedia.org/wiki/Ethernet_frame> — "Preamble and
      start frame delimiter are not displayed by packet sniffing software because these bits are
      stripped away at OSI layer 1 by the network interface controller (NIC) before being passed on
      to the OSI layer 2, which is where packet sniffers collect their data."
    - Ask Wireshark, "Where is the FCS field shown in the Wireshark output?" —
      <https://ask.wireshark.org/question/19874/where-is-the-fcs-field-shown-in-the-wireshark-output/>
      — the FCS is present in a capture "only if: the Ethernet adapter can be configured to provide
      it to the host; the driver for the adapter configures it to do so; the packet capture code
      path in the driver and the OS networking code provides" it — confirming FCS/padding are
      hardware/driver responsibilities, not user-space ones.
- The 64-byte floor exists so that **CSMA/CD collision detection** works correctly on half-duplex
  links: a shorter frame could finish transmitting before a collision signal propagated back to
  the sender:
    - monocalc, "Ethernet Frame Size Calculator" —
      <https://monocalc.com/tool/networking/ethernet_frame_size_calculator> — "IEEE 802.3 mandates
      a minimum frame size of 64 bytes … This requirement exists so that collision detection
      (CSMA/CD) works correctly — a frame shorter than 64 bytes would complete transmission before
      the collision signal could propagate back to the sender", and "If your application data is
      shorter [than 46 bytes], zero-padding is added automatically."
    - IEEE Std 802.3-2018 §3.3 and Annex 31A
      (doi:[10.1109/IEEESTD.2018.8457469](https://doi.org/10.1109/IEEESTD.2018.8457469)) — normative
      basis for the slot-time / minimum-frame relationship, as referenced by the Wikipedia article
      above.

**Causal conclusion.** Scapy is a user-space Layer-2+ crafting library that operates **above** the
hardware. By default it emits **no FCS** at the `Ether` layer and performs **no minimum-frame
padding** on build, because that padding and the FCS are conventionally added by the
NIC/driver/hardware at transmission time. This is exactly why `raw(Ether()/IP()/TCP()) == 54` (R2)
and why the size sweep shows `added == 0` for every payload length (R5): it is **expected, correct
behavior — not a bug**. Padding appears in Scapy only when it **dissects** a captured frame that
already carries trailing bytes (the provenance demonstration), because in that direction the
trailing octets are real data present in the buffer.
