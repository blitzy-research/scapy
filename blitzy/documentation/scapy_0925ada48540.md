# Scapy Ethernet Frame-Building Behavior — Investigation (branch `scapy_0925ada48540`)

This document answers, from **observed runtime output**, the reported *"confusing behavior when
building Ethernet frames with Scapy"*: what Scapy actually does when an Ethernet frame is (a) built,
(b) serialized to raw bytes with `raw()`, and (c) re-parsed with `Ether(raw(packet))`. Every
behavioral claim is placed next to the exact console line that demonstrates it, and every mechanism
claim is grounded in an exact `file:line` citation into the source at HEAD
`0925ada485406684174d6f068dbd85c4154657b3`. Statements that come from reading the source rather than
from runtime observation are explicitly labeled **(inferred from source)**.

---

## Executive Summary (TL;DR)

- **Scapy does NOT auto-pad short Ethernet frames.** The build path (`raw()`/`build()`) never injects
  minimum-Ethernet-frame padding. A bare `Ether()/IP()/TCP()` serializes to **`54`** bytes — below the
  802.3 60-byte header+payload minimum — and stays there.
- **`raw()` length is exactly `54 + payload`** at every payload size tested (`0→54, 1→55, 2→56, 4→58,
  6→60, 8→62, 10→64, 20→74`). There is **no threshold at which padding "stops," because it never
  starts.**
- **Round-trip (`Ether(raw(packet))`) preserves padding only when padding actually exists on the
  wire**, and then it comes back as a **distinct `Padding` layer**. An ordinary Scapy-built frame has
  no padding to preserve, so its trailing bytes re-dissect as the upper layer's `Raw` payload, not as
  `Padding`.
- **An unknown EtherType yields a `Raw` data dump — no error, no guess.** `type=0x9000` and a random
  `type=0x9999` both dissect their payload as `Raw`.
- **A `type` value ≤ 1500 is not treated as an EtherType at all** — `Ether.dispatch_hook` interprets it
  as an 802.3 length and re-routes dissection to **`Dot3`** (802.3). Example: `type=5 → Dot3`.
- **`0x9000` is Scapy's DEFAULT `Ether.type`** (`scapy/layers/l2.py:248`) and has **no** name entry in
  `ETHER_TYPES`, which is exactly why it looks "unrecognized" and prints as hex.

## Q1 — Baseline: `Ether()/IP()/TCP()`

**Claim.** The baseline frame serializes to **54 bytes**, which is *below* the Ethernet 60-byte
header+payload minimum (64 bytes including the 4-byte FCS).

**Evidence (observed):**

```text
Q1 len(raw(Ether()/IP()/TCP())) = 54
```

**Why (structural fact).** `54 = 14 (Ether header) + 20 (IP header, ihl=5) + 20 (TCP header,
dataofs=5)`. The Ethernet header is `dst(6) + src(6) + type(2) = 14` bytes
(`scapy/layers/l2.py:246-248`); the IP and TCP defaults are their minimum 20-byte headers. No trailing
bytes are added.

## Q2 — Short payload: does Scapy auto-pad to the Ethernet minimum? **NO.**

**Claim.** Adding a *"really short payload (like 10 bytes)"* yields exactly **64 bytes** (`54 + 10`).
The frame is **never floored to 60**, and the 54-byte baseline stays 54 (`< 60`). This is reported
exactly as observed and is **not** "corrected" toward what a NIC/802.3 would do.

**Evidence (observed):**

```text
Q2 len(raw(Ether()/IP()/TCP()/Raw(b'X'*10))) = 64
```

and, from the Q5 sweep, the baseline stays small rather than being padded up to 60:

```text
   payload= 0 -> frame_len=54
```

**Mechanism pointer.** The build pipeline never adds minimum-frame padding — see **Q6(a)** for the
cause-and-effect grounded in source.

## Q3 — `Ether(raw(packet))` round-trip: does the padding stick around or disappear, and in what form?

The answer has **two required sub-cases**, because "sticks around vs. disappears" depends entirely on
whether any padding exists on the wire.

### Q3A — Unpadded, normally-built frame

Re-parsing the 64-byte `Ether()/IP()/TCP()/Raw(b"X"*10)` yields the four layers below with **no
`Padding` layer**. The 10 trailing bytes come back as the **TCP `Raw` payload**, not as `Padding` —
because there was no padding to preserve (Scapy did not add any on build; see Q2/Q5).

**Evidence (observed):**

```text
Q3A layer names: ['Ether', 'IP', 'TCP', 'Raw']
Q3A has Padding?  0
```

### Q3B — Wire-padded frame (as a NIC pads 54 → 60 with zero bytes)

Now simulate genuine on-the-wire padding by appending six zero bytes to a 54-byte frame
(`raw(Ether()/IP()/TCP()) + b"\x00"*6`) and re-parsing it with `Ether(...)`. The padding **survives**
and re-dissects into a **distinct `Padding` layer**, because `IP.len` bounds the IP portion (`40`
bytes here) and the trailing bytes are split off and wrapped in `conf.padding_layer` (= `Padding`).

**Evidence (observed):**

```text
Q3B has Padding layer? True
Q3B Padding.load = b'\x00\x00\x00\x00\x00\x00'
Q3B IP len = 40
```

### Answer synthesis

- On a **normally-built** Scapy frame there is **nothing to preserve** — no auto-padding on build
  (Q2/Q5) means the round-trip yields `Ether/IP/TCP/Raw` with `haslayer(Padding) == 0` (Q3A).
- **Genuine wire padding** (the zero bytes a real NIC adds) **sticks around** and re-dissects into a
  separate **`Padding`** layer whose `load` is exactly the appended bytes (Q3B). The `file:line`
  mechanism is in **Q6(d)**.

This padding-layer behavior is corroborated by existing regression tests (read-only reference):
`test/regression.uts:1283` (`= Padding assembly`) and `test/regression.uts:1297` (`= Padding and
length computation`), and the assertions at `test/regression.uts:2126` and `test/regression.uts:2144`
(`assert isinstance(pkt, Padding) and pkt.load == b'\xeay$\xf6'`).

## Q4 — Unknown EtherType: what does Scapy show after the Ethernet layer? **A raw data dump — no error, no guess.**

### `type=0x9000` (the user's first example — and Scapy's DEFAULT)

The payload is dissected as **`Raw`**; `.show()` prints the Ethernet header, then a `Raw` load. Scapy
neither raises an error nor guesses a protocol.

**Evidence (observed):**

```text
Q4a type=0x9000 -> payload class = Raw
```

```text
---- Q4a .show() ----
###[ Ethernet ]### 
  dst       = ff:ff:ff:ff:ff:ff
  src       = fa:a8:4b:bc:c5:74
  type      = 0x9000
###[ Raw ]### 
     load      = 'HELLODATA'
```

Two important notes:

- **`0x9000` is Scapy's DEFAULT `Ether.type`** — the field is declared
  `XShortEnumField("type", 0x9000, ETHER_TYPES)` at `scapy/layers/l2.py:248`, confirmed at runtime:

  ```text
  default Ether().type = 0x9000
  ```

- **`0x9000` has no name in `ETHER_TYPES`**, which is *why* `.show()` prints the hex value `0x9000`
  rather than a protocol name, and why it appears "unrecognized." Confirmed at runtime — looking up the
  value raises `KeyError`:

  ```text
  ETHER_TYPES[0x9000]  ->  KeyError: 36864
  ```

- The `dst = ff:ff:ff:ff:ff:ff` (broadcast) is the fallback discussed in the *Warnings observed*
  section (this frame has no routable IP layer). The `src` MAC is host-specific
  (`fa:a8:4b:bc:c5:74` here) and will differ per machine; the invariant evidence is `type = 0x9000`
  and `load = 'HELLODATA'`.

### `type=0x9999` (the user's *"something random"* — an arbitrary unbound value > 1500)

Same behavior: the payload class is **`Raw`**.

**Evidence (observed):**

```text
Q4b type=0x9999 -> payload class = Raw
```

### Required nuance — a value ≤ 1500 is NOT an EtherType

If the 2-byte field is ≤ 1500 it is interpreted as an **802.3 length**, not an EtherType, and
`Ether.dispatch_hook` re-routes the *entire* dissection to **`Dot3`** (802.3). Example with `type=5`:

**Evidence (observed):**

```text
Q4c type=5    -> top class    = Dot3
```

The mechanism (with `file:line`) is in **Q6(e)**.

## Q6 — Mechanism (cause → effect), grounded in exact `file:line`

Line numbers below were re-verified against the live source at HEAD `0925ada4` while authoring this
document. The "no auto-pad" conclusion is confirmed by **both** source reading **and** the Q2/Q5
runtime evidence; other sub-parts are labeled **(inferred from source)** where they describe code that
was read rather than directly observed at runtime.

### (a) WHERE padding is decided (build path) — explains Q2 / Q5

The serialization entry point is `Packet.build()`:

- `Packet.build()` — `scapy/packet.py:746` — is `do_build()` + `build_padding()` + `build_done()`
  (the body at `scapy/packet.py:753-756`: `p = self.do_build(); p += self.build_padding();
  p = self.build_done(p); return p`).
- `Packet.build_padding()` — `scapy/packet.py:742` — merely returns `self.payload.build_padding()`
  (`scapy/packet.py:744`), i.e. it walks the payload chain and appends whatever that chain yields.
- The default `Packet.post_build()` — `scapy/packet.py:758` — returns `pkt + pay`
  (`scapy/packet.py:767`): pure concatenation of layer bytes and payload bytes, with **no** padding.
- `NoPayload.build_padding()` — `scapy/packet.py:1770` — returns `b""` (`scapy/packet.py:1772`): the
  chain terminator contributes nothing.
- The **only** source of padding bytes is an explicit `Padding` layer: `class Padding(Raw)` at
  `scapy/packet.py:1906`, whose `build_padding()` at `scapy/packet.py:1913` emits its own `load`.

**Conclusion (inferred from source, confirmed by runtime).** There is **no automatic
minimum-Ethernet-frame padding** anywhere in `Ether` or the generic build engine. Unless an explicit
`Padding` layer is present, zero padding bytes are produced — which is exactly why the baseline is
`54` (Q1/Q2) and the sweep is linear `54 + payload` with no 60-byte floor (Q5).

### (b) HOW the next protocol is chosen (dissect path) — explains Q4 dispatch

- `Packet.dissect()` — `scapy/packet.py:1049` — calls `do_dissect_payload()` on the remaining bytes
  (`scapy/packet.py:1058`).
- `Packet.do_dissect_payload()` — `scapy/packet.py:1023` — asks `guess_payload_class()`
  (`scapy/packet.py:1031`) for the next class, then instantiates it.
- `Packet.guess_payload_class()` — `scapy/packet.py:1062` — iterates each aliastype's `payload_guess`
  criteria (registered by `bind_layers`/`bind_bottom_up`) and returns the first class whose bound
  field values all match, via `all(v == self.getfieldval(k) for k, v in fval.items())`
  (`scapy/packet.py:1074-1075`, returning at `scapy/packet.py:1076`).
- For Ethernet, the binding that matches IPv4 is `bind_layers(Ether, IP, type=2048)` at
  `scapy/layers/inet.py:1101` (i.e. `type=0x0800 → IP`). Other Ethernet bindings live in
  `scapy/layers/l2.py`: `LLC type=122` (`scapy/layers/l2.py:687`), `LLC type=34928`
  (`scapy/layers/l2.py:688`), `Dot1Q type=33024` (`scapy/layers/l2.py:689`), `Dot1AD type=0x88a8`
  (`scapy/layers/l2.py:690`), `Ether-in-Ether type=1` (`scapy/layers/l2.py:694`), and `ARP type=2054`
  (`scapy/layers/l2.py:695`).
- The `ETHER_TYPES` table — `scapy/data.py:526` (Windows) / `scapy/data.py:530` (non-Windows), backed
  by `scapy/libs/ethertypes.py` via `from scapy.libs.ethertypes import DATA` (`scapy/data.py:359`)
  passed as `_fallback=DATA` (`scapy/data.py:361`) into `load_protocols()`, where the fallback is parsed
  when `/etc/ethertypes` is unavailable (`scapy/data.py:324-325`); the bundled backup registry `DATA`
  begins at `scapy/libs/ethertypes.py:41` (`DATA = b"""`) — supplies only **display names**, independent
  of class dispatch. A name's presence or absence does **not** change which class is chosen.
  **(inferred from source)**

### (c) Unrecognized-protocol fallback — explains Q4 `Raw`

- When **no** binding criterion matches, `guess_payload_class()` falls through at
  `scapy/packet.py:1079` to `default_payload_class()`.
- `Packet.default_payload_class()` — `scapy/packet.py:1081` — returns `conf.raw_layer`
  (`scapy/packet.py:1090`).
- The binding `conf.raw_layer = Raw` is set at `scapy/packet.py:1921` (and `conf.padding_layer =
  Padding` at `scapy/packet.py:1922`). This is precisely why the `0x9000` and `0x9999` payloads become
  **`Raw`** (Q4a/Q4b). **(inferred from source, confirmed by runtime)**
- Additionally, if constructing the guessed class raises an exception, `do_dissect_payload()` catches
  it (`scapy/packet.py:1036`) and, under control of `conf.debug_dissector` (`scapy/packet.py:1037`),
  falls back to `conf.raw_layer` at `scapy/packet.py:1046`. **(inferred from source)**

### (d) Round-trip padding form — explains Q3B

- `IP.post_build()` — `scapy/layers/inet.py:539` — sets `self.len` when it is `None`
  (`scapy/layers/inet.py:545-547`: `tmp_len = len(p) + len(pay)` then packs it into the length field).
  This is why the re-parsed frame reports `IP len = 40`.
- `IP.extract_padding()` — `scapy/layers/inet.py:553` — computes `tmp_len = self.len - (self.ihl << 2)`
  (`scapy/layers/inet.py:554`) and returns `s[:tmp_len], s[tmp_len:]` (`scapy/layers/inet.py:557`), so
  any bytes beyond the IP length are split off as trailing padding.
- Back in `Packet.dissect()`, those trailing bytes are wrapped as `conf.padding_layer` (= `Padding`):
  `if pad and conf.padding: self.add_payload(conf.padding_layer(pad))` at
  `scapy/packet.py:1059-1060`. This is the cause of the Q3B observation `Padding.load =
  b'\x00\x00\x00\x00\x00\x00'` with `IP len = 40`. **(inferred from source, confirmed by runtime)**

### (e) Ether disambiguation — explains Q4 `Dot3` and the `0x9000` default

- `class Ether(Packet)` — `scapy/layers/l2.py:244` — declares its type field as
  `XShortEnumField("type", 0x9000, ETHER_TYPES)` at `scapy/layers/l2.py:248`. This is why the **default**
  `Ether().type` is `0x9000` (Q4a).
- `Ether.dispatch_hook` — `scapy/layers/l2.py:266-267` — inspects the raw bytes: `if _pkt and
  len(_pkt) >= 14:` (`scapy/layers/l2.py:269`), then `if struct.unpack("!H", _pkt[12:14])[0] <= 1500:
  return Dot3` (`scapy/layers/l2.py:270-271`); otherwise `return cls` (`scapy/layers/l2.py:272`).
- `class Dot3(Packet)` — `scapy/layers/l2.py:275` — uses `LenField("len", None, "H")`
  (`scapy/layers/l2.py:279`) and its own `extract_padding` (`scapy/layers/l2.py:281`) which uses that
  length. This is why `type=5` (≤ 1500) re-routes the whole dissection to **`Dot3`** (Q4c).
  **(inferred from source, confirmed by runtime)**

## Cross-reference to the standard (background only — not a Scapy runtime observation)

For context only: IEEE 802.3 specifies a **64-byte minimum frame** including the 4-byte FCS — i.e.
**60 bytes** of header+payload on the wire and a **46-byte minimum payload**. That standard is the
reference point against which Scapy's build path is *measured* in this document; it is **not** a Scapy
runtime behavior. The key finding is precisely that Scapy's `raw()`/`build()` path does **not** enforce
this 60-byte floor (Q2/Q5). This paragraph is stable, established standards knowledge and is provided
purely as background.
