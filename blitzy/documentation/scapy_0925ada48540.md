# How Scapy Behaves at Runtime: Building, Sending, and Sniffing an `Ether/IP/TCP` Packet

This document answers, from **live runtime observation**, what Scapy displays and reports as one concrete multi‑layer packet moves through three lifecycle stages — **built → sent → sniffed back** — followed by a **summary**. Every claim below is paired with the exact command that produced it, its complete unedited output, and a `file:line` citation naming the function/method responsible.

The single packet exercised across all stages is:

The investigation was performed by running Scapy's real code paths (canonical entry points: `python -m scapy`, `from scapy.all import *`, `interact()`) and transcribing the output. Observation scripts were kept outside the repository (under `/tmp/probe_scapy`) so the checked‑out tree stays unchanged.

## Section 2 — Build & display the packet

**Direct answer.** Building the stack one layer at a time, Scapy's interactive `repr` shows **only the fields that were set or overloaded**, and stacking layers triggers **binding side‑effects** (`Ether.type` becomes `IPv4`, `IP.proto` becomes `tcp`, `IP.frag` shows `0`). A freshly built packet displays auto‑computed fields (`IP.ihl`, `IP.len`, `IP.chksum`, `TCP.dataofs`, `TCP.chksum`) as `None`; those values are computed only during serialization and shown concretely by `show2()`. The whole build is **deterministic** across runs.

### 2.1 Incremental construction and the interactive `repr`

Command:

```bash
python3 - <<'PY' 2>/dev/null
from scapy.all import *
print(repr(Ether()))
print(repr(Ether()/IP(dst="127.0.0.1")))
print(repr(Ether()/IP(dst="127.0.0.1")/TCP(dport=80)))
PY
```

Output:

```
<Ether  |>
<Ether  type=IPv4 |<IP  dst=127.0.0.1 |>>
<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http |>>>
```

The interactive `repr` is `Packet.__repr__` [scapy/packet.py:L552]. The `/` operator is `__div__` [scapy/packet.py:L596] with `__truediv__ = __div__` [scapy/packet.py:L607]; it calls `add_payload()` [scapy/packet.py:L360] to stack the lower layer over the upper one. The **binding side‑effects** are:

- Stacking `Ether` over `IP` auto‑sets `Ether.type = IPv4` via `bind_layers(Ether, IP, type=2048)` [scapy/layers/inet.py:L1101].
- Stacking `IP` over `TCP` shows `proto=tcp` and `frag=0` via `bind_layers(IP, TCP, frag=0, proto=6)` [scapy/layers/inet.py:L1113].

The classes involved: `Ether` [scapy/layers/l2.py:L244], `IP` [scapy/layers/inet.py:L521], `TCP` [scapy/layers/inet.py:L753]. Note the `repr` shows `dport=http` (not `80`) and, for `IP`/`TCP`, human‑readable enum names, because these are enum fields. The `repr` lists a field when it is present in the layer's set fields or overloaded fields — which is why `dport` (explicitly set) appears while the unset `sport` does not.

The resolution happens on the serialization path: `__bytes__` [scapy/packet.py:L592] → `build()` [scapy/packet.py:L746] → `do_build()` [scapy/packet.py:L724] → `post_build()` [scapy/packet.py:L758], where lengths and checksums are computed. **Key nuance:** `build()` computes those values on a serialization copy and does **not** mutate the live object — so even after calling `raw(pkt)`, reading `pkt[IP].len` still returns `None` (demonstrated in §2.6). - **Frame‑length distinction (Correction #5):** `IP.len == 40` is the IP total length (IP header 20 + TCP header 20). The full **Ethernet frame** `len(raw(pkt))` is **54** bytes (14‑byte Ethernet header + 40). These are different quantities.

## Section 5 — Summary: what Scapy revealed at each stage

For the single packet `Ether()/IP(dst="127.0.0.1")/TCP(dport=80)`, the three lifecycle stages reveal three distinct faces of the same object, unified by one theme — the **auto‑field resolution transition**.

**The analytical spine — auto‑fields resolve from `None` to concrete.** A freshly built packet displays `IP.ihl`, `IP.len`, `IP.chksum`, `TCP.dataofs`, and `TCP.chksum` as `None` (§2.2). Serialization computes them via `build()` [scapy/packet.py:L746] → `post_build()` [scapy/packet.py:L758] — but on a copy, so the live object keeps showing `None` (`pkt[IP].len` is still `None` after `raw(pkt)`, §2.6). Only when the bytes are re‑interpreted — by `show2()` (§2.2) or by capture‑and‑dissect (§4.1) — do the fields appear concretely: `ihl=5`, `len=40`, `chksum=0x7ccd`, `dataofs=5`. The TCP checksum depends on the ports: `0x917c` for `dport=80` and `0x6abd` for `dport=9999`.

**How Scapy DISPLAYS at build (§1–§2).** The interactive `repr` [scapy/packet.py:L552] shows only set/overloaded fields and applies binding side‑effects (`Ether.type=IPv4`, `IP.proto=tcp`, `frag=0`) from `bind_layers(...)` [scapy/layers/inet.py:L1101,L1113]. `show()` [scapy/packet.py:L1459] renders the live object (auto‑fields `None`); `show2()` [scapy/packet.py:L1473] renders after rebuild (auto‑fields resolved). `summary()` [scapy/packet.py:L1642] joins per‑layer `mysummary()`; `command()` [scapy/packet.py:L1662] emits the constructor form; `ls()` [scapy/packet.py:L2328] tabulates every field with its type and default; and the `hexdump` family [scapy/utils.py:L273,L304,L326,L348] plus `raw()` expose the 54‑byte wire frame (vs. `IP.len=40`). The build is fully deterministic (`IP.id=1`, `TCP.sport=20`).

**How Scapy REPORTS on send (§3).** `send()`/`sendp()` [scapy/sendrecv.py:L422,L452] resolve egress from `conf.route` (`Route.__repr__` [scapy/route.py:L47], `route()` [scapy/route.py:L146] returning `(iface, output_ip, gateway)`), select `L3PacketSocket`/`L2Socket` [scapy/arch/linux.py:L587,L475], and — via `__gen_send()` [scapy/sendrecv.py:L332] — print an unbuffered progress dot [scapy/sendrecv.py:L380] then `Sent N packets.` [scapy/sendrecv.py:L392]; `verbose=0` is silent. Unresolved destination MACs on a broadcast interface trigger a warning and a broadcast fallback [scapy/layers/l2.py:L178].

**How Scapy PRESENTS/RECONSTRUCTS on sniff (§4).** `AsyncSniffer`/`sniff()` [scapy/sendrecv.py:L981,L1308] capture bytes on an `L2ListenSocket` [scapy/arch/linux.py:L579] and run the dissection chain (`__init__` [scapy/packet.py:L141] → `dissect()` [scapy/packet.py:L1049] → `do_dissect()` [scapy/packet.py:L1002] → `guess_payload_class()` [scapy/packet.py:L1062]). The reconstructed packet shows concrete auto‑fields and a **synthetic Ethernet header** for a layer‑3 send. Unbound bytes fall back to `Raw` (`conf.raw_layer`), and `conf.debug_dissector` toggles between silent fallback and log‑and‑re‑raise (`do_dissect_payload()` [scapy/packet.py:L1023]).

### The five corrections vs. the baseline

1. **Version is DATE‑DERIVED** — observed `2026.07.08` (the run date), from the mtime fallback `strftime('%Y.%m.%d')` [scapy/__init__.py:L161], exposed via `conf.version` [scapy/config.py:L726]. Not hardcoded; the baseline's `2026.07.07` was simply its own run date. (§1.5)
2. **`TCP.sport` is a fixed `ShortEnumField` = 20 (`ftp_data`), not `RandShort`**, and `IP.id` = 1; the build is deterministic (≥2‑run transcript in §2.7).
3. **libpcap is PRESENT here** — BPF `filter=` compiles and works (`compile_filter` returns a `bpf_program`; `filter="tcp port 9999"` captures, `filter="udp"` excludes); the "Cannot set filter" error path does not fire. The baseline environment lacked libpcap; `lfilter=` is shown as the backend‑independent alternative. (§4.5)
4. **`Ether.src` comes from the routed egress interface** (`lo` → `00:00:00:00:00:00`; `eth0` → hardware address, volatile); an unresolved `dst` becomes broadcast, with a WARNING on `eth0` and silence on `lo` [scapy/layers/l2.py:L178]. (§3.5)
5. **`IP.len` = 40 (IP 20 + TCP 20) vs. the full Ethernet frame `raw(pkt)` = 54 (Ether 14 + 40)** — distinct quantities. (§2.6)
