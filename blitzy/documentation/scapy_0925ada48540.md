# How Scapy Behaves at Runtime: Building, Sending, and Sniffing an `Ether/IP/TCP` Packet

This document answers, from **live runtime observation**, what Scapy displays and reports as one concrete multi‑layer packet moves through three lifecycle stages — **built → sent → sniffed back** — followed by a **summary**. Every claim below is paired with the exact command that produced it, its complete unedited output, and a `file:line` citation naming the function/method responsible.

## Packet under study and environment

The single packet exercised across all stages is:

```python

```

The investigation was performed by running Scapy's real code paths (canonical entry points: `python -m scapy`, `from scapy.all import *`, `interact()`) and transcribing the output. ## Section 2 — Build & display the packet

**Direct answer.** Building the stack one layer at a time, Scapy's interactive `repr` shows **only the fields that were set or overloaded**, and stacking layers triggers **binding side‑effects** (`Ether.type` becomes `IPv4`, `IP.proto` becomes `tcp`, `IP.frag` shows `0`). A freshly built packet displays auto‑computed fields (`IP.ihl`, `IP.len`, `IP.chksum`, `TCP.dataofs`, `TCP.chksum`) as `None`; those values are computed only during serialization and shown concretely by `show2()`. The whole build is **deterministic** across runs.

### 2.1 Incremental construction and the interactive `repr`

Command:

```bash
python3 - <<'PY' 2>/dev/null
from scapy.all import *
print(repr(Ether()))
print(repr(Ether()/IP(dst="127.0.0.1")))
print(repr(Ether()/IP(dst="127.0.0.1")/TCP(dport=80)))
PY
```

Output:

```
<Ether  |>
<Ether  type=IPv4 |<IP  dst=127.0.0.1 |>>
<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http |>>>
```

The interactive `repr` is `Packet.__repr__` [scapy/packet.py:L552]. The `/` operator is `__div__` [scapy/packet.py:L596] with `__truediv__ = __div__` [scapy/packet.py:L607]; it calls `add_payload()` [scapy/packet.py:L360] to stack the lower layer over the upper one. The **binding side‑effects** are:

- Stacking `Ether` over `IP` auto‑sets `Ether.type = IPv4` via `bind_layers(Ether, IP, type=2048)` [scapy/layers/inet.py:L1101].
- Stacking `IP` over `TCP` shows `proto=tcp` and `frag=0` via `bind_layers(IP, TCP, frag=0, proto=6)` [scapy/layers/inet.py:L1113].

The classes involved: `Ether` [scapy/layers/l2.py:L244], `IP` [scapy/layers/inet.py:L521], `TCP` [scapy/layers/inet.py:L753]. Note the `repr` shows `dport=http` (not `80`) and, for `IP`/`TCP`, human‑readable enum names, because these are enum fields. The `repr` lists a field when it is present in the layer's set fields or overloaded fields — which is why `dport` (explicitly set) appears while the unset `sport` does not.

## Section 3 — Send & report

**Direct answer.** On send, Scapy resolves egress from its **routing table** (`conf.route`), selects a socket (layer‑3 `send()` uses `iface.l3socket()`, layer‑2 `sendp()` uses `iface.l2socket()`), and — at the default verbose level — prints a per‑packet progress **dot** followed by `Sent N packets.` `verbose=0` is completely silent. If the destination MAC cannot be resolved on a broadcast interface (e.g. `eth0`), Scapy warns and falls back to the broadcast address.

### 3.2 `send()` (layer 3) and `sendp()` (layer 2), default verbose

`send()` [scapy/sendrecv.py:L422] transmits at **layer 3** — it selects `iface.l3socket()` (which is `L3PacketSocket` on Linux, so the kernel supplies the link header). `sendp()` [scapy/sendrecv.py:L452] transmits at **layer 2** — it selects `iface.l2socket()` (`L2Socket`), emitting the full frame.

This matches the **official Scapy documentation**, which is cited here rather than merely asserted. The Usage guide's `lsc()` command listing documents `send` as *"Send packets at layer 3"* and `sendp` as *"Send packets at layer 2"*, and the `scapy.sendrecv` API reference states that `send` *"determines the interface (or L2 source to use) based on the routing table: conf.route / conf.route6"* — corroborating the routing‑driven layer‑3 egress observed in §3.1. The same API reference documents the `AsyncSniffer` start/stop/join model used in §4.1 and its `lfilter` predicate, and the Usage guide documents `show()` vs `show2()` (used in §2.2). Sources:
- Scapy Usage guide — `https://scapy.readthedocs.io/en/latest/usage.html`
- `scapy.sendrecv` API reference — `https://scapy.readthedocs.io/en/latest/api/scapy.sendrecv.html`

### 4.4 `conf.debug_dissector`: swallow‑and‑fallback vs. log‑and‑re‑raise

### 4.5 libpcap and BPF filters — the libpcap‑absent path (Correction #3)

**Direct answer.** In the canonical baseline, **libpcap is absent**. A BPF `filter=` string therefore cannot be compiled, so `sniff(filter=...)` emits a **handled** error to stderr — `ERROR: Cannot set filter: libpcap is not available. Cannot compile filter !` — and then **continues without crashing**, returning a normal (here empty) `PacketList`. This is exactly why the bounded captures in §4.1/§4.2 use the Python `lfilter=` predicate: `lfilter=` is evaluated in Python and needs no BPF backend, so it works whether or not libpcap is present. This is mandatory Correction #3.

**The mechanism (with anchors).** A BPF filter is compiled by `compile_filter()` [scapy/arch/common.py:L53], which imports the `winpcapy` ctypes wrapper. That wrapper calls `find_library("pcap")` [scapy/libs/winpcapy.py:L38]; when libpcap is not installed this returns `None`, so the wrapper raises `OSError("Cannot find libpcap.so library")` [scapy/libs/winpcapy.py:L40]. `compile_filter()` catches that `OSError` and re‑raises `ImportError("libpcap is not available. Cannot compile filter !")` [scapy/arch/common.py:L74-L75]. On the sniff path this `ImportError` is caught in the Linux listen socket and logged (not propagated) by `log_runtime.error("Cannot set filter: %s", ex)` [scapy/arch/linux.py:L503] — which is precisely the `ERROR: Cannot set filter: ...` line observed, and why the sniff proceeds unfiltered instead of crashing. Note that `conf.use_pcap == False` (native `PF_PACKET` is the default socket backend on Linux) is independent of this: libpcap is consulted *only* for BPF `filter=` compilation, never for the sockets themselves.

**Reproduction (genuine, in an isolated environment).** Because the particular host used for §1–§4 happened to have libpcap incidentally installed, the canonical libpcap‑absent path is reproduced here in a **purpose‑built, throwaway container** in which libpcap is *physically removed* so that `find_library("pcap")` genuinely returns `None` — no monkeypatching, no stubbing, the real code path with a real absent library. ## Section 5 — Summary: what Scapy revealed at each stage

For the single packet `Ether()/IP(dst="127.0.0.1")/TCP(dport=80)`, the three lifecycle stages reveal three distinct faces of the same object, unified by one theme — the **auto‑field resolution transition**.

**The analytical spine — auto‑fields resolve from `None` to concrete.** A freshly built packet displays `IP.ihl`, `IP.len`, `IP.chksum`, `TCP.dataofs`, and `TCP.chksum` as `None` (§2.2). Serialization computes them via `build()` [scapy/packet.py:L746] → `post_build()` [scapy/packet.py:L758] — but on a copy, so the live object keeps showing `None` (`pkt[IP].len` is still `None` after `raw(pkt)`, §2.6). Only when the bytes are re‑interpreted — by `show2()` (§2.2) or by capture‑and‑dissect (§4.1) — do the fields appear concretely: `ihl=5`, `len=40`, `chksum=0x7ccd` (IP), `dataofs=5`, and `chksum=0x917c` (TCP) — all deterministic for this `dport=80` packet.

**How Scapy DISPLAYS at build (§1–§2).** The interactive `repr` [scapy/packet.py:L552] shows only set/overloaded fields and applies binding side‑effects (`Ether.type=IPv4`, `IP.proto=tcp`, `frag=0`) from `bind_layers(...)` [scapy/layers/inet.py:L1101,L1113]. `show()` [scapy/packet.py:L1459] renders the live object (auto‑fields `None`); `show2()` [scapy/packet.py:L1473] renders after rebuild (auto‑fields resolved). `summary()` [scapy/packet.py:L1642] joins per‑layer `mysummary()`; `command()` [scapy/packet.py:L1662] emits the constructor form; `ls()` [scapy/packet.py:L2328] tabulates every field with its type and default; and the `hexdump` family [scapy/utils.py:L273,L304,L326,L348] plus `raw()` expose the 54‑byte wire frame (vs. `IP.len=40`). The build is fully deterministic (`IP.id=1`, `TCP.sport=20`).

**How Scapy REPORTS on send (§3).** `send()`/`sendp()` [scapy/sendrecv.py:L422,L452] resolve egress from `conf.route` (`Route.__repr__` [scapy/route.py:L47], `route()` [scapy/route.py:L146] returning `(iface, output_ip, gateway)`), select `L3PacketSocket`/`L2Socket` [scapy/arch/linux.py:L587,L475], and — via `__gen_send()` [scapy/sendrecv.py:L332] — print an unbuffered progress dot [scapy/sendrecv.py:L380] then `Sent N packets.` [scapy/sendrecv.py:L392]; `verbose=0` is silent. Unresolved destination MACs on a broadcast interface trigger a warning and a broadcast fallback [scapy/layers/l2.py:L178].

**How Scapy PRESENTS/RECONSTRUCTS on sniff (§4).** `AsyncSniffer`/`sniff()` [scapy/sendrecv.py:L981,L1308] capture bytes on an `L2ListenSocket` [scapy/arch/linux.py:L579] and run the dissection chain (`__init__` [scapy/packet.py:L141] → `dissect()` [scapy/packet.py:L1049] → `do_dissect()` [scapy/packet.py:L1002] → `guess_payload_class()` [scapy/packet.py:L1062]). The reconstructed packet shows concrete auto‑fields and a **synthetic Ethernet header** for a layer‑3 send. Unbound bytes fall back to `Raw` (`conf.raw_layer`), and `conf.debug_dissector` toggles between silent fallback and log‑and‑re‑raise (`do_dissect_payload()` [scapy/packet.py:L1023]).
