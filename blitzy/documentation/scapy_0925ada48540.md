# How Scapy Behaves Across the Packet Lifecycle — Build → Send → Sniff

This document answers, with **verbatim output captured by actually running Scapy from this working copy**, how Scapy behaves at runtime across the full packet lifecycle: **building** a multi‑layer `Ether/IP/TCP` packet, **sending** it, and **sniffing** the same traffic back. Scapy describes itself as *"a powerful Python-based interactive packet manipulation program and library"* (`README.md:L13-14`).

The user's question decomposes into four asks, each answered explicitly below and re‑checked in the **Coverage pass**:

- **R1** — Start Scapy and build a multi‑layer `Ether/IP/TCP` packet; observe the per‑layer display as each layer is added and how the final structure looks before sending. → **§1**
- **R2** — Send the packet using Scapy's usual mechanism; note routing information printed, what Scapy shows about the packet as it leaves, and any other transmission output. → **§2**
- **R3** — Sniff the same traffic; observe how Scapy presents/dissects the received bytes and reconstructs the layers when displaying. → **§3**
- **R4** — Summarize what Scapy revealed (connect the built packet → bytes on the wire → sniffed reconstruction). → **§4**

Every factual claim carries an exact `file:line` citation into this repository's source, or a verbatim observed‑output reference. Where a value is environment‑specific or could not be asserted universally, that is stated explicitly rather than implied.

### Per‑layer display as each layer is added

The building block is `conf` and the layer classes, all imported by `from scapy.all import *`. The startup line printed by `/tmp/obs_build.py`:

```text
scapy.VERSION = 2026.07.01 | conf.verb = 2 | conf.use_pcap = False
Ether() -> <Ether  |>
Ether()/IP() -> <Ether  type=IPv4 |<IP  |>>
full stack -> <Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http flags=S |>>>
```

The three `repr(...)` lines show exactly **how each layer is displayed as it is added**:

- `Ether()` → `<Ether  |>` — an empty `Ether()` shows **no fields at all**.
- `Ether()/IP()` → `<Ether  type=IPv4 |<IP  |>>` — stacking `IP` makes `type=IPv4` appear on the Ethernet layer.
- The full stack → `<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http flags=S |>>>`.

Why does an empty `Ether()` show nothing while stacking reveals `type=IPv4`? Because the `__repr__` renderer (`scapy/packet.py:L552` — `def __repr__(self):`) prints **only** fields that are explicitly set (present in `self.fields`) or overloaded by the payload (present in `self.overloaded_fields`), and it **skips unset fields and empty collections** (its loop does `if f.name in self.fields: ...elif f.name in self.overloaded_fields: ...else: continue`, and `continue`s when a list/dict/set value has `len == 0`). A freshly‑constructed `Ether()` has neither set nor overloaded fields, so nothing renders.

The `/` operator that stacks the layers is `__div__` (`scapy/packet.py:L596` — `def __div__(self, other):`, aliased to `__truediv__`): it copies both operands and calls `add_payload`. Stacking **overloads the lower layer's demultiplexing fields** — so `Ether.type` becomes `IPv4` and `IP.proto` becomes `tcp`, i.e. the upper layers make the lower layers self‑describe. The layer defaults come from `Ether` (`scapy/layers/l2.py:L244` — `class Ether(Packet):`), `IP` (`scapy/layers/inet.py:L521` — `class IP(Packet, IPTools):`) and `TCP` (`scapy/layers/inet.py:L753` — `class TCP(Packet):`).

The packet under study — the user's *"simple multi‑layer packet such as an Ethernet/IP/TCP stack"* — is:

```text
>>> pkt = Ether()/IP(dst="127.0.0.1")/TCP(dport=80, flags="S")
```

That is precisely why `show()` and `show2()` differ even after `show2()` has run: the deferred fields are resolved on the copy, not written back to `pkt`.

### Sending the packet and the transmission output

`send()` (`scapy/sendrecv.py:L422` — `def send(x, ...`) transmits at **layer 3** (the caller supplies no Ethernet header; Scapy uses the L3 socket). Its layer‑2 counterpart is `sendp()` (`scapy/sendrecv.py:L452` — `def sendp(x, ...`). Both delegate to the internal `__gen_send` (`scapy/sendrecv.py:L332` — `def __gen_send(s, ...`).

Transmission output is **gated by `conf.verb`** (default `2`, `scapy/config.py:L759`): inside `__gen_send`, `if verbose is None: verbose = conf.verb`. When verbose, it writes **one `.` per packet** via `os.write(1, b".")` (`scapy/sendrecv.py:L380`) and prints the summary line via `print("\nSent %i packets." % n)` (`scapy/sendrecv.py:L392`).

Running a single default `send()` in an interactive (TTY) session produced exactly:

```text
>>> send(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"))
.
Sent 1 packets.
```

i.e. the progress marker `.` followed by `Sent 1 packets.` — Scapy sent **1** packet and said so.

**Output‑ordering nuance (stated honestly).** `os.write(1, b".")` writes **unbuffered** straight to file descriptor 1, whereas `print()` uses Python's **buffered** stdout. In an interactive terminal they appear in order (`.` then `Sent 1 packets.`, as above). But when STDOUT is **redirected to a file/pipe**, the buffered `print` output is flushed later, so the unbuffered `.` can appear **clustered/out of order** relative to the buffered text. On this machine, redirecting the send script to a file put the `.` at the very top of the capture — the first line read:

```text
.conf.verb = 2
```

That single leading `.` is the send's progress marker landing ahead of the buffered `print("conf.verb =", conf.verb)` output. The interleaving therefore depends on whether stdout is a TTY; it is not a fixed sequence.

**Verbosity gate, demonstrated.** Calling `send(..., verbose=0)` printed **nothing at all** — no `.`, no `Sent` line. In the redirected run there was exactly **one** `.` and **one** `Sent 1 packets.` line total (from the first, default‑verbose call); the second `verbose=0` call was silent. This confirms `conf.verb` (and the per‑call `verbose=` override) fully controls the transmission chatter.

**Socket backend.** Because libpcap/tcpdump is absent, sends use **native raw sockets** (`conf.use_pcap = False`, `scapy/config.py:L832`), implemented by Scapy's socket layer (`scapy/supersocket.py`) and the Linux backend (`scapy/arch/linux.py`). No external transmission occurs: the packet is confined to the local host via `lo`.

## §3 — Sniffing & observing reconstruction (answers R3)

### Why a Python `lfilter`, not a BPF `filter=` string

A BPF `filter=` string requires libpcap, which is absent here. Attempting it does **not** raise — it logs an `ERROR` to STDERR and returns an **empty** result:

```text
>>> sniff(iface='lo', filter='tcp and port 80', count=1, timeout=3)
ERROR: Cannot set filter: libpcap is not available. Cannot compile filter !
<Sniffed: TCP:0 UDP:0 ICMP:0 Other:0>
```

The returned `<Sniffed: TCP:0 UDP:0 ICMP:0 Other:0>` object confirms zero packets were captured. The workaround is a native capture with a **Python `lfilter` callable** instead of a BPF string.

### Capturing the round trip with `AsyncSniffer`

`sniff()` (`scapy/sendrecv.py:L1308` — `def sniff(*args, **kwargs):`) and its threaded form `AsyncSniffer` were used to capture on `lo` while concurrently sending the same packet. The pattern:

```text
>>> built = IP(dst="127.0.0.1")/TCP(dport=80, flags="S"); raw_built = raw(built)
>>> t = AsyncSniffer(iface="lo", lfilter=lambda p: TCP in p and p[TCP].dport == 80, count=1, timeout=6)
>>> t.start(); time.sleep(1); send(built, verbose=0); time.sleep(1); t.join()
>>> cap = t.results[0]
```

Captured packets are read from **`t.results`** after `.join()`. Note the sniffer **auto‑stops** once `count` is reached, so an explicit `.stop()` afterwards raises `Scapy_Exception`. Catching it and printing `type(ex).__name__, "->", ex` yields — verbatim:

```text
>>> try:
...     t.stop()
... except Exception as ex:
...     print(type(ex).__name__, "->", ex)
...
Scapy_Exception -> Not running ! (check .running attr)
```

This is the guard `raise Scapy_Exception("Not running ! (check .running attr)")` at `scapy/sendrecv.py:L1299`. The lesson: read `sniffer.results` after `.join()`; do not call `.stop()` on an already‑stopped sniffer.

### How Scapy presents and reconstructs the received bytes

Scapy **dissects** the raw bytes back into layers (`dissect`, `scapy/packet.py:L1049` — `def dissect(self, s):`). The captured frame reconstructs cleanly:

```text

['Ether', 'IP', 'TCP']
>>> cap.summary()
Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S
```

`cap.show()` on the **sniffed** frame shows **every field resolved — no `None`** — because these bytes came off the wire fully formed (lengths and checksums already present):


Compare this with the pre‑send `show()` in §1: there, `ihl`, `len`, `chksum`, `dataofs` were `None`; here they are `ihl = 5`, `len = 40`, IP `chksum = 0x7ccd`, `dataofs = 5`, TCP `chksum = 0x917c`. Dissection recovered the exact values Scapy computed at build time.

## §4 — Summary: build → wire → sniff continuity (answers R4)

Putting the three phases together, the same information is visible at **three stages** — a symbolic build‑time view, the raw bytes on the wire, and the dissected reconstruction — and they line up exactly.

**Sizes.** The built layer‑3 payload `raw(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"))` is **40 bytes**; the full built frame `raw(Ether()/IP(...)/TCP(...))` is **54 bytes**. The sniffed frame is likewise 54 bytes.

**Byte‑for‑byte continuity (measured, not asserted).** The sniff script compared the sniffed packet against the built one:

```text
raw(cap[IP]) == raw(built) ? True
raw(cap) == raw(Ether()/built) ? True
len(raw(built)) = 40 | len(raw(cap)) = 54
```

- `raw(cap[IP]) == raw(built)` → **`True`**: the IP/TCP portion of the sniffed frame equals the built layer‑3 payload byte‑for‑byte.
- `raw(cap) == raw(Ether()/built)` → **`True`**: the *entire* 54‑byte sniffed frame equals the built full frame.
- `len(raw(built)) = 40 | len(raw(cap)) = 54` confirms the 40‑byte payload inside the 54‑byte frame.

**Matching checksums prove the round trip.** The IP checksum **`0x7ccd`** and the TCP checksum **`0x917c`** are identical in the built `show2()` (§1) and the sniffed `show()` (§3), and the IP `len` field is `40` in both. The full built frame's hex from §1 —

```text
ffffffffffff0000000000000800450000280001000040067ccd7f0000017f00000100140050000000000000000050022000917c0000
```

— is exactly the 54 bytes that came back from the sniffer (hence `raw(cap) == raw(Ether()/built)` is `True`).

**Tying it back to display.** `show()` deferred the computed fields (`ihl`, `len`, `chksum`, `dataofs`) as `None` before sending; `build()`/`raw()` computed them into the wire bytes; and `show()` on the sniffed frame displays them **resolved**. Same packet, viewed at three stages: **symbolic build view → bytes on the wire → dissected reconstruction**, with the checksums (`0x7ccd`, `0x917c`) and the 40‑byte payload proving they are one and the same.
