## Q2 — What version is it running?

**Direct answer.** `scapy.VERSION == "2026.07.08"`. This is **not** a released version tag — it is the
**mtime-derived fallback**: the UTC modification date (`%Y.%m.%d`) of `scapy/__init__.py` in this
checkout. The same value is exposed as `scapy.__version__` and `conf.version`, and it is the string
shown in the Q1 banner and the Q7 test-runner header.

**Command & output:**

```
.venv/bin/python -c "import scapy; print(scapy.VERSION, scapy.__version__)"
```
```
2026.07.08 2026.07.08
```

**Why this value (the `_version()` fallback chain).** `VERSION = __version__ = _version()` at
`scapy/__init__.py:169`. `_version()` (`scapy/__init__.py:122`) tries five sources in order; here it
falls through the first four to the mtime fallback:

1. **`SCAPY_VERSION` env var** — `os.environ['SCAPY_VERSION']` at `scapy/__init__.py:131`. Unset here.
2. **bundled `VERSION` file** — opened at `scapy/__init__.py:136-141`. Absent here.
3. **`_version_from_git_archive()`** — called at `scapy/__init__.py:147` (def `:38`). Raises
   `ValueError('not a git archive')` at `scapy/__init__.py:56` because the export-subst marker
   `'$Format:%ct %(describe:tags=true)$'` is unsubstituted (still literally contains `Format`).
4. **`_version_from_git_describe()`** — called at `scapy/__init__.py:153` (def `:72`). Runs
   `git describe --tags --always --long` (`:114`); since the result does not start with `v`
   (`:115`) it then runs `git rev-list --tags --max-count=1` (`:117`); with **zero tags** that is
   empty, and `_parse_tag` raises `ValueError('tag has invalid format')` at `scapy/__init__.py:35`.
5. **mtime fallback** — `datetime.datetime.utcfromtimestamp(os.path.getmtime(__file__)).strftime('%Y.%m.%d')`
   at `scapy/__init__.py:158-161` → `2026.07.08`. (The last-resort `'0.0.0'` at `:166` is not reached.)

**Corroborating probes (verbatim):**

```
$ echo "SCAPY_VERSION=${SCAPY_VERSION:-<unset>}"
SCAPY_VERSION=<unset>
$ ls scapy/VERSION
ls: cannot access 'scapy/VERSION': No such file or directory
$ git describe --tags --always --long
0925ada4
$ git rev-list --tags --max-count=1        # (prints nothing — 0 tags)
$ git tag | wc -l
0
$ .venv/bin/python -c "import scapy; scapy._version_from_git_archive()"
ValueError: not a git archive
$ .venv/bin/python -c "import scapy; scapy._version_from_git_describe()"

```

**Reasoning.** Because there is no `SCAPY_VERSION`, no `VERSION` file, the tree is not a git archive,
and the clone carries **no git tags**, control necessarily reaches the mtime fallback. The observed
`2026.07.08` therefore equals the modification date of `scapy/__init__.py` and must be read as a
*build/checkout artifact*, not an upstream release number. Both edge functions were exercised directly
and raise exactly the `ValueError`s the fallback logic depends on.

## Q3 — Which IP-header fields get auto-populated for `IP()/ICMP()`

**Direct answer.** For a basic ICMP echo request `IP()/ICMP()`, the IP-header fields that are
**auto-populated at serialization** (stored as `None` until the packet is built) are exactly three:
**`ihl`, `len`, and `chksum`**. Separately, `proto` is auto-set to `1` (icmp) — not from a stored
default but injected by the ICMP payload binding — and `src`/`dst` *render* as `127.0.0.1` even though
their stored value is `None`. Every other IP field carries a static default: `version=4`, `tos=0`,
`id=1`, `flags=0`, `frag=0`, `ttl=64`, `options=[]`.

**Command & output:**

```
.venv/bin/python -c "
from scapy.all import IP, ICMP
p = IP()/ICMP()
print('repr:', repr(p))
print('summary:', p.summary())
ip = IP()
print('bare IP().fields:', ip.fields)
print('getfieldval src:', ip.getfieldval('src'), '| attr ip.src:', ip.src)
print('getfieldval dst:', ip.getfieldval('dst'), '| attr ip.dst:', ip.dst)
print('ICMP overload_fields:', ICMP().overload_fields)
print('proto after bind:', (IP()/ICMP()).getfieldval('proto'))
"
```
```
repr: <IP  frag=0 proto=icmp |<ICMP  |>>
summary: IP / ICMP 127.0.0.1 > 127.0.0.1 echo-request 0
bare IP().fields: {'options': []}
getfieldval src: None | attr ip.src: 127.0.0.1
getfieldval dst: None | attr ip.dst: 127.0.0.1
ICMP overload_fields: {<class 'scapy.layers.inet.IP'>: {'frag': 0, 'proto': 1}}
proto after bind: 1
```

Per-field stored-vs-rendered view for the IP layer of `IP()/ICMP()`:

```
  version  stored=4          rendered=4
  ihl      stored=None       rendered=None
  tos      stored=0          rendered=0
  len      stored=None       rendered=None
  id       stored=1          rendered=1
  flags    stored=<Flag 0 ()> rendered=<Flag 0 ()>
  frag     stored=0          rendered=0
  ttl      stored=64         rendered=64
  proto    stored=1          rendered=1
  chksum   stored=None       rendered=None
  src      stored=None       rendered='127.0.0.1'
  dst      stored=None       rendered='127.0.0.1'
  options  stored=[]         rendered=[]
```

**Citations & mechanism.** The defaults come from `IP.fields_desc` at `scapy/layers/inet.py:524-537`:

```
BitField("version", 4, 4), BitField("ihl", None, 4), XByteField("tos", 0),
ShortField("len", None), ShortField("id", 1),
FlagsField("flags", 0, 3, ["MF", "DF", "evil"]), BitField("frag", 0, 13),
ByteField("ttl", 64), ByteEnumField("proto", 0, IP_PROTOS), XShortField("chksum", None),
Emph(SourceIPField("src", "dst")), Emph(DestIPField("dst", "127.0.0.1")),
PacketListField("options", [], IPOption, length_from=lambda p:p.ihl * 4 - 20)
```

- **Deferred/auto fields** are the ones declared with a `None` default — `ihl` (`BitField("ihl", None, 4)`),
  `len` (`ShortField("len", None)`) and `chksum` (`XShortField("chksum", None)`). They stay `None`
  at construction and are computed only during serialization (see Q6). This is confirmed above:
  `getfieldval`/attribute both return `None` for all three.
- **`proto` is overload-injected, not a stored default.** A bare `IP()` has `proto` default `0`
  (`ByteEnumField("proto", 0, IP_PROTOS)`), but with an ICMP payload it becomes `1`. This comes from
  `bind_layers(IP, ICMP, frag=0, proto=1)` at `scapy/layers/inet.py:1112`, which populates ICMP's
  `overload_fields` — observed above as `{<class 'scapy.layers.inet.IP'>: {'frag': 0, 'proto': 1}}`,
  and `(IP()/ICMP()).getfieldval('proto') == 1`. `proto=icmp` is how it renders (name from `IP_PROTOS`).
- **`src`/`dst` render `127.0.0.1` while stored `None`.** `dst` is `DestIPField("dst", "127.0.0.1")`
  (`scapy/layers/inet.py:536`, class at `scapy/layers/inet.py:503`), whose default target is
  `127.0.0.1`; `src` is `SourceIPField("src", "dst")` (`scapy/fields.py:854`), which computes the
  source from the route to `dst`. The `bare IP().fields == {'options': []}` line shows that only
  `options` is materialized in the instance dict; `src`/`dst` are resolved on read, which is why
  `getfieldval` returns the stored `None` but attribute access renders `127.0.0.1`.
- ICMP `type` defaults to `8` (echo-request): `ByteEnumField("type", 8, icmptypes)` at
  `scapy/layers/inet.py:954` — hence `echo-request` in the summary.

So three distinct categories answer "what gets auto-populated": **computed-at-build** (`ihl`, `len`,
`chksum`), **overload-injected** (`proto=1`, and `frag=0` which also happens to match its default),
and **resolved-on-read** (`src`/`dst` → `127.0.0.1`). Everything else is a plain static default.

## Q4 — What `show()` prints (and how `show2()` differs)

**Direct answer.** `show()` prints the packet's **current stored** field values, so the deferred
auto-fields print as `None` — `ihl = None`, `len = None`, `chksum = None` (and ICMP `chksum = None`).
`show2()` first serializes and re-dissects the packet, so it prints the **computed** values —
`ihl = 5`, `len = 28`, `chksum = 0x7cde`, and ICMP `chksum = 0xf7ff`. Everything else is identical
between the two.

**Command:**

```
.venv/bin/python -c "from scapy.all import IP, ICMP; (IP()/ICMP()).show()"
```

**`show()` output (verbatim; no ANSI in `show` output):**

```
###[ IP ]### 
  version   = 4
  ihl       = None
  tos       = 0x0
  len       = None
  id        = 1
  flags     = 
  frag      = 0
  ttl       = 64
  proto     = icmp
  chksum    = None
  src       = 127.0.0.1
  dst       = 127.0.0.1
  \options   \
###[ ICMP ]### 
     type      = echo-request

```

```
  ihl       = 5
  tos       = 0x0
  len       = 28

  chksum    = 0x7cde
  src       = 127.0.0.1
  dst       = 127.0.0.1
  \options   \
###[ ICMP ]### 
     type      = echo-request
     code      = 0
     chksum    = 0xf7ff
     id        = 0x0
     seq       = 0x0
     unused    = ''
```

**Citations & mechanism.**

- `Packet.show()` at `scapy/packet.py:1459` returns `self._show_or_dump(...)`, which walks the layers
  and renders each field's **current** value. Since `ihl`/`len`/`chksum` are still `None` (Q3), they
  print literally as `None`. The empty `flags` (`Flag 0`) renders blank, `tos`/`id` etc. show their
  static defaults, and the ICMP `unused` field is the zero-length `StrFixedLenField` (renders `''`),
  with `id`/`seq` present because echo-request (`type 8`) is in `icmp_id_seq_types`.
- `Packet.show2()` at `scapy/packet.py:1473` returns `self.__class__(raw(self)).show(...)`. The
  `raw(self)` call **builds** the packet (running `IP.post_build`, which computes `ihl`, `len`,
  `chksum`), and then the bytes are **re-dissected** by `self.__class__(...)`. The re-dissected packet
  carries the computed values, so `show2()` prints `ihl=5, len=28, chksum=0x7cde` and ICMP
  `chksum=0xf7ff`. Its docstring (`scapy/packet.py:1476-1478`) states it shows "an assembled version
  of the packet, so that automatic fields are calculated (checksums, etc.)".

In short: `show()` is the *pre-serialization* view (what you have set so far, `None` for unresolved
auto-fields); `show2()` is the *on-the-wire* view (what will actually be sent). The `show2()` numbers
here are exactly the bytes decoded in Q6.

## Q5 — Sending a crafted ICMP packet to localhost: what happens at the network layer

**Direct answer.** `sr1(IP(dst="127.0.0.1")/ICMP(), timeout=5)` sends the echo-request but matches
**0 answers and returns `None`**. No echo-reply is matched. This is the honest, observed outcome — not
an idealized "you get a reply".

**Command & output (run as root):**

```
.venv/bin/python -c "
from scapy.all import IP, ICMP, sr1, conf
print('route 127.0.0.1:', conf.route.route('127.0.0.1'))
print('L3socket:', conf.L3socket)
ans = sr1(IP(dst='127.0.0.1')/ICMP(), timeout=5)
print('sr1 returned:', repr(ans))
"
```
```
.route 127.0.0.1: ('lo', '127.0.0.1', '0.0.0.0')
L3socket: <L3PacketSocket: read/write packets at layer 3 using Linux PF_PACKET sockets>
Begin emission:
Finished sending 1 packets.

Received 1 packets, got 0 answers, remaining 1 packets
sr1 returned: None
```

(The stray leading `.` before `route` is Scapy's per-sent-packet progress dot: `os.write(1, b".")` at
`scapy/sendrecv.py:298` writes directly to file-descriptor 1, bypassing Python's block-buffered
`print()` — so, when stdout is a pipe, the dot surfaces ahead of the buffered lines. On a real TTY it
appears inline during emission.)

**State transitions observed on the loopback.** Sniffing `lo` with `AsyncSniffer(iface="lo")` while
sending shows the request is emitted and observable, but no reply appears:

```
=== sr1 answer: None
=== frames captured on lo: 2
  frame[0]: Ether / IP / ICMP 127.0.0.1 > 127.0.0.1 echo-request 0
  frame[1]: Ether / IP / ICMP 127.0.0.1 > 127.0.0.1 echo-request 0
```

So the lifecycle is: **request built → request emitted and seen on `lo` (twice — the injected frame is
reflected back to the `AF_PACKET` receive path) → no matched echo-reply → `sr1` returns `None`.**

**Concrete mechanism (not a vague "environment" claim).** Three facts pin the cause:

1. Routing sends the packet to the loopback interface: `conf.route.route('127.0.0.1')` returns
   `('lo', '127.0.0.1', '0.0.0.0')` (interface `lo`), from `Route.route()` at `scapy/route.py:146`.
2. The default Layer-3 sender is `conf.L3socket = L3PacketSocket` (Linux `PF_PACKET`), selected at
   `scapy/config.py:647`; the class is `L3PacketSocket` at `scapy/arch/linux.py:587` with
   `desc = "read/write packets at layer 3 using Linux PF_PACKET sockets"` at `scapy/arch/linux.py:588`.
   Emission and answer-matching run through `sr1` (`scapy/sendrecv.py:656`) → `sndrcv`
   (`scapy/sendrecv.py:322`); the printed lines are `"Begin emission:"` (`:239`),
   `"Finished sending %i packets."` (`:250`) and `"Received %i packets, got %i answers, remaining %i
   packets"` (`:217-222`).
3. The kernel's ICMP responder **is enabled** — `sysctl net.ipv4.icmp_echo_ignore_all = 0` — and it
   *does* generate a reply. This was proven by swapping only the socket implementation: setting
   `conf.L3socket = L3RawSocket` (an `AF_INET`/`SOCK_RAW` socket) and re-sending returned a real reply:

   ```
   VARIANT L3PacketSocket -> sr1: None
   VARIANT L3RawSocket   -> sr1: <IP  version=4 ihl=5 tos=0x0 len=28 id=4576 flags= frag=0 ttl=64 proto=icmp chksum=0x6aff src=127.0.0.1 dst=127.0.0.1 |<ICMP  type=echo-reply code=0 chksum=0x0 id=0x0 seq=0x0 |>>
      L3RawSocket reply summary: IP / ICMP 127.0.0.1 > 127.0.0.1 echo-reply 0
   ```
   (The reply's `id=4576` / `chksum=0x6aff` are values the kernel chose for this specific run and will
   differ on re-run; the point is that an `echo-reply` is received at all.)

   > This `L3RawSocket` run is a **non-canonical diagnostic** used only to locate the cause; it is
   > *not* the default and the default was not changed in the answer path. The default remains
   > `L3PacketSocket` → `None`.

Therefore the "0 answers" is specific to how the default `PF_PACKET` Layer-3 socket injects and
captures on the loopback in this container: the echo-request is placed on `lo` and looped back (seen
twice by the `AF_PACKET` capture), but the reply the kernel produces is not delivered to / matched by
that `PF_PACKET` receive path. It is **not** a disabled ICMP responder (proven `= 0`) and **not** a
dropped request (the request is observed on `lo`); switching to the raw `AF_INET` socket on the same
host yields the `echo-reply`, which isolates the behavior to the default `L3PacketSocket` loopback
path. (`ping` is not installed in the container, so no external tool contradicts this.)

## Q6 — How Scapy builds the default IP header (from the source)

**Direct answer.** The default IP-header values are declared in `IP.fields_desc` at
`scapy/layers/inet.py:524-537`; the three fields left `None` there (`ihl`, `len`, `chksum`) are filled
in during serialization by **`IP.post_build()`** at `scapy/layers/inet.py:539-551`. Serialization is
driven by the generic build lifecycle in `scapy/packet.py`.

**Command & output — the actual on-the-wire bytes:**

```
.venv/bin/python -c "from scapy.all import IP, ICMP; print(bytes(IP()/ICMP()).hex())"
```
```
4500001c0001000040017cde7f0000017f0000010800f7ff00000000
```

**Byte-by-byte decode (28 bytes; matches `show2()` from Q4):**

| Bytes | Value | Meaning |
|-------|-------|---------|
| `45` | version 4, ihl 5 | IPv4, header length 5×4 = 20 bytes (computed) |
| `00` | `0x00` | tos |
| `001c` | 28 | total length (computed) |
| `0001` | 1 | id |
| `0000` | flags 0, frag 0 | |
| `40` | 64 | ttl |
| `01` | 1 | proto = icmp |
| `7cde` | `0x7cde` | IP header checksum (computed) |
| `7f000001` | 127.0.0.1 | src |
| `7f000001` | 127.0.0.1 | dst |
| `0800` | type 8, code 0 | ICMP echo-request |
| `f7ff` | `0xf7ff` | ICMP checksum (computed) |
| `00000000` | 0, 0 | ICMP id + seq |

**Citations & mechanism.**

- **Defaults**: `IP.fields_desc` (`scapy/layers/inet.py:524-537`) supplies every static default
  (`version=4`, `tos=0`, `id=1`, `flags=0`, `frag=0`, `ttl=64`) and marks `ihl`/`len`/`chksum` as
  `None`. `proto` becomes `1` from `bind_layers(IP, ICMP, frag=0, proto=1)` at
  `scapy/layers/inet.py:1112`. The underlying field machinery lives in `scapy/fields.py`: e.g.
  `BitField` (`scapy/fields.py:2362`) for `version`/`ihl`/`frag`, `ShortField` (`scapy/fields.py:1244`)
  for `len`/`id`, `XShortField` (`scapy/fields.py:1268`) for `chksum`, `XByteField`
  (`scapy/fields.py:1008`) for `tos`, `ByteField` (`scapy/fields.py:1002`) for `ttl`, `ByteEnumField`
  (`scapy/fields.py:2620`) for `proto`, and `FlagsField` (`scapy/fields.py:2997`) for `flags`. During
  build each field's `addfield`/`i2m` serializes its value into the header bytes.
- **Auto-computation**: `IP.post_build(self, p, pay)` at `scapy/layers/inet.py:539-551` does the work:
  - `ihl`: when `self.ihl is None`, `ihl = len(p) // 4` and the first byte is rewritten as
    `(version<<4) | ihl` — `scapy/layers/inet.py:542-544` → `0x45`.
  - `len`: when `self.len is None`, `tmp_len = len(p) + len(pay)` and bytes 2–3 are rewritten via
    `struct.pack("!H", tmp_len)` — `scapy/layers/inet.py:545-547` → `0x001c` (28).
  - `chksum`: when `self.chksum is None`, `ck = checksum(p)` and bytes 10–11 are rewritten —
    `scapy/layers/inet.py:548-550` → `0x7cde`. (`checksum` is imported at `scapy/layers/inet.py:18`,
    `chb`/`struct` at `:26`/`:11`.)
- **Build lifecycle** (generic, in `scapy/packet.py`): `bytes(pkt)`/`show2()` trigger `build()` at
  `scapy/packet.py:746`, which calls `do_build()` at `:724` → `self_build()` at `:678` (iterates
  `fields_desc`, calling each field's `addfield`) → `post_build()` at `:758` (the base is a no-op
  `return pkt + pay`, but `IP` overrides it with the auto-computation above) → `do_build_payload()`
  at `:715` and `build_padding()` at `:742`, producing the final wire bytes.

These computed values (`ihl=5`, `len=28`, `chksum=0x7cde`, ICMP `chksum=0xf7ff`) are exactly what
`show2()` reported in Q4 and what the hex dump above decodes to — the three representations agree.

**Runner mechanics** — `scapy/tools/UTscapy.py`: the header is printed at
`scapy/tools/UTscapy.py:972-974` (`"… UTScapy - Scapy %s - %s" % (scapy.__version__,
sys.version.split(" ")[0])`). The **per-campaign** summary `PASSED=%i FAILED=%i` is printed at
`scapy/tools/UTscapy.py:619` (verbose>2) and `:622` (verbose) — there is **no aggregate total**, which

(`scapy/tools/UTscapy.py:990`); `-q` decrements it (`:1006-1007`). `BREAKFAILED` defaults to `True`
(`:988`); with the config's `breakfailed: true` (loaded via `-c` at `:1032-1034`) the campaign loop
`break`s after the first failing campaign (`if BREAKFAILED: break` at `:1187-1188`) — the `-b` flag
sets `BREAKFAILED = False` (`:1002-1003`) so all 190 campaigns run. `-N` appends `needs_root` to the
skip set (`if NON_ROOT or os.getuid() != 0: KW_KO.append("needs_root")` at `:1094-1096`); `-K` extends
the skip set with the given keywords (`:1079-1080`); `disabled` is always skipped (`:1107`).

> **Why no `-W` / `PYTHONWARNINGS`.** At `scapy/tools/UTscapy.py:1240-1252`, when `sys.warnoptions`
> is non-empty the runner switches to warning-as-error mode; because `cryptography 49.0.0` emits a
> `CryptographyDeprecationWarning` on import (Q1/divergences), that would turn into errors and inflate
> the failure count. Both runs above were launched with `sys.warnoptions == []`, so this did not apply.

**Default (no `-b`) behavior.** Because `breakfailed: true`, running without `-b`
(`.venv/bin/python -m scapy.tools.UTscapy -c ./test/configs/linux.utsc`) stops at the **first** failing
campaign — `test/tls/tests_tls_netaccess.uts`, the first TLS file in the glob order — and prints
`UTscapy ended with error code 1`. `-b` is required to observe the full 190-campaign magnitude.

**What the failures are (concrete root cause, not "environment").** The 222 (root) / 198 (non-root)
failures are dominated by the TLS/certificate test files and trace to a single, reproducible import
error against the installed `cryptography 49.0.0`:

- Root-run failures break down as ≈**136 TLS/SSL** handshake/record tests, ≈**60**
  certificate/`PrivKey`/crypto tests (`test/cert.uts`: `PrivKey`/`PubKey`, `Chain`, `CRL`, `PKCS`,
  `OCSP`, `GeneralizedTime`, …), a handful (**3**) of network-access tests (manuf DB, `ARPing`,
  external connect), and a few miscellaneous. The non-root run shows the same shape (≈116 TLS + 72
  cert).
- The first failing test, `test/tls/tests_tls_netaccess.uts` → *"Load server util functions"*, fails
  when importing the TLS automaton, with this exact traceback:

  ```
  >>> from scapy.layers.tls.automaton_srv import TLSServerAutomaton
    File ".../scapy/layers/tls/automaton_srv.py", line 31, in <module>
      from scapy.layers.tls.automaton import _TLSAutomaton
    File ".../scapy/layers/tls/automaton.py", line 20, in <module>
      from scapy.layers.tls.cert import Cert, PrivKey
    File ".../scapy/layers/tls/cert.py", line 51, in <module>
      from cryptography.hazmat.backends.openssl.ec import InvalidSignature
  ModuleNotFoundError: No module named 'cryptography.hazmat.backends.openssl.ec'
  ```

- Reproduced directly: `from scapy.layers.tls.cert import Cert, PrivKey` raises
  `ModuleNotFoundError: No module named 'cryptography.hazmat.backends.openssl.ec'`. The offending line
  is `scapy/layers/tls/cert.py:51`, reached because `conf.crypto_valid` is `True` (the guard at
  `scapy/layers/tls/cert.py:47`) so the block that imports from cryptography is entered. **cryptography
  49.0.0 removed the private module path `cryptography.hazmat.backends.openssl.ec`** (`InvalidSignature`
  now lives at `cryptography.exceptions.InvalidSignature`). Because `scapy.layers.tls.cert` cannot be
  imported, `scapy.layers.tls.automaton`/`automaton_srv`/`automaton_cli` fail too, the TLS test setup
  never defines its helper functions, and every dependent test fails — many with the cascade error
  `NameError: name 'test_tls_server' is not defined`.

So the failures are a **version-compatibility issue** between this pinned Scapy checkout and the newer
`cryptography 49.0.0` installed in the container (plus a few tests that need real network access), **not
defects in Scapy's core packet-crafting layers** — the IP/TCP/UDP/ICMP/Ethernet/DNS and similar
protocol campaigns pass. Per the task's read-only mandate, this is documented and explained, not fixed.

Reported honestly (observed values are never adjusted toward an expectation):

  (version `2026.07.08`, the `3.12.3` in the UTScapy header) remain coherent across Q1, Q2, and Q7.
