## R1 — Startup welcome message & version

**Question:** *What welcome message and version information does Scapy display when it starts?*

**Direct answer.** At startup Scapy prints a welcome banner — an ASCII "Scapy dragon" logo beside a short text block — and reports version **`2026.06.26`**. That version is exposed identically as `scapy.VERSION` and `conf.version` (verified equal at runtime). The banner is emitted by `interact()`, Scapy's console entry point [scapy/main.py:L503].

**Code evidence — the banner text.** With `conf.fancy_prompt = True` (the default) [scapy/config.py:L903], `interact()` enters the fancy-banner branch [scapy/main.py:L589] and renders two parallel columns: the logo (`the_logo`) [scapy/main.py:L593-L613] and a text block (`the_banner`) [scapy/main.py:L628-L639]. The text-block lines include `"   | Welcome to Scapy"` [scapy/main.py:L632] and `"   | Version %s" % conf.version` [scapy/main.py:L633], and a random quote chosen from `QUOTES` is appended [scapy/main.py:L646]. Rendered on this host, the text column reads verbatim:

```
   | Welcome to Scapy
   | Version 2026.06.26
   |
   | https://github.com/secdev/scapy
   |
   | Have fun!
```

(A randomly chosen quote follows, e.g. `   | Craft packets before they craft you.  -- Socrate`.) When `conf.fancy_prompt` is `False`, the banner collapses to the single line `Welcome to Scapy (2026.06.26)` [scapy/main.py:L657].

On this host the live run *also* prints, before the banner, `WARNING: IPython not available. Using standard Python shell instead.` [scapy/main.py:L575-L576] — the standard-REPL fallback, because `ipython` is absent (see Environment Context).

**Code evidence — how `2026.06.26` is derived.** The version string is computed by `_version()` [scapy/__init__.py:L122], which walks a fallback chain and returns the first method that succeeds:

1. environment variable `SCAPY_VERSION` [scapy/__init__.py:L131];
2. a `VERSION` file shipped in sdists/wheels [scapy/__init__.py:L136-L141];
3. a git-archive substitution, `_version_from_git_archive()` [scapy/__init__.py:L147];
4. `git describe --tags`, via `_version_from_git_describe()` [scapy/__init__.py:L153];
5. **fallback** — the modification time of `__init__.py`: `os.path.getmtime(__file__)` [scapy/__init__.py:L160] formatted with `strftime('%Y.%m.%d')` [scapy/__init__.py:L161].

The resolved value is assigned by `VERSION = __version__ = _version()` [scapy/__init__.py:L169]; `conf.version` returns the same string.

**Rationale — why the version is a date, not a semantic tag.** This clone has **zero git tags** (`git tag` returns nothing), so methods 1–4 all fail: there is no `SCAPY_VERSION` env var, no generated `VERSION` file in a plain clone, no git-archive substitution, and `git describe --tags` has no tag to describe. The chain therefore falls through to the mtime fallback. The working tree's `scapy/__init__.py` has a modification time of **2026-06-26 (UTC)**, which `strftime('%Y.%m.%d')` formats as **`2026.06.26`** — the deterministic reason the banner shows a date rather than a release number such as `2.5.0`.

## R2 — Protocol layers actually loaded

**Question:** *How many protocol layers are actually available in the environment — not just files in the source tree, but what's actually loaded and ready to use?*

**Direct answer.** "Actually loaded and ready to use" has **two** complementary, equally-correct runtime measures, and both differ sharply from the raw file count on disk:

| Measure | Value | Meaning |
|---|---|---|
| `len(conf.load_layers)` | **49** | Layer *modules* loaded by default |
| `len(conf.layers)` | **1319** | Registered `Packet` *classes* ready to use |
| Layer `.py` files in source tree | **56** (88 incl. TLS subpkg) | Files on disk (not all loaded) |
| `scapy/contrib/` modules | **149** | Optional, **not** loaded by default |

**Code evidence — why 49 and not 48.** The default layer set, `conf.load_layers`, is a statically-defined list of **48** module names [scapy/config.py:L848-L897]. At import time on Linux, `scapy/arch/__init__.py` appends one architecture-specific layer, **`tuntap`** [scapy/arch/__init__.py:L149]. Captured directly: `len(conf.load_layers)` is **48 before** `import scapy.all` and **49 after**, with `'tuntap'` then present. The layer-load loop in `scapy/layers/all.py` iterates `conf.load_layers` and imports each named module via `load_layer(...)` [scapy/layers/all.py:L24-L27], and `scapy/all.py` aggregates `scapy.layers.all` [scapy/all.py:L40] so the default modules register their classes.

**Code evidence — why 1319.** Each loaded layer module defines and registers many `Packet` subclasses; `conf.layers` is the live registry of every such class, so `len(conf.layers) == 1319` is the most faithful answer to "ready to use." This figure includes the TLS/crypto classes that are registered *only because* `cryptography` (`41.0.7`) is installed and `crypto_valid` is `True` [scapy/config.py:L901]; without `cryptography`, the count would be lower.

**File-count methodology (reproducible).** The on-disk figures count `.py` files **excluding `__init__.py`**:

- `ls scapy/layers/*.py | grep -v __init__ | wc -l` → **56** (top-level layer files)
- `find scapy/layers -name '*.py' | grep -v __init__ | wc -l` → **88** (adds the `scapy/layers/tls/` subpackage)
- `find scapy/contrib -name '*.py' | grep -v __init__ | wc -l` → **149** (optional contrib modules)

**Rationale — files on disk vs. actually loaded.** The source tree carries far more protocol code than a default session uses: 56 top-level layer files (88 counting the TLS subpackage) plus 149 contrib modules. The contrib modules and many TLS files are **not** listed in `conf.load_layers`, so they are never imported at startup — they exist as files but are not "ready to use" until explicitly loaded (e.g., via `load_contrib(...)`). The honest runtime answer is therefore two numbers: **49 layer modules** are loaded by default, and those register **1319 `Packet` classes** that are immediately usable — which is precisely what "actually loaded and ready to use" asks for.

## R3 — Default verbosity & socket implementation

**Question:** *What's the verbosity level set to at startup, what does that number actually mean for output behavior, and what networking socket implementation does it use on this system?*

### Verbosity

**Direct answer.** The startup verbosity is **`conf.verb = 2`** [scapy/config.py:L759]. The in-code comment on that line documents the scale as "level of verbosity, from 0 (almost mute) to 3 (verbose)."

**What `2` actually means for output.** Verbosity gates how much the send/receive functions print; the behavior is enforced in `scapy/sendrecv.py`:

| `conf.verb` | Output behavior |
|---|---|
| 0 | Almost mute — status output suppressed |
| 1 | Minimal — single-character progress markers (`*` on answer, `.` on timeout) plus a one-line summary (branch `if verbose == 1:` [scapy/sendrecv.py:L766]) |
| 2 (default) | Detailed multi-line send/receive reporting: a `RECV n:` block [scapy/sendrecv.py:L750-L755], a `fail n:` block [scapy/sendrecv.py:L756-L761], and a `recv:/fail:` breakdown when no per-packet printer is set [scapy/sendrecv.py:L762-L765] |
| 3 | Adds further debug output |

At the default level 2, a successful run also prints the summary line `Sent %i packets, received %i packets. %3.1f%% hits.` [scapy/sendrecv.py:L780-L781].

**Rationale.** Every detailed-reporting branch is guarded by `if verbose > 1`, so level 2 is the lowest level at which Scapy emits the full multi-line received/answered/failed breakdown. Setting `conf.verb = 0` silences it; `conf.verb = 1` switches to the compact single-character progress markers plus the one-line summary. That is exactly what the number "2" means for output behavior.

### Socket implementation

**Direct answer.** On this **Linux** host, Scapy uses **native `PF_PACKET` sockets**, not libpcap/BPF. The resolved runtime values are:

- `conf.use_pcap = False`
- `conf.use_bpf = False`
- `conf.L3socket = L3PacketSocket`
- `conf.L2socket = L2Socket`
- `conf.L2listen = L2ListenSocket`

**Rationale.** The operating system drives this selection. `_set_conf_sockets()` [scapy/config.py:L606] resolves the default socket classes from the `use_*` flags; because `use_pcap` and `use_bpf` are both `False`, control reaches the `if LINUX:` branch, which imports and assigns `conf.L3socket = L3PacketSocket`, `conf.L2socket = L2Socket`, and `conf.L2listen = L2ListenSocket` [scapy/config.py:L645-L658]. Those classes are the native `PF_PACKET` implementations: `L3PacketSocket` is described as "read/write packets at layer 3 using Linux PF_PACKET sockets" [scapy/arch/linux.py:L587-L588], built on `L2Socket` ("read/write packets at layer 2 using Linux PF_PACKET sockets") [scapy/arch/linux.py:L475-L476], with `L2ListenSocket` [scapy/arch/linux.py:L579-L580]. With `use_pcap` and `use_bpf` both `False`, no libpcap or BSD-BPF code path is taken on this system — confirming the native-socket answer.

## R4 — ICMP ping packet structure

**Question:** *When you construct a basic ICMP ping packet, what's the actual structure of that packet object? Is Scapy creating a single composite object or something else — what layer types are involved, and how are they related?*

**Direct answer.** `IP()/ICMP()` produces a **single composite `Packet` object** — not a list or tuple of separate objects. Verified at runtime:

- `type(p)` is `IP` (the object *is* its outermost layer)
- `isinstance(p, Packet)` is `True`; `isinstance(p, (list, tuple))` is `False`
- `p.summary()` → `IP / ICMP 127.0.0.1 > 127.0.0.1 echo-request 0`
- `p.layers()` → `[IP, ICMP]`

Internally that one object is a **linked list of layers** terminated by a sentinel `NoPayload`:

```mermaid
graph LR
    IP["IP (outermost layer)"] -- "payload" --> ICMP["ICMP"]
    ICMP -- "payload" --> NP["NoPayload (terminal sentinel)"]
    ICMP -- "underlayer" --> IP
```

**Code evidence — the composition mechanism.** The `/` operator is `Packet.__div__`, aliased as `__truediv__` [scapy/packet.py:L596-L607]. It copies *both* operands and links them:

```python
def __div__(self, other):
    if isinstance(other, Packet):
        cloneA = self.copy()
        cloneB = other.copy()
        cloneA.add_payload(cloneB)
        return cloneA
    ...
__truediv__ = __div__
```

`add_payload` [scapy/packet.py:L360] performs the actual linking: when the lower layer's payload is still `NoPayload`, it sets `self.payload = payload` and calls `payload.add_underlayer(self)` — which sets the upper layer's `underlayer` back to the lower layer [scapy/packet.py:L368-L369] — then copies the upper layer's `overload_fields` into the lower layer's `overloaded_fields` [scapy/packet.py:L370-L373].

**Code evidence — the chain endpoints.** Every `Packet` constructor initializes `self.payload = NoPayload()` [scapy/packet.py:L161] and `self.underlayer = _underlayer` [scapy/packet.py:L163], whose parameter default is `_underlayer=None` [scapy/packet.py:L145]; so an unextended layer ends in `NoPayload` with no underlayer. After `IP()/ICMP()` the relationships are (all verified at runtime):

- `p[IP].payload` is the `ICMP` instance
- `p[ICMP].underlayer` is the `IP` instance
- `p[ICMP].payload` is a `NoPayload` (the terminal sentinel); its own `underlayer` stays `None`, because `NoPayload.add_underlayer()` is a no-op [scapy/packet.py:L1721-L1723] — the chain is **not** linked back from `NoPayload` up to `ICMP`

`IP` and `ICMP` are defined in `scapy/layers/inet.py` — `class IP(Packet, IPTools)` [scapy/layers/inet.py:L521] and `class ICMP(Packet)` [scapy/layers/inet.py:L952].

**Rationale.** This bidirectional linkage — each layer points "down" to its `payload` and "up" to its `underlayer` — together with the `overload_fields` that `add_payload` copies, is what lets a lower layer's field defaults resolve from the layer stacked above it (e.g., `IP.proto` auto-resolving to `1`/ICMP because `ICMP` advertises it via `overload_fields`). So the answer to "single composite object or something else" is unambiguous: it is **one** composite `Packet`, internally a chained linked-list of `Packet` layers (`IP → ICMP → NoPayload`), not a collection of independent objects.

## R5 — Active default theme

**Question:** *What theme is active in a default session, and what's it called in the code?*

**Direct answer.** In a default **interactive** session the active theme is **`DefaultTheme`** — that is its exact class name in the code.

**Code evidence.** `interact()` sets `conf.interactive = True` [scapy/main.py:L513] and then, unconditionally, `conf.color_theme = DefaultTheme()` [scapy/main.py:L514]. Verified live: piping `print(type(conf.color_theme).__name__)` into `./run_scapy` prints `DefaultTheme`, and `conf.interactive` is `True`.

**Contrast / rationale — why this differs from a plain import.** The *static* class default inside the `Conf` object is `NoTheme()` [scapy/config.py:L818] (wrapped in an `Interceptor`). That is what a bare `import scapy` / `import scapy.all` sees — verified: without calling `interact()`, `type(conf.color_theme).__name__` is `NoTheme`. The interactive console deliberately **upgrades** the theme from `NoTheme` to `DefaultTheme` so colored output is enabled at the REPL. (Cross-platform note: a `BlackAndWhite()` fallback exists [scapy/main.py:L582] but applies **only** to Windows sessions without IPython — it does not apply on this Linux host.)

**Catalog.** `scapy/themes.py` defines **13 classes** whose names end in `Theme` (`grep -cE '^class .*Theme' scapy/themes.py` → 13). These comprise the abstract bases `ColorTheme` [scapy/themes.py:L94] and `AnsiColorTheme` [scapy/themes.py:L121] alongside concrete themes including `NoTheme` [scapy/themes.py:L117], `BlackAndWhite` [scapy/themes.py:L163], and `DefaultTheme` [scapy/themes.py:L167], plus `BrightTheme`, `RastaTheme`, `ColorOnBlackTheme`, and the markup themes `FormatTheme`, `LatexTheme`, `LatexTheme2`, `HTMLTheme`, and `HTMLTheme2`.
