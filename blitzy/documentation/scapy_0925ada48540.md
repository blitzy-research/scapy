# Scapy ISO-TP (ISO 15765-2) Segmentation — Onboarding Q&A

This document answers seven onboarding questions about how Scapy's automotive
ISO-TP contrib module (`scapy/contrib/isotp/`) segments diagnostic payloads
across CAN frames. **ISO-TP is ISO 15765-2, "Road vehicles — Diagnostic
communication over Controller Area Network (DoCAN) — Part 2: Transport protocol
and network layer services"** — the transport layer that sits beneath UDS and
OBD and lets a diagnostic message larger than a single 8-byte CAN frame be split
across many frames and reassembled by the receiver.

Every behavioral claim below is backed by **runtime output** captured by
executing the real Scapy code paths (send-side `ISOTP.fragment()` and the
receive-side `ISOTPSoftSocket` state machine), not by reading the code alone.
For each question you will find: **(a)** the exact command that was run, **(b)**
the complete, unedited observed output, **(c)** a `file:line` citation naming the
function/method/class responsible, and **(d)** the causal reasoning that ties the
output back to the code. A closing coverage pass and a methodology note round out
the document.

## Q2 — What triggers segmentation (a payload larger than one CAN frame)

**Command:**

```bash
PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_probe.py
```

**Observed output (the Q2 lines):**

```text
Q2 8-byte: payload=8 bytes -> 2 CAN frame(s)
  frame[0] first2=1008 full=1008000102030405
  frame[1] first2=2106 full=210607
```

**Answer.** A diagnostic payload that does not fit in a single CAN frame is split
into a **First Frame (FF)** followed by one or more **Consecutive Frames (CF)**.
An 8-byte payload produces **2** CAN frames — one FF (`1008000102030405`) plus one
CF (`210607`) — confirming that segmentation kicks in as soon as the payload
exceeds **7 bytes** (the single-frame capacity established in Q5). The FF carries
the total length and the first 6 data bytes; the lone CF carries the remaining
2 bytes.

**Citations.**

- `def fragment(self, *args, **kargs):` at `scapy/contrib/isotp/isotp_packet.py:92`
  — the send-side builder that turns one `ISOTP` message into a list of `CAN`
  frames.
- The per-frame data capacity `data_bytes_in_frame = 7` at
  `scapy/contrib/isotp/isotp_packet.py:99`.
- The single-frame test `if len(self.data) <= data_bytes_in_frame:` at
  `scapy/contrib/isotp/isotp_packet.py:106` (the single-frame branch spans
  `scapy/contrib/isotp/isotp_packet.py:106-117`).
- The multi-frame branch (First Frame + Consecutive Frames) at
  `scapy/contrib/isotp/isotp_packet.py:119-152`.

**Reasoning.** `fragment()` compares `len(self.data)` against
`data_bytes_in_frame` (7 for normal addressing). When the length is `<= 7` it
takes the single-frame branch at `isotp_packet.py:106`; when it is `> 7` — as with
the 8-byte payload — it falls through to the First-Frame construction at
`isotp_packet.py:119` and then loops emitting Consecutive Frames at
`isotp_packet.py:137`, yielding the observed FF + CF pair.

## Q3 — How many frames does a 20-byte payload generate?

**Command:**

```bash
PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_probe.py
```

This runs `ISOTP(data=bytes(range(20))).fragment()`.

**Observed output (the Q3/Q4 lines):**

```text
Q3/Q4 20-byte: payload=20 bytes -> 3 CAN frame(s)
  frame[0] first2=1014 full=1014000102030405
  frame[1] first2=2106 full=21060708090a0b0c
  frame[2] first2=220d full=220d0e0f10111213
```

**Answer.** A 20-byte payload produces **exactly 3 CAN frames** — one First Frame
plus two Consecutive Frames — and this count is stable across repeated runs.

**Citations.**

- `def fragment(...)` at `scapy/contrib/isotp/isotp_packet.py:92`.
- The FF holds `idx = 8 - len(frame_header)` data bytes, computed at
  `scapy/contrib/isotp/isotp_packet.py:126` (here `frame_header` is 2 bytes, so
  the FF carries 6 data bytes).
- Each Consecutive Frame carries `data_bytes_in_frame` (= 7) bytes, sliced at
  `scapy/contrib/isotp/isotp_packet.py:138` inside the
  `while idx < len(self.data):` loop at `scapy/contrib/isotp/isotp_packet.py:137`.

**Reasoning.** With `len(data) = 20 > 7`, `fragment()` takes the multi-frame
branch. Because `20 <= ISOTP_MAX_DLEN` (4095), the First Frame uses the 2-byte
header (Q4), leaving `8 - 2 = 6` data bytes in the FF (`isotp_packet.py:126`).
That leaves `20 - 6 = 14` bytes for Consecutive Frames; each CF carries 7 bytes
(`isotp_packet.py:138`), so `ceil(14 / 7) = 2` CFs are emitted. Total =
`1 (FF) + 2 (CF) = 3` frames, matching the observed `-> 3 CAN frame(s)`.

## Q4 — What do the first bytes (PCI) of each generated frame look like?

**Command:**

```bash
PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_probe.py
```

**Observed output (same 20-byte run as Q3):**

```text
Q3/Q4 20-byte: payload=20 bytes -> 3 CAN frame(s)
  frame[0] first2=1014 full=1014000102030405
  frame[1] first2=2106 full=21060708090a0b0c
  frame[2] first2=220d full=220d0e0f10111213
```

**Answer.** The leading byte(s) of each frame are the **Protocol Control
Information (PCI)**, whose high nibble encodes the frame type:

- **First Frame** — `frame[0]` begins `0x10 0x14`. The high nibble `1` marks a
  First Frame; the remaining 12 bits form the length field `0x014 = 20`, i.e. the
  total payload length. The 6 bytes after the 2-byte header are the first 6
  payload bytes (`00 01 02 03 04 05`).
- **Consecutive Frame #1** — `frame[1]` begins `0x21`. The high nibble `2` marks
  a Consecutive Frame; the low nibble `1` is the sequence number. The 7 bytes
  after it (`06 07 08 09 0a 0b 0c`) are the next payload slice.
- **Consecutive Frame #2** — `frame[2]` begins `0x22`. Consecutive Frame,
  sequence number `2`, carrying the final 7 payload bytes
  (`0d 0e 0f 10 11 12 13`).
- **Single Frame (for contrast)** — a Single Frame's first byte is `0x0N` where
  `N` is the length (see Q5's `0x07`).

**Citations.**

- The First-Frame header
  `frame_header = struct.pack(">H", len(self.data) + 0x1000)` at
  `scapy/contrib/isotp/isotp_packet.py:121` — packs `20 + 0x1000 = 0x1014`
  big-endian, producing the `10 14` bytes.
- The Consecutive-Frame PCI
  `frame_header = struct.pack("b", (n % 16) + N_PCI_CF)` at
  `scapy/contrib/isotp/isotp_packet.py:139` — produces `0x21`, `0x22`, ...
- The PCI-type constants `N_PCI_SF = 0x00`, `N_PCI_FF = 0x10`, `N_PCI_CF = 0x20`,
  `N_PCI_FC = 0x30` at `scapy/contrib/isotp/isotp_packet.py:42-45`.
- The Single-Frame length byte `struct.pack('B', len(self.data))` at
  `scapy/contrib/isotp/isotp_packet.py:108`.

**Reasoning.** The First Frame packs `length + 0x1000` as a big-endian 16-bit
value (`isotp_packet.py:121`); `0x1000 | 0x014 = 0x1014`, so the first two bytes
are `10 14` and the low 12 bits decode straight back to the length `20`. Each
Consecutive Frame's PCI comes from `(n % 16) + N_PCI_CF` (`isotp_packet.py:139`),
where `N_PCI_CF = 0x20` (`isotp_packet.py:44`) and `n` is the CF counter starting
at 1 — giving `0x20 + 1 = 0x21` for the first CF and `0x20 + 2 = 0x22` for the
second. This matches the ISO 15765-2 rule that CF sequence numbers start at 1 and
increment (wrapping `0x2F -> 0x20`).

## Q5 — What is the maximum payload before segmentation kicks in?

**Command:**

```bash
PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_probe.py
```

**Observed output (the Q5 lines):**

```text
Q5 7-byte: payload=7 bytes -> 1 CAN frame(s)
  frame[0] first2=0700 full=0700010203040506
```

**Answer.** The maximum single-frame payload is **7 bytes** with normal
addressing (and **6 bytes** with extended addressing). A 7-byte payload produces
exactly **1** CAN frame — a Single Frame `0700010203040506` (PCI `0x07` = Single
Frame of length 7, followed by the 7 data bytes `00 01 02 03 04 05 06`). Adding a
single byte (the 8-byte case in Q2) tips it over into 2 frames, so the boundary is
exactly 7.

**Citations.**

- `data_bytes_in_frame = 7` at `scapy/contrib/isotp/isotp_packet.py:99`.
- The extended-addressing reduction
  `if self.rx_ext_address is not None: data_bytes_in_frame = 6` at
  `scapy/contrib/isotp/isotp_packet.py:100-101`.
- The Single-Frame length byte in the branch guarded by
  `if len(self.data) <= data_bytes_in_frame:` (`isotp_packet.py:106`):
  `frame_data = struct.pack('B', len(self.data)) + self.data` at
  `scapy/contrib/isotp/isotp_packet.py:108`.

**Reasoning.** A CAN frame has 8 payload bytes. The Single-Frame PCI consumes 1
byte (`0x0N`, the length nibble), leaving 7 bytes for data under normal
addressing (`isotp_packet.py:99`). When an extended-address byte is prepended,
one more byte is consumed, so `data_bytes_in_frame` drops to 6
(`isotp_packet.py:100-101`). The single-frame test at `isotp_packet.py:106` is
therefore true for `len <= 7` (or `<= 6` extended) and false above it — which is
why 7 bytes stay in one frame and 8 bytes segment. The observed `frame[0] = 0x07`
is precisely `struct.pack('B', 7)` from `isotp_packet.py:108`.

## Q6 — What happens with an "absurdly large" payload such as 5000 bytes?

**No error occurs.** A 5000-byte payload segments cleanly — it does **not** raise
an exception. This is the key, and slightly counter-intuitive, result: 5000 bytes
is well within ISO-TP's addressable range once the 2016 revision's 32-bit "escape"
First Frame is used.

**Command (the 5000-byte case):**

```bash
PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_probe.py
```

**Observed output (the Q6 lines):**

```text
Q6 5000-byte: payload=5000 bytes -> 715 CAN frame(s)
  frame[0] first2=1000 full=100000001388aaaa
  frame[714] first2=2aaa full=2aaaaaaaaaaaaaaa
```

A 5000-byte payload becomes **715** CAN frames. The First Frame is
`100000001388aaaa`: the bytes `0x10 0x00` are a First Frame whose 12-bit length
field is **zero**, which signals the **32-bit escape**; the escape is immediately
followed by the true length as a 32-bit big-endian value `0x00001388 = 5000`,
then 2 data bytes (`aa aa`). The last frame, `frame[714]`, is a Consecutive Frame
`2aaaaaaaaaaaaaaa` — PCI `0x2a`, i.e. sequence number `(714 % 16) = 10 = 0xa`.

**The true error boundary** is a payload strictly larger than
`ISOTP_MAX_DLEN_2015` (= `4294967295`, i.e. `2**32 - 1`, ~4 GiB). Only then does
`fragment()` raise. This was exercised directly:

**Command (the true-error boundary; allocates a real ~4 GiB `bytes`):**

```bash
PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_boundary.py
```

**Observed output:**

```text
ISOTP_MAX_DLEN = 4095
ISOTP_MAX_DLEN_2015 = 4294967295
2**32 = 4294967296
EXCEPTION TYPE: scapy.error.Scapy_Exception
EXCEPTION MESSAGE: 'Too much data in ISOTP message'
```

**Citations.**

- The constants `ISOTP_MAX_DLEN_2015 = (1 << 32) - 1` at
  `scapy/contrib/isotp/isotp_packet.py:35` and `ISOTP_MAX_DLEN = (1 << 12) - 1`
  at `scapy/contrib/isotp/isotp_packet.py:36`.
- The oversized guard `if len(self.data) > ISOTP_MAX_DLEN_2015:` at
  `scapy/contrib/isotp/isotp_packet.py:103` and the raise
  `raise Scapy_Exception("Too much data in ISOTP message")` at
  `scapy/contrib/isotp/isotp_packet.py:104`.
- The two First-Frame encodings, chosen by
  `if len(self.data) <= ISOTP_MAX_DLEN:` at `scapy/contrib/isotp/isotp_packet.py:120`:
  the normal 16-bit header `struct.pack(">H", len(self.data) + 0x1000)` at
  `scapy/contrib/isotp/isotp_packet.py:121`, versus the 32-bit escape header
  `struct.pack(">HI", 0x1000, len(self.data))` at
  `scapy/contrib/isotp/isotp_packet.py:123`.

**Reasoning.** `5000 > ISOTP_MAX_DLEN` (4095) but `5000 <= ISOTP_MAX_DLEN_2015`,
so the oversized guard at `isotp_packet.py:103` is **not** tripped, and the
First-Frame selector at `isotp_packet.py:120` takes its `else` branch: it emits
`0x1000` (a First Frame with a zero 12-bit length) followed by the 32-bit length
via `struct.pack(">HI", 0x1000, 5000)` (`isotp_packet.py:123`). That header is 6
bytes, so `idx = 8 - 6 = 2` (`isotp_packet.py:126`) — the escape FF holds only 2
data bytes, leaving `5000 - 2 = 4998` bytes for Consecutive Frames. Each CF
carries 7 bytes, so `ceil(4998 / 7) = 714` CFs, giving `1 + 714 = 715` frames.
The 714th (last) CF has sequence counter `n = 714`, so its PCI is
`(714 % 16) + N_PCI_CF = 10 + 0x20 = 0x2a` (`isotp_packet.py:139`), matching the
observed `frame[714] first2=2aaa`. A payload strictly greater than
`ISOTP_MAX_DLEN_2015` is required to trip the guard at `isotp_packet.py:103`;
`2**32 = 4294967296` is the smallest such value, and it produced the observed
`scapy.error.Scapy_Exception: 'Too much data in ISOTP message'`.

## Q7 — When receiving, if a middle frame never arrives, what timeout applies and what error appears?

**Direct answer: the applicable timeout is `cf_timeout = 1` second, and NO
exception is raised.** When a middle (Consecutive) frame never arrives, the
receiver **silently discards** the partial message: its RX state machine resets
from `ISOTP_WAIT_DATA` back to `ISOTP_IDLE`, a pending `sniff()` returns 0
packets, and a blocking `recv()` simply keeps waiting. Nothing is enqueued and no
exception propagates.

The receive path was driven end-to-end with the project's own hardware-free
`TestSocket(CAN)` pair: a stimulus socket sends a First Frame
(`10 09 01 02 03 04 05 06`, announcing a 9-byte message), the receiver replies
with a Flow Control frame (`30 00 00`, hence `FC=300000` in the output), and then
the Consecutive Frame is **withheld** so the timeout fires.

**Command (run with `2`, `2`, then `3`):**

```bash

PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_q7.py 2
PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u /tmp/isotp_q7.py 3
```

**Observed output (all three runs):**

```text

RUN | verb=2 | cf_timeout=1s | FC=300000 | WAIT_DATA->IDLE=1.000s | sniff got 0 pkt(s) | exception=None | log=(empty)
RUN | verb=3 | cf_timeout=1s | FC=300000 | WAIT_DATA->IDLE=1.000s | sniff got 0 pkt(s) | exception=None | log=WARNING: RX state was reset due to timeout
```

The 1-second value is **stable across the two default (`verb=2`) runs** (measured
`1.000 s` each; each run takes ~1 s for the `WAIT_DATA -> IDLE` transition).
`sniff got 0 pkt(s)` and `exception=None` in every run confirm the silent
discard.

**Warning text is verbosity-gated.** The message

At the DEFAULT `conf.verb = 2` the reset is silent (`log=(empty)`); the third run
above uses `conf.verb = 3` — a **NON-DEFAULT** setting used solely to surface the
string — and only then does `log=WARNING: RX state was reset due to timeout`
appear.

**TX-side contrast (also observed).** The transmit side behaves asymmetrically:

## Methodology note

- **Run-first.** Every value in this document was produced by executing the real
  ISO-TP code paths and capturing their output; nothing is inferred from reading.
  The send side exercises the genuine `ISOTP.fragment()` builder
  (`scapy/contrib/isotp/isotp_packet.py:92`); the receive side exercises the
  genuine `ISOTPSoftSocket` state machine
  (`scapy/contrib/isotp/isotp_soft_socket.py`).
- **Canonical invocation & default configuration.** Everything ran as
  `PYTHONPATH=/tmp/blitzy/scapy/scapy_0925ada48540_ca08b7 python3 -u <script>` on
  **Python 3.13.7**, with `scapy.VERSION = 2026.07.13` imported from the checkout
  at `HEAD = 0925ada485406684174d6f068dbd85c4154657b3`. The default config is
  `conf.verb = 2` and `USE_CAN_ISOTP_KERNEL_MODULE = False`; the only NON-default
  condition used was `conf.verb = 3` in Q7 (to reveal the RX warning text), which
  is labelled as such where it appears.
- **Hardware-free harness (Q7).** The receive path is driven by the project's own
  `TestSocket(CAN)` socket pair (`test/testsocket.py`) — a real in-memory CAN
  pairing, **not** a mock — the same mechanism the regression suite uses
  (`test/contrib/isotp_soft_socket.uts:88-105`, section "Two frame receive"). No
  physical CAN bus, `python-can`, or Linux `CAN_ISOTP` kernel support was needed.
- **Magnitude / timing rigor (Q7).** Each timeout run lasts ~1 s; the 1-second
  `cf_timeout` was confirmed stable across two default runs (both `1.000 s`), and
  the `fc_timeout` likewise across two TX-contrast runs.
- **ISO 15765-2 validation.** The observed behavior matches the standard: a
  Single Frame (type 0) carries ≤ 7 bytes (6 with extended addressing); a First
  Frame (type 1) uses a 12-bit length up to 4095 bytes; the 2016 revision adds a
  32-bit escape (a zero 12-bit length followed by a 32-bit length) extending the
  maximum to `2**32 - 1 = 4294967295` bytes; Consecutive Frames (type 2) carry a
  sequence number that starts at 1 and wraps `0x2F -> 0x20`; Flow Control (type 3)
  carries a block size and a minimum separation time (STmin). The standard's
  consecutive-frame receive timer (N_Cr) is realized in Scapy as `cf_timeout`.
  ISO 15765-2 is "Road vehicles — Diagnostic communication over CAN (DoCAN) —
  Part 2: Transport protocol and network layer services," the transport used by
  UDS/OBD.
- **Read-only & cleanup.** No repository file was modified; the only new file is
  this document. All four observation scripts lived under `/tmp`, outside the
  repository, and were deleted after use; `git status --porcelain` is clean apart
  from this document, and `HEAD = 0925ada4...` is unchanged.
