# What Scapy Displays and Reports at Runtime — Building, Sending, and Sniffing an Ethernet/IP/TCP Packet

## Introduction

Scapy is "a powerful Python-based interactive packet manipulation program and library" (`README.md:13-14`). By its own description it "is able to forge or decode packets of a wide number of protocols, send them on the wire, capture them, store or read them using pcap files, match requests and replies, and much more" (`README.md:16-18`). This document answers, with evidence, a four‑part question about **what Scapy displays and reports at runtime** as one packet travels through its full lifecycle — **build → send → sniff → summarize** — using the user's exact example stack:

```python
Ether()/IP(dst="127.0.0.1")/TCP(dport=80)
```

Each behavioral claim below is paired with the **verbatim** console output that produced it, and each source‑grounded claim carries an exact `file:line` reference. The five sections are: (1) Building, (2) Sending, (3) Sniffing, (4) Summary, and (5) a Coverage confirmation.

## Section 1 — Building the packet (what Scapy displays as each layer is added)

### 1.1 The `/` operator stacks layers

Scapy composes protocol layers with the division operator `/`. This is implemented by `Packet.__div__` at `scapy/packet.py:596`, which clones both operands and calls `add_payload()` (`scapy/packet.py:360`) so that in `A/B` the layer **`B` becomes the payload of `A`**. Stacking `Ether()/IP()/TCP()` therefore nests **TCP inside IP inside Ethernet**. The three layers named in the question are distinct classes:

- **Ethernet** — `class Ether(Packet)` at `scapy/layers/l2.py:244`.
- **IP** — `class IP(Packet, IPTools)` at `scapy/layers/inet.py:521`.
- **TCP** — `class TCP(Packet)` at `scapy/layers/inet.py:753`.

### 1.2 Building incrementally — the `repr` changes as each layer is attached

Every time a layer is added, the object's textual representation (from `Packet.__repr__` at `scapy/packet.py:552`) reflects the new nested structure. Adding one layer at a time produced exactly this, verbatim:

```text
>>> Ether()
<Ether  |>
>>> Ether()/IP(dst="127.0.0.1")
<Ether  type=IPv4 |<IP  dst=127.0.0.1 |>>
>>> Ether()/IP(dst="127.0.0.1")/TCP(dport=80)
<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http |>>>
```

**Auto‑populated linkage fields (observed).** Notice what appears *without being set*:

- `Ether` gains **`type=IPv4`** the moment an `IP` layer is attached — evidence: the bare `<Ether  |>` becomes `<Ether  type=IPv4 |...>`. The Ethernet header advertises the next protocol so the receiver can dissect it.
- `IP` gains **`proto=tcp`** the moment a `TCP` layer is attached — evidence: `<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP ...>>`. The IP header advertises its L4 payload type.

These linkage values are applied **at stacking time — not at build/serialization**. When a layer is attached as a payload, `add_payload()` (`scapy/packet.py:360`) copies the payload's registered overload fields into the lower layer with `self.overloaded_fields = payload.overload_fields[t]` (`scapy/packet.py:370-372`); those overloads are registered by the layer bindings `bind_layers(Ether, IP, type=2048)` (`scapy/layers/inet.py:1101`) and `bind_layers(IP, TCP, frag=0, proto=6)` (`scapy/layers/inet.py:1113`). So `type=IPv4` (`0x0800` = `2048`) and `proto=tcp` (`6`) are present the instant the *next* layer is stacked — which is exactly why they appear in the `repr` above, before anything is serialized. Inspecting the objects immediately after stacking, **before any build**, confirms the overloads are already stored — verbatim:

```text
>>> p1 = Ether()/IP(dst="127.0.0.1")
>>> p1.overloaded_fields                    # Ether, after IP was stacked onto it
{'type': 2048}
>>> p2 = Ether()/IP(dst="127.0.0.1")/TCP(dport=80)
>>> p2[Ether].overloaded_fields
{'type': 2048}
>>> p2[IP].overloaded_fields                # IP, after TCP was stacked onto it
{'frag': 0, 'proto': 6}
```

This is distinct from the *computed* fields (`ihl`, `len`, `chksum`, `dataofs`), which are **not** set here and instead resolve later, at assembly, via the protocol‑specific `post_build()` hooks (see §1.5).

**Human‑readable field renderings (observed).** Scapy prints well‑known port numbers as service names, not integers:

- TCP destination port **80** renders as **`dport=http`** — evidence: `<TCP  dport=http |>`.
- The default TCP source port renders as **`sport=ftp_data`** (port 20) — shown in the `.show()` tree in §1.3.

### 1.5 Why (rationale): the build chain fills the computed fields

This section is about the **computed** fields (`ihl`, `len`, `chksum`, `dataofs`) — the length, header‑size, and checksum values that resolve at assembly. It is **not** about the **linkage** fields (`Ether.type`, `IP.proto`): those are overload fields set earlier, at *stacking* time, by `add_payload()` (`scapy/packet.py:360`) / `bind_layers` (`scapy/layers/inet.py:1101,1113`) — see §1.2 — and are already stored (in `overloaded_fields`) before any build runs. With that distinction drawn, the difference between §1.3 and §1.4 is *assembly*. Serializing a packet runs the build chain `self_build()` (`scapy/packet.py:678`) → `do_build()` (`scapy/packet.py:724`) → `build()` (`scapy/packet.py:746`). Inside `do_build()`, each layer's `post_build(pkt, pay)` hook is invoked — the call is `return self.post_build(pkt, pay)` at `scapy/packet.py:738` (within `do_build()` at `scapy/packet.py:724-740`). That hook is the *dispatch point* for per‑protocol computed fields, but the **base** implementation `Packet.post_build()` is only a generic pass‑through — its body is `return pkt + pay` (`scapy/packet.py:758-767`) and it fills **no** lengths or checksums. The values that resolve in §1.4 are computed by the **protocol‑specific overrides** of that hook:

- **IP** — `IP.post_build()` (`scapy/layers/inet.py:539-551`) fills `ihl` when it is `None` (`scapy/layers/inet.py:542-544`), the total `len` (`scapy/layers/inet.py:545-547`), and the header `chksum` (`scapy/layers/inet.py:548-550`).
- **TCP** — `TCP.post_build()` (`scapy/layers/inet.py:767-786`) fills `dataofs` when it is `None` (`scapy/layers/inet.py:770-774`) and the segment `chksum` (`scapy/layers/inet.py:775-785`).

Therefore:

- `.show()` reflects fields **as currently stored** — an unset auto field is `None` (evidence: the `None` lines in §1.3).
- `.show2()` reflects fields **after assembly**, because it rebuilds via `self.__class__(raw(self))` (`scapy/packet.py:1486`) — so `ihl`, `len`, `chksum`, and `dataofs` acquire concrete values (evidence: the resolved lines in §1.4).

## Section 2 — Sending the packet (what Scapy reports during transmission)

### 2.1 Two send functions: layer 3 vs layer 2

Scapy offers two "usual" ways to transmit, differing by the layer at which they operate:

- **`send()`** transmits at **layer 3** (`scapy/sendrecv.py:422`). You hand it an `IP(...)` packet; Scapy builds the L2 header for you and **resolves the egress interface from the routing table** (§2.2).
- **`sendp()`** transmits at **layer 2** (`scapy/sendrecv.py:452`). You supply the explicit `Ether(...)` header, and Scapy sends the frame on the interface you name.

(The send‑and‑receive family is analogous: `sr` (`scapy/sendrecv.py:635`) and `sr1` (`scapy/sendrecv.py:656`) at L3, `srp` (`scapy/sendrecv.py:668`) and `srp1` (`scapy/sendrecv.py:693`) at L2. They are not needed to answer the question but are the reply‑collecting counterparts.)

### 2.2 Routing information (the "routing" sub‑question)

Because `send()` works at L3, it must decide *which interface* and *which source IP* to use. That decision comes from `Route.route()` at `scapy/route.py:146`, whose docstring states it "returns: (iface, output_ip, gateway_ip)" (`scapy/route.py:152`). Resolving the example destination produced verbatim:

```text
>>> conf.route.route("127.0.0.1")
('lo', '127.0.0.1', '0.0.0.0')
```

Reading the triple against the documented order (`iface, output_ip, gateway_ip`):

- egress interface **`iface = 'lo'`** — the loopback, matching `conf.loopback_name` (`scapy/config.py:911`);
- outgoing address **`output_ip = '127.0.0.1'`**;
- **`gateway_ip = '0.0.0.0'`** — meaning the destination is directly reachable (no gateway hop).

### 2.3 The routing table Scapy prints

The whole routing table is rendered by `Route.__repr__` at `scapy/route.py:47`, whose six‑column header tuple is defined at `scapy/route.py:60` as `("Network", "Netmask", "Gateway", "Iface", "Output IP", "Metric")`. Printing `conf.route` renders every configured route; the excerpt below is **minimized to the header and the single loopback route** that governs our send. The container's full table also contains unrelated, environment‑specific routes (a default route and container‑internal routes on other interfaces) which have no bearing on the `127.0.0.1` send and are omitted here to avoid quoting incidental host/network details:

```text
Network     Netmask          Gateway     Iface    Output IP     Metric
127.0.0.0   255.0.0.0        0.0.0.0     lo       127.0.0.1     1
```

The six columns, named exactly, are **Network / Netmask / Gateway / Iface / Output IP / Metric**, and the loopback row shown is the deterministic route that governs our send.

This is precisely why `route("127.0.0.1")` in §2.2 selected `iface='lo'`, `output_ip='127.0.0.1'`, `gateway_ip='0.0.0.0'`: `127.0.0.1` falls in `127.0.0.0/255.0.0.0`, whose gateway is `0.0.0.0` (direct) on interface `lo`.

### 2.4 The transmission report (what Scapy prints while sending)

The console output during transmission is written by the internal send loop `__gen_send()` at `scapy/sendrecv.py:332`. It emits a **per‑packet progress dot** via `os.write(1, b".")` at `scapy/sendrecv.py:380`, and after the loop prints the summary line `print("\nSent %i packets." % n)` at `scapy/sendrecv.py:392`. This prints **by default** because verbosity defaults to `conf.verb = 2` (`scapy/config.py:759`).

Sending the example at **layer 3** produced verbatim (the leading `.` is the progress dot; captured with unbuffered output to preserve the true console ordering):

```text
>>> send(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"))
.
Sent 1 packets.
```

Sending the equivalent frame at **layer 2** produced the identical report:

```text
>>> sendp(Ether()/IP(dst="127.0.0.1")/TCP(dport=80, flags="S"), iface="lo")
.
Sent 1 packets.
```

The literal summary string is exactly `Sent 1 packets.` (from the format `"\nSent %i packets."` at `scapy/sendrecv.py:392`, with `n = 1`).

> **Observed ordering nuance (reported truthfully).** The dot is written straight to file descriptor 1 with `os.write(1, b".")` (`scapy/sendrecv.py:380`), bypassing Python's buffered `sys.stdout`, whereas `Sent 1 packets.` goes through buffered `print()` (`scapy/sendrecv.py:392`). When output is piped rather than shown on a TTY, the buffered `print()` can flush *after* the raw dot; running the interpreter unbuffered (`python -u`) restores the natural `.` ‑then‑ `Sent 1 packets.` order shown above.

### 2.5 What leaves the system

When the stack is sent at **layer 3** over loopback, Scapy synthesizes the Ethernet header itself. The concrete bytes that go out are captured and shown in Section 3: a frame whose Ethernet header is `dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4` (the same all‑broadcast destination / all‑zero source already visible in the pre‑send `.show()` tree of §1.3).

## Section 3 — Sniffing the packet (how Scapy presents, interprets, and reconstructs the bytes)

### 3.1 Capturing with `AsyncSniffer` on `lo`

Capture was done with **`AsyncSniffer`** (`scapy/sendrecv.py:981`) on interface `lo`, while a matching packet was sent so the capture is self‑contained. The blocking equivalent is **`sniff()`** (`scapy/sendrecv.py:1308`). The exact pattern used was:

```python
t = AsyncSniffer(iface="lo", count=1,
                 lfilter=lambda p: TCP in p and p[TCP].dport == 80 and p[TCP].flags == "S")
t.start()
time.sleep(0.5)
send(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"), verbose=0)
t.join(timeout=5)
pkt = t.results[0]
```

A Python `lfilter` callback (`lambda p: TCP in p and ...`) is used to select exactly the SYN we send; it runs in‑process and needs no external library.

**BPF filter behavior in this container (reported truthfully).** A capture‑layer BPF string filter (e.g. `filter="tcp and dst port 80"`) *also works here*, and was verified to capture the packet — summary `Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S`. This is because **libpcap is present** on this host: Scapy reports its version as `b'libpcap version 1.10.5 (with TPACKET_V3)'`, so BPF compilation succeeds even though `conf.use_pcap = False` (native `PF_PACKET` sockets are still used for the actual capture). No "libpcap is not available" error was observed in this environment, so none is quoted here. On a host that genuinely lacks libpcap, a BPF `filter=` would fail to compile while an `lfilter=` callback would keep working — that is why the `lfilter` approach is used above as the portable default.

Producing command and its verbatim output (one claim, one line: `conf.use_pcap` is `False`, the libpcap version string, the captured count, and the summary):

```python
from scapy.all import IP, TCP, AsyncSniffer, send, conf
from scapy.libs.winpcapy import pcap_lib_version
print("conf.use_pcap =", conf.use_pcap)
print("libpcap version =", pcap_lib_version())
t = AsyncSniffer(iface="lo", count=1, filter="tcp and dst port 80")   # BPF string filter
t.start(); time.sleep(0.5)
send(IP(dst="127.0.0.1")/TCP(dport=80, flags="S"), verbose=0)
t.join(timeout=5)
print("captured count =", len(t.results))
print("summary =", t.results[0].summary())
```

```text

captured count = 1
summary = Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S
```

### 3.4 Layer reconstruction (the "layer reconstruction" sub‑question), by name

Turning raw bytes back into `Ether/IP/TCP` is **dissection**, driven by `dissect()` at `scapy/packet.py:1049` (which runs `pre_dissect → do_dissect → post_dissect → extract_padding → do_dissect_payload`) and `guess_payload_class()` at `scapy/packet.py:1062`, which chooses the *next* layer's class from the registered layer bindings. This is the inverse of the build chain from §1.5, and it is why the linkage fields matter: `Ether.type=IPv4` tells the dissector the next layer is `IP`, and `IP.proto=tcp` tells it the layer after that is `TCP`.

**Round‑trip demonstration (observed).** Serializing the built stack to bytes and re‑parsing them recovers the same three layers:

```text
>>> pkt = Ether()/IP(dst="127.0.0.1")/TCP(dport=80, flags="S")
>>> b = raw(pkt)                 # serialize the built stack to bytes
>>> len(b)
54
>>> pkt2 = Ether(b)              # re-parse the raw bytes back into layers
>>> pkt2
<Ether  dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4 |<IP  version=4 ihl=5 tos=0x0 len=40 id=1 flags= frag=0 ttl=64 proto=tcp chksum=0x7ccd src=127.0.0.1 dst=127.0.0.1 |<TCP  sport=ftp_data dport=http seq=0 ack=0 dataofs=5 reserved=0 flags=S window=8192 chksum=0x917c urgptr=0 |>>>
>>> [layer.__name__ for layer in pkt2.layers()]
['Ether', 'IP', 'TCP']
```

The recovered layer list `['Ether', 'IP', 'TCP']` is the concrete evidence that dissection rebuilt every layer from bytes alone.

**`Raw` fallback (observed).** When `guess_payload_class()` (`scapy/packet.py:1062`) cannot match the next layer to any registered binding, it falls back to `default_payload_class()` (`scapy/packet.py:1081`) — the fallback call is `return self.default_payload_class(payload)` at `scapy/packet.py:1079` — and that method's body is `return conf.raw_layer` (`scapy/packet.py:1090`), so the undissected bytes are kept as a `Raw` layer rather than being discarded. To exercise this on the **dissection** path, we serialize a packet whose IP protocol number is `253` (an unassigned value bound to no `bind_layers(IP, …)` entry — contrast `bind_layers(IP, TCP, frag=0, proto=6)` at `scapy/layers/inet.py:1113`) and then re‑parse the raw bytes; the dissector cannot guess a class for `proto=253`, so `guess_payload_class()` returns `conf.raw_layer` and the trailing bytes are reconstructed as `Raw`, verbatim:

```text
>>> p = Ether()/IP(dst="127.0.0.1", proto=253)/Raw(b"UNKNOWN_PAYLOAD_1234")
>>> p2 = Ether(raw(p))          # serialize to bytes, then dissect them back
>>> p2
<Ether  dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4 |<IP  version=4 ihl=5 tos=0x0 len=40 id=1 flags= frag=0 ttl=64 proto=253 chksum=0x7bd6 src=127.0.0.1 dst=127.0.0.1 |<Raw  load='UNKNOWN_PAYLOAD_1234' |>>>
>>> Raw in p2
True
```

Because `proto=253` matches no IP binding during dissection, the re‑parsed packet keeps its payload as `<Raw  load='UNKNOWN_PAYLOAD_1234'>` and the membership test `Raw in p2` returns `True` (both shown verbatim above) — in direct contrast to the well‑known `proto=6` (TCP) binding, which drove the SYN above to reconstruct all the way to `TCP`. (The distinction matters: simply appending raw `bytes` with `/` — e.g. `Ether()/IP()/b"…"` — *also* produces a `Raw` layer, but at **construction** time, because `add_payload()` wraps trailing bytes in `conf.raw_layer(load=…)` at `scapy/packet.py:375`; the serialize‑then‑reparse above is what actually exercises the **dissection‑time** `guess_payload_class()` fallback that this claim is about.)

## Section 4 — Summary (what the observations reveal)

Running the exact stack `Ether()/IP(dst="127.0.0.1")/TCP(dport=80)` through its full lifecycle revealed a consistent story — *forge → send → capture* — end to end. One claim, one line of evidence:

- **Build.** The `/` operator (`scapy/packet.py:596`) stacks the layers Ethernet → IP → TCP, and **at stacking time** — via `add_payload()` (`scapy/packet.py:360,370-372`) reading the `bind_layers` overloads (`scapy/layers/inet.py:1101,1113`) — Scapy auto‑populates the **linkage fields** so each layer advertises the next: `Ether` acquires `type=IPv4` and `IP` acquires `proto=tcp` (evidence: `<Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=http |>>>`, with `overloaded_fields` already `{'type': 2048}` and `{'frag': 0, 'proto': 6}` before any build). The **computed fields** (`ihl`, `len`, `chksum`, `dataofs`) are unset — printed as `None` by `.show()` (evidence: `ihl       = None`) — until the packet is **assembled**, at which point `.show2()` resolves them (evidence: `ihl       = 5`, `len       = 40`, `chksum    = 0x7ccd`). The reason is the build chain `self_build → do_build → build` (`scapy/packet.py:678,724,746`), whose `do_build()` invokes each layer's `post_build()` hook (`scapy/packet.py:738`); the actual length/checksum arithmetic lives in the protocol‑specific `IP.post_build()` (`scapy/layers/inet.py:539-551`) and `TCP.post_build()` (`scapy/layers/inet.py:767-786`), **not** in the generic `Packet.post_build()` pass‑through (`scapy/packet.py:758-767`) — see §1.5.

- **Send.** The layer‑3 `send()` (`scapy/sendrecv.py:422`) consults the **routing table** to choose an egress path — `conf.route.route("127.0.0.1")` returned `('lo', '127.0.0.1', '0.0.0.0')` (evidence: that triple) — whereas layer‑2 `sendp()` (`scapy/sendrecv.py:452`) uses the explicit `Ether` header instead. Both report transmission the same way under the default `conf.verb = 2` (`scapy/config.py:759`): a progress dot then `Sent 1 packets.` (evidence: the `.` and `Sent 1 packets.` lines from `scapy/sendrecv.py:380,392`).

- **Sniff.** The captured bytes are **dissected** straight back into `Ether/IP/TCP` (evidence: the captured `repr` in §3.2), tagged with the capturing interface `sniffed_on = 'lo'` (evidence: `'lo'`), and reconstructed field‑by‑field by `dissect()`/`guess_payload_class()` (`scapy/packet.py:1049,1062`) — recovering the layer list `['Ether', 'IP', 'TCP']` — with a `Raw` fallback when the dissector can't guess the next class: re‑parsing an unknown IP `proto=253` yields `<Raw  load='UNKNOWN_PAYLOAD_1234' |>` via `guess_payload_class()` → `conf.raw_layer` (`scapy/packet.py:1079,1090`). The whole packet collapses to a one‑line `.summary()` (`scapy/packet.py:1642`): `Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S`.

Taken together, the runtime behavior is exactly the lifecycle Scapy advertises for itself — it can "forge or decode packets ... send them on the wire, capture them" (`README.md:16-18`): the build stage *forges* the layers (applying the linkage overloads at stacking time, then filling the computed length/checksum fields at assembly), the send stage *puts them on the wire* (resolving a route and reporting the count), and the sniff stage *captures and decodes* them back into the same layered structure.
