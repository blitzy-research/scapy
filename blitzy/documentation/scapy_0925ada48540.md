# What Scapy Reveals as a Packet Moves Through Build → Send → Sniff

## Introduction

This document answers a single question by **observation, not by reading alone**: when you
start Scapy in its normal configuration, build a simple multi-layer packet (an
`Ether()/IP()/TCP()` stack), send it, and then sniff for that same traffic, **what does
Scapy actually show you at each stage, and why?**

Everything below was produced by **running Scapy from its own source tree** and capturing the
real output. The direct answer is stated plainly for each item, backed by the **exact
observed output** and a **`file:line` citation** into the source, with cause→effect reasoning.

## 2. Building `Ether()/IP()/TCP()` — What Scapy Shows as Each Layer Is Added

### 2.1 The `/` operator stacks layers

**Direct answer.** The `/` operator composes layers: `Ether()/IP()/TCP()` builds a three-layer
packet where `Ether` carries `IP` as its payload, and `IP` carries `TCP`. `/` is implemented by
`Packet.__div__` [scapy/packet.py:L596] (`__truediv__ = __div__` [scapy/packet.py:L607]); it
clones both operands and attaches the right operand as the left operand's payload via
`add_payload()` [scapy/packet.py:L360].

### 2.2 Selective `__repr__`: only set/overloaded fields are shown

**Direct answer.** The interactive `repr` shows a layer's fields **selectively** — only fields
the user set, or fields *overloaded* by a protocol binding. Everything left at its plain
default is omitted. Observed, building up one layer at a time:

```
repr(Ether())            -> <Ether  |>
repr(Ether()/IP())       -> <Ether  type=IPv4 |<IP  |>>
repr(Ether()/IP()/TCP()) -> <Ether  type=IPv4 |<IP  frag=0 proto=tcp |<TCP  |>>>
```

**Cause → effect.** `Packet.__repr__` [scapy/packet.py:L552] iterates the field descriptors and
prints a field **only if** its name is in `self.fields` (explicitly set) [scapy/packet.py:L559]
**or** in `self.overloaded_fields` (binding-driven) [scapy/packet.py:L564]; any other field
hits the `else: continue` branch [scapy/packet.py:L569] and is skipped. The output wrapper
`<LayerName field=val |payload>` is formatted at [scapy/packet.py:L581].

- **`Ether()` alone shows no fields** because every field is a plain default. Its `type` default
  is `0x9000` (observed: `Ether().get_field("type").default` → `0x9000`), which is neither set
  nor overloaded, so it is skipped.
- **Stacking overloads fields.** The overloads come from `bind_layers` declarations. Observed on
  the composite packet `eit = Ether()/IP()/TCP()`:

```
eit[Ether].overloaded_fields = {'type': 2048}
eit[Ether].fields            = {}
eit[IP].overloaded_fields    = {'frag': 0, 'proto': 6}
eit[IP].fields               = {'options': []}
eit[TCP].overloaded_fields   = {}
eit[TCP].fields              = {}
```

So `type=IPv4` (2048 = `0x0800`) appears once `IP` is stacked under `Ether`, and `frag=0` and
`proto=tcp` (6) appear once `TCP` is stacked under `IP` — even though the user never set them.
These overloads are registered by `bind_layers(Ether, IP, type=2048)`
[scapy/layers/inet.py:L1101] and `bind_layers(IP, TCP, frag=0, proto=6)`
[scapy/layers/inet.py:L1113]. The layer classes themselves are `Ether`
[scapy/layers/l2.py:L244], `IP` [scapy/layers/inet.py:L521], and `TCP`
[scapy/layers/inet.py:L753].

### 2.3 `summary()` and `command()`

**Direct answer.** `summary()` gives a one-line human description; `command()` reconstructs the
Python constructor call that would rebuild the packet. Observed:

```
(Ether()/IP()/TCP()).summary() -> 'Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S'
(Ether()/IP()/TCP()).command() -> 'Ether()/IP()/TCP()'
```

`summary()` [scapy/packet.py:L1642] renders `Ether / IP / TCP` plus a protocol-specific tail;
the ports print as **service names** — `ftp_data` (20) for `sport` and `http` (80) for `dport`
— because they are enum fields, and `S` is the TCP **SYN** flag (the default `TCP.flags`).
`command()` [scapy/packet.py:L1662] rebuilds the constructor string from each layer's
`self.fields`; since no fields were explicitly set, it round-trips to exactly `Ether()/IP()/TCP()`.

### 2.4 `show()` (pre-build, in-memory) vs `show2()` (post-build, re-dissected)

**Direct answer.** `show()` prints the packet **as it currently sits in memory**, where
auto-computed fields (`IP.ihl/len/chksum`, `TCP.dataofs/chksum`) are still **`None`** because
they are only filled in when the packet is serialized. `show2()` first **builds the packet to
bytes and re-dissects it**, so those computed fields are now **resolved to real values**.

`show()` — computed fields are `None`:

```
###[ Ethernet ]### 
  dst       = ff:ff:ff:ff:ff:ff
  src       = 00:00:00:00:00:00
  type      = IPv4
###[ IP ]### 
     version   = 4
     ihl       = None
     tos       = 0x0
     len       = None
     id        = 1
     flags     = 
     frag      = 0
     ttl       = 64
     proto     = tcp
     chksum    = None
     src       = 127.0.0.1
     dst       = 127.0.0.1
     \options   \
###[ TCP ]### 
        sport     = ftp_data
        dport     = http
        seq       = 0
        ack       = 0
        dataofs   = None
        reserved  = 0
        flags     = S
        window    = 8192
        chksum    = None
        urgptr    = 0
        options   = ''
```

`show2()` — same packet after `self.__class__(raw(self))` (build + re-dissect); the previously
`None` fields are now filled (all other fields are identical to `show()` above):

```
###[ IP ]### 
     ...
     ihl       = 5
     len       = 40
     chksum    = 0x7ccd
     ...
###[ TCP ]### 
     ...
     dataofs   = 5
     chksum    = 0x917c
     ...
```

**Cause → effect.** `show()` [scapy/packet.py:L1459] prints the live in-memory object; the
auto-computed fields have not been calculated yet, so they read `None`. `show2()`
[scapy/packet.py:L1473] returns `self.__class__(raw(self)).show(...)`
[scapy/packet.py:L1486] — it serializes the packet through `raw()` [scapy/compat.py:L112],
which runs the build pipeline `build()` [scapy/packet.py:L746] → `do_build()`
[scapy/packet.py:L724] → `self_build()` [scapy/packet.py:L678] and then `post_build()`
[scapy/packet.py:L758], where `IP` and `TCP` override `post_build` to compute the length and
checksum. Re-parsing those bytes yields `ihl=5`, `len=40`, IP `chksum=0x7ccd`, TCP `dataofs=5`,
and TCP `chksum=0x917c`.

### 2.5 `hexdump()` — the assembled bytes before it leaves

**Direct answer.** The fully built packet is **54 bytes**; `hexdump()` shows them in the classic
tcpdump grid (offset, 16 hex bytes/row, ASCII column). Observed:

```
len(bytes(Ether()/IP()/TCP())) = 54
0000  FF FF FF FF FF FF 00 00 00 00 00 00 08 00 45 00  ..............E.
0010  00 28 00 01 00 00 40 06 7C CD 7F 00 00 01 7F 00  .(....@.|.......
0020  00 01 00 14 00 50 00 00 00 00 00 00 00 00 50 02  .....P........P.
0030  20 00 91 7C 00 00                                 ..|..
```

`hexdump()` is [scapy/utils.py:L273]. Reading the bytes against the layers confirms the build:
`08 00` is the Ethernet `type` (IPv4); `45` is IP `version=4`/`ihl=5`; `40 06` shows `ttl=64`
and `proto=6`; `7C CD` is the IP checksum (matching `show2()`'s `chksum=0x7ccd`); `7F 00 00 01`
twice is the loopback `127.0.0.1` source and destination; and the trailing `91 7C` is the TCP
checksum `0x917c`.

## 3. Sending — Routing, Interface Selection, and Transmission Reporting

### 3.1 The routing table Scapy consults

**Direct answer.** Before it can send, Scapy decides *which interface and source IP* to use by
consulting its own routing table, `conf.route`. Observed (`repr(conf.route)`, ANSI-stripped):

```
Network     Netmask          Gateway     Iface    Output IP     Metric
0.0.0.0     0.0.0.0          10.236.0.1  eth0     10.236.0.248  0     
10.236.0.0  255.255.255.0    10.236.0.1  eth0     10.236.0.248  0     
10.236.0.1  255.255.255.255  0.0.0.0     eth0     10.236.0.248  0     
127.0.0.0   255.0.0.0        0.0.0.0     lo       127.0.0.1     1     
172.17.0.0  255.255.0.0      0.0.0.0     docker0  172.17.0.1    0     
```

The six columns — **Network, Netmask, Gateway, Iface, Output IP, Metric** — are produced by
`Route.__repr__` [scapy/route.py:L47] (the header tuple is at [scapy/route.py:L60]). The `Route`
class itself is [scapy/route.py:L31]. The concrete IP addresses (`10.236.0.*`) are
**host-specific and will differ on another machine**; the structurally important row is
`127.0.0.0 / 255.0.0.0 → lo`, which is why a packet addressed to `127.0.0.1` is routed out the
loopback interface.

### 3.2 Route resolution: `(iface, output_ip, gateway_ip)`

**Direct answer.** Resolving a destination returns a 3-tuple `(iface, output_ip, gateway_ip)`.
For a loopback destination, both surfaces agree:

```
IP(dst="127.0.0.1").route()   -> ('lo', '127.0.0.1', '0.0.0.0')
conf.route.route("127.0.0.1") -> ('lo', '127.0.0.1', '0.0.0.0')
```

`IP.route()` [scapy/layers/inet.py:L559] delegates to `conf.route.route(dst)` (`return
conf.route.route(dst)` at [scapy/layers/inet.py:L566]), i.e. `Route.route()`
[scapy/route.py:L146], which returns the tuple and chooses the **most-specific** matching route
(greatest netmask, then metric). When Scapy sends, `_interface_selection()`
[scapy/sendrecv.py:L616] picks the outgoing interface from the first packet's route —
`iff = next(packet.__iter__()).route()[0]` [scapy/sendrecv.py:L626], falling back to
`conf.iface` [scapy/sendrecv.py:L629] if the packet has no route method. The gateway `0.0.0.0`
means "directly connected, no next-hop router," which is correct for loopback.

### 3.3 Transmission — both send paths and the progress report

**Direct answer.** At the default verbosity (`conf.verb = 2`), sending prints **one `.` per
packet** followed by a summary line **`Sent N packets.`**. This is identical for the **layer-3**
`send()` and the **layer-2** `sendp()` — they share one send engine. Observed on loopback:

```
>>> send(IP(dst="127.0.0.1")/TCP(), iface="lo")        # Layer 3
.
Sent 1 packets.

>>> sendp(Ether()/IP()/TCP(), iface="lo")              # Layer 2
.
Sent 1 packets.

>>> send(IP(dst="127.0.0.1")/TCP(), iface="lo", count=3)
...
Sent 3 packets.

>>> send(IP(dst="127.0.0.1")/TCP(), iface="lo", verbose=0)   # silent — no output
```

**Cause → effect.** `send()` [scapy/sendrecv.py:L422] is the layer-3 path: it calls
`_interface_selection()` [scapy/sendrecv.py:L442] and then `_send(...)` with a layer-3 socket
factory (`lambda iface: iface.l3socket()` [scapy/sendrecv.py:L445]). `sendp()`
[scapy/sendrecv.py:L452] is the layer-2 path, using `lambda iface: iface.l2socket()` instead.
Both funnel through `_send()` [scapy/sendrecv.py:L396] into the shared engine `__gen_send()`
[scapy/sendrecv.py:L332]. There, `verbose` defaults to `conf.verb` [scapy/sendrecv.py:L355];
each packet is transmitted with `s.send(p)` [scapy/sendrecv.py:L375]; **only if `verbose`** is
truthy does it write one `.` per packet via `os.write(1, b".")` [scapy/sendrecv.py:L380] and
finally `print("\nSent %i packets." % n)` [scapy/sendrecv.py:L392]. That gate is why
`verbose=0` produces no output at all, while `count=3` prints three dots and `Sent 3 packets.`.

The socket factories are `NetworkInterface.l3socket` [scapy/interfaces.py:L165] and
`l2socket` [scapy/interfaces.py:L157]; `_send()` resolves the interface with `resolve_iface()`
[scapy/interfaces.py:L386]. On this Linux host those factories yield the native `AF_PACKET`
sockets `L3PacketSocket` [scapy/arch/linux.py:L587] and `L2Socket` [scapy/arch/linux.py:L475],
whose platform-independent `send`/`recv` primitives live on `SuperSocket`
[scapy/supersocket.py:L172]. Because the destination is `127.0.0.1`, the packet is sent on `lo`
and never leaves the host.

> **Observed nuance (fd-level vs buffered output).** The `.` is written straight to file
> descriptor 1 with `os.write` (unbuffered), whereas `Sent N packets.` goes through buffered
> `print`. Under captured/piped stdout the two can interleave out of order; running with
> `python3 -u` (or interactively) shows them in the natural order above.

## 4. Sniffing — Capturing the Same Traffic and Reconstructing the Layers

To capture "the same traffic," an `AsyncSniffer` is started on the loopback interface, and one
packet is sent on `lo` a moment later; the sniffer captures it and stops. This self-correlates
send and sniff on one host.

### 4.1 What the capture returns

**Direct answer.** The result is a `PacketList` whose `repr` summarizes it by protocol, and each
captured packet has been **fully reconstructed into typed `Ether/IP/TCP` layers** — not left as
raw bytes. A distinctive `dport=9999` was used so the captured packet is unmistakably the one
that was sent. Observed:

```
results               -> <Sniffed: TCP:1 UDP:0 ICMP:0 Other:0>
len(results)          -> 1
results[0].sniffed_on -> 'lo'
results[0].haslayer(IP), results[0].haslayer(TCP) -> True, True
results[0][TCP].dport -> 9999
results[0].summary()  -> 'Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:9999 S'
```

The list summary `<Sniffed: TCP:1 UDP:0 ICMP:0 Other:0>` is `PacketList.__repr__`
[scapy/plist.py:L105] (the `PacketList` class is [scapy/plist.py:L741]; it also offers
`summary` [scapy/plist.py:L193] and `show` [scapy/plist.py:L236]). The **`sniffed_on = 'lo'`**
metadata is attached during capture at [scapy/sendrecv.py:L1252]
(`p.sniffed_on = sniff_sockets[s]`). Live capture is driven by `AsyncSniffer`
[scapy/sendrecv.py:L981] (its worker `_run` is [scapy/sendrecv.py:L1064]); the synchronous
`sniff()` [scapy/sendrecv.py:L1308] is the same machinery. That `haslayer(IP)` and
`haslayer(TCP)` are both `True`, and `[TCP].dport` reads back `9999`, is the direct proof that
the raw bytes were parsed back into the original typed layers.

### 4.2 How raw bytes become typed layers (dissection)

**Direct answer.** On capture, the raw bytes are dissected top-down: each layer decides the
class of the next layer from the protocol-binding registry, reversing exactly what stacking did
during the build.

The dissected packet's `repr` shows **every** parsed field:

```
<Ether  dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4 |<IP  version=4 ihl=5 tos=0x0 len=40 id=1 flags= frag=0 ttl=64 proto=tcp chksum=0x7ccd src=127.0.0.1 dst=127.0.0.1 |<TCP  sport=ftp_data dport=9999 seq=0 ack=0 dataofs=5 reserved=0 flags=S window=8192 chksum=0x6abd urgptr=0 |>>>
```

**Cause → effect.** The raw bytes enter through `Packet.__init__(_pkt=...)`
[scapy/packet.py:L141] and are parsed by `dissect()` [scapy/packet.py:L1049] (which drives
`do_dissect()` [scapy/packet.py:L1002] and `extract_padding()` [scapy/packet.py:L982]). The
crucial step is choosing each next layer: `guess_payload_class()` [scapy/packet.py:L1062]
consults the `payload_guess` entries populated by the same `bind_layers` calls used for the
build — `Ether.type == 2048` selects `IP` [scapy/layers/inet.py:L1101] and `IP.proto == 6`
with `frag == 0` selects `TCP` [scapy/layers/inet.py:L1113]. If no binding matched, it would
fall back to `default_payload_class()` [scapy/packet.py:L1081] → `conf.raw_layer`
[scapy/packet.py:L1090] (a raw byte blob) — but here every layer matched, so `Ether/IP/TCP`
is fully rebuilt. (The TCP checksum reads `0x6abd` here rather than the §2 default `0x917c`
simply because `dport=9999` changes the checksummed bytes.)

### 4.3 The key contrast: built `repr` vs dissected `repr`

**Direct answer.** This is the single clearest demonstration of Scapy's selective display: the
**same logical packet** prints *few* fields when freshly built, but *all* fields once captured
and dissected.

```
BUILT   repr(Ether()/IP(dst="127.0.0.1")/TCP(dport=9999))
  -> <Ether  type=IPv4 |<IP  frag=0 proto=tcp dst=127.0.0.1 |<TCP  dport=9999 |>>>

SNIFFED repr (the dissected packet from §4.2)
  -> <Ether  dst=ff:ff:ff:ff:ff:ff src=00:00:00:00:00:00 type=IPv4 |<IP  version=4 ihl=5 tos=0x0 len=40 id=1 flags= frag=0 ttl=64 proto=tcp chksum=0x7ccd src=127.0.0.1 dst=127.0.0.1 |<TCP  sport=ftp_data dport=9999 seq=0 ack=0 dataofs=5 reserved=0 flags=S window=8192 chksum=0x6abd urgptr=0 |>>>
```

**Cause → effect.** The **built** packet's `repr` shows only what was set (`dst`, `dport`) or
overloaded (`type`, `frag`, `proto`); every other default is skipped at
[scapy/packet.py:L569]. The **dissected** packet shows every field because `dissect()`
[scapy/packet.py:L1049] populates `self.fields` with *every* value it parsed off the wire, so
each field passes the "is it in `self.fields`?" test at [scapy/packet.py:L559] and prints. Same
`__repr__` logic [scapy/packet.py:L552]; opposite outcome, entirely due to how many fields are
populated.

### 4.4 libpcap absent — the observed error, and why capture still works

**Lead with the observed output.** When a BPF `filter=` argument is supplied, Scapy prints this
error to stderr:

```
ERROR: Cannot set filter: libpcap is not available. Cannot compile filter !
```

**Yet the capture still succeeds.** With `AsyncSniffer(iface="lo", filter="tcp port 9999", ...)`
plus a concurrent send, the sniffer still returned **one** packet (`len(results) == 1`).

**Cause → effect.** Compiling a BPF filter expression requires `libpcap`/`tcpdump`, which are
**not installed** here, so the compile step fails and prints the error. But sniffing does not
depend on libpcap: Scapy captures through the native Linux `AF_PACKET` listener
`L2ListenSocket` [scapy/arch/linux.py:L579] (a subclass of `L2Socket`
[scapy/arch/linux.py:L475], reading frames via `recv_raw()` [scapy/arch/linux.py:L555]). The
socket simply receives **unfiltered**, and Scapy hands back the packet. This is an environment

## 5. Summary — What Scapy Revealed at Each Stage

Following one `Ether()/IP()/TCP()` packet through its whole lifecycle, Scapy revealed a
consistent design at every stage:

- **BUILD.** The `/` operator [scapy/packet.py:L596] stacks layers, and **protocol bindings
  drive field overloading**: `bind_layers` [scapy/layers/inet.py:L1101, L1113] silently set
  `type=IPv4`, `proto=tcp`, and `frag=0` so the stack is internally consistent without the user
  touching them. The display is deliberately **selective and pre-serialization**:
  `__repr__` [scapy/packet.py:L552] shows only set/overloaded fields, and `show()`
  [scapy/packet.py:L1459] leaves auto-computed fields (`ihl`, `len`, checksums, `dataofs`) as
  `None`. Those values are **deferred until the packet is built to bytes** — `show2()`
  [scapy/packet.py:L1473] / `raw()` [scapy/compat.py:L112] run `post_build`
  [scapy/packet.py:L758] to compute them, and `hexdump()` [scapy/utils.py:L273] confirms the
  final 54-byte wire form.

- **SEND.** Transmission is **route-driven**: Scapy resolves `(iface, output_ip, gateway_ip)`
  via `IP.route()` [scapy/layers/inet.py:L559] → `Route.route()` [scapy/route.py:L146] and picks
  the outgoing interface in `_interface_selection()` [scapy/sendrecv.py:L616], reading its
  routing table `Route.__repr__` [scapy/route.py:L47]. Layer-3 `send()`
  [scapy/sendrecv.py:L422] and layer-2 `sendp()` [scapy/sendrecv.py:L452] differ only in which
  socket they open; both report through **one shared engine** `__gen_send()`
  [scapy/sendrecv.py:L332], whose terse `verb=2` output is a `.` per packet
  [scapy/sendrecv.py:L380] and a final `Sent N packets.` [scapy/sendrecv.py:L392].

- **SNIFF.** Capture uses the native Linux `AF_PACKET` listener `L2ListenSocket`
  [scapy/arch/linux.py:L579], and the raw bytes are **reconstructed into typed layers** by the
  *same* binding registry used to build them: `dissect()` [scapy/packet.py:L1049] +
  `guess_payload_class()` [scapy/packet.py:L1062] walk `Ether → IP → TCP` and, because
  dissection populates every field, the packet now **displays all of them** — the mirror image
  of the sparse built-packet `repr`. Capture even succeeds with `libpcap` absent (the BPF
  filter is skipped with an error, but the native socket still receives).

**In one sentence:** Scapy builds by *overloading* fields through bindings and *deferring*
computed values until serialization; it sends by *resolving a route* and reporting tersely
through one engine for L3 and L2; and it sniffs by *capturing raw bytes* and *re-dissecting*
them through the same bindings — so the packet you built, sent, and captured is provably the
same one, shown sparsely when constructed and fully when parsed.

### 5.1 Inferred edge case — no matching route

**Labeled inferred (not triggered here).** Because a default route (`0.0.0.0`) is present in
this environment, `Route.route()` always finds a match, so the no-route branch could not be
exercised. From reading the source: when no route matches, `Route.route()` emits
`warning("No route found (no default route?)")` [scapy/route.py:L189] and returns the loopback
fallback `(conf.loopback_name, "0.0.0.0", "0.0.0.0")` [scapy/route.py:L190]. This is derived
from code inspection, not observed output.
