### ⚠ Correction to the brief: the TripleDES warning **DOES** appear here `[observed]`

The investigation brief's "CORRECTION #3" predicted that **no** `CryptographyDeprecationWarning: TripleDES` line would appear, on the assumption that `cryptography` was 41.0.7. **That is not this container.** Here, `cryptography` is **43.0.0** `[observed]` and **two** TripleDES deprecation warnings appear on **every** run (3/3 runs, stable) `[observed]`, at exactly `scapy/layers/ipsec.py:573` and `scapy/layers/ipsec.py:577`.

Root cause, grounded in source `[source-derived + inferred causation]`:

- `scapy/layers/ipsec.py` is imported at Scapy startup and defines the DES and 3DES crypto algorithms using `cipher=algorithms.TripleDES`: DES at [scapy/layers/ipsec.py:L572-L573] and 3DES at [scapy/layers/ipsec.py:L576-L577]. The `cipher=algorithms.TripleDES,` keyword line is L573 (DES) and L577 (3DES) — the exact lines named in the captured warnings. **[observed]**
- The `warnings.catch_warnings()` / `warnings.filterwarnings("ignore", category=CryptographyDeprecationWarning)` suppression block begins at [scapy/layers/ipsec.py:L581-L584] and **only wraps the subsequent CAST5 and Blowfish** algorithm definitions [scapy/layers/ipsec.py:L585 onward]. The DES/3DES definitions at L572-L577 are **outside** that block, so any deprecation warning they raise is **not** suppressed. **[observed]**
- With `cryptography` 43.0.0, the warning is triggered simply by **accessing/referencing the deprecated `TripleDES` class attribute** — i.e. by evaluating the name `algorithms.TripleDES` so it can be passed as the `cipher=` keyword argument to `CryptAlgo(...)`. No cipher is *instantiated* at this point; the module-level attribute lookup on `cryptography.hazmat.primitives.ciphers.algorithms` itself emits the `CryptographyDeprecationWarning` (the message text says TripleDES "has been moved to `cryptography.hazmat.decrepit.ciphers.algorithms.TripleDES` and will be removed from this module in 48.0.0"). Because these two `cipher=algorithms.TripleDES` references are evaluated when `scapy/layers/ipsec.py` is imported at startup, the two warnings surface at import time. **[observed]**
- **[inferred]** With an *older* `cryptography` (e.g. the brief's assumed 41.0.7) that had not yet added the TripleDES deprecation, these two lines would not appear — which is exactly what the brief predicted for its (different) environment. The presence/absence of the warning is therefore a function of the installed `cryptography` version, and in this canonical container it is **present**.

### This is a NON-CANONICAL, file-mtime-derived value

`2026.07.13` is **not** a Scapy release number — it is the **modification date of `scapy/__init__.py`** formatted as `%Y.%m.%d`, produced by the *last-resort fallback* inside `_version()`. Proof of the causal chain, all **[observed]**:

```bash
# The mtime fallback reproduces the exact value; this one-liner deliberately mirrors
# Scapy's own fallback call at scapy/__init__.py:L160 (which also uses utcfromtimestamp).
# Complete output (stdout AND stderr) shown below:
PYTHONPATH=. python3 -c "import datetime,os; print(datetime.datetime.utcfromtimestamp(os.path.getmtime('scapy/__init__.py')).strftime('%Y.%m.%d'))" 2>&1
```
```text
<string>:1: DeprecationWarning: datetime.datetime.utcfromtimestamp() is deprecated and scheduled for removal in a future version. Use timezone-aware objects to represent datetimes in UTC: datetime.datetime.fromtimestamp(timestamp, datetime.UTC).
2026.07.13
```

> **stdout vs stderr, explained `[observed + source-derived]`.** The value on **stdout** is `2026.07.13` — an EXACT match with `scapy.VERSION`. The line on **stderr** is a Python 3.13 `DeprecationWarning` emitted because this one-liner calls the (deprecated) `utcfromtimestamp` **directly in `__main__`**; it deliberately mirrors Scapy's own fallback call at [scapy/__init__.py:L160]. Scapy's *own import* does **not** surface this warning — Python's default warning filter shows `DeprecationWarning` only for code running in `__main__`, whereas `_version()` executes inside the `scapy` package — which is why the Q1 banner and the Q2 `import` show only the two `TripleDES` warnings and never this one (verified: `import scapy` emits no `utcfromtimestamp` warning).

### Mechanism — the ordered fallback chain in `_version()` [scapy/__init__.py:L122]

`_version()` tries five sources in order and returns the first that succeeds [scapy/__init__.py:L122-L166]:

1. **Method 0 — env `SCAPY_VERSION`** [scapy/__init__.py:L128-L133]: `return os.environ['SCAPY_VERSION']`. **Skipped** — the variable is unset (`KeyError` → `pass`). **[observed]**
2. **Method 1 — the packaged `VERSION` file** [scapy/__init__.py:L135-L143]: opens `scapy/VERSION`. **Raises `FileNotFoundError`** — that file is written only during packaging by `setup.py` `_build_version()` [setup.py:L56-L62], and this checkout is imported in place, never packaged. **[observed]**
3. **Method 2 — git-archive tag** `_version_from_git_archive()` [scapy/__init__.py:L145-L149]: **Raises `ValueError`** — the checkout is a real clone, not a `git archive` export. **[observed]**
4. **Method 3 — `git describe`** `_version_from_git_describe()` (call site [scapy/__init__.py:L153]; definition [scapy/__init__.py:L72-L120]): shells out to **`git describe --tags --always --long`** [scapy/__init__.py:L114]. With **zero tags** this yields a bare abbreviated commit hash — observed here as **`22140bed`**, the **current HEAD**, because `git describe` reflects whatever HEAD is, **not** the source commit `0925ada4`. Since that string does not start with `v`, the function retries via `git rev-list --tags --max-count=1` (empty with zero tags) then describes again, still `22140bed` [scapy/__init__.py:L115-L119]. `_parse_tag("22140bed")` then fails its regex `^v?(.+?)-(\d+)-g[a-f0-9]+$` [scapy/__init__.py:L30] and raises **`ValueError('tag has invalid format')`** [scapy/__init__.py:L35], which the surrounding `except Exception:` at the call site [scapy/__init__.py:L154-L155] swallows. **[observed]** — verified by invoking `_version_from_git_describe()` directly, which raises `ValueError: tag has invalid format`. **[observed]**
5. **Fallback — file mtime (REACHED)** [scapy/__init__.py:L157-L163]: `d = datetime.datetime.utcfromtimestamp(os.path.getmtime(__file__))` [scapy/__init__.py:L160] then `return d.strftime('%Y.%m.%d')` [scapy/__init__.py:L161]. This is the branch that produces `2026.07.13`. **[observed]**
6. Last resort `return '0.0.0'` [scapy/__init__.py:L166] — **not reached**. **[inferred]**

The result is assigned at `VERSION = __version__ = _version()` [scapy/__init__.py:L169], and `VERSION_MAIN` is derived from it by a numeric regex [scapy/__init__.py:L171-L172] (which for a purely numeric date string yields the same value). The banner surfaces it because the console entry point is `scapy = "scapy.main:interact"` [pyproject.toml:L47] and the project's dynamic version is `version = { attr = "scapy.VERSION" }` [pyproject.toml:L78].

### Corroboration (web — used only to confirm, not replace, the run)

Public sources confirm that real Scapy releases use **semantic** version numbers: the current released line is **2.7.x** — `2.7.0` shipped in December 2025 and `2.7.1` is the current documented release — and Scapy supports Python 3.7–3.13. A date-formatted string like `2026.07.13` therefore **does not** correspond to any real Scapy release number, which corroborates the runtime finding that the observed value is a computed fallback rather than a release identifier. Authoritative sources: `https://pypi.org/project/scapy/`, `https://github.com/secdev/scapy/releases`, and `https://scapy.readthedocs.io/`. **[corroboration only — the release-numbering scheme is confirmed from the web; the `2026.07.13` value itself is observed at runtime and the git-`describe`/mtime mechanism that produces it is source-derived from `scapy/__init__.py`, above]**

**Conclusion:** a canonical *packaged* or *tagged* build would report a **semantic** version (e.g. `2.7.0`); the `2026.07.13` observed here is the **file-mtime fallback** and is explicitly **non-canonical**. It is reported and explained, not "fixed" (no `scapy/VERSION` file was created and no git tag was added).

## Q6 — Source-code explanation: how Scapy builds the default IP header

This section explains, from the source, how the IP header is constructed by default and ties each observed Q3 value to the exact line that produces it.

### The build lifecycle

When a packet is serialized — `bytes(pkt)` (or when it is sent) — Scapy walks a fixed lifecycle (all in `scapy/packet.py` unless noted):

1. `bytes(pkt)` invokes `Packet.build()` [scapy/packet.py:L746].
2. `build()` calls `do_build()` [scapy/packet.py:L724].
3. `do_build()` calls `self_build()` [scapy/packet.py:L678] (at [scapy/packet.py:L733]). `self_build()` serializes this layer by iterating `fields_desc` and, for each field, reading its **current stored value** via `val = self.getfieldval(f.name)` [scapy/packet.py:L698] and appending it with `f.addfield(...)`. It serializes *whatever is currently on the object* — not "the defaults" per se. For a freshly-built `IP()/ICMP()` those current values happen to be the `fields_desc` defaults [scapy/layers/inet.py:L524-L537] for most fields, the binding-set `proto=1`, and the lazily-resolved `src`; an explicitly-set or payload-overloaded field would be emitted in place of its default.
4. `do_build()` then calls `self.post_build(pkt, pay)` [scapy/packet.py:L738]. The **default** `Packet.post_build()` [scapy/packet.py:L758] is a no-op that just returns `pkt + pay` [scapy/packet.py:L767] — but `IP` **overrides** it.

### `IP.post_build()` — where `ihl`, `len`, and `chksum` are computed [scapy/layers/inet.py:L539-L551]

The override recomputes exactly the three fields that were `None` sentinels in Q3, and only when they are `None` (so a user-supplied value is never clobbered):

- **`ihl`** — when `self.ihl is None`, it is set to `len(p) // 4` (the header length in 32-bit words) and written into the low nibble of byte 0 [scapy/layers/inet.py:L542-L544]. For a plain 20-byte header this yields `ihl = 5` — matching Q3.
- **`len`** — when `self.len is None`, the total length is computed as `len(p) + len(pay)` and packed into bytes 2–3 [scapy/layers/inet.py:L545-L547]. For a 20-byte IP header + 8-byte ICMP echo this yields `len = 28` — matching Q3.
- **`chksum`** — when `self.chksum is None`, the header checksum is computed by `checksum(p)` and written into bytes 10–11 [scapy/layers/inet.py:L548-L550]. This yields `chksum = 0x7cde` — matching Q3.
- Finally it returns `p + pay` [scapy/layers/inet.py:L551].

### `src` resolution — lazy, via `SourceIPField` (not `IP.route()`)

The `src` field is a `SourceIPField("src", "dst")` [scapy/layers/inet.py:L535], whose **internal default is `None`** — set by `IPField.__init__(self, name, None)` [scapy/fields.py:L859]. It holds **no static address**; it resolves the source lazily whenever the field is *read* or *serialized*, and only when the stored value is still `None`:

- On **read** (e.g. `getattr`, `show()`), `SourceIPField.i2h()` [scapy/fields.py:L885-L889] resolves it.
- On **serialize** (during `self_build`), `SourceIPField.i2m()` [scapy/fields.py:L879-L883] resolves it.

Both call the private `__findaddr(pkt)` [scapy/fields.py:L862-L877], which reads the destination via `self.dstname` and returns **`conf.route.route(dst)[1]`** — element `[1]`, the *source-address* member of the route tuple [scapy/fields.py:L877]. For a loopback `dst` this yields `127.0.0.1`, which is why `src` both reads and serializes as `127.0.0.1` (Q3).

This is **distinct** from `IP.route()` [scapy/layers/inet.py:L559-L566], a separate packet-level helper that returns the **full** `conf.route.route(dst)` tuple `('lo', '127.0.0.1', '0.0.0.0')` [scapy/layers/inet.py:L566] (the call surfaced in Q5). `SourceIPField` does **not** invoke `IP.route()`; it calls `conf.route.route(dst)` directly inside `__findaddr` and takes element `[1]`. **[source-derived]**

### The `None`-sentinel → computed-value mechanism, and *why*

The design splits IP-header fields into two groups:

- **Static defaults that "just work"** without user input — `version=4`, `tos=0`, `id=1`, `flags=0`, `frag=0`, `ttl=64`, `dst="127.0.0.1"` — declared directly in `fields_desc` [scapy/layers/inet.py:L524-L537].
- **Derived fields that can only be known once the bytes are laid out** — `ihl` (depends on options length), `len` (depends on header + payload length), and `chksum` (depends on the final header bytes). These are declared with a `None` default and **deferred to serialization**, computed in `post_build()` [scapy/layers/inet.py:L539-L551]. Using `None` as a sentinel lets a user override any of them explicitly (in which case `post_build` leaves the user's value alone), while defaulting to automatic computation.

### Counting method (what the parser actually counts)

A unit test is introduced by a line **whose first character is `=`** — *not* necessarily `= ` with a trailing space. The parser is explicit: `parse_campaign_file()` [scapy/tools/UTscapy.py:L357-L382] classifies each line by its **first character only**, and the test-title branch is `elif line[0] == "=":` [scapy/tools/UTscapy.py:L375]. So a title such as `=bridge and sniff setup vcan0 vcan1 ...` (in `test/contrib/cansocket_native.uts`) or `=MQTTConnack, packet instantiation` **is** a test even though no space follows the `=`.

**Consequence for counting `[observed static count]`.** The naïve `^= ` pattern (requiring a space) **undercounts**. Counting the parser's real predicate (`line[0] == '='`) over the exact globs the config selects yields:

```text

test/*.uts 848 | scapy/layers 1800 | contrib 1795 | tools 25 |
automotive/* 416 | obd 98 | scanner 102 | gm 136 | bmw 9 | xcp 43 | autosar 7 |
tls/tests_tls_netaccess 25
  RAW (all selected globs)                 = 5304
  minus remove_testfiles (windows+bpf, 30) = 5274
  actually executed at runtime             = 5248   (5274 − 26 excluded by kw_ko + optional-layer load effects)
```

**Pass/fail mechanism, and why the *process* exit code is `1`, not `321` (cited).** Each `.uts` file is its own campaign. `run_campaign()` [scapy/tools/UTscapy.py:L575] initializes `passed = failed = 0`, increments them per test, prints a line literally formatted `PASSED=%i FAILED=%i` [scapy/tools/UTscapy.py:L619,L622], and **returns the per-campaign `failed` count** [scapy/tools/UTscapy.py:L623]. `execute_campaign()` collapses that to a boolean `result` — it returns `output, (result == 0), test_campaign`, so the second element is `True` only when the campaign's failed-count was 0 [scapy/tools/UTscapy.py:L955]. `main()` then computes a **binary** aggregate exit status: it starts `glob_result = 0` [scapy/tools/UTscapy.py:L1146], and for each campaign does `if not result: glob_result = 1` (then `break` when `BREAKFAILED`) [scapy/tools/UTscapy.py:L1186-L1188], finally `return glob_result` [scapy/tools/UTscapy.py:L1237] which `sys.exit(main())` [scapy/tools/UTscapy.py:L1252] uses as the process status. Hence the shell sees `EXITCODE=1` (≥1 campaign failed) — **not** the 321 failed-test count. The `321` figure comes only from the **aggregation** step above (summing the per-campaign `FAILED=` lines), not from the exit code.
