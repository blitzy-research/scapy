## Section 1 — The question

You were building Ethernet frames with Scapy and saw some confusing behavior. Concretely,
you wanted to know what actually happens when you:

- **(P1)** build a normal stack — `Ether()/IP()/TCP()`;
- **(P2)** build a frame with a really short payload (like 10 bytes) — `Ether()/IP()/TCP()/Raw(b"A"*10)`;
- **(P3)** build a frame with a weird EtherType that Scapy doesn't recognize
  (you suggested `0x9000` or something random) — `Ether(type=0x9000)/Raw(b"hello")`.

…and then answer these behavioral questions:

- **(Q1)** Does Scapy **automatically pad** a short frame up to the minimum Ethernet frame
  size, or does it stay small?
- **(Q2)** When you serialize to bytes and re-parse with `Ether(raw(packet))`, does the
  padding **stick around or disappear**?
- **(Q3)** For the unknown EtherType, what does Scapy **show after the Ethernet layer** when
  printed — dump raw data, throw an error, or try to guess?
- **(Q4)** Across a sweep of payload sizes, at what **threshold** does Scapy stop adding
  padding?

…plus three code-investigation questions:

- **(Q5)** **Where** in the Ethernet layer code does Scapy decide to add padding?
- **(Q6)** **How** does Scapy determine which protocol comes next from the EtherType field?
- **(Q7)** What **logic** does Scapy apply when it hits a protocol number it doesn't recognize?

### Headline answer (read this first)

**For the ordinary frames the user asked about — `Ether()/IP()/TCP()` and `Ether()/Raw(...)` —
Scapy's generic `raw()` / `build()` path does *not* add minimum-Ethernet-frame padding.** Short
frames stay exactly `header + payload` bytes long. In the IEEE 802.3 standard the 64-byte
minimum frame (60 bytes before the FCS) is reached by a **PAD** that the MAC sublayer appends at
*transmit-encapsulation* time — conventionally in the NIC / driver / hardware — so a generic
in-memory `raw()` call has no reason to synthesize it. That is a statement about the **generic
serialization path exercised here**, not a claim that Scapy contains *no* min-frame padding
anywhere: Scapy's own Linux socket send path pads **as a fallback** after the kernel rejects an
undersized frame, and the contrib **EtherCAT** layer pads to 64 bytes in its *own* `post_build`.
Both are out of the `raw()` path used in this investigation and are pointed out explicitly under
Q1 and Q5 so the scoped conclusion is not over-read.

The padding you *do* sometimes see is the **`Padding` layer**, which is a completely different
thing: it models **genuine trailing bytes** that a length-bearing layer (like IP, which
declares its own total length) splits off during **dissection**. That `Padding` layer re-emits
its bytes on rebuild, so it *survives* `Ether(raw(packet))`. The heart of the confusion is the
**`Padding` vs `Raw`** distinction, explained in detail under Q2.

And a small surprise up front: your "weird" `0x9000` is literally Scapy's **own default**
`Ether.type` value — see Section 6.

## Section 4 — Behavioral answers (Q1–Q4)

### Q1 — Does Scapy auto-pad short frames? → **No.**

Serialization performs **no** minimum-Ethernet-frame padding. The evidence:

```python
>>> len(raw(Ether()/IP()/TCP()))              # P1
>>> len(raw(Ether()/IP()/TCP()/Raw(b"A"*10))) # P2
>>> for n in [0, 1, 5, 10, 20]:
...     len(raw(Ether()/Raw(b"A"*n)))          # bare frames
```

```
P1 len(raw)= 54
P2 len(raw)= 64
Q1 n=0 bare len=14 (14+n=14)
Q1 n=1 bare len=15 (14+n=15)
Q1 n=5 bare len=19 (14+n=19)
Q1 n=10 bare len=24 (14+n=24)
Q1 n=20 bare len=34 (14+n=34)
```

A bare `Ether()/Raw(b"A"*n)` is **always** exactly `14 + n` bytes — even `n=0` gives just the
14-byte header, and `n=20` gives 34, both well under the 60-byte minimum-frame floor. Scapy did
not pad any of them.

**Background — standards framing (external authority, not a runtime observation).** The
authoritative source is **IEEE Std 802.3** (the Ethernet standard). Its MAC frame definition
sets `minFrameSize` to 512 bits = **64 octets** *including* the 4-byte FCS, which leaves a
**46-octet** minimum data field for an untagged Ethernet II frame (60 octets on the wire before
the FCS). When the MAC client data is shorter, the standard's transmit procedure appends a
**PAD** field to reach that floor: the MAC sublayer's `TransmitDataEncap` calls `ComputePad`
(then computes the FCS) — i.e. the padding is generated at **transmit-encapsulation** time, and
in practice by the NIC / driver / MAC hardware. (Accessible summary: the "Ethernet frame"
article on Wikipedia; normative text: IEEE Std 802.3, MAC frame structure / PAD field.) *This
paragraph is background, cross-checked against the standard — it is not something the runtime
probe measured.*

How that maps onto Scapy — three distinct behaviors, only the first of which was exercised
above:

- **(a) Generic in-memory serialization (`raw()` / `build()`) — no min-frame padding.** This is
  what the runtime evidence above shows for `Ether/IP/TCP` and `Ether/Raw`: `raw()` returns
  exactly the bytes you built. The reason is in the base build machinery (Q5): nothing on that
  path knows about a 60-byte floor.
- **(b) Scapy's platform send path — pads as a fallback.** When you actually *transmit*, Scapy's
  Linux L2/L3 sockets will pad an undersized frame to `conf.min_pkt_size` (default `60`,
  `scapy/config.py:778`) — but only **reactively**, after the kernel rejects the short frame with
  `EINVAL` (`L2Socket.send` @ `scapy/arch/linux.py:565-576`; `L3PacketSocket.send` @
  `scapy/arch/linux.py:598-624`). That is the send path, not `raw()`.
- **(c) Protocol-specific build padding — exists for some contrib layers.** The EtherCAT layer
  computes and appends its own zero-PAD to a 64-byte minimum inside `post_build`
  (`scapy/contrib/ethercat.py:549-607`, using the constants at `scapy/contrib/ethercat.py:515-518`)
  — i.e. min-frame padding *does* happen at serialization time, but only for that specific layer,
  never on the generic `Ether/IP/TCP` path here.

So the observed "short frames stay small" result is correct **for the generic `raw()` path**;
it is not a claim that Scapy performs no min-frame padding anywhere.

### Q2 — Does padding stick around through `Ether(raw(packet))`? → **It depends on what "padding" means — and this is the core of the confusion.**

There are two very different things people call "padding" here, and Scapy models them with two
different layers: **`Raw`** and **`Padding`**.

**(a) Round-tripping P2 — the 10 "A" bytes are TCP *payload* (`Raw`), not padding.**

**The distinction, stated plainly:**

- **`Raw`** = generic leftover / payload bytes when Scapy has no more-specific class for them
  (in case (a), the bytes beyond TCP's header that TCP itself doesn't further structure).
- **`Padding`** = trailing bytes *separated out by a length-bearing layer's `extract_padding`*
  during dissection (in case (b), IP declares its total length, so anything past the IP
  datagram is not IP/TCP payload — it's trailing padding). The `Padding` layer **re-emits its
  bytes on build**, which is precisely why it survives `Ether(raw(packet))`.

So: **there was never any minimum-frame padding for P2 to persist** (answer to the literal
question), whereas **real trailing bytes are modeled as a persistent `Padding` layer**. The
code reasons for both are in Q5.

### Q3 — What does Scapy show after the Ethernet layer for an unknown EtherType? → **As `Raw`.**

### Q5 — Where does Scapy decide to add padding?

**In Scapy's generic build path — the one `raw()` uses for `Ether/IP/TCP` and `Ether/Raw` — there
is no minimum-frame padding step** (per-layer/protocol exceptions are noted at the end of this
section). The serialization chain is
`Packet.build` (`scapy/packet.py:746`) → `Packet.do_build` (`scapy/packet.py:724`, which calls
`self_build` @ `scapy/packet.py:678`, `do_build_payload` @ `scapy/packet.py:715`, and
`post_build` @ `scapy/packet.py:758`) → then `build_padding`.

The base `Packet.build_padding` (`scapy/packet.py:742`) does nothing but recurse into the
payload:

```python
# scapy/packet.py:742  (Packet.build_padding)
def build_padding(self):
    # type: () -> bytes
    return self.payload.build_padding()
```

The recursion bottoms out at `NoPayload.build_padding` (`scapy/packet.py:1770`), which returns
`b""`. So **no bytes are ever synthesized to reach a minimum size** — nothing in `build()`
knows or cares about a 60-byte floor.

Correspondingly, the base `Packet.extract_padding` (`scapy/packet.py:982`) treats nothing as
padding by default:

```python
# scapy/packet.py:982  (Packet.extract_padding)
def extract_padding(self, s):
    # type: (bytes) -> Tuple[bytes, Optional[bytes]]
    ...
    return s, None
```

`Padding` is therefore a **layer**, not a build step. It is defined as
`class Padding(Raw)` (`scapy/packet.py:1906`) and wired up as
`conf.padding_layer = Padding` (`scapy/packet.py:1922`) alongside
`conf.raw_layer = Raw` (`scapy/packet.py:1921`). It gets attached during **dissection** in
`Packet.dissect` (`scapy/packet.py:1049`):

```python
# scapy/packet.py:1049  (Packet.dissect)
def dissect(self, s):
    ...
    payl, pad = self.extract_padding(s)
    self.do_dissect_payload(payl)
    if pad and conf.padding:
        self.add_payload(conf.padding_layer(pad))   # scapy/packet.py:1060
```

Only **length-bearing** layers override `extract_padding` to hand back a non-empty remainder —
for example `Dot3.extract_padding` (`scapy/layers/l2.py:281`):

```python
# scapy/layers/l2.py:281  (Dot3.extract_padding)
def extract_padding(self, s):
    # type: (bytes) -> Tuple[bytes, bytes]
    tmp_len = self.len
    return s[:tmp_len], s[tmp_len:]
```

(Other examples: `Dot1Q.extract_padding` @ `scapy/layers/l2.py:394`, `ARP.extract_padding` @
`scapy/layers/l2.py:539`.) In the Q2 case the equivalent split is driven by **IP's declared
length** — `IP.extract_padding` @ `scapy/layers/inet.py:553`: bytes past the IP datagram
become the `Padding` remainder.

Finally, this ties directly back to Q2's "survives re-serialization": `Padding.self_build`
returns `b""` (`scapy/packet.py:1909`), so a `Padding` layer emits nothing during the normal
`do_build`, **but** `Padding.build_padding` (`scapy/packet.py:1913`) re-emits its `load`:

```python
# scapy/packet.py:1913  (Padding.build_padding)
def build_padding(self):
    # type: () -> bytes
    return (
        bytes_encode(self.load) if self.raw_packet_cache is None
        else self.raw_packet_cache
    ) + self.payload.build_padding()
```

That override is exactly why a dissected `Padding` layer's bytes reappear when you serialize
again — and why the trailing-bytes frame in Q2(b) came back at length 60.

**Where min-frame padding *does* live in Scapy (outside the generic `raw()` path).** So the
answer is not "nowhere" — it is "not on the generic build path exercised here." Two other places
add min-frame padding, and both are worth naming so the scope is exact:

- **The send path, as an `EINVAL` fallback.** When you actually transmit, `L2Socket.send`
  (`scapy/arch/linux.py:565-576`) and `L3PacketSocket.send`
  (`scapy/arch/linux.py:598-624`) catch the kernel's `errno == 22` (`EINVAL`) on an undersized
  frame and *then* append `b"\x00" * (conf.min_pkt_size - len)` (with `conf.min_pkt_size = 60`,
  `scapy/config.py:778`) before retrying. This is reactive, at send time, and never runs during
  `raw()`.
- **Protocol-specific build padding (EtherCAT).** `EtherCat.post_build`
  (`scapy/contrib/ethercat.py:549-607`) computes `pad_len` against a 64-byte minimum (constants at
  `scapy/contrib/ethercat.py:515-518`) and, when positive, appends `b'\x00' * pad_len` as a
  `Padding()` during **build**. So a specific layer *does* pad at serialization time — but only
  that layer, not the `Ether/IP/TCP` or `Ether/Raw` stacks measured for Q1/Q4.

Neither exception changes the Q1/Q4 result; they are called out so the "no min-frame padding"
statement is read as scoped to the generic serialization path, not as universal.

### Q6 — How does Scapy pick the next protocol from the EtherType?

**Two steps: an Ethernet-II-vs-802.3 disambiguation, then a field-value match against
registered bindings.**

First, `Ether.dispatch_hook` (`scapy/layers/l2.py:266`) decides whether the frame is Ethernet
II or IEEE 802.3 by comparing bytes 12:14 against 1500:

```python
# scapy/layers/l2.py:266  (Ether.dispatch_hook)
@classmethod
def dispatch_hook(cls, _pkt=None, *args, **kargs):
    if _pkt and len(_pkt) >= 14:
        if struct.unpack("!H", _pkt[12:14])[0] <= 1500:   # scapy/layers/l2.py:270
            return Dot3
    return cls
```

If the 2-byte value is `<= 1500` it is a length (802.3, dissected as `Dot3`); otherwise it is an
EtherType and the class stays `Ether` (Ethernet II). `0x9000` = 36864 is `> 1500`, so P3 stays
`Ether`.

Then the payload class is chosen by `Packet.guess_payload_class` (`scapy/packet.py:1062`), which
walks the registered bindings and returns the first class whose bound field-values all match:

```python
# scapy/packet.py:1062  (Packet.guess_payload_class)
def guess_payload_class(self, payload):
    ...
    for t in self.aliastypes:
        for fval, cls in t.payload_guess:
            try:
                if all(v == self.getfieldval(k)
                       for k, v in fval.items()):
                    return cls  # type: ignore
            except AttributeError:
                pass
    return self.default_payload_class(payload)
```

The `payload_guess` list is populated by `bind_layers(...)`. The two entries relevant to
EtherType are:

- `bind_layers(Ether, IP, type=2048)` — `scapy/layers/inet.py:1101` ⇒ `type=2048` (`0x0800`) → `IP`
- `bind_layers(Ether, IPv6, type=0x86dd)` — `scapy/layers/inet6.py:4083` ⇒ `type=0x86dd` → `IPv6`

So the actual dispatch is driven by matching the `type` field against `payload_guess`.

**A clarifying note about the name table.** The human-readable EtherType *names* live in a
separate table, `ETHER_TYPES`, built by `load_ethertypes` (`scapy/data.py:355`) from the bundled
`scapy.libs.ethertypes` data (`scapy/data.py:526`) or `/etc/ethertypes` (`scapy/data.py:530`),
exposed lazily as `conf.ethertypes` (`scapy/config.py:921`), and accessed as an integer-keyed
`DADict` (documented at `scapy/dadict.py:63` as `ETHER_TYPES[2048] -> IPv4`). This table is
**purely cosmetic** — it decides whether `.show()`/`repr()` prints a *name* (`IPv4`) or the raw
hex (`0x9000`). It does **not** drive dispatch; the next-layer decision is `payload_guess`. That
is why an EtherType can dispatch fine while still printing as hex, and vice-versa.

### Q7 — What does Scapy do with an unrecognized protocol number?

**By default it neither errors nor guesses — it dumps the residual bytes as `Raw`.**

When **no binding matches**, `guess_payload_class` falls through to
`self.default_payload_class(...)` (`scapy/packet.py:1081`), whose entire job is to return the
configured raw layer:

```python
# scapy/packet.py:1081  (Packet.default_payload_class)
def default_payload_class(self, payload):
    ...
    return conf.raw_layer     # scapy/packet.py:1090   (conf.raw_layer is Raw)
```

This is exactly the path P3/Q3 takes: no `bind_layers(Ether, ..., type=0x9000)` exists anywhere
in the tree (verified by search), so nothing matches `type=0x9000`, and the payload becomes
`conf.raw_layer` = `Raw`. No exception is involved on this path.

There is a **second, separate** fallback for when a *chosen* class raises while parsing — in
`Packet.do_dissect_payload` (`scapy/packet.py:1023`):

```python
# scapy/packet.py:1023  (Packet.do_dissect_payload)
if s:
    cls = self.guess_payload_class(s)
    try:
        p = cls(s, _internal=1, _underlayer=self)
    except KeyboardInterrupt:
        raise
    except Exception:
        if conf.debug_dissector:
            ...
            if cls is not None:
                raise
        p = conf.raw_layer(s, _internal=1, _underlayer=self)   # scapy/packet.py:1046
    self.add_payload(p)
```

This fallback is gated by `conf.debug_dissector`, whose **default is `False`**
(`scapy/config.py:817`; the comment on the previous line reads "raise exception when a packet
dissector raises an exception"):

- **default (`False`)** ⇒ a parsing exception is swallowed and the bytes fall back to `Raw`
  *silently*;
- **any truthy value** ⇒ it logs the failure and, for a non-`None` class, **re-raises** the
  exception.

*(Precise wording: it is "default `False` → silent `Raw`; truthy → raises" — not a specific
integer. Any truthy value triggers the re-raise for a non-`None` class.)* Separately,
`conf.padding` (default `1`, `scapy/config.py:787`) is the flag consulted in `dissect` (Q5)
that controls whether a trailing `Padding` layer is attached at all.

**Bottom line:** for an unknown EtherType like `0x9000`, Scapy's default behavior is to place
the leftover bytes into a `Raw` layer — it does not raise, and it does not try to guess a more
specific protocol.
