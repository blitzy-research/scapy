### (b) The version string

The version displayed is the literal `2026.07.01`:

```text

```

`conf.version` is a read‑only attribute wired to the package `VERSION` — `version = ReadOnlyAttribute("version", VERSION)` [`scapy/config.py:726`].

### (c) Where the version comes from

`2026.07.01` is **not** a released git tag; it is produced by the **modification‑time fallback** inside `_version()` [`scapy/__init__.py:122`], because this checkout has no tags and no `VERSION` file. `_version()` tries, in order:

1. Environment override `SCAPY_VERSION` — `return os.environ['SCAPY_VERSION']` [`scapy/__init__.py:131`] (not set here).
2. A bundled `VERSION` file — `version_file = os.path.join(_SCAPY_PKG_DIR, 'VERSION')` [`scapy/__init__.py:136`], returning `return tag` [`scapy/__init__.py:141`] — **absent here** (`ls scapy/VERSION` → *No such file or directory*).
3. A git‑archive substituted tag — `return _version_from_git_archive()` [`scapy/__init__.py:147`] (defined at [`scapy/__init__.py:38`]).
4. `git describe --tags` — `return _version_from_git_describe()` [`scapy/__init__.py:153`] (defined at [`scapy/__init__.py:72`]) — **fails, because there are 0 tags** (`git tag | wc -l` → `0`).
5. **mtime fallback (the branch taken):** `d = datetime.datetime.utcfromtimestamp(os.path.getmtime(__file__))` [`scapy/__init__.py:160`] then `return d.strftime('%Y.%m.%d')` [`scapy/__init__.py:161`] — this formats the modification date of `scapy/__init__.py` as `%Y.%m.%d`, yielding `2026.07.01`.
6. Last resort `return '0.0.0'` [`scapy/__init__.py:166`] (not reached).

The result is assigned once at import time: `VERSION = __version__ = _version()` [`scapy/__init__.py:169`]. In short, **because there are no tags and no `VERSION` file, the date‑shaped version is the file modification date of `scapy/__init__.py`.**

## Q2 — "How many protocol layers are actually available in the environment — not just files in the source tree, but what's actually loaded and ready to use?"

This asks for **(a)** the count of layers **loaded and ready to use** at runtime, and **(b)** an explicit distinction from the number of layer **files** present in the tree.

### (a) Runtime loaded count = 49

The number of protocol‑layer groups actually loaded and ready to use in this default session is **49**, measured as `len(conf.load_layers)`:

```text
PROBE_NUM_LOAD_LAYERS= 49
```

That 49 is a **base list of 48 entries plus one platform‑conditional addition on this Linux system**:

- The static list is defined at `load_layers = [` [`scapy/config.py:848`] and contains **48** entries (from `'bluetooth'` through `'zigbee'`).
- On Linux (or BSD), one more layer is appended at import time: the guard `if LINUX or BSD:` [`scapy/arch/__init__.py:148`] runs `conf.load_layers.append("tuntap")` [`scapy/arch/__init__.py:149`]. That `tuntap` entry is confirmed present at runtime:

```text
PROBE_HAS_TUNTAP= True
```

So **48 base + `tuntap` = 49** on this Linux host. The append is guarded by platform, so on Windows the count would be **48** (the `if LINUX or BSD:` guard is false there). The platform flags themselves are decided in `scapy/consts.py`: `LINUX = platform.startswith("linux")` [`scapy/consts.py:13`], `BSD = DARWIN or FREEBSD or OPENBSD or NETBSD` [`scapy/consts.py:21`].

### (b) Loaded ("ready to use") vs. files present in the tree

This is the crux of the question. The `scapy/layers/` directory contains more Python files than there are loaded layer groups:

```text
# ls scapy/layers/*.py | wc -l
57
# (excluding __init__.py)
56
```

So there are **56 protocol‑module source files** on disk (57 counting `__init__.py`), but only **49 layer groups are actually loaded and ready to use** in the default session. The gap exists because `conf.load_layers` is a curated default set, not "every file in the folder": some modules on disk are not in the default list, while the loaded set additionally contains the runtime‑appended `tuntap`. In short — **files present ≠ layers loaded**: `56` files vs `49` loaded.

## Q3 — Default configuration: verbosity value, its meaning, and the socket implementation

### Q3a — "What's the verbosity level set to at startup?"

The startup verbosity is **2**:

```text
PROBE_VERB= 2
```

This matches the class default `verb = 2` [`scapy/config.py:759`].

### Q3b — "What does that number actually mean for output behavior?"

The value is documented inline on the same line, verbatim:

```text
verb = 2  #: level of verbosity, from 0 (almost mute) to 3 (verbose)
```

— i.e. the scale runs `0` (almost mute) to `3` (verbose) [`scapy/config.py:759`]. Operationally, `conf.verb` seeds a local `verbose` variable in the send/receive machinery and then gates output at graduated thresholds:

- It seeds the default: `verbose = conf.verb` [`scapy/sendrecv.py:133`], and likewise at [`scapy/sendrecv.py:355`] and [`scapy/sendrecv.py:730`].
- Any output at all requires a truthy value (`>= 1`): `if verbose:` [`scapy/sendrecv.py:216`], [`scapy/sendrecv.py:379`], [`scapy/sendrecv.py:391`].
- A compact single‑line progress path is used specifically at level 1: `if verbose == 1:` [`scapy/sendrecv.py:766`].
- Richer per‑result detail requires more than 1: `if verbose > 1:` [`scapy/sendrecv.py:745`].
- The most detailed debugging output requires more than 2: `elif conf.verb > 2:` [`scapy/sendrecv.py:552`].
- Related gates elsewhere: the answering machine defaults its own verbosity from `conf.verb` — `self.verbose = kargs.get("verbose", conf.verb >= 0)` [`scapy/ansmachine.py:82`] — and packet‑list rendering checks `if conf.verb >= 2:` [`scapy/plist.py:608`].

**Meaning at the default of 2:** because `2` is `>= 1` and `> 1` but not `> 2`, send/receive summaries and per‑result/result‑table detail **are** shown, while the most verbose level‑3 debugging output is **withheld**. Level 0 would make it almost mute; level 3 would add the extra debugging detail. This matches Scapy's official configuration documentation, which describes `verb = 2` as the level of verbosity "from 0 (almost mute) to 3 (verbose)."

### Q3c — "What networking socket implementation does it use on this system?"

On this Linux system the bound socket classes are **`L3PacketSocket`** (layer 3), **`L2Socket`** (layer 2 send/receive), and **`L2ListenSocket`** (layer 2 listen), all Linux **PF_PACKET** sockets. Verbatim:

```text
PROBE_L3SOCKET= <L3PacketSocket: read/write packets at layer 3 using Linux PF_PACKET sockets> NAME= L3PacketSocket
PROBE_L2SOCKET= <L2Socket: read/write packets at layer 2 using Linux PF_PACKET sockets> NAME= L2Socket
PROBE_L2LISTEN_NAME= L2ListenSocket
```

- These classes are implemented in `scapy/arch/linux.py`: `class L3PacketSocket(L2Socket):` [`scapy/arch/linux.py:587`], `class L2Socket(SuperSocket):` [`scapy/arch/linux.py:475`], and `class L2ListenSocket(L2Socket):` [`scapy/arch/linux.py:579`].
- `conf.L3socket`, `conf.L2socket`, and `conf.L2listen` are declared as plain attributes initialized to `None` on the config class — `L3socket = None` [`scapy/config.py:772`], `L2socket = None` [`scapy/config.py:774`], `L2listen = None` [`scapy/config.py:775`] — and are then **populated at import time** by `def _set_conf_sockets():` [`scapy/config.py:606`].
- The Linux branch of that function is what binds the observed classes: `if LINUX:` [`scapy/config.py:645`] imports them (`from scapy.arch.linux import L3PacketSocket, L2Socket, L2ListenSocket` [`scapy/config.py:646`]) and assigns `conf.L3socket = L3PacketSocket` [`scapy/config.py:647`], `conf.L2socket = L2Socket` [`scapy/config.py:655`], and `conf.L2listen = L2ListenSocket` [`scapy/config.py:656`].
- `_set_conf_sockets()` is invoked during architecture import — `_set_conf_sockets()` [`scapy/arch/__init__.py:151`] — after `from scapy.config import conf, _set_conf_sockets` [`scapy/arch/__init__.py:14`].

These values are specific to **this Linux host**. On Windows a different branch runs — `if WINDOWS:` [`scapy/config.py:659`] binds `conf.L3socket = L3WinSocket` and `conf.L2socket = _NotAvailableSocket` — so the socket implementation is genuinely platform‑dependent.

## Q4 — "When you construct a basic ICMP ping packet, what's the actual structure of that packet object? … single composite object or something else — what layer types are involved, and how are they related?"

The canonical basic ICMP ping packet is constructed with `IP()/ICMP()`. This decomposes into **(a)** the concrete type, **(b)** whether it is a single object or a collection, **(c)** the layer types involved, and **(d)** how they relate.

### (a) & (b) It is a single composite `Packet` object — not a list/collection

`IP()/ICMP()` yields **one** object whose concrete type is `scapy.layers.inet.IP`, and it **is** a `Packet` (not a list or tuple):

```text
PROBE_PKT_TYPE= <class 'scapy.layers.inet.IP'>
PROBE_PKT_IS_PACKET= True
PROBE_PKT_IS_LIST= False
```

So Scapy does **not** create a container of two separate objects; it creates a single composite `Packet` whose outermost type is `IP`. (`PROBE_PKT_IS_PACKET= True` confirms it is a `Packet`; `PROBE_PKT_IS_LIST= False` confirms it is neither a `list` nor a `tuple`.)

### (c) The layer types involved are `IP` and `ICMP`

Enumerating the stacked layers yields exactly two layer classes, `IP` then `ICMP`:

```text
PROBE_PKT_LAYERS= ['IP', 'ICMP']
```

The human‑readable summary and the reconstructive command corroborate the two‑layer composition:

```text
PROBE_PKT_SUMMARY= IP / ICMP 127.0.0.1 > 127.0.0.1 echo-request 0
PROBE_PKT_COMMAND= IP()/ICMP()
```

The two layer classes are defined in `scapy/layers/inet.py`: `class IP(Packet, IPTools):` [`scapy/layers/inet.py:521`] and `class ICMP(Packet):` [`scapy/layers/inet.py:952`]. Both are subclasses of `Packet`.

### (d) How they relate — a bidirectional payload/underlayer chain

The two layers are linked in **both** directions. The top layer is `IP`, and its `.payload` is the `ICMP` layer:

```text
PROBE_TOP_TYPE= IP PAYLOAD_TYPE= ICMP
```

Conversely, the `ICMP` layer's `.underlayer` points back up to the `IP` layer:

```text
PROBE_PAYLOAD_UNDERLAYER= IP
```

**The mechanism** behind this composition is the `/` operator on the `Packet` base class:

- `/` is implemented as `def __div__(self, other):` [`scapy/packet.py:596`], aliased for Python 3 as `__truediv__ = __div__` [`scapy/packet.py:607`].
- It clones both operands and stacks them: `cloneA = self.copy()` [`scapy/packet.py:599`], `cloneB = other.copy()` [`scapy/packet.py:600`], then `cloneA.add_payload(cloneB)` [`scapy/packet.py:601`].
- `add_payload()` [`scapy/packet.py:360`] establishes the **downward** link `self.payload = payload` [`scapy/packet.py:368`] and immediately the **upward** link via `payload.add_underlayer(self)` [`scapy/packet.py:369`].
- `add_underlayer()` [`scapy/packet.py:385`] sets `self.underlayer = underlayer` [`scapy/packet.py:387`], completing the bidirectional chain.

This is why `IP()/ICMP()` is a single `IP` object that carries `ICMP` as its payload, and the `ICMP` payload knows its underlayer is `IP`. This matches Scapy's official documentation, which describes `/` as a composition operator between two layers where the lower layer's default fields may be overloaded by the upper layer.

## Q5 — "What theme is active in a default session, and what's it called in the code?"

The active theme in a default interactive session is **`DefaultTheme`**. There is an important nuance worth stating explicitly to avoid a common trap: the **static config default is `NoTheme`**, but the interactive console **overrides** it to `DefaultTheme`.

**Active theme in the default interactive session — `DefaultTheme`:**

```text
PROBE_COLOR_THEME_CLASS= DefaultTheme
PROBE_COLOR_THEME_REPR= <DefaultTheme>
PROBE_INTERACTIVE= True
```

- The static class default (before `interact()` runs) is `NoTheme()`: `color_theme = Interceptor("color_theme", NoTheme(), _prompt_changer)` [`scapy/config.py:818`].
- A default interactive session runs `interact()`, which flips interactive mode on and installs the theme: `conf.interactive = True` [`scapy/main.py:513`] and `conf.color_theme = DefaultTheme()` [`scapy/main.py:514`]. The observed `PROBE_INTERACTIVE= True` confirms `interact()` executed, and `PROBE_COLOR_THEME_CLASS= DefaultTheme` confirms the override took effect.

**What it's called in the code — `DefaultTheme`:** the class is defined as `class DefaultTheme(AnsiColorTheme):` [`scapy/themes.py:167`]. Its ancestry is `AnsiColorTheme` — `class AnsiColorTheme(ColorTheme):` [`scapy/themes.py:121`] — which in turn extends the base `class ColorTheme:` [`scapy/themes.py:94`]. The static‑default `NoTheme` is a sibling: `class NoTheme(ColorTheme):` [`scapy/themes.py:117`].

**Platform contrast:** on Windows, the interactive theme is instead `BlackAndWhite()` [`scapy/main.py:582`], whose class is `class BlackAndWhite(AnsiColorTheme, NoTheme):` [`scapy/themes.py:163`]. On this Linux host the active theme is `DefaultTheme`, as observed.
