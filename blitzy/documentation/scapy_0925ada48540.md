# How Scapy Computes & Caches Packet Fields (Checksums and Lengths) on `build()`

## Overview

A common source of confusion when working with Scapy is *when* derived packet fields — most notably the **IP header checksum**, the **TCP checksum**, and the **IP total-length (`len`)** — get **recomputed** versus when Scapy hands back **previously cached bytes**. This document answers that question across six concrete IP/TCP scenarios.

Every behavioral claim here is grounded in the **Scapy source code (the source of truth)** with exact `file:line` citations, and is **corroborated by real runtime output** captured by building and running the library against the working tree (no values are assumed). For each scenario you get four parts: **(a)** the question restated, **(b)** the governing code path with citations, **(c)** the captured runtime evidence (full hex/numeric blocks), and **(d)** the reasoning that ties the code to the observed result.

The short version, proven below: a layer's `post_build` writes a derived field **only when that field is `None`**, and the serialization cache (`raw_packet_cache`) that can short-circuit `post_build` is populated **only by dissection** — so a packet you *construct* (e.g. `IP()/TCP()/Raw()`) always recomputes on every `bytes()`.

## Shared setup

- **Packet recipe (used by every scenario):**
  ```python
  IP(src="192.0.2.2", dst="192.0.2.1") / TCP() / Raw(load=...)
  ```
- **Read-back idiom (re-dissection).** Building does **not** write computed values back into a *constructed* packet's Python fields. This was verified directly: after `bytes(p)`, the Python attributes `p.chksum`, `p.len`, and `p[TCP].chksum` are all still `None`. The computed values exist **only in the emitted bytes**. We therefore read them back by **re-dissecting** the produced bytes with `IP(bytes(p))` — the canonical Scapy idiom — and reading `IP.chksum`, `TCP.chksum`, and `IP.len` off the dissected packet.
- **Field byte offsets in the full IP buffer** (stated so byte-position comparisons are precise):
  - `IP.len`   -> bytes `[2:4]`
  - `IP.chksum` -> bytes `[10:12]`
  - the TCP segment starts at byte `20`, so `TCP.chksum` -> bytes `[36:38]`
- **Environment (for reproducibility).** Scapy `2026.06.26`, CPython `3.12.3`, branch `scapy_0925ada48540` @ `0925ada485406684174d6f068dbd85c4154657b3`. The machinery under study is pure Python and the project's `requires-python` is `>=3.7, <4`; the behavior is invariant across that range, so the captured values are representative of every supported interpreter (they were reproduced byte-for-byte on the interpreter above).

## Two governing rules (these explain all six answers)

Everything below reduces to two rules. Read these first; each scenario is then just an application of them.

### Governing Rule 1 — "Compute-only-when-`None`"

> A protocol layer's `post_build` writes a derived field (checksum/length) **only when that field is `None`**. An explicitly supplied value is **always preserved**.

The `IP` field defaults are `None`, which is what *opts the field in* to automatic computation:

- `class IP(Packet, IPTools)` is defined at `scapy/layers/inet.py:521`.
- `ShortField("len", None)` — `scapy/layers/inet.py:527`
- `XShortField("chksum", None)` — `scapy/layers/inet.py:533`

`IP.post_build` (`scapy/layers/inet.py:539-551`) computes those fields **only under an `is None` guard**:

```python
# scapy/layers/inet.py:539-551 (IP.post_build), key branches:
if self.len is None:                                   # :545
    tmp_len = len(p) + len(pay)                         # :546
    p = p[:2] + struct.pack("!H", tmp_len) + p[4:]      # :547
if self.chksum is None:                                # :548
    ck = checksum(p)                                    # :549
    p = p[:10] + chb(ck >> 8) + chb(ck & 0xff) + p[12:] # :550
return p + pay                                          # :551
```

`TCP.post_build` (`scapy/layers/inet.py:767-786`) follows the same pattern for its checksum (TCP `class` at `scapy/layers/inet.py:753`; its `XShortField("chksum", None)` default at `scapy/layers/inet.py:763`):

```python
# scapy/layers/inet.py:767-786 (TCP.post_build), key branch:
if self.chksum is None:                                       # :775
    if isinstance(self.underlayer, IP):                       # :776
        ck = in4_chksum(socket.IPPROTO_TCP, self.underlayer, p)  # :777
        p = p[:16] + struct.pack("!H", ck) + p[18:]           # :778
    ...
return p                                                       # :786
```

**Takeaway:** because both writes are guarded by `is None`, any value you set explicitly (e.g. `chksum=0xAAAA`) is **not** recomputed — it is emitted verbatim. This single rule answers Scenarios 1, 3, 4, and 6.

### Governing Rule 2 — "Dissection-only, per-layer caching that short-circuits `post_build`"

> `raw_packet_cache` is populated **only by dissection**, tracked **per layer**, and **invalidated** whenever you assign or delete a field. When valid, it makes `do_build` emit cached header bytes verbatim, **bypassing** `post_build`.

- **Initialized to `None`** in the constructor: `self.raw_packet_cache = None` (`scapy/packet.py:169`) and `self.raw_packet_cache_fields = None` (`scapy/packet.py:170`).
- **Populated ONLY in `do_dissect`** (`scapy/packet.py:1002-1020`): the per-layer header slice is stored with `self.raw_packet_cache = _raw[:-len(s)] if s else _raw` (`scapy/packet.py:1019`) and `self.explicit = 1` (`scapy/packet.py:1020`); the mutable/list/packet fields that must be watched are recorded into `raw_packet_cache_fields` (`scapy/packet.py:1005,1015-1017`). A packet **built from fields** (e.g. `IP()/TCP()/Raw()`) **never** runs this path, so its cache stays `None`.
- **The short-circuit lives in `do_build`** (`scapy/packet.py:724-740`):
  ```python
  # scapy/packet.py:737-740
  if self.raw_packet_cache is None:
      return self.post_build(pkt, pay)   # no cache -> (re)compute derived fields
  else:
      return pkt + pay                   # valid cache -> emit cached bytes verbatim
  ```
- **Per-layer re-validation in `self_build`** (`scapy/packet.py:678-713`): before trusting a cache, each tracked field is compared against its cached snapshot; on any mismatch the layer's cache is dropped, otherwise the cached header bytes are returned directly (`scapy/packet.py:685-695`, with `return self.raw_packet_cache` at `:694-695`).
- **Invalidation on mutation.** Assigning a field clears that layer's cache — `self.raw_packet_cache = None` inside `setfieldval` (`scapy/packet.py:485-487`); attribute writes route there via `__setattr__` (`scapy/packet.py:494-502`). Deleting a field clears it in `delfieldval` (`scapy/packet.py:509-511`).
- **Context.** The public entry point is `build` (`scapy/packet.py:746-756`); the base-class `post_build` is just `return pkt + pay` (`scapy/packet.py:758-767`), which is what layers like `IP`/`TCP` override.

**Takeaway:** for a packet you *constructed*, there is no cache, so `do_build` always re-enters `post_build` and recomputes. The cache only matters for *dissected* packets, and because it is per-layer it can let a stale parent header survive when only a deep child field changes (Scenario 2's documented nuance).

### Checksum primitives

`checksum()` (`scapy/utils.py:496-504`) is the standard 16-bit one's-complement Internet checksum:

```python
# scapy/utils.py:496-504
def checksum(pkt):
    if len(pkt) % 2 == 1:        # :498  pad odd length
        pkt += b"\0"             # :499
    s = sum(array.array("H", pkt))         # :500  sum 16-bit words
    s = (s >> 16) + (s & 0xffff)           # :501  fold carries
    s += s >> 16                           # :502  fold again
    s = ~s                                 # :503  one's complement
    return checksum_endian_transform(s) & 0xffff   # :504  endian-transform + mask
```

Step by step: it pads an odd-length buffer with `b"\0"` (`scapy/utils.py:498-499`), sums the 16-bit words via `array.array("H", pkt)` (`scapy/utils.py:500`), folds the carries twice (`scapy/utils.py:501-502`), takes the one's complement `~s` (`scapy/utils.py:503`), and finally endian-transforms and masks with `& 0xffff` (`scapy/utils.py:504`).

The **IP header checksum** is computed over the 20-byte IP header only. The **TCP checksum** additionally covers an **IPv4 pseudo-header** (RFC 793) via `in4_chksum` (`scapy/layers/inet.py:692`), invoked from `TCP.post_build` at `scapy/layers/inet.py:776-778`. This is *why* the TCP checksum depends on the **payload** and on **src/dst**, while the IP header checksum does not — a fact that shows up directly in Scenario 2.

## The six scenarios

### Scenario 1 — Compute-on-build

**(a) Question.** Construct a basic `IP/TCP/Raw(load=b"hello")` packet with **no** checksum fields set, call `bytes()`, and report the hex values Scapy computes for **both** the IP header checksum and the TCP checksum.

**(b) Governing code path.** Both `chksum` fields default to `None` (`scapy/layers/inet.py:533` for IP, `:763` for TCP). The packet is *constructed*, so its `raw_packet_cache` is `None` and `do_build` enters `post_build` (`scapy/packet.py:737-738`). `IP.post_build` then computes the length and checksum because both are `None` (`scapy/layers/inet.py:545-550`), and `TCP.post_build` computes its checksum via the pseudo-header because it too is `None` (`scapy/layers/inet.py:775-778`).

**(c) Runtime evidence.** Values read back via `IP(bytes(p))`:

```text
IP.chksum  = 0xf6c6
TCP.chksum = 0xc7a3
IP.len     = 45
total bytes = 45

Full 45-byte buffer:
4500002d000100004006f6c6c0000202c000020100140050000000000000000050022000c7a3000068656c6c6f
```

The constructed Python object keeps its fields `None` even after building (verified):

```text
p.len is None         -> True
p.chksum is None      -> True
p[TCP].chksum is None -> True
```

**(d) Reasoning.** The derived fields are computed *at serialization time* by the per-layer `post_build` hooks precisely because they were left `None` (Governing Rule 1). Note that building does not write those computed values back onto the Python object — they live only in the emitted bytes — which is exactly why we re-dissect with `IP(bytes(p))` to read them. In the buffer you can see `f6c6` at offset `[10:12]` (the IP checksum) and `c7a3` at offset `[36:38]` (the TCP checksum), with the ASCII payload `68656c6c6f` = `"hello"` at the tail.

### Scenario 2 — Recompute vs. cache on mutation

**(a) Question.** Tweak one byte of the payload, call `bytes()` again, and determine whether Scapy returns freshly recomputed checksums or hands back previously cached bytes. Show the full before/after wire hex (complete buffers, not diffs) so byte positions can be compared.

**(b) Governing code path.** A *constructed* packet has `raw_packet_cache is None` at **every** layer (verified: IP, TCP, and Raw all report `True`), so each `bytes()` re-enters `post_build` and recomputes (`scapy/packet.py:737-740`). Independently, mutating the payload via `p[Raw].load = ...` routes through `__setattr__` -> `setfieldval`, which would clear any cache anyway (`scapy/packet.py:494-502,485-487`). Either way, there is nothing cached to hand back.

**(c) Runtime evidence.** Flip `b"hello"` -> `b"Hello"` (i.e. byte `0x68` -> `0x48`). Full before/after buffers (**not** diffs):

```text
BEFORE: 4500002d000100004006f6c6c0000202c000020100140050000000000000000050022000c7a3000068656c6c6f
AFTER:  4500002d000100004006f6c6c0000202c000020100140050000000000000000050022000e7a3000048656c6c6f
```

```text
IP checksum  UNCHANGED: 0xf6c6 -> 0xf6c6   (covers only the 20-byte IP header, which did not change)
TCP checksum CHANGED:   0xc7a3 -> 0xe7a3   (covers the payload via the pseudo-header)

Exactly two byte positions differ:
  byte [36]: 0xc7 -> 0xe7   (high byte of TCP.chksum, which lives at [36:38])
  byte [40]: 0x68 -> 0x48   (the flipped payload byte: 'h' -> 'H')
```

**(d) Reasoning.** For a packet you *constructed* (not dissected), there is no serialization cache, so Scapy **always recomputes** derived fields on every `bytes()` (Governing Rule 2). The IP header checksum is stable here because the IP header bytes are byte-for-byte identical between the two builds; only the TCP checksum moves (it incorporates the payload via the pseudo-header) along with the single flipped payload byte. The fact that exactly **two** positions change — and that they are the TCP checksum and the payload byte, not the IP checksum — is the visible proof that recomputation happened and that the IP and TCP checksums cover different spans.

**Documented nuance (observed characteristic — reported, not "fixed") — dissected per-layer STALE cache.**

The story changes for a packet obtained by **dissection**. `d = IP(bytes(...))` runs `do_dissect`, which **populates** the per-layer cache (`scapy/packet.py:1019`): verified, `d.raw_packet_cache is None` is `False` at the IP, TCP, **and** Raw layers. If you then change only a **deep payload field**, e.g. `d[Raw].load = b"hello!"` (one byte longer), only the **Raw** layer's cache is cleared (`scapy/packet.py:485-487`). The parent **IP** and **TCP** caches **survive** — their tracked fields did not change, so `self_build` keeps them (`scapy/packet.py:685-695`) — and `do_build` emits those cached headers **verbatim** (`scapy/packet.py:737-740`). The result is a **stale IP header**:

```text
STALE  (dissected, only Raw.load changed):  IP.len = 45,  IP.chksum = 0xf6c6,  actual total bytes = 46
FRESH  (rebuilt from scratch, same payload): IP.len = 46,  IP.chksum = 0xf6c5,  actual total bytes = 46
```

Here the dissected packet emits `len = 45` even though the buffer is now 46 bytes, and it keeps the old IP checksum `0xf6c6`; a freshly constructed equivalent recomputes `len = 46` and (because the `len` field inside the header changed) a different IP checksum `0xf6c5`. This is precisely the per-layer, dissection-populated cache short-circuiting `post_build` for the layers whose tracked fields were untouched. Per the investigation's rules this is **documented as observed behavior, not altered** — and it is reconciled with Rule 2: the cache exists only because the packet was *dissected*, and it is only the *parent* layers (untouched) that stay cached.

### Scenario 3 — Manual override BEFORE build

**(a) Question.** Force the IP checksum to `0xAAAA` **before** the packet is ever built. Does that value survive into the final bytes, or does Scapy overwrite it?

**(b) Governing code path.** `IP.post_build` writes the checksum only `if self.chksum is None` (`scapy/layers/inet.py:548-550`). Supplying `chksum=0xAAAA` in the `IP(...)` constructor makes the field **non-`None`**, so the guard is false and the computation is skipped — the explicit value is preserved (Governing Rule 1).

**(c) Runtime evidence.** `IP(src="192.0.2.2", dst="192.0.2.1", chksum=0xAAAA)/TCP()/Raw(load=b"hello")`:

```text
buffer:        4500002d000100004006aaaac0000202c000020100140050000000000000000050022000c7a3000068656c6c6f
bytes[10:12]:  aaaa
re-dissected IP.chksum: 0xaaaa
```

It **survives** — note `aaaa` at offset `[10:12]` where Scenario 1 had the computed `f6c6`.

**(d) Reasoning.** An explicit value makes the field non-`None`, so the compute-only-when-`None` guard skips it. Scapy will happily emit a deliberately "wrong" checksum if you tell it to — which is exactly what you want when crafting test or fuzzing packets. (The TCP checksum was left unset here, so it is still computed: `c7a3` at `[36:38]`, matching Scenario 1.)

### Scenario 4 — Manual override AFTER build

**(a) Question.** Build the packet **first**, then assign `0xAAAA` and rebuild. Does the behavior differ from Scenario 3?

**(b) Governing code path.** The key insight is that building a *constructed* packet does **not** write computed values back into its Python fields (verified: `p.chksum` is still `None` after the first `bytes(p)`). So after building once, `chksum` is still `None`; explicitly assigning `p.chksum = 0xAAAA` then makes it non-`None` (and, via `__setattr__` -> `setfieldval`, also clears the already-`None` cache, `scapy/packet.py:494-502,485-487`). The subsequent rebuild therefore preserves the explicit value exactly as in Scenario 3 (the `is None` guard at `scapy/layers/inet.py:548-550` is false).

**(c) Runtime evidence.**

```text
first build, re-dissected IP.chksum: 0xf6c6        (computed, because chksum was still None)
p.chksum is None after first build:  True

then p.chksum = 0xAAAA and rebuild:
buffer:        4500002d000100004006aaaac0000202c000020100140050000000000000000050022000c7a3000068656c6c6f
bytes[10:12]:  aaaa
re-dissected IP.chksum: 0xaaaa
```

**(d) Reasoning.** The behavior is **effectively identical to Scenario 3** — the explicit value survives **regardless of ordering**. What matters is solely whether the field is `None` *at the moment of the build that produces the bytes you keep*. The only internal difference between the two scenarios is that the post-build assignment also clears the cache — but for a *constructed* packet that cache was already `None`, so it has no observable effect. **Verdict: ordering does not matter; an explicitly set value always wins.**

### Scenario 5 — Deep-copy isolation

**(a) Question.** Build a packet to bytes, make a deep copy, modify the copy's payload, and verify the original is **not** corrupted by showing the original's bytes **before** and **after** the copy is modified.

**(b) Governing code path.** `copy.deepcopy(orig)` dispatches to `Packet.__deepcopy__` (`scapy/packet.py:239-244`), which simply calls `copy()` (`scapy/packet.py:407-426`). `copy()` clones each layer's field dictionaries and then **recursively clones the payload chain** via `clone.payload = self.payload.copy()` (`scapy/packet.py:422`), re-linking the underlayer with `clone.payload.add_underlayer(clone)` (`scapy/packet.py:423`). The clone therefore owns independent field dicts, so mutating the copy's `Raw.load` (routed through `setfieldval` on the **copy only**, `scapy/packet.py:485-487`) cannot reach the original.

**(c) Runtime evidence.** `load=b"AAAAA"`; `copy.deepcopy(orig)`; then set the copy's `load=b"ZZZZZZZZZZ"`. The original's full buffer **before** and **after** the copy is modified, plus the divergent copy:

```text
ORIG BEFORE: 4500002d000100004006f6c6c0000202c00002010014005000000000000000005002200047f300004141414141
ORIG AFTER : 4500002d000100004006f6c6c0000202c00002010014005000000000000000005002200047f300004141414141
COPY       : 45000032000100004006f6c1c0000202c00002010014005000000000000000005002200047ad00005a5a5a5a5a5a5a5a5a5a
```

`ORIG BEFORE == ORIG AFTER` -> **isolation confirmed** (verified equal, 45 bytes each). The copy diverges in `IP.len` (`002d` -> `0032`, i.e. 45 -> 50), `IP.chksum` (`f6c6` -> `f6c1`), `TCP.chksum` (`47f3` -> `47ad`), and the payload (`4141414141` = `"AAAAA"` -> `5a5a5a5a5a5a5a5a5a5a` = `"ZZZZZZZZZZ"`, five bytes longer).

**(d) Reasoning.** Scapy copies are **deep**: the payload chain is cloned recursively (`scapy/packet.py:422`), so the copy is a fully independent object graph. Rebuilding the (constructed) copy recomputes *its own* derived fields from *its own* mutated state — hence the copy's different `len` and both checksums — while the original's bytes are untouched. The byte-identical `ORIG BEFORE`/`ORIG AFTER` buffers are the direct proof that no aliasing leaked from the copy back to the original.

### Scenario 6 — Length field on growth

**(a) Question.** Build with a small payload, append ten more bytes, rebuild, and report the decimal value of the IP `len` field, the actual total byte count, and whether the two match or diverge.

**(b) Governing code path.** `IP.post_build` sets `len = len(p) + len(pay)` **only when it is unset** (`scapy/layers/inet.py:545-547`). The constructed packet has `len = None` (default at `scapy/layers/inet.py:527`), so every `bytes()` recomputes `len` to equal the real serialized size (Governing Rule 1, and — because the packet is constructed — Rule 2 guarantees no cache interferes).

**(c) Runtime evidence.**

```text
small payload  load=b"A"*10:   IP.len = 50, total bytes = 50  -> MATCH
grown payload  load=b"A"*20:   IP.len = 60, total bytes = 60  -> MATCH
(delta len = 10, delta bytes = 10)
```

Both cases **MATCH**. (Sizes break down as 20-byte IP header + 20-byte TCP header + payload: `20 + 20 + 10 = 50` and `20 + 20 + 20 = 60`.)

**(d) Reasoning.** Because `len` is left `None`, Scapy recomputes it on **every** build to equal the actual length, so the field and the true byte count stay in agreement; growing the payload by ten bytes grows **both** the `len` field and the real buffer by exactly ten. (Contrast this with the dissected stale-cache nuance in Scenario 2, where a *dissected* packet can keep a stale `len` because its parent IP cache survives — that only happens for dissected packets, never for the constructed packets used here.)

## Summary / mental model

Everything above collapses into the two governing rules:

1. **Derived fields are computed at build time ONLY when left `None`.** `IP.post_build` and `TCP.post_build` write `len`/`chksum` under an `is None` guard (`scapy/layers/inet.py:545-550,775-778`). Set a field explicitly and it **survives regardless of before/after ordering** (Scenarios 1, 3, 4, 6). This is why a `chksum=0xAAAA` you supply — whether in the constructor or by assignment after a build — always wins.

2. **The serialization cache (`raw_packet_cache`) exists ONLY for dissected packets.** It is initialized to `None` (`scapy/packet.py:169-170`), populated solely by `do_dissect` (`scapy/packet.py:1019`), tracked **per layer**, and it short-circuits `post_build` in `do_build` (`scapy/packet.py:737-740`). It is invalidated whenever you assign or delete a field (`scapy/packet.py:485-487,509-511`). Consequently a **freshly constructed** packet has no cache and **always recomputes** on every `bytes()` (Scenarios 1, 2, 5, 6); a **dissected** packet can emit a **stale parent-layer header** if you change only a deep child field, because the untouched parent layers keep their caches (Scenario 2's documented nuance).

Put differently: the IP checksum covers only the IP header, while the TCP checksum covers a pseudo-header plus the payload (`scapy/layers/inet.py:692,776-778`) — which is why, in Scenario 2, a payload tweak moves the TCP checksum but not the IP checksum.

**Forcing recomputation on a dissected packet (brief analogous note).** If you have a *dissected* packet and want a field recomputed, **delete the field** so it becomes `None` again — e.g. `del pkt[IP].chksum`. This routes through `delfieldval`, which clears that layer's cache (`scapy/packet.py:509-511`), so the next build re-enters `post_build` and recomputes the value under the `is None` guard (Governing Rule 1). This is the standard idiom for "re-checksum a packet I parsed off the wire," and it keeps the scope of automatic computation entirely under your control.
