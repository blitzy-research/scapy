# How Scapy Builds Ethernet Frames: Payload Padding & EtherType Dispatch

**An evidence-grounded investigation** into two questions about Scapy's Ethernet (`Ether`) layer:
(1) does Scapy automatically pad short frames up to the Ethernet minimum, and what happens to
padding when you serialize and parse a frame back; and (2) how Scapy decides which protocol comes
next from the EtherType field, including what it does with an unrecognized value.

> **One-paragraph summary of findings.** Scapy **does not** auto-pad short frames at build time — a
> `Ether()/IP()/TCP()` serializes to `54` bytes and stays there, and a `Ether()/Raw(b"X"*10)` is just
> `24` bytes, both below the 60-byte on-wire Ethernet minimum. A payload-size sweep is strictly linear
> (frame size always equals header + payload), so there is **no padding "threshold"** at build time.
> Padding is a **dissection-time** concept: when you round-trip a self-built short frame via
> `Ether(raw(packet))` there is **no** `Padding` layer (`haslayer(Padding) -> 0`), but when the bytes
> genuinely carry trailing pad, dissection attaches a `Padding` layer (`Padding.load = b'\x00\x00\x00\x00'`,
> `len= 4`) that survives re-serialization. For an unknown EtherType such as `0x9000`, Scapy neither
> raises nor blindly hex-dumps — it renders `type = 0x9000` and falls back to a `Raw` payload. The
> code that makes each of these decisions lives in `scapy/packet.py` (build, dissect, payload-class
> guessing) and `scapy/layers/l2.py` (the `Ether` class and its `bind_layers` table), and every claim
> below is cited to an exact `file:line`.

---

## The question, restated

The investigation was framed by a user who wanted to understand, empirically, how Scapy assembles an
Ethernet frame and dispatches to the next protocol. Restated in plain terms, two topics are in play:

1. **Padding.** Does Scapy auto-pad short frames to the Ethernet minimum, and what happens to any
   padding on a round-trip (serialize to bytes, then parse back)?
2. **Dispatch.** How does Scapy figure out which protocol comes next from the EtherType, and what
   happens for an unknown/unrecognized EtherType?

To answer these concretely, three test packets are built (the user's own examples are preserved
verbatim below):

| Purpose | Build command |
|---------|---------------|
| **Normal frame** | `Ether()/IP()/TCP()` |
| **Short payload "(like 10 bytes)"** | `Ether()/IP()/TCP()/Raw(b"X"*10)` and `Ether()/Raw(b"X"*10)` |
| **Unknown EtherType "0x9000 or something random"** | `Ether(type=0x9000)/Raw(...)` (and `type=0x1234` to represent "random") |

The round-trip is exercised with the idiom the user asked about, used verbatim throughout:

```python
Ether(raw(packet))
```

The full set of sub-questions this document answers explicitly is **Q1–Q8**:

- **Q1** — Normal frame: how does Scapy assemble `Ether()/IP()/TCP()` (auto-resolved fields, summary, length)?
- **Q2** — Short payload / auto-pad: does Scapy pad a "(like 10 bytes)" payload up to the Ethernet minimum?
- **Q3** — Round-trip padding survival via `Ether(raw(packet))`: does padding persist, and as what layer?
- **Q4** — Unknown EtherType: what does `print()`/`show()` display after the Ethernet layer for `0x9000`?
- **Q5** — Padding threshold: sweeping payload sizes, at what point does padding start/stop?
- **Q6** — Code: where is padding decided?
- **Q7** — Code: how does Scapy figure out the next protocol from the EtherType?
- **Q8** — Code: what runs when Scapy meets a protocol number it does not recognize?

The observation script (reproduced so it can be re-run):

```python

# Q1 normal frame

# Q2 short payload -> auto-pad?
```

## Empirical answers (Q1–Q5)

### Q1 — Normal frame `Ether()/IP()/TCP()` (how Scapy assembles it)

**Observed.**

```
summary : Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S
len(raw): 54
```

`summary()` returns `Ether / IP / TCP 127.0.0.1:ftp_data > 127.0.0.1:http S`, and `len(raw(...)) = 54`.

**Rationale.** Scapy fills in the unset fields with sensible defaults and auto-resolves the ones that
depend on context:

- `Ether.dst` auto-resolves to the broadcast `ff:ff:ff:ff:ff:ff` when there is no route (hence the
  `WARNING: Mac address to reach destination not found. Using broadcast.`), and `Ether.src` auto-fills
  a locally-generated MAC.
- `Ether.type` is set to `0x0800` (IP) automatically: assembling `Ether()/IP()` matches the
  `bind_layers(Ether, IP, type=2048)` overload (`2048 == 0x0800`), so the bound field value is written
  into `type` during build.
- `IP.src`/`IP.dst` default to `127.0.0.1`; `TCP` defaults to `sport = ftp_data` (port `20`),
  `dport = http` (port `80`), and `flags = S` (SYN) — exactly what the summary shows.

The `54` bytes decompose as `14` (Ethernet header: 6-byte `dst` + 6-byte `src` + 2-byte `type`)
`+ 20` (IPv4 header) `+ 20` (TCP header).

**Citations.** The `Ether` class and its `fields_desc` are at `scapy/layers/l2.py:244-248`
(`XShortEnumField("type", 0x9000, ETHER_TYPES)` — note the field's **default literal is `0x9000`**, but
building `Ether()/IP()` overrides `type` to `0x0800` via the binding). The `0x0800 -> IP` binding is
`bind_layers(Ether, IP, type=2048)` at `scapy/layers/inet.py:1101`. The serialized bytes are produced
by `Packet.build()` at `scapy/packet.py:746-756`.

### Q2 — Short payload / auto-pad (does Scapy pad "(like 10 bytes)" up to the Ethernet minimum?)

**Answer: NO — Scapy does not auto-pad at build time.**

**Observed.**

```
============ Q2b: very short frame Ether/Raw(10) -> auto-pad to 60? ============
len(raw): 24 raw = b'\xff\xff\xff\xff\xff\xff\xa6\xf2\xb3\x06zP\x90\x00XXXXXXXXXX'

============ Q2c: bare Ether/IP/TCP len vs Ethernet minimum 60 ============
len(raw(Ether/IP/TCP)) = 54 -> < 60? True
```

`Ether()/Raw(b"X"*10)` serializes to `len(raw): 24` — that is `14` (Ethernet header) `+ 10`
(the `XXXXXXXXXX` payload), **not** padded up to `60`. And a bare `Ether()/IP()/TCP()` is `54`, with
`54 -> < 60? True`: it is below the Ethernet minimum yet emitted as-is with no padding added.

**Rationale.** The build path emits only header + payload. `Packet.build()` is
`do_build()` + `build_padding()` + `build_done()` at `scapy/packet.py:746-756`; crucially
`build_padding()` merely chains to the payload's own `build_padding()` (`return self.payload.build_padding()`)
at `scapy/packet.py:742-744` and injects **no** zero-padding. The `Ether` class itself contains no
minimum-frame / "60" / auto-pad logic at all (`scapy/layers/l2.py:244-248`).

**Citations.** `scapy/packet.py:742-744` (`build_padding`), `scapy/packet.py:746-756` (`build`),
`scapy/layers/l2.py:244-248` (`Ether` has no padding logic).

### Q3 — Round-trip padding survival via `Ether(raw(packet))`

**Answer: a self-built short frame round-trips with NO `Padding` layer; a genuinely padded byte string
round-trips WITH a `Padding` layer that then survives re-serialization.**

**Observed — self-built short frame.**

```
============ Q3: round-trip Ether(raw(pkt)) for short Ether/IP/TCP/Raw(10) ============
orig len: 64  round-trip len: 64
round-trip has Padding layer? -> 0
```

`Ether(raw(Ether()/IP()/TCP()/Raw(b"X"*10)))` gives `orig len: 64`, `round-trip len: 64`, and
`round-trip has Padding layer? -> 0`. The 10 `X` bytes parse back as `Raw`, **not** `Padding` — there
were never any trailing pad bytes; the frame was 64 bytes of real content.

**Observed — genuinely padded bytes.**

```
============ Q3b: round-trip when REAL trailing pad exists (pad to 60) ============
base frame len: 56
manually padded to: 60
round-trip Padding present? -> True
Padding.load = b'\x00\x00\x00\x00' len= 4
re-serialize len: 60 (padding survives re-build?)
```

Taking a 56-byte frame (`Ether()/IP()/TCP()/Raw(b"X"*2)`) and manually appending zeros to reach `60`,
the round-trip reports `round-trip Padding present? -> True`, with `Padding.load = b'\x00\x00\x00\x00'`
(`len= 4`), and re-serialization yields `re-serialize len: 60` — the padding **survives** the rebuild.

**Rationale.** `raw(x)` is literally `bytes(x)` (`scapy/compat.py:112-118`), which is why
`Ether(raw(packet))` means "serialize, then parse back." On parse, `dissect()`
(`scapy/packet.py:1049-1060`) calls `extract_padding(s)` and then attaches a padding layer **only**
`if pad and conf.padding:` via `self.add_payload(conf.padding_layer(pad))`. Whether any trailing bytes
exist is decided by `extract_padding`: the default returns `s, None` (`scapy/packet.py:982-990`), so an
unbounded layer like `Raw` swallows everything as payload — hence **no** `Padding` in the self-built
case. Length-bounded layers (e.g. `IP`, or `Dot3.extract_padding` at `scapy/layers/l2.py:275-284`)
instead split off the trailing bytes, which is how the 4 zero bytes become `Padding` in the second
case. `conf.padding = 1` by default (`scapy/config.py:787`) is what permits the attachment. The padding
survives re-serialization because `class Padding(Raw)` has `self_build -> b""` but its `build_padding`
re-emits `load` at the end of the frame (`scapy/packet.py:1906-1918`, with `class Raw` at
`scapy/packet.py:1877-1903`).

### Q4 — Unknown EtherType `print()`/`show()` behavior

**Answer: graceful fallback to `Raw` — no exception, no blind hex dump.**

**Observed.**

```
repr: <Ether  type=0x9000 |<Raw  load='hello unknown ethertype payload' |>>
###[ Ethernet ]###
  dst       = ff:ff:ff:ff:ff:ff
  src       = a6:f2:b3:06:7a:50
  type      = 0x9000
###[ Raw ]###
     load      = 'hello unknown ethertype payload'
```

`repr(Ether(type=0x9000)/Raw(load=b"hello unknown ethertype payload"))` is
`<Ether  type=0x9000 |<Raw  load='hello unknown ethertype payload' |>>`. `show()` renders
`###[ Ethernet ]###` with `type = 0x9000` (the raw hex literal — no name is mapped for `0x9000`)
followed by a `###[ Raw ]###` layer whose `load = 'hello unknown ethertype payload'`. No error is
raised and no undecoded hex is dumped in place of a layer name.

**Rationale.** `type` renders as a hex literal because it is an `XShortEnumField`
(`class XShortEnumField(ShortEnumField)` at `scapy/fields.py:2660`) backed by the `ETHER_TYPES`
name-to-number table loaded at `scapy/data.py:526` (`ETHER_TYPES = load_ethertypes(None)`); since
`0x9000` has no name in that table, the raw hex is shown. When the same value is presented as bytes to
dissect, an unrecognized EtherType matches no binding, so `guess_payload_class` falls through to
`default_payload_class`, which returns `conf.raw_layer` (i.e. `Raw`) at `scapy/packet.py:1081-1090`.
(The same "random" behavior holds for `type=0x1234` or any other unmapped value.)

### Q5 — Padding threshold (sweep to find where padding starts/stops)

**Answer: there is NO threshold; frame size is strictly linear = header + payload.**

**Observed.**

```
============ Q5: payload-size sweep (Ether/IP/TCP/Raw(n)) ============
payload= 0 -> total raw bytes = 54
payload= 1 -> total raw bytes = 55
payload= 6 -> total raw bytes = 60
payload=10 -> total raw bytes = 64
payload=20 -> total raw bytes = 74

============ Q5b: payload sweep on Ether/Raw(n) ============
payload= 0 -> total raw bytes = 14
payload=45 -> total raw bytes = 59
payload=46 -> total raw bytes = 60
payload=47 -> total raw bytes = 61
payload=60 -> total raw bytes = 74
```

Both sweeps are strictly linear. For `Ether/IP/TCP/Raw(n)`: `0 -> 54`, `1 -> 55`, `6 -> 60`, `10 -> 64`,
`20 -> 74`. For `Ether/Raw(n)`: `0 -> 14`, `45 -> 59`, `46 -> 60`, `47 -> 61`, `60 -> 74`. Every step
increases by exactly the payload delta; there is no size at which bytes are added or removed to reach
`60`.

**Interpretation.** The "threshold" premise does not hold — Scapy never adds minimum-frame padding at
build time. The appearance of `60` at `Ether/Raw(46)` (or `Ether/IP/TCP/Raw(6)`) is simply `14 + 46`
(or `54 + 6`) — real bytes, **not** padding. Notably `47 -> 61` shows the size continues past `60`
one-for-one, confirming nothing special happens at the minimum.

**Citations.** Same build path as Q2 — `scapy/packet.py:742-744` and `scapy/packet.py:746-756`; and no
minimum-frame logic in `Ether` (`scapy/layers/l2.py:244-248`).

## Code-level answers (Q6–Q8)

### Q6 — Where padding is decided (in the source)

**Padding is a dissection-time concept, not a build-time one — and the `Ether` class decides nothing
about it.**

- **Build side (no pad added).** `Packet.build()` at `scapy/packet.py:746-756` is
  `p = self.do_build(); p += self.build_padding(); p = self.build_done(p); return p`. The
  `build_padding()` method at `scapy/packet.py:742-744` is just `return self.payload.build_padding()`
  — it chains down the layer stack and never injects zero-padding to reach `60`.
- **Dissect side (pad may be attached).** `dissect()` at `scapy/packet.py:1049-1060` does
  `payl, pad = self.extract_padding(s)`, then `self.do_dissect_payload(payl)`, and finally
  `if pad and conf.padding: self.add_payload(conf.padding_layer(pad))`. So a `Padding` layer is only
  ever added here, on dissect, and only when two conditions hold: (a) `extract_padding` reported
  trailing bytes, and (b) `conf.padding` is truthy.
- **Who reports trailing bytes.** The decision of whether *any* trailing bytes exist is made by
  `extract_padding`. The default implementation returns `s, None` (`scapy/packet.py:982-990`) — i.e.
  "no padding, the whole remainder is my payload" — which is why an unbounded layer such as `Raw`
  never yields `Padding`. Layers with an explicit length field override it; e.g.
  `Dot3.extract_padding` at `scapy/layers/l2.py:275-284` returns `s[:tmp_len], s[tmp_len:]`, splitting
  off everything past the declared length as padding. (`IP`, via its total-length field, behaves
  analogously — which is what produced the `Padding` layer in Q3b.)
- **The gating flag.** `conf.padding = 1` by default at `scapy/config.py:787` (commented
  "includes padding in disassembled packets").

**Conclusion.** There is no build-time padding decision at all, and the `Ether` class contains no
minimum-frame logic (`scapy/layers/l2.py:244-248`). Padding is decided entirely on the dissect path in
`scapy/packet.py`.

### Q7 — Protocol dispatch (how the EtherType selects the next protocol)

**Mechanism: a data-driven binding lookup.** `guess_payload_class(payload)` at
`scapy/packet.py:1062-1079` iterates `self.aliastypes`, and for each `(fval, cls)` pair in
`t.payload_guess` it returns `cls` as soon as every bound field value matches
(`if all(v == self.getfieldval(k) for k, v in fval.items()): return cls`). For Ethernet this means:
when `self.type` equals a bound EtherType, the corresponding class is chosen.

The `payload_guess` table is populated by `bind_layers(...)` calls:

- **Ethernet bindings** live at `scapy/layers/l2.py:686-716` — for example
  `bind_layers(Ether, LLC, type=122)`, `bind_layers(Ether, Dot1Q, type=33024)`,
  `bind_layers(Ether, Dot1AD, type=0x88a8)`, `bind_layers(Ether, Ether, type=1)`, and
  `bind_layers(Ether, ARP, type=2054)`.
- **IP and IPv6** are bound in their own modules: `bind_layers(Ether, IP, type=2048)` at
  `scapy/layers/inet.py:1101` (`0x0800 -> IP`) and `bind_layers(Ether, IPv6, type=0x86dd)` at
  `scapy/layers/inet6.py:4083` (`0x86dd -> IPv6`).

There is also a related "front-door" dispatch decision in `Ether.dispatch_hook` at
`scapy/layers/l2.py:266-272`: when the 2 bytes at offset 12–14 are `<= 1500`, the value is interpreted
as an IEEE 802.3 **length** rather than an EtherType, and the frame is dispatched to `Dot3` instead of
Ethernet II. For genuine EtherTypes (which are all `> 1500`, e.g. `0x0800 = 2048`), this hook returns
the `Ether` class itself and normal `guess_payload_class` dispatch proceeds.

### Q8 — Unrecognized protocol number (what logic runs)

**Answer: no exception is raised; Scapy falls back to `Raw`.** There are two convergent paths:

- **Path 1 — no binding matches.** When no `payload_guess` entry matches, `guess_payload_class` returns
  `self.default_payload_class(payload)` (`scapy/packet.py:1062-1079`), and `default_payload_class`
  returns `conf.raw_layer` (`scapy/packet.py:1081-1090`). `conf.raw_layer` is `Raw`
  (`class Raw` at `scapy/packet.py:1877-1903`). This is exactly what happens for `type=0x9000` in Q4.
- **Path 2 — a bound class exists but its dissection raises.** `do_dissect_payload` at
  `scapy/packet.py:1023-1047` wraps construction of the guessed class in `try/except`. A
  `KeyboardInterrupt` is re-raised; any other `Exception` is caught and it falls back to
  `p = conf.raw_layer(s, _internal=1, _underlayer=self)` — again `Raw` — unless
  `conf.debug_dissector` is enabled, in which case it re-raises to aid debugging.

Both paths converge on `Raw`, which is why an unknown or malformed next-protocol never crashes the
parser and never produces a blind hex dump in place of a named layer.

## Background: the 64 / 60 / 46-byte minimum frame

Why does a padding question arise at all? Because Ethernet defines a **minimum frame size of 64 bytes**.
That 64 is made of 18 bytes of overhead — a 6-byte destination MAC, a 6-byte source MAC, a 2-byte
type/length field, and a 4-byte Frame Check Sequence (FCS/CRC) — plus a **minimum 46-byte payload**. If
the upper-layer data is shorter than 46 bytes, the frame is padded with trailing zeros so the payload
reaches 46.

Scapy does **not** emit the 4-byte FCS (that is generated by hardware), so the relevant on-wire minimum
*in Scapy terms* is **60 bytes**: a 14-byte header (6 + 6 + 2) plus the 46-byte minimum payload. This is
exactly why the investigation targets "60," and why a bare `Ether()/IP()/TCP()` at `54` bytes is
"too short" (`54 -> < 60? True`).

The key design point: this minimum-frame zero-padding is performed by the **NIC / hardware / driver, not
by the application**. That is precisely why Scapy does not pad at build time — it leaves minimum-frame
padding to the hardware — and only surfaces a `Padding` layer when **dissecting** bytes that were
*already* padded (for example a real captured frame that a NIC padded up to 60). The classic
encapsulation arithmetic lines up with the observed sweep: a 46-byte minimum payload split as
IPv4 (20) + TCP (20) leaves room for 6 bytes of data, and indeed `Ether/IP/TCP/Raw(6) = 60` bytes in the
Q5 sweep.

## Coverage

Every sub-question posed by the investigation is answered above; a one-line confirmation of each:
