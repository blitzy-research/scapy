# Scapy `Ether()/IP()/TCP()` — Build, Send, Sniff, and Dissect: An Observed Runtime Walkthrough

This document answers, **from verbatim observed runtime output**, exactly what Scapy reveals when you start it normally, build a layered `Ether()/IP()/TCP()` packet, send it on the wire (including the routing it consults), and sniff it back (including how it dissects the raw bytes). It closes with a synthesis and the environment caveats needed to reproduce the results.

Scapy is described by the project itself as a Python-based interactive packet-manipulation program and library able to forge/decode packets, send them on the wire, and capture them (`README.md:L13-L17`). The subject packet studied throughout is the user's exact packet: **`Ether()/IP()/TCP()`**.

```text

git describe --tags --always --long 0925ada485406684174d6f068dbd85c4154657b3   -> 0925ada4
```

**Reproducibility note (the value is commit-independent).** Because the repository carries **zero tags**, `git describe --tags --always --long` can only ever emit the *current* HEAD's bare commit abbreviation, so its literal output tracks whatever commit is checked out — `bb13f7ca` at the reviewed deliverable commit, `0925ada4` at the source baseline, and a different abbreviation again for any later commit (for example, the commit that carries these review corrections). What does **not** change is the resolved version: with no tags, no release version is ever parseable, so `_version()` always lands on the mtime fallback and returns `2026.07.02`. The reproducible, commit-independent facts are therefore `git tag | wc -l -> 0`, `git rev-list --tags --max-count=1 -> ''`, and `mtime(scapy/__init__.py) -> 2026.07.02`.

Cause → effect, step by step (values shown for the final checkout `bb13f7ca`; the source baseline `0925ada4` behaves identically — in both cases `git describe` yields only a bare commit abbreviation because there are zero tags):

1. `git describe --tags --always --long` returns the bare commit abbreviation — `bb13f7ca` at the final checkout (`0925ada4` at the source baseline). It does **not** start with `v` and has no `TAG-N-gHASH` shape, so `_version_from_git_describe()` (`scapy/__init__.py:L72-L119`, whose `git describe` call is at `scapy/__init__.py:L114`) yields no parseable release version and raises.
2. `git rev-list --tags --max-count=1` returns empty (no tagged revision exists), so the retry inside `_version_from_git_describe()` also fails.
3. `_version()` (`scapy/__init__.py:L122`) therefore falls through Methods 0–3 to the **Fallback** block at `scapy/__init__.py:L157-L162`, which computes the file modification time: `d = datetime.datetime.utcfromtimestamp(os.path.getmtime(__file__))` (`scapy/__init__.py:L160`) and `return d.strftime('%Y.%m.%d')` (`scapy/__init__.py:L161`).
4. The mtime of `scapy/__init__.py` is `2026-07-02`, so the fallback yields `2026.07.02`.

The value `2026.07.02` is therefore reported **verbatim** but is explicitly a **file-modification-time fallback**; the canonical `git describe` path yields no release version in this tagless checkout at *any* commit — the reviewed deliverable commit (`bb13f7ca`), the source baseline (`0925ada4`), or any later commit — so the mtime fallback `2026.07.02` is what a normal user observes regardless.

## 2. Building & displaying `Ether()/IP()/TCP()`

### The three layer classes under study

Each layer in `Ether()/IP()/TCP()` is a `Packet` subclass defined in Scapy's protocol-layer modules; constructing one with no arguments yields the default field values observed throughout this section:

- **`Ether`** — defined at `scapy/layers/l2.py:L244` (`class Ether(Packet):`). Cause → effect: its `fields_desc` provides the Ethernet defaults seen in the `repr`/`show()` output below (`dst = ff:ff:ff:ff:ff:ff`, `src = 00:00:00:00:00:00`) and the `type` field that the `/` binding sets to `IPv4` when an `IP()` payload is attached.
- **`IP`** — defined at `scapy/layers/inet.py:L521` (`class IP(Packet, IPTools):`). Cause → effect: it supplies the IPv4 defaults observed below — `src`/`dst` default to `127.0.0.1` (rendered in `summary()`), and the computed `ihl`/`len`/`chksum` fields that display as `None` in `show()` but resolve to `ihl=5`, `len=40`, `chksum=0x7ccd` in `show2()`. Its `proto` field is set to `tcp` by the `/` binding when a `TCP()` payload is attached.
- **`TCP`** — defined at `scapy/layers/inet.py:L753` (`class TCP(Packet):`). Cause → effect: it supplies the TCP defaults observed below — `sport=ftp_data` (20), `dport=http` (80), and `flags=S` (SYN) in `summary()`, and the computed `dataofs`/`chksum` fields that show as `None` in `show()` but resolve to `dataofs=5`, `chksum=0x917c` in `show2()`.

(The `file:line` locations above are source references; the specific default values attributed to each class are the ones observed in the `repr`, `summary()`, `show()`, and `show2()` captures that follow.)

### The `/` operator stacks layers

The `/` (division) operator is how Scapy stacks protocol layers. It is implemented by `Packet.__div__` (`scapy/packet.py:L596`), aliased as `__truediv__ = __div__` (`scapy/packet.py:L607`). It clones both operands and calls `cloneA.add_payload(cloneB)`, which is what applies the underlayer's binding/overload fields onto the layer beneath it.

### `repr` progression (`Packet.__repr__`, `scapy/packet.py:L552`)

Watching the `repr` grow as each layer is added shows the bindings being applied:

- `repr(Ether())`:
  ```python
  <Ether  |>
  ```
  A bare Ethernet header with no bound payload yet.

- `repr(Ether()/IP())`:
  ```python
  <Ether  type=IPv4 |<IP  |>>
  ```
  Cause → effect: dividing by `IP()` binds `IP` as the payload of `Ether`, and the binding sets the Ethernet **`type=IPv4`** field automatically (the underlayer's overload field).

- `repr(Ether()/IP()/TCP())`:
  ```python
  <Ether  type=IPv4 |<IP  frag=0 proto=tcp |<TCP  |>>>
  ```
  Cause → effect: dividing the `IP` layer by `TCP()` binds `TCP` beneath `IP`, and the binding sets the IP **`proto=tcp`** field. (`frag=0` is also shown on the IP layer.)

## 3. Sending & routing

### `sendp()` (Layer 2) vs `send()` (Layer 3)

Because the subject packet is rooted at `Ether()`, the correct "usual sending mechanism" is the **Layer-2** sender `sendp()` (`scapy/sendrecv.py:L452`). The **Layer-3** sender `send()` (`scapy/sendrecv.py:L422`) is for an `IP()`-rooted packet. Both dispatch to the common emitter `__gen_send()` (`scapy/sendrecv.py:L332`).

Cause → effect: `sendp()` opens a **Layer-2** socket (`conf.L2socket`) and puts the raw Ethernet frame on the wire exactly as built; `send()` opens a **Layer-3** socket (`conf.L3socket`) and lets the socket prepend the link-layer header. On **Linux** — the canonical runtime here — `conf.L3socket` is **`L3PacketSocket`** (Linux `PF_PACKET`), *not* `L3RawSocket`. Observed:

```text
conf.L3socket = <L3PacketSocket: read/write packets at layer 3 using Linux PF_PACKET sockets>
```

Grounding: `_set_conf_sockets()` (`scapy/config.py:L606`) takes the `if LINUX:` branch and sets `conf.L3socket = L3PacketSocket` (`scapy/config.py:L645-L648`); `L3PacketSocket` is defined in `scapy/arch/linux.py:L587-L619` (its `desc` is exactly `"read/write packets at layer 3 using Linux PF_PACKET sockets"`, matching the observed repr, and it implements its own `send()` over `PF_PACKET`). By contrast `L3RawSocket` (`scapy/supersocket.py:L283`, `desc = "Layer 3 using Raw sockets (PF_INET/SOCK_RAW)"`) is used **only** in the non-Linux `else` branch (`scapy/config.py:L669-L673`) — it is not the Linux L3 path. The base socket-send contract is `SuperSocket.send()` (`scapy/supersocket.py:L97`), which the Linux PF_PACKET sockets (including `L3PacketSocket`) override with their own `send()`.

### Related send/receive machinery: `sr()` and `SndRcvHandler`

`send`/`sendp` only transmit; Scapy's **stimulus/response** functions additionally *match replies*. The Layer-3 form is `sr()` (`scapy/sendrecv.py:L635`), whose docstring is:

```text
Send and receive packets at layer 3
```

Cause → effect: `sr()` opens a Layer-3 socket (`conf.L3socket` — `L3PacketSocket` on Linux, as above) and hands the send-and-match loop to `sndrcv()` (`scapy/sendrecv.py:L322`), which instantiates the `SndRcvHandler` (`scapy/sendrecv.py:L100`, created at `scapy/sendrecv.py:L328`) and returns its results (`scapy/sendrecv.py:L329`). `SndRcvHandler`'s docstring states:

```text
Util to send/receive packets, used by sr*().
Do not use directly.
```

So `SndRcvHandler` is the engine behind `sr`/`sr1`/`srp`/`srp1`. **(inferred)** From reading the class, it sends each packet, records the outgoing timestamps, and matches incoming answers to their requests; `sr*()` was not executed in this investigation, so this behavioral description is derived from the source and docstrings above, not from observed output. What *is* observed is that the plain `sendp()`/`send()` used to put this `Ether()/IP()/TCP()` frame on the wire only emit (Section 3 verbose output) and return no answers; `sr*()` is documented here as the related, receive-capable machinery for completeness.

### Verbose emitter output (default `conf.verb = 2`)

With the default verbosity, `__gen_send()` writes one `.` per packet via `os.write(1, b".")` (`scapy/sendrecv.py:L379-L380`) and then prints the summary line `print("\nSent %i packets." % n)` (`scapy/sendrecv.py:L391-L392`). Observed:

- `sendp(p, iface="lo", count=1)`:
  ```console
  .
  Sent 1 packets.
  ```

- `sendp(p, iface="lo", count=3)`:
  ```console
  ...
  Sent 3 packets.
  ```

- `send(IP(dst="127.0.0.1")/TCP(), count=1)` (the Layer-3 sender):
  ```console
  .
  Sent 1 packets.
  ```

Aside on output ordering (observed): when this output is captured **through a pipe**, the unbuffered dots (written directly to fd 1 via `os.write`) are flushed immediately and can appear coalesced ahead of the buffered `print` lines — e.g. all five dots from the three sends above rendered together as `.....` at the very start of the piped capture. In an interactive REPL the dots render inline immediately before each `\nSent N packets.` line. This is a stdout-buffering artifact, not a Scapy behavior change.

### The routing table `conf.route`

Before sending, Scapy selects the egress interface from the routing table `conf.route`, rendered by `Route.__repr__` (`scapy/route.py:L47`), whose column header tuple is `("Network", "Netmask", "Gateway", "Iface", "Output IP", "Metric")` (`scapy/route.py:L59-L60`). The live table observed in this environment:

```console
Network     Netmask      Gateway     Iface  Output IP   Metric
0.0.0.0     0.0.0.0      172.17.0.1  eth0   172.17.0.2  0     
127.0.0.0   255.0.0.0    0.0.0.0     lo     127.0.0.1   1     
172.17.0.0  255.255.0.0  0.0.0.0     eth0   172.17.0.2  0     
```

Which rows are stable vs environment-specific:

- The header and columns are stable.
- The **`lo`** row is stable: `127.0.0.0   255.0.0.0   0.0.0.0   lo   127.0.0.1   1`.
- The **`eth0`** rows contain **environment-specific IPs** — here the Docker bridge gateway `172.17.0.1` and Output IP `172.17.0.2` — which **will differ** on other hosts/containers. They are reported as observed in *this* container run, not as universal values. (No `docker0` row appears inside the container; the container's own `eth0` sits on the `172.17.0.0/16` Docker bridge.)

### One route resolution (`Route.route`, `scapy/route.py:L146`)

```python
conf.route.route("127.0.0.1") -> ('lo', '127.0.0.1', '0.0.0.0')
```

The returned 3-tuple is `(interface, output/source IP, gateway)`: to reach `127.0.0.1`, Scapy chooses interface **`lo`**, uses source IP **`127.0.0.1`**, and needs no gateway (**`0.0.0.0`**). This is exactly the consultation Scapy performs to pick an egress interface before sending.

### The default interface `conf.iface`

```python
<NetworkInterface eth0 [UP+BROADCAST+RUNNING+SLAVE]>
```

`conf.iface` (`scapy/config.py:L734`) is the default interface used for sending/sniffing when none is given — here **`eth0`**. Per-packet routing for an `IP()`-rooted send is resolved by `IP.route` (`scapy/layers/inet.py:L559`).

## 4. Sniffing & dissection

### Capturing the frame

The emitted frames are captured with `sniff()` (`scapy/sendrecv.py:L1308`) or its threaded form `AsyncSniffer` (`scapy/sendrecv.py:L981`). In the canonical Docker image `libpcap` is present, so a BPF `filter=` compiles and runs (Section 6); the round-trip probe nonetheless scopes the capture with `count`/`lfilter` over native `AF_PACKET` (no BPF filter needed) to keep it self-contained.

The round-trip probe started `AsyncSniffer(iface="lo", count=1, lfilter=<TCP in pkt and pkt[TCP].dport == 12345>)`, then sent a **marked** frame on `lo` with `sendp()` — `Ether(dst="00:11:22:33:44:55", src="66:77:88:99:aa:bb")/IP(dst="127.0.0.1")/TCP(dport=12345)` — and joined the sniffer. Observed:

```python
captured count = 1
type(received).__name__ = Ether
```

The capture returned exactly one packet, and Scapy reconstructed its top layer as an **`Ether`** object.

### The received packet is FULLY populated

Unlike the pre-send in-memory packet (whose `show()` had `None` computed fields in Section 2), the sniffed packet is fully resolved:


The received `show()` confirms the same, with every computed field populated:

### KEY CONTRAST — why the sniffed packet is fully populated

Cause → effect: the pre-send packet held Python defaults with computed fields unresolved (`None`), but the sniffed packet is instantiated **from raw wire bytes**, so Scapy *parses* every field out of the bytes. The parse path is `dissect()` (`scapy/packet.py:L1049`) → `do_dissect()` (`scapy/packet.py:L1002`) → `guess_payload_class()` (`scapy/packet.py:L1062`), which walks the `bind_layers` table to choose the next layer class:

- Ether → IP because the EtherType is `0x0800`.
- IP → TCP because the IP `proto` is `6`.
- When no binding matches, it falls back to `conf.raw_layer` (`Raw`) via `default_payload_class` (`scapy/packet.py:L1090`).

That reconstruction from bytes is exactly why a received packet shows fully-resolved layers and computed fields, while the in-memory pre-send packet does not.

### CHECKSUM PAIRING — each checksum paired with the packet that produced it

The checksums must not be mixed between packets:

- **Marked** packet (`dport=12345`): TCP `chksum = 0x6193`. The full verbatim `repr` of the sniffed marked frame (`dport=12345` and `chksum=0x6193` both visible in the TCP layer):
  ```python
  <Ether  dst=00:11:22:33:44:55 src=66:77:88:99:aa:bb type=IPv4 |<IP  version=4 ihl=5 tos=0x0 len=40 id=1 flags= frag=0 ttl=64 proto=tcp chksum=0x7ccd src=127.0.0.1 dst=127.0.0.1 |<TCP  sport=ftp_data dport=12345 seq=0 ack=0 dataofs=5 reserved=0 flags=S window=8192 chksum=0x6193 urgptr=0 |>>>
  ```
- **Default** packet (`dport=http`, i.e. 80) from Section 2: TCP `chksum = 0x917c`.
  ```python
  chksum    = 0x917c
  ```
  Cause → effect: the TCP checksum covers the destination port (among other fields), so changing `dport` from `80` to `12345` changes the TCP checksum from `0x917c` to `0x6193`.
- IP `chksum = 0x7ccd` is **identical** in both packets, because the IP header fields (version, ihl, tos, len, id, flags, frag, ttl, proto, src, dst) are the same in both — the differing port lives in the TCP header, which the IP checksum does not cover.

### Session / reassembly classes

Scapy's sniffing can run through a session object that reassembles traffic. The default is `DefaultSession` (`scapy/sessions.py:L32`); `IPSession` (`scapy/sessions.py:L114`) defragments IP on the fly, and `TCPSession` (`scapy/sessions.py:L223`) reassembles certain TCP streams. **(inferred)** Their internal defragmentation/reassembly behavior is described from reading these classes; the round-trip above used the default single-packet capture and did not exercise IP defragmentation or TCP stream reassembly.

## 5. Summary

Tracing the exact packet `Ether()/IP()/TCP()` from construction to capture, Scapy reveals a consistent build → send → sniff story, each step backed by the observed output above:

- **Build/display.** The `/` operator (`__div__`, `scapy/packet.py:L596`) stacks layers and applies bindings, visible in the `repr` progression as `type=IPv4` on Ether and `proto=tcp` on IP. `summary()` names the defaults (`ftp_data`→`http`, flag `S`), and `command()` echoes the reconstructable `Ether()/IP()/TCP()`.
- **Computed fields are deferred.** The in-memory packet leaves length/checksum fields unresolved (`show()` shows IP `ihl/len/chksum` and TCP `dataofs/chksum` as `None`) until `build()`/`post_build()` (`scapy/packet.py:L758`) fills them — which is why `show2()`, `hexdump()`, and `bytes()` reveal IP `ihl=5 len=40 chksum=0x7ccd`, TCP `dataofs=5 chksum=0x917c`, and a total length of `54` bytes.
- **Send/route.** `sendp()` (`scapy/sendrecv.py:L452`) puts the 54-byte Layer-2 frame on the interface chosen from `conf.route` (for `127.0.0.1` that resolves to `('lo', '127.0.0.1', '0.0.0.0')`), while the common emitter `__gen_send` (`scapy/sendrecv.py:L332`) prints one `.` per packet and then `Sent N packets.`. `send()` (`scapy/sendrecv.py:L422`) is the Layer-3 counterpart.
- **Sniff/dissect.** Capturing with `sniff`/`AsyncSniffer` recovers the frame, and `dissect()`/`guess_payload_class()` (`scapy/packet.py:L1049`, `L1062`) reconstruct Ether/IP/TCP from raw bytes — so the received packet is fully populated (e.g. the marked packet's TCP `chksum=0x6193`), in direct contrast to the unresolved pre-send packet.

In short: Scapy defers computed fields in memory and resolves them at build time; routing is consulted from `conf.route` before transmission; and dissection rebuilds a complete, fully-typed packet from the raw bytes seen on the wire.
