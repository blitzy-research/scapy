## Overview — the two-stage matching model

Scapy's `sr()`-family functions (`sr`, `sr1`, `srp`, …) match received replies to sent requests in **two stages**, implemented by the `SndRcvHandler` engine in `scapy/sendrecv.py`. Understanding this model is the foundation for every question below, because both stages are driven by two per-packet methods — `hashret()` and `answers()`.

**Stage 1 — bucket by hash (an O(1) index).** As each packet is sent, it is stored in a dictionary keyed by its `hashret()` value:

- `self.hsent = {}` at `scapy/sendrecv.py:168`
- `self.hsent.setdefault(p.hashret(), []).append(p)` at `scapy/sendrecv.py:244`

`hashret()` returns a `bytes` value designed to be **identical for a request and its expected answer**, so the dictionary groups together every sent packet that could plausibly be answered by a reply hashing to the same key.

**Stage 2 — confirm by `answers()` (the authoritative field-level test).** When a packet is received, its own `hashret()` is used to look up the candidate bucket, and each candidate is then confirmed with `answers()`:

- `h = r.hashret()` at `scapy/sendrecv.py:276`
- `if h in self.hsent:` at `scapy/sendrecv.py:277`
- `hlst = self.hsent[h]` at `scapy/sendrecv.py:278`
- `for i, sentpkt in enumerate(hlst):` at `scapy/sendrecv.py:279`
- `if r.answers(sentpkt):` at `scapy/sendrecv.py:280`

So `hashret()` is the **fast bucket index** and `answers()` is the **definitive confirmation**. A reply is accepted only if its hash lands in a sent packet's bucket *and* `answers()` returns truthy for that specific sent packet.

**Recursive per-layer delegation.** Both methods are defined on the base `Packet` class and then overridden per layer. The base implementations delegate to the payload:

- `Packet.hashret` at `scapy/packet.py:1215`, whose body is `return self.payload.hashret()` at `scapy/packet.py:1219` — each layer hands the hash computation down to the next layer.
- `Packet.answers` at `scapy/packet.py:1221`: it returns `self.payload.answers(other.payload)` at `scapy/packet.py:1225` **only when** `other.__class__ == self.__class__` (`scapy/packet.py:1224`), otherwise `return 0` at `scapy/packet.py:1226`.

The ICMP-error path overrides this delegation so that, instead of walking straight down its own payload, the `IP`/`ICMP` layers **redirect into the embedded original datagram** carried inside the ICMP error. That redirection is the crux of Q1 and Q2, and every subsequent question builds on it.

## Q1 — Matching strategy: Scapy extracts & compares the EMBEDDED original packet

**Restatement.** When an ICMP echo request is sent to an unreachable host and an ICMP *destination-unreachable* error returns, how does Scapy decide the error matches the original request — does it extract the original packet embedded inside the ICMP error payload and compare fields, or does it use a different strategy?

**Answer.** Scapy re-parses the **embedded original datagram** carried in the ICMP error payload and compares *its* fields — not the router's outer IP header. The governing code:

- `IP.answers` is defined at `scapy/layers/inet.py:583`. The ICMP-error guard is `(self.proto == socket.IPPROTO_ICMP) and isinstance(self.payload, ICMP) and (self.payload.type in [3, 4, 5, 11, 12])` at `scapy/layers/inet.py:600-602`, annotated with the comment `# ICMP error message` at `scapy/layers/inet.py:603`. When that guard matches, it **delegates to the embedded datagram** with `return self.payload.payload.answers(other)` at `scapy/layers/inet.py:604`. Note that `self.payload.payload` is the datagram *quoted inside* the ICMP error, so the comparison is against the embedded copy, not the error router's outer header.
- The embedded datagram is auto-classified as `IPerror` by `ICMP.guess_payload_class`, defined at `scapy/layers/inet.py:1000`: `if self.type in [3, 4, 5, 11, 12]:` at `scapy/layers/inet.py:1001` returns `IPerror` at `scapy/layers/inet.py:1002`.
- The actual field comparison is performed by `IPerror.answers`, defined at `scapy/layers/inet.py:1016`; the embedded transport layers are compared by `TCPerror.answers` (`scapy/layers/inet.py:1043`), `UDPerror.answers` (`scapy/layers/inet.py:1066`), and `ICMPerror.answers` (`scapy/layers/inet.py:1082`).
- Base delegation is provided by `Packet.answers` at `scapy/packet.py:1221`.

**Setup code:**

```python
from scapy.all import IP, ICMP, conf
from scapy.layers.inet import IPerror, ICMPerror
req = IP(src="10.0.0.1", dst="10.0.0.2", id=0x1234)/ICMP(type=8, id=0x1234, seq=7)
err = IP(bytes(IP(src="10.0.0.9", dst="10.0.0.1")/ICMP(type=3, code=1)/bytes(req)))
print("IPerror in err? %s | ICMPerror in err? %s" % (IPerror in err, ICMPerror in err))
print("err.answers(req) = %d" % err.answers(req))
```

**Observed output:**

```text
IPerror in err? True | ICMPerror in err? True
err.answers(req) = 1
```

**Rationale.** The `IP(bytes(...))` round-trip forces Scapy to re-dissect the embedded copy into the `IPerror`/`ICMPerror` "citation" chain — confirmed by `IPerror in err? True` and `ICMPerror in err? True`. `IP.answers` sees the outer type-3 error and delegates via `self.payload.payload.answers(other)` (`scapy/layers/inet.py:604`), so the match (`err.answers(req) = 1`) is decided by comparing the *embedded* original datagram's fields against the request, not the error router's outer header. This confirms the strategy is embedded-packet extraction and field comparison, not (for example) matching on the error router's source address.

## Q2 — Hashing: the error's hash EQUALS the original request's hash

**Restatement.** When Scapy processes an ICMP error carrying a copy of the original IP header plus partial payload, what hash value does it generate for matching, and how does that hash relate to the hash of the original outgoing packet?

**Answer.** `IP.hashret` applies the **same delegation** as `IP.answers`, hashing the embedded datagram, so the ICMP error's `hashret()` is **byte-identical** to the request's — which is exactly why the error lands in the same `self.hsent` bucket during Stage 1. The governing code:

- `IP.hashret` is defined at `scapy/layers/inet.py:568`; the ICMP-error guard is at `scapy/layers/inet.py:569-571`, and it delegates with `return self.payload.payload.hashret()` at `scapy/layers/inet.py:572`.
- `ICMP.hashret` is defined at `scapy/layers/inet.py:986`; its guard `if self.type in icmp_id_seq_types:` is at `scapy/layers/inet.py:987`, and it packs `struct.pack("HH", self.id, self.seq) + self.payload.hashret()` at `scapy/layers/inet.py:988`. The format `"HH"` uses **native (little-endian on x86) byte order**, which is why `id=0x1234` serializes as `3412` and `seq=0x0007` serializes as `0700` in the hash below.
- `icmp_id_seq_types = [0, 8, 13, 14, 15, 16, 17, 18, 37, 38]` at `scapy/layers/inet.py:949` — type `8` (echo request) is in this list, so its `id`/`seq` are hashed.
- Base delegation is `Packet.hashret` at `scapy/packet.py:1215`. Two-stage bucketing occurs at `scapy/sendrecv.py:244` (store) and `scapy/sendrecv.py:276-280` (lookup + confirm).

**Setup code** (continues from Q1's `req`/`err`):

```python
print("req.hashret() = %s" % req.hashret().hex())
print("err.hashret() = %s" % err.hashret().hex())
print("HASHES EQUAL?  %s" % (req.hashret() == err.hashret()))
```

**Observed output:**

```text
req.hashret() = 000000030134120700
err.hashret() = 000000030134120700
HASHES EQUAL?  True
```

**Rationale.** Decode the 9 bytes: `src ⊕ dst` = `00000003` (the XOR of `10.0.0.1` and `10.0.0.2`), the protocol byte `01` (ICMP), then `ICMP.hashret` (`scapy/layers/inet.py:988`) packs `id=0x1234` and `seq=0x0007` in host/little-endian order as `3412` and `0700`. Because the embedded `IPerror`/`ICMPerror` reconstruct the same fields as the outgoing request, the two hashes are byte-identical (`HASHES EQUAL? True`). Consequently the error lands in the same `self.hsent` bucket (`scapy/sendrecv.py:244`, `scapy/sendrecv.py:277`) *before* `answers()` confirms it (`scapy/sendrecv.py:280`) — i.e., the hash is what routes the error to the correct request in Stage 1, and `answers()` (Q1) provides the Stage-2 confirmation.


## Q3 — Tolerance to mutation: subtle TTL/checksum changes still match

**Restatement.** If the embedded original packet is subtly modified (for example, a changed TTL or checksum), does Scapy still consider it a valid match, or does matching fail?

**Answer.** It **still matches**. `IPerror.answers` (`scapy/layers/inet.py:1016`) compares **only** source address, destination address, IP identification, and protocol — TTL and checksum are never examined. The relevant lines:

- `test_IPsrc = not conf.checkIPsrc or self.src == other.src` at `scapy/layers/inet.py:1021`
- `test_IPdst = self.dst == other.dst` at `scapy/layers/inet.py:1022`
- `test_IPid = not conf.checkIPID or self.id == other.id` at `scapy/layers/inet.py:1025`
- `test_IPproto = self.proto == other.proto` at `scapy/layers/inet.py:1029`
- combined check `if not (test_IPsrc and test_IPdst and test_IPid and test_IPproto):` at `scapy/layers/inet.py:1031`
- delegation to the embedded payload `return self.payload.answers(other.payload)` at `scapy/layers/inet.py:1034`

There is no reference to `ttl` or `chksum` anywhere in `IPerror.answers`, so mutating those fields cannot change the outcome.

**Setup code** (continues from Q1's `err`/`req`):

```python
err2 = IP(bytes(err))
err2[IPerror].ttl = 3
err2[IPerror].chksum = 0xDEAD
err2[ICMPerror].chksum = 0xBEEF
print("mutated embedded ttl=%d chksum=%d inner_icmp_chksum=%d" % (
    err2[IPerror].ttl, err2[IPerror].chksum, err2[ICMPerror].chksum))
print("err2.answers(req) = %d" % err2.answers(req))
```

**Observed output:**

```text
mutated embedded ttl=3 chksum=57005 inner_icmp_chksum=48879
err2.answers(req) = 1
```

**Rationale.** The values `0xDEAD = 57005` and `0xBEEF = 48879` confirm the embedded TTL and both checksums were actually mutated, yet `answers()` still returns `1`, because `IPerror.answers` never inspects TTL or checksum — only `src`/`dst`/`id`/`proto` and then the embedded payload (`scapy/layers/inet.py:1021-1034`). This tolerance is deliberate: routers legitimately decrement the TTL and recompute checksums on the quoted datagram, so requiring those fields to match would reject genuine ICMP errors.

## Q4 — Configurable strictness: source-IP and TCP seq/ack

**Restatement.** What runtime behavior results from toggling the configuration flags governing (a) source-IP validation and (b) TCP sequence/acknowledgment verification inside error packets? Does toggling change which packets qualify as valid responses, and what are the trade-offs of strict matching versus tolerating real-world variation?

**Answer.** Two independent flags gate this strictness:

- `conf.checkIPsrc` gates the embedded **source-address** comparison in `IPerror.answers`: `test_IPsrc = not conf.checkIPsrc or self.src == other.src` at `scapy/layers/inet.py:1021`. The *same* flag also gates the embedded **port** comparison in `TCPerror.answers` (`if conf.checkIPsrc:` at `scapy/layers/inet.py:1046`) and `UDPerror.answers` (`if conf.checkIPsrc:` at `scapy/layers/inet.py:1069`). Its default is `True` (`scapy/config.py:751`).
- `conf.check_TCPerror_seqack` gates the embedded TCP **sequence/acknowledgment** comparison in `TCPerror.answers`: the guard `if conf.check_TCPerror_seqack:` is at `scapy/layers/inet.py:1050`, comparing `seq` at `scapy/layers/inet.py:1051-1053` and `ack` at `scapy/layers/inet.py:1054-1056`. Its default is `False` (`scapy/config.py:758`).

**Setup code** (continues from Q1's `req`):

```python
from scapy.all import TCP
# error whose embedded citation has a NAT-rewritten src (192.168.1.1 vs 10.0.0.1)
err_nat = IP(bytes(IP(src="10.0.0.9", dst="10.0.0.1")/ICMP(type=3, code=1) /
                   bytes(IP(src="192.168.1.1", dst="10.0.0.2", id=0x1234)/ICMP(type=8, id=0x1234, seq=7))))
conf.checkIPsrc = True
print("checkIPsrc=True  -> err.answers(req)=%d" % err_nat.answers(req))
conf.checkIPsrc = False
print("checkIPsrc=False -> err.answers(req)=%d" % err_nat.answers(req))
conf.checkIPsrc = True  # restore default

# TCP error with a different embedded seq (9999 vs 1000)
treq = IP(src="10.0.0.1", dst="10.0.0.2")/TCP(sport=1234, dport=80, seq=1000, ack=0)
terr = IP(bytes(IP(src="10.0.0.9", dst="10.0.0.1")/ICMP(type=3, code=3) /
                bytes(IP(src="10.0.0.1", dst="10.0.0.2")/TCP(sport=1234, dport=80, seq=9999, ack=0))))
conf.check_TCPerror_seqack = False
print("check_TCPerror_seqack=False -> terr.answers(treq)=%d" % terr.answers(treq))
conf.check_TCPerror_seqack = True
print("check_TCPerror_seqack=True  -> terr.answers(treq)=%d" % terr.answers(treq))
conf.check_TCPerror_seqack = False  # restore default
```

**Observed output:**

```text
checkIPsrc=True  -> err.answers(req)=0
checkIPsrc=False -> err.answers(req)=1
check_TCPerror_seqack=False -> terr.answers(treq)=1
check_TCPerror_seqack=True  -> terr.answers(treq)=0
```

**Rationale + security framing.** Toggling each flag flips the outcome, so it **does** change which packets qualify as valid responses. With `checkIPsrc=True`, the NAT-rewritten embedded source (`192.168.1.1` vs the request's `10.0.0.1`) fails `test_IPsrc`, so the error is rejected (`err.answers(req)=0`); with `checkIPsrc=False` the source is ignored and the error matches (`err.answers(req)=1`). Symmetrically, `check_TCPerror_seqack=False` (default) ignores the differing embedded sequence number (`9999` vs `1000`) and matches (`terr.answers(treq)=1`), while `check_TCPerror_seqack=True` enforces it and rejects (`terr.answers(treq)=0`).

The trade-off is **fidelity versus robustness**. *Strict* checking rejects spoofed or corrupted citations (fewer false positives — an attacker cannot forge a matching error as easily), but *tolerant* defaults accommodate real-world variation and avoid false negatives on legitimate errors: a NAT device may rewrite the embedded original datagram's source address (RFC 3022 permits exactly this), and many stacks quote an inaccurate or truncated seq/ack in the citation. That is why `checkIPsrc` defaults to `True` (the embedded source is usually trustworthy and is a cheap, valuable check) while `check_TCPerror_seqack` defaults to `False` (seq/ack inside citations is frequently unreliable, so enforcing it would reject genuine errors).


## Q5 — IP-ID byte-swap tolerance

**Restatement.** Sending a packet with a specific IP identification value and receiving an ICMP error whose embedded IP header carries a *different, byte-swapped* ID is sometimes still accepted as a match. Under what exact conditions does this byte-order tolerance apply, and what numeric transformation relates the original ID to the accepted alternative?

**Answer.** `IPerror.answers` accepts a citation whose IP ID is the **byte-swapped** form of the original, computed via `socket.htons()`, gated on `conf.checkIPID`. The exact lines:

- `# Check if IP ids match` at `scapy/layers/inet.py:1024`
- `test_IPid = not conf.checkIPID or self.id == other.id` at `scapy/layers/inet.py:1025`
- `test_IPid |= conf.checkIPID and self.id == socket.htons(other.id)` at `scapy/layers/inet.py:1026`

The numeric transformation is a **16-bit byte swap**: `socket.htons()` exchanges the two bytes of the 16-bit value, so `0x1234 → 0x3412`. The default is `conf.checkIPID = False` (`scapy/config.py:748`).

**Setup code** (continues from Q1's `req`):

```python
import socket
print("socket.htons(0x1234) = 0x%04x (=%d)" % (socket.htons(0x1234), socket.htons(0x1234)))
# embedded IP id = 0x3412 (byte-swapped) vs original 0x1234; inner ICMP id kept 0x1234
err_swap = IP(bytes(IP(src="10.0.0.9", dst="10.0.0.1")/ICMP(type=3, code=1) /
                    bytes(IP(src="10.0.0.1", dst="10.0.0.2", id=0x3412)/ICMP(type=8, id=0x1234, seq=7))))
for v in (0, 1, 2):
    conf.checkIPID = v
    print("checkIPID=%d -> err.answers(req)=%d" % (v, err_swap.answers(req)))
conf.checkIPID = False  # restore default
```

**Observed output:**

```text
socket.htons(0x1234) = 0x3412 (=13330)
checkIPID=0 -> err.answers(req)=1
checkIPID=1 -> err.answers(req)=1
checkIPID=2 -> err.answers(req)=1
```

**Rationale + ANOMALY (reported exactly; documented, not fixed).** The exact conditions are:

- With **`checkIPID=0`** (the default) the ID is **not checked at all**: `not conf.checkIPID` is `True` in `test_IPid` at `scapy/layers/inet.py:1025`, so the citation matches regardless of its ID (`err.answers(req)=1`).
- With **`checkIPID=1`** the **byte-swapped** value is tolerated: the clause at `scapy/layers/inet.py:1026` (`test_IPid |= conf.checkIPID and self.id == socket.htons(other.id)`) accepts `self.id == socket.htons(other.id)`. This is a documented workaround for stacks that byte-swap the ID — the config comment at `scapy/config.py:745-746` reads "if 1, checks that they either are equal or byte swapped equals (bug in some IP stacks)". Here the embedded ID `0x3412` equals `socket.htons(0x1234)`, so it matches (`err.answers(req)=1`).
- With **`checkIPID=2`** the config comment at `scapy/config.py:747` states it should "strictly checks that they are equals" — **yet the byte-swapped value STILL matches** (`err.answers(req)=1`). This is an **anomaly**: because Python evaluates `2 and X` to `X` (any non-zero integer is truthy), the byte-swap clause at `scapy/layers/inet.py:1026` remains active for value `2` as well, so `checkIPID=2` behaves identically to `checkIPID=1` rather than performing the documented strict-equality check.

Per the read-only mandate, this discrepancy between the documented intent (`scapy/config.py:747`) and the observed runtime behavior is **documented here exactly as observed, and is not corrected** — no source change is made.

## Q6 — RFC 4884 extensions: structure changes, match outcome does not

**Restatement.** When an ICMP error exceeds a size threshold and carries additional structured data beyond the embedded original packet, does loading Scapy's extension parsing alter the packet structure in a way that changes whether the response is considered a valid match?

**Answer.** Loading `load_contrib("icmp_extensions")` reclassifies trailing `Padding` into a structured `ICMPExtensionHeader`/`ICMPExtensionMPLS`, but the **match outcome is unchanged** — `answers()` stays `1` and the hashes stay equal in both cases. RFC 4884 parsing lives in the contrib module `scapy/contrib/icmp_extensions.py`, which must be **explicitly loaded** and which monkey-patches a `post_dissection` handler onto the error classes:

- `def ICMPExtension_post_dissection(self, pkt):` at `scapy/contrib/icmp_extensions.py:67`; its comment (paraphrasing RFC 4884 §5.2, "if the ICMP packet length is >144 then ICMP extensions start at byte 137") is at `scapy/contrib/icmp_extensions.py:68-69`.
- The IPv4 guard `pkt[ICMP].type in [3, 11, 12]` is at `scapy/contrib/icmp_extensions.py:77` and the size threshold `pkt.len > 144` is at `scapy/contrib/icmp_extensions.py:78`.
- The extension bytes are taken at `bytes = pkt[ICMP].build()[136:]` at `scapy/contrib/icmp_extensions.py:79` (offset `136` = the 137th octet).
- Checksum validation: `ieh = ICMPExtensionHeader(bytes)` at `scapy/contrib/icmp_extensions.py:93`; if `checksum(ieh.build())` is non-zero the handler bails (`return  # failed`) — the check is at `scapy/contrib/icmp_extensions.py:94`. On success it reclassifies by truncating the padding at `lastlayer.load = lastlayer.load[:-len(ieh)]` (`scapy/contrib/icmp_extensions.py:97`) and attaching the parsed header with `lastlayer.add_payload(ieh)` (`scapy/contrib/icmp_extensions.py:98`).
- `class ICMPExtensionHeader` is at `scapy/contrib/icmp_extensions.py:36` (fields `version`/`reserved`/`chksum` at `scapy/contrib/icmp_extensions.py:38-40`); its `post_build` at `scapy/contrib/icmp_extensions.py:44-48` computes `checksum()` over **only** the 4-byte header (it excludes any appended objects).
- `class ICMPExtensionMPLS` is at `scapy/contrib/icmp_extensions.py:101`; the monkey-patch onto `ICMPerror`/`TCPerror`/`UDPerror` is at `scapy/contrib/icmp_extensions.py:176-178` (with the IPv6 error classes at `scapy/contrib/icmp_extensions.py:180-181`), and `bind_layers(ICMPExtensionHeader, ICMPExtensionMPLS, classnum=1, classtype=1)` is at `scapy/contrib/icmp_extensions.py:186`. The `MPLS` layer itself is `class MPLS(Packet)` at `scapy/contrib/mpls.py:29`.
- **External grounding (RFC 4884).** RFC 4884 specifies that when an ICMP Extension Structure is appended, the "original datagram" field MUST contain at least **128 octets** (zero-padded to 128 if the original was shorter), and ICMPv4 repurposes a previously reserved octet as a length attribute. The 144-octet threshold decomposes as 8 (the first two ICMPv4 words) + 128 (the original datagram) + 4 (the ICMP Extension Header) + 4 (one ICMP Object header). This is cited as an external reference (RFC 4884), not a `file:line`.

**Setup code** (note the checksum-patch recipe and the two-process requirement):

```python
# BUILD (one process): the ICMPExtensionHeader checksum covers only its 4-byte header,
# so build with chksum=0 then patch bytes [2:4] with a checksum over the WHOLE structure.
import struct
from scapy.all import IP, ICMP, UDP, Raw
from scapy.contrib.icmp_extensions import ICMPExtensionHeader, ICMPExtensionMPLS
from scapy.contrib.mpls import MPLS
from scapy.utils import checksum
orig = IP(src="10.0.0.1", dst="10.0.0.2", id=0x1234)/UDP(sport=1234, dport=53)/(b"X"*40)
orig_128 = bytes(orig)[:128].ljust(128, b"\x00")           # RFC 4884: >=128 octets, zero-padded
raw_ext = bytes(ICMPExtensionHeader(version=2, chksum=0) /
                ICMPExtensionMPLS(classnum=1, classtype=1, stack=[MPLS(label=16, ttl=255)]))
ck = checksum(raw_ext)
ext_bytes = raw_ext[:2] + struct.pack("!H", ck) + raw_ext[4:]
assert checksum(ext_bytes) == 0                            # verified True
err = IP(src="10.0.0.9", dst="10.0.0.1")/ICMP(type=3, code=3)/Raw(orig_128 + ext_bytes)
# outer IP.len == 168 (> 144); serialize err to hex and dissect in TWO SEPARATE processes:

# DISSECT (separate process per mode; 'with' calls load_contrib FIRST):
#   load_contrib("icmp_extensions") monkey-patches the error classes GLOBALLY,
#   so 'without' and 'with' MUST be different processes.
pkt = IP(bytes(err))
print([l.__name__ for l in pkt.layers()])
print("pkt.answers(orig) = %d ; hashret equal? %s" % (pkt.answers(orig), pkt.hashret() == orig.hashret()))
```

**Observed output (from two separate processes):**

```text
WITHOUT load_contrib: layers = ['IP', 'ICMP', 'IPerror', 'UDPerror', 'Raw', 'Padding']
                      pkt.answers(orig) = 1 ; hashret equal? True
WITH load_contrib:    layers = ['IP', 'ICMP', 'IPerror', 'UDPerror', 'Raw', 'Padding', 'ICMPExtensionHeader', 'ICMPExtensionMPLS']
                      pkt.answers(orig) = 1 ; hashret equal? True
```

**Rationale.** Loading the extension parser reclassifies the trailing `Padding` into a structured `ICMPExtensionHeader`/`ICMPExtensionMPLS` (the layer list grows by two entries), but `answers()` stays `1` and the hashes stay equal — because matching operates on the **embedded original datagram**, whose parse boundary is fixed by the embedded IP's own length field. The trailing extension bytes never participate in `IPerror.answers()` (which compares only `src`/`dst`/`id`/`proto`) or in `hashret()`. There is a reproduction subtlety worth noting: because `ICMPExtensionHeader.post_build` (`scapy/contrib/icmp_extensions.py:44-48`) checksums only its own 4-byte header, a naive `ICMPExtensionHeader(version=2)/ICMPExtensionMPLS(...)` build yields a non-zero checksum *over the whole structure*, so `checksum(ieh.build())` at `scapy/contrib/icmp_extensions.py:94` is non-zero and the handler bails — leaving the bytes as `Padding` (no reclassification). To trigger reclassification, the checksum computed over the **entire** extension structure must be patched into bytes `[2:4]` so that `checksum(ieh.build()) == 0`. (A `Raw`/`Padding` split may appear differently depending on construction; that detail is immaterial to the core claim — the reproduced run shows `Raw` then `Padding`.) The bottom line: RFC 4884 extension parsing changes the *structure* of the dissected packet but not the *match outcome*.
