### 1.1 Startup Flow

The Scapy interactive shell startup follows this call chain:

1. **`scapy/__main__.py`** (lines 13–15): When `python -m scapy` is executed, this module simply imports and calls `interact()`:
   ```python

   interact()
   ```

2. **`scapy/main.py:interact()`** (line 503): The main entry point. It:
   - Sets `conf.interactive = True` and `conf.color_theme = DefaultTheme()` (lines 513–514)
   - Parses command-line options (`-s`, `-c`, `-C`, `-p`, `-P`, `-H`, `-d`) at lines 526–551

   - Calls `init_session()` (line 560)

3. **`scapy/main.py:init_session()`** (line 415): Initializes the interactive session:
   - Optionally loads a saved session from a pickle file (lines 423–443)
   - Calls `_scapy_builtins()` (line 458) to load the full Scapy import surface
   - Stores the session in `builtins.__dict__["scapy_session"]` (line 462)

### 1.9 Thinking / Rationale

> **Why does the startup flow work this way?**
>
> The Scapy shell startup is designed as a layered pipeline: `__main__.py` provides the `python -m scapy` entry point, `interact()` handles CLI argument parsing and shell selection, `init_session()` manages persistent state (session save/restore), and `_scapy_builtins()` centralizes the import surface through `scapy/all.py`. This separation of concerns allows each stage to be independently tested and reused — for example, a library user can call `from scapy.all import *` without triggering the interactive console.
>
> The IPython detection at lines 567–587 follows a "try-import" pattern rather than checking for IPython's presence via `importlib.util.find_spec()`. This is a deliberate design choice: the actual `import IPython` call at line 571 not only checks for availability but also triggers IPython's initialization, ensuring that version-specific features (like traitlets Config) are accessible before the shell starts.
>
> The quote system adds personality to the startup experience. The `_prepare_quote()` function at line 476 implements word-wrapping with a `max_len=39` constraint for the non-mini banner, ensuring quotes fit alongside the ASCII art logo when rendered side-by-side via `zip_longest()`.
>
> The 48 default layers in `conf.load_layers` represent the core protocol stack that Scapy supports out of the box. Layers like `tls`, `http`, and `can` are excluded because they have heavy optional dependencies (`cryptography`, etc.) or are specialized for specific use cases. The dynamic addition of `tuntap` on Linux/BSD (line 149 of `scapy/arch/__init__.py`) demonstrates Scapy's platform-aware configuration model.

## Section 2 — Version Identification

### 2.1 The `_version()` Function

The Scapy version is computed at import time by the `_version()` function defined at lines 122–166 of `scapy/__init__.py`. It uses a chain of five resolution methods, tried in order, with each falling through on failure:

#### Method 0 — Environment Variable Override (lines 129–133)

```python
try:
    return os.environ['SCAPY_VERSION']
except KeyError:
    pass
```

If the `SCAPY_VERSION` environment variable is set, its value is returned directly. This is intended for external packaging systems (e.g., Linux distributions) that want to override the version without modifying the source.

#### Method 1 — VERSION File (lines 136–143)

```python
version_file = os.path.join(_SCAPY_PKG_DIR, 'VERSION')
try:
    with open(version_file, 'r') as fdsec:
        tag = fdsec.read()
    return tag
except FileNotFoundError:
    pass
```

Reads the `scapy/VERSION` file, which is generated during `sdist` and `wheel` builds by `setup.py`. This file is present in distributed packages but **not** in a git clone.

#### Method 2 — Git Archive Export-Subst (lines 146–149)

```python
try:
    return _version_from_git_archive()
except ValueError:
    pass
```

The `_version_from_git_archive()` function (line 38) parses the git archive substitution string `$Format:%ct %(describe:tags=true)$` (line 47). The `.gitattributes` file configures `scapy/__init__.py` with the `export-subst` attribute, so when `git archive` is used, git replaces this placeholder with the commit timestamp and describe output. If the archive is from a tagged commit, `_parse_tag()` is called; otherwise the commit timestamp is formatted as `YYYY.MM.DD`.

If the string still contains `"Format"`, the method raises `ValueError` (line 56) — this means the file was not created via `git archive`.

#### Method 3 — Git Describe (lines 152–155)

```python
try:
    return _version_from_git_describe()
except Exception:
    pass
```

The `_version_from_git_describe()` function (line 72) runs `git describe --tags --always --long` (line 114) from within the `scapy/` package directory. This requires a `.git` directory to be present (checked at line 97). If the result doesn't start with `v` (indicating upstream tags weren't fetched), it falls back to finding tags via `git rev-list --tags --max-count=1` (line 117). The output is parsed by `_parse_tag()`.

#### Fallback — File Modification Time (lines 158–163)

```python
try:
    d = datetime.datetime.utcfromtimestamp(os.path.getmtime(__file__))
    return d.strftime('%Y.%m.%d')
except Exception:
    pass
```

As a last resort, the modification time of `scapy/__init__.py` is used to generate a date-formatted version string like `2026.04.13`.

#### Last Resort (line 166)

```python
return '0.0.0'
```

If all methods fail, the version is `0.0.0`.

### 2.2 The `_parse_tag()` Function

Defined at lines 21–35 of `scapy/__init__.py`, this function converts a `git describe` tag into a PEP 440-compatible version:

```python
def _parse_tag(tag):
    match = re.match('^v?(.+?)-(\\d+)-g[a-f0-9]+$', tag)
    if match:
        return '%s.dev%s' % (match.group(1), match.group(2))
    else:
        raise ValueError('tag has invalid format')
```

- **Regex**: `^v?(.+?)-(\\d+)-g[a-f0-9]+$`
  - `v?` — optional `v` prefix
  - `(.+?)` — version number (non-greedy, e.g., `2.3.2`)
  - `-(\\d+)-` — number of commits after the tag
  - `g[a-f0-9]+$` — the git commit hash prefix
- **Example**: `v2.3.2-346-g164a52c075c8` → `2.3.2.dev346`

### 2.3 Version Assignment

At line 169:
```python

```

Both `VERSION` and `__version__` are set to the computed string. Then at lines 171–172:
```python
_tmp = re.search(r"([0-9]|\.[0-9])+", VERSION)
VERSION_MAIN = _tmp.group() if _tmp is not None else VERSION
```

`VERSION_MAIN` extracts just the numeric portion (e.g., `2026.04.13` from `2026.04.13`).

### 2.4 Integration with setuptools

At line 78 of `pyproject.toml`:
```toml

```

This tells setuptools to read the version dynamically from the `scapy.VERSION` attribute at build time, ensuring the package version always matches the runtime version.

### 2.5 Version at This Commit

At commit `0925ada4`, in this environment (editable install from a git clone), the version resolves to **`2026.04.13`**. The resolution path is:
- Method 0: No `SCAPY_VERSION` env var → skipped
- Method 1: No `scapy/VERSION` file in a git clone → skipped
- Method 2: The `$Format:...` string is not substituted in a non-archive checkout → raises ValueError → skipped
- Method 3: `git describe --tags --always --long` — in the Blitzy environment the git history may be shallow or tags may not be fully fetched, so this can raise an exception → skipped
- **Fallback**: `os.path.getmtime(__file__)` → formats the modification time of `scapy/__init__.py` as `2026.04.13`

### 2.6 Thinking / Rationale

> **Why does Scapy need five version resolution methods?**
>
> Scapy supports multiple distribution channels: PyPI wheels/sdists (Method 1), `git archive` tarballs from GitHub releases (Method 2), direct `git clone` checkouts (Method 3), and external packaging by Linux distributions (Method 0). Each channel provides version information differently — pip installs include a `VERSION` file, git archives have export-subst metadata, git clones have the full git history, and distro packages can set an environment variable. The chain tries each method in order of specificity and falls back gracefully.
>
> The fallback to file modification time (lines 158–163) is a pragmatic choice for environments where git metadata is unavailable (e.g., extracted tarballs without git info, Docker containers with shallow clones). The date-based format `YYYY.MM.DD` is PEP 440-compliant and provides a rough indication of when the code was obtained.
>
> The `_parse_tag()` function converts git's native `v2.3.2-346-g164a52c075c8` format to PEP 440's `2.3.2.dev346`, which pip and setuptools understand for dependency resolution. The `.devN` suffix correctly indicates a development version N commits ahead of the last release tag.

## Section 3 — ICMP Echo Request Construction

### 3.1 Construction Steps

Building `IP(dst="127.0.0.1")/ICMP()` involves two operations: constructing the IP layer with a user-supplied destination, then stacking the ICMP layer as a payload.

#### Step 1: `IP(dst="127.0.0.1")`

This calls `Packet.__init__()` at line 141 of `scapy/packet.py`:

1. **`init_fields()`** (line 162, defined at line 246): Deep-copies default values from `IP.fields_desc` into `self.default_fields`. Each field's default is stored by name (line 266: `default_fields[f.name] = copy.deepcopy(f.default)`).

2. **User-supplied fields** (lines 182–189): The keyword argument `dst="127.0.0.1"` is matched against `fields_desc` by name. At line 188, it is stored in `self.fields["dst"]` after conversion via `DestIPField.any2i()`.

At this point, the IP packet has `self.fields = {"dst": "127.0.0.1"}` and all other fields retain their defaults from `self.default_fields`.

#### Step 2: `/ ICMP()`

The `/` operator calls `Packet.__div__()` at line 596 of `scapy/packet.py`:

```python
def __div__(self, other):
    if isinstance(other, Packet):
        cloneA = self.copy()
        cloneB = other.copy()
        cloneA.add_payload(cloneB)
        return cloneA
```

(`__truediv__ = __div__` at line 607)

The `add_payload()` method (line 360) performs three key actions:
1. Sets `self.payload = ICMP()` (line 368)
2. Calls `payload.add_underlayer(self)` (line 369) to establish the bidirectional parent-child link
3. **Triggers `overload_fields`** (lines 370–373): Iterates `self.aliastypes` and checks if `IP` (or its aliases) is in `ICMP.overload_fields`. Because `bind_layers(IP, ICMP, frag=0, proto=1)` was registered at line 1112 of `scapy/layers/inet.py`, the ICMP class has `overload_fields[IP] = {"frag": 0, "proto": 1}`. This means `self.overloaded_fields` is set to `{"frag": 0, "proto": 1}`, causing the IP layer to automatically use `proto=1` (ICMP) and `frag=0`.

### 3.4 Field Categories

The fields of the constructed `IP(dst="127.0.0.1")/ICMP()` packet fall into four categories:

1. **User-supplied**: Only `dst="127.0.0.1"` was explicitly provided by the user. Everything else is automatic.

2. **Auto-populated defaults**: Static default values from `fields_desc`:
   - IP: `version=4`, `tos=0`, `id=1`, `flags=0`, `frag=0`, `ttl=64`, `options=[]`
   - ICMP: `type=8` (echo-request), `code=0`, `id=0`, `seq=0`

3. **Deferred (computed at build time)**: Fields with `None` defaults that are computed by `post_build()` from the assembled raw bytes:
   - IP: `ihl=None`, `len=None`, `chksum=None`
   - ICMP: `chksum=None`

4. **Auto-resolved at access time**:
   - `proto=1` (icmp): Set via `bind_layers(IP, ICMP, frag=0, proto=1)` at line 1112 of `scapy/layers/inet.py`, stored in `self.overloaded_fields`
   - `src="127.0.0.1"`: Resolved lazily by `SourceIPField.__findaddr()` (line 862 of `scapy/fields.py`) which calls `conf.route.route("127.0.0.1")` → returns `("lo", "127.0.0.1", "0.0.0.0")` → takes index `[1]` as the source address

### 3.5 Thinking / Rationale

> **Why do deferred fields exist?**
>
> Fields like `ihl`, `len`, and `chksum` cannot be computed until the entire packet (including payload) has been serialized into raw bytes. The IP header length (`ihl`) depends on the number of options, the total length (`len`) depends on the payload size, and the checksum (`chksum`) depends on the header's byte content. Setting these to `None` as defaults allows Scapy to compute them accurately at build time via `post_build()`, while still allowing users to override them with explicit values for testing purposes (e.g., crafting malformed packets).
>
> The `bind_layers()` mechanism is a declarative binding system: `bind_layers(IP, ICMP, frag=0, proto=1)` at line 1112 tells Scapy that when ICMP is used as a payload of IP, the IP fields `frag` and `proto` should automatically be set to 0 and 1, respectively. This is stored in the ICMP class's `overload_fields` dictionary and applied during `add_payload()` at lines 370–373 of `scapy/packet.py`. This eliminates the need for users to manually set `proto=1` every time they create an ICMP packet.
>
> The `SourceIPField` lazy resolution (line 862 of `scapy/fields.py`) is a key design feature: the source IP is not resolved until the field value is actually needed (via `i2m()` at line 879 or `i2h()` at line 885). This means that changing the destination address after construction will automatically update the source address, since it's re-resolved from the routing table each time.

| Aspect | `show()` | `show2()` |
|---|---|---|
| **State** | Pre-build (template) | Post-build (wire-ready) |
| **Deferred fields** | `None` | Computed values |
| **Trigger** | Direct field inspection | Build → dissect → inspect |
| **Use case** | See what the user specified | See what goes on the wire |
| **Performance** | Fast (no serialization) | Slower (full build + dissect cycle) |

### 4.6 Thinking / Rationale

> **Why does Scapy separate show() and show2()?**
>
> This design implements a lazy evaluation pattern. `show()` reveals the packet's logical state — what the user has explicitly set and what defaults are in place. `show2()` reveals the physical state — what bytes will actually be sent on the wire. This distinction is invaluable for debugging: if a packet behaves unexpectedly, comparing `show()` and `show2()` output immediately reveals whether the issue is in the user's specification or in Scapy's automatic field computation.
>
> The `show2()` implementation as `self.__class__(raw(self)).show()` is elegant: rather than building a separate "resolved view" mechanism, it simply builds the packet, then dissects it back from scratch. This guarantees that the displayed values are exactly what a remote receiver would parse, since the dissection path is the same one used for incoming packets.
>
> The lazy evaluation approach also means that a packet can be modified at any point before sending — fields like `chksum` are computed only at the last moment during `build()`, so changing the payload after construction doesn't leave stale checksums.

### 5.2 Socket Selection

An alternative is `L3RawSocket` (line 283 of `scapy/supersocket.py`):

- **Receiving**: `AF_PACKET/SOCK_RAW` (line 296)

**Container note**: In container environments, `L3PacketSocket` can yield 0 matched answers on the loopback interface (`lo`) because the `AF_PACKET` socket on loopback may not see the kernel-generated echo-reply. Using `L3RawSocket` or `conf.L3socket=L3RawSocket` provides more reliable loopback operation.

### 5.3 Routing Resolution

The routing is resolved via `conf.route.route("127.0.0.1")` (defined at line 146 of `scapy/route.py`):

1. The destination `"127.0.0.1"` is converted to a numeric address via `atol()` (line 174)
2. The routing table is scanned (line 176): for each route `(d, m, gw, i, a, me)`:
   - At lines 179–183: If the output address `a` matches the destination (`aa == atol_dst`), the route is added as a perfect local match with maximum netmask `0xffffffff` and metric 1:
     ```python

     ```
3. Result for `127.0.0.1`: **`("lo", "127.0.0.1", "0.0.0.0")`**
   - Interface: `lo` (loopback)
   - Output IP (source): `127.0.0.1`
   - Gateway: `0.0.0.0` (direct delivery, no gateway)

### 5.4 The Send/Receive Matching Engine

The `SndRcvHandler` class (line 100 of `scapy/sendrecv.py`) manages the bidirectional packet exchange:

#### Sending: `_sndrcv_snd()` (line 232)

For each packet `p` in the send queue:
1. Computes `p.hashret()` and stores the packet in `self.hsent[p.hashret()]` (line 244) — this builds a lookup table keyed by hash
2. Sends the packet via `self.pks.send(p)` (line 246)
3. Sleeps for `self.inter` seconds between packets (line 247)

#### Receiving: `_process_packet()` (line 270)

For each received packet `r`:
1. Computes `h = r.hashret()` (line 276)
2. Looks up `h` in `self.hsent` (line 277) — finds candidate sent packets
3. For each candidate `sentpkt`, calls `r.answers(sentpkt)` (line 280)
4. If a match is found, the pair `(sentpkt, r)` is added to `self.ans` (line 281)

#### ICMP-specific Matching

**`ICMP.hashret()`** (lines 986–989 of `scapy/layers/inet.py`):
```python
def hashret(self):
    if self.type in icmp_id_seq_types:
        return struct.pack("HH", self.id, self.seq) + self.payload.hashret()
    return self.payload.hashret()
```
For echo-request/reply (types 0 and 8, both in `icmp_id_seq_types`), the hash includes the `id` and `seq` fields.

**`ICMP.answers()`** (lines 991–998):
```python
def answers(self, other):
    if not isinstance(other, ICMP):
        return 0
    if ((other.type, self.type) in [(8, 0), (13, 14), (15, 16), (17, 18), (33, 34), (35, 36), (37, 38)] and
        self.id == other.id and
            self.seq == other.seq):
        return 1
    return 0
```
An ICMP echo-reply (type=0) answers an echo-request (type=8) when `(other.type, self.type) == (8, 0)` and the `id` and `seq` fields match.

### 5.5 Kernel Behavior on Loopback

When the ICMP echo-request reaches the kernel's network stack via the loopback interface:

1. The kernel recognizes the ICMP echo-request (type=8, code=0)
2. The kernel generates an ICMP echo-reply (type=0, code=0) with the same `id`, `seq`, and data payload
3. The kernel computes the ICMP checksum for the reply
4. The reply is delivered back through the loopback interface
5. Scapy's receive socket captures the reply and `SndRcvHandler._process_packet()` matches it

### 5.6 Expected Response

The response packet has:
- **IP layer**: `src=127.0.0.1`, `dst=127.0.0.1`, `proto=icmp`, `ttl=64`
- **ICMP layer**: `type=0` (echo-reply), `code=0`, `id=0x0`, `seq=0x0`, `chksum` kernel-computed

### 5.7 Thinking / Rationale

> **Why is loopback ICMP special?**
>
> On most systems, the loopback interface (`lo`) handles packets entirely within the kernel — packets never reach a physical NIC. For `AF_PACKET` sockets (used by `L3PacketSocket`), the kernel behavior on loopback can differ between systems: some kernels deliver both the sent packet and the reply to the `AF_PACKET` socket, while others only deliver one direction. In container environments with limited network namespaces, the `AF_PACKET` socket on `lo` may not see the kernel-generated echo-reply at all, resulting in 0 matched answers.
>
> The `L3RawSocket` alternative uses `PF_INET/SOCK_RAW` for sending, which operates at the IP layer rather than the link layer. This avoids the `AF_PACKET` loopback issue because the receive side still uses `AF_PACKET` but the send path goes through the standard IP stack, which more reliably triggers the kernel's ICMP echo handler.
>
> The `SndRcvHandler` matching engine at line 100 of `scapy/sendrecv.py` is hash-based for performance: `hashret()` produces a compact key that narrows down the candidate list, then `answers()` performs the semantic check. This two-level matching avoids O(n²) comparison of all sent packets against all received packets.
>
> The ICMP `answers()` check at line 994 is a tuple-based lookup in a list of `(request_type, reply_type)` pairs, covering all standard ICMP request/reply pairs: echo (8→0), timestamp (13→14), information (15→16), address-mask (17→18), and several extended types.

### 6.4 `IP.post_build()` — Deferred Field Computation

Defined at lines 539–551 of `scapy/layers/inet.py`:

```python
def post_build(self, p, pay):
    ihl = self.ihl
    p += b"\0" * ((-len(p)) % 4)  # pad IP options if needed
    if ihl is None:
        ihl = len(p) // 4
        p = chb(((self.version & 0xf) << 4) | ihl & 0x0f) + p[1:]
    if self.len is None:
        tmp_len = len(p) + len(pay)
        p = p[:2] + struct.pack("!H", tmp_len) + p[4:]
    if self.chksum is None:
        ck = checksum(p)
        p = p[:10] + chb(ck >> 8) + chb(ck & 0xff) + p[12:]
    return p + pay
```

Three computations happen in sequence:

#### IHL (Internet Header Length) — lines 540–544
- Pads the IP options to a 4-byte boundary (line 541)
- If `self.ihl is None`: computes `ihl = len(p) // 4` — the header length in 32-bit words
- Patches byte 0: `chb(((self.version & 0xf) << 4) | ihl & 0x0f)` — combines the 4-bit version and 4-bit IHL into the first byte
- For a standard header with no options: `20 // 4 = 5`, so `ihl = 5`

#### Total Length — lines 545–547
- If `self.len is None`: computes `tmp_len = len(p) + len(pay)` — IP header + payload
- Patches bytes 2–3 with `struct.pack("!H", tmp_len)` (big-endian unsigned short)
- For IP()/ICMP(): `20 + 8 = 28`

#### Checksum — lines 548–550
- If `self.chksum is None`: computes `ck = checksum(p)` — the one's complement checksum of the IP header
- Patches bytes 10–11 with the checksum bytes
- For the standard IP/ICMP packet: `0x7cde`

The function returns `p + pay` — the complete IP header concatenated with the payload.

### 6.8 Thinking / Rationale

> **What is the design philosophy behind IP header construction?**
>
> The IP class's `fields_desc` (lines 524–537 of `scapy/layers/inet.py`) declares the 13 fields of the IPv4 header in their wire-order layout, with each field specifying its name, default value, and serialization format. Three fields — `ihl`, `len`, and `chksum` — are intentionally defaulted to `None` to signal that they should be computed from the assembled raw bytes rather than specified statically.
>
> This design separates *what the user wants* (the logical packet specification) from *what goes on the wire* (the physical byte sequence). The `post_build()` override at line 539 acts as a "fixup" pass that computes derived values from the actual byte representation, ensuring correctness:
>
> - **IHL** must reflect the actual header length including options — it can't be known until all options are serialized
> - **Total length** must include the payload — which may itself be computed dynamically
> - **Checksum** must be computed over the final header bytes — any earlier computation would be invalidated by the IHL and length fixups
>
> The three computations in `post_build()` are ordered specifically: IHL first (because it modifies byte 0), then length (bytes 2–3), then checksum (bytes 10–11, computed over the entire header including the already-patched IHL and length).
>
> The `SourceIPField` lazy resolution (line 862 of `scapy/fields.py`) ensures that the source IP is always consistent with the current routing state. Unlike a static default, this dynamic resolution means that if a user changes `pkt.dst` after construction, the source IP will automatically adjust when the packet is built or displayed — no manual update required.
>
> The `bind_layers()` mechanism provides declarative protocol stacking without hardcoding parent-child relationships. By registering `bind_layers(IP, ICMP, frag=0, proto=1)`, the ICMP class doesn't need to know about IP — the binding is external and bidirectional. This is what makes Scapy's layering system composable and extensible: new protocols can be added without modifying existing classes.

### 7.5 Full Suite Behavior

Running the full Linux test suite (`-c ./test/configs/linux.utsc`) processes 190 test files sequentially. With `breakfailed: true` set in the configuration, execution within a file halts at the first failed test. This means that if an early file like `test/cert.uts` has failures (e.g., due to TLS layer preexec issues), subsequent tests in that file are skipped, but other files continue to be processed.

The `-K scanner` flag excludes automotive scanner tests that require specialized `python-can` hardware interfaces.

### 7.6 Thinking / Rationale

> **Why does Scapy use a custom test harness instead of pytest or unittest?**
>
> UTscapy's `.uts` file format is a domain-specific testing language designed for Scapy's unique needs. Each `.uts` file reads like an interactive Scapy session — test cases are written as sequences of Python statements with assertions, separated by `= <test_name>` headers. This format has several advantages:
>
> 1. **Readability**: Tests look like documentation — they show how Scapy is actually used, making them both tests and examples
> 2. **Keyword filtering**: Tests can be annotated with `~ <keywords>` (e.g., `~ ipv6`, `~ windows`, `~ root`) for platform-specific and capability-based filtering
> 3. **Campaign structure**: Test files are organized as "campaigns" where each `=` section is an independent test case, allowing granular pass/fail reporting
> 4. **Preexec support**: The `preexec` configuration in `.utsc` files allows automatic setup (e.g., `load_contrib("%name%")`) before running tests, eliminating boilerplate
>
> The `breakfailed: true` setting reflects a testing philosophy where cascading failures are undesirable — if a fundamental test fails, running dependent tests would produce noise rather than useful information. The `onlyfailed: true` setting keeps the output manageable when running hundreds of tests.
>
> The 16 regression.uts failures all share a common pattern: they depend on system tools (`tcpdump`, `tshark`, `libpcap`) or network capabilities (IPv6) that are absent in the container. This is expected and documented behavior — the `-N` (non-root) flag already excludes many privileged tests, but some tests for offline pcap analysis still require these tools to be installed.
