# How Scapy Decides Where to Send Packets — An Evidence-Backed Investigation

## Overview

This document onboards to the [Scapy](https://github.com/secdev/scapy) packet-manipulation
library directly from the in-repo checkout and empirically answers five questions about **how
Scapy decides where to send a packet** — which interface it picks, which MAC address it targets,
what happens on a repeated send, and where/how a send fails when there is no route.

Every behavioural claim is backed by output captured by **running the real code path inside the
user-pinned Docker image**, together with the exact command that produced it. The document is
organised as one section per question (Q0–Q4) and closes with a coverage pass.

### Task

Answer, with observed runtime evidence, the following:

- **Q0** — Set up and run Scapy from the repository and start the interactive session.
- **Q1** — When no interface is specified, how does Scapy choose the outgoing interface?
- **Q2** — Once an interface is chosen, how does Scapy know which MAC address to send to in order
  to reach an **external (off-link)** destination?
- **Q3** — If the **same packet is sent twice** in quick succession, is an ARP request emitted on
  both sends, or only once (a cache hit)?
- **Q4** — For a destination with **no route**, at what point does the send fail, and what is the
  exact error message?

## Q1 — Choosing the outgoing interface when none is specified

**Answer (short).** The interface is **not** a fixed default — it is **derived from the packet's
route**. When `iface` is not supplied, `send()` calls the private helper `_interface_selection()`
[scapy/sendrecv.py:616], which evaluates `next(packet.__iter__()).route()[0]`
[scapy/sendrecv.py:626] — i.e. element `[0]` of the packet's route tuple — and returns that, or
`conf.iface` only as a fallback [scapy/sendrecv.py:629]. For an `IP` packet, `route()` delegates to
`conf.route.route(dst)` [scapy/layers/inet.py:566], a longest-prefix-match lookup over Scapy's own
routing table [scapy/route.py:146]. For `dst=8.8.8.8` the observed tuple is
`('eth0', '172.17.0.2', '172.17.0.1')`, so the chosen interface is **`eth0`** (element `[0]`).

### Mechanism (source-derived — *inferred* from reading; confirmed by the run below)

- Entry: `send()` [scapy/sendrecv.py:422] → `_send()` [scapy/sendrecv.py:396] →
  `__gen_send()` [scapy/sendrecv.py:332]; the interface is resolved by
  `_interface_selection(iface, packet)` [scapy/sendrecv.py:616].
- Inside `_interface_selection`: `if iface is None:` [scapy/sendrecv.py:624] →
  `iff = next(packet.__iter__()).route()[0]` [scapy/sendrecv.py:626] →
  `return iff or conf.iface` [scapy/sendrecv.py:629]. If an `iface` *is* passed, it short-circuits to
  `return iface` [scapy/sendrecv.py:631].
- `packet.route()` for an `IP` packet is `IP.route()` [scapy/layers/inet.py:559], which returns
  `conf.route.route(self.dst)` [scapy/layers/inet.py:566].
- `conf.route.route(dst)` [scapy/route.py:146] performs the longest-prefix match and returns the
  3-tuple `(interface, outgoing_ip, gateway)` — the tuple ordering documented in this checkout at
  `doc/scapy/routing.rst:54`.

### Cause → effect

The interface is a **computed** value: Scapy performs a longest-prefix-match route lookup for the
destination and takes the interface bound to the winning route. `conf.iface` is consulted **only**
when the packet's own route cannot yield an interface (the `iff or conf.iface` fallback
[scapy/sendrecv.py:629]). So "which interface?" is answered by the routing table for *that
destination*, not by a global default.

## Q2 — Which MAC to send to for an external (off-link) destination

**Answer (short).** For an **off-link** destination Scapy does **not** ARP for the final IP — it
ARPs for the **next hop (the gateway)**. `getmacbyip()` [scapy/layers/l2.py:122] looks up the route,
and because the route to `8.8.8.8` has a **non-zero gateway** it executes `ip = gw`
[scapy/layers/l2.py:134-135] and issues an ARP `who-has` for the **gateway** address. The returned
MAC is the **gateway's** (`26:cf:e6:0d:86:0f`). The IP header still carries the final destination
`8.8.8.8`; only the Ethernet frame is addressed to the gateway's MAC.

### Mechanism (source-derived — *inferred* from reading; confirmed by the run below)

- On Linux the default L3 send socket is `L3PacketSocket` [scapy/config.py:647]; its `send()`
  [scapy/arch/linux.py:598] builds the Ethernet header, whose destination MAC is produced by the
  layer-2 resolver registered for IP — `inet_register_l3()` [scapy/layers/inet.py:1125] returns
  `getmacbyip(l3.dst)` [scapy/layers/inet.py:1126], wired at [scapy/layers/inet.py:1129-1130].
- `getmacbyip(ip)` [scapy/layers/l2.py:122]: looks up the route [scapy/layers/l2.py:131]; a
  loopback/broadcast destination short-circuits to the broadcast MAC [scapy/layers/l2.py:132-133];
  **if the route's gateway is non-zero it sets `ip = gw`** [scapy/layers/l2.py:134-135] (the gateway
  substitution); it then checks the ARP cache [scapy/layers/l2.py:137-139]; on a miss it sends
  `srp1(Ether(dst="ff:ff:ff:ff:ff:ff")/ARP(op="who-has", pdst=ip))` [scapy/layers/l2.py:141-148],
  stores the reply MAC in the cache [scapy/layers/l2.py:152-155], and returns it
  [scapy/layers/l2.py:155].

gateway's while the IP packet keeps `dst=8.8.8.8`. This is ordinary IP forwarding — the L3
destination is unchanged; only the L2 next-hop address is the gateway.

## Q3 — Repeated send: is ARP emitted twice, or once (cache hit)?

**Answer (short).** **Only once.** The first send resolves the gateway's MAC and stores it in
Scapy's ARP cache (120-second TTL); the second send — and any further sends within that TTL — hit
the cache and emit **no** new ARP `who-has`. Observed: across **2** sends there is exactly **1**
gateway `who-has`, reproduced identically in **5** fresh-process runs (distribution
`[1, 1, 1, 1, 1]`), and still exactly **1** across **10** sends in a separate run.

### Mechanism (source-derived — *inferred* from reading; confirmed by the runs below)

- The ARP cache is `_arp_cache = conf.netcache.new_cache("arp_cache", 120)`
  [scapy/layers/l2.py:118], created next to the comment "…entries expire after 120s"
  [scapy/layers/l2.py:117]. It is a `CacheInstance` [scapy/config.py:347] with a **120-second TTL**.
- Inside `getmacbyip()`, after the gateway substitution, a cache **hit** short-circuits and returns
  the cached MAC **without** issuing ARP [scapy/layers/l2.py:137-139]. On a **miss**, the resolved
  reply MAC is stored back into the cache [scapy/layers/l2.py:152-155]. So the ARP is a
  once-per-TTL cost, not a per-send cost.

### Observed — the same packet sent repeatedly (canonical `send()`)

The observation script sends `IP(dst="8.8.8.8")/ICMP()` `N` times in **one process** while an async
sniffer counts only gateway-targeted `who-has` frames (`op==1 and pdst==gateway`, so background
gratuitous ARPs are excluded, exactly as in Q2). `conf.verb = 0` silences `send()`'s progress dots
so the per-send cache/counter state is legible — `send()` remains the canonical path. Each `docker
run` is a fresh container ⇒ a fresh process ⇒ an empty ARP cache, which is why every run starts at
`cache=None`.

## Q4 — No route: where does the send fail, and what is the exact message?

**Answer (short).** A send to an unreachable destination **does not raise by default** — the
"failure" is a *soft* degradation, and there are **two distinct surfaces** with two different exact
messages:

1. **No route at all (Q4a).** `Route.route()` never raises; when nothing matches it (optionally)
   warns `No route found (no default route?)` [scapy/route.py:188-189] and returns the **loopback
   fallback** `('lo', '0.0.0.0', '0.0.0.0')` [scapy/route.py:190]. A following `send()` still reports
   `Sent 1 packets.` and does **not** raise. Its frame gets the broadcast MAC from `getmacbyip()`'s
   **silent loopback short-circuit** [scapy/layers/l2.py:132-133] — so in this case there is **no**
   "Using broadcast" message; the only text emitted is the route warning(s).
2. **A route exists but the on-link next hop can't be ARP-resolved (Q4b).** The "no destination MAC"
   surface is `DestMACField.i2h` [scapy/layers/l2.py:166-178]. By **default**
   (`conf.raise_no_dst_mac = False` [scapy/config.py:910]) it warns `Mac address to reach
   destination not found. Using broadcast.` [scapy/layers/l2.py:178] and broadcasts; **only** when
   `conf.raise_no_dst_mac = True` does it **raise** `ScapyNoDstMacException`
   [scapy/layers/l2.py:174-175], [scapy/error.py:38].

So the two exact messages are **`No route found (no default route?)`** (no-route case) and
**`Mac address to reach destination not found. Using broadcast.`** (unresolvable-L2 case). The
exception `ScapyNoDstMacException` appears **only** under the non-default `raise_no_dst_mac=True`,
and only on the Q4b surface. The "Using broadcast" warning belongs to Q4b — it does **not** appear
in the Q4a no-route case.

### Mechanism (source-derived — *inferred* from reading; confirmed by the runs below)

- **Route soft-fail:** `Route.route()` [scapy/route.py:146]; when `if not paths:`
  [scapy/route.py:187] it warns only if `verbose` [scapy/route.py:188-189] (route's `verbose`
  defaults to `conf.verb`, which is `2`) and returns `conf.loopback_name, "0.0.0.0", "0.0.0.0"`
  [scapy/route.py:190]. It never raises.
- **Broadcast surface #1 — silent (loopback short-circuit):** in `getmacbyip()`
  [scapy/layers/l2.py:122], `iff, _, gw = conf.route.route(ip)` [scapy/layers/l2.py:131], then
  `if (iff == conf.loopback_name) or (ip in conf.route.get_if_bcast(iff)): return
  "ff:ff:ff:ff:ff:ff"` [scapy/layers/l2.py:132-133] — **no warning**. In the no-route case the route
  has degraded to `lo`, so this branch fires and returns broadcast silently.
- **Broadcast surface #2 — warns or raises (`DestMACField`):** `DestMACField.i2h`
  [scapy/layers/l2.py:166]; when the resolved MAC is `None` [scapy/layers/l2.py:173],
  `if conf.raise_no_dst_mac: raise ScapyNoDstMacException()` [scapy/layers/l2.py:174-175] else
  `x = "ff:ff:ff:ff:ff:ff"` + `warning("Mac address to reach destination not found. Using
  broadcast.")` [scapy/layers/l2.py:176-178].
- **Default gate:** `conf.raise_no_dst_mac = False` [scapy/config.py:910] (docstring
  [scapy/config.py:908-909]); the exception type is `ScapyNoDstMacException` [scapy/error.py:38].

### Cause → effect

The "failure" for a route-less destination is a **soft fallback, not an exception** (by default).
Route resolution degrades to loopback with a warning [scapy/route.py:187-190]; the layer-2
resolution then either short-circuits **silently** to broadcast because the route is loopback
(Q4a, [scapy/layers/l2.py:132-133]) or — when a real route exists but ARP finds no answer — warns
`Using broadcast` and broadcasts (Q4b default, [scapy/layers/l2.py:176-178]). In both default cases
`send()` reports `Sent 1 packets.`. A **hard** failure requires opting in via
`conf.raise_no_dst_mac = True`, which makes the Q4b surface raise `ScapyNoDstMacException`
[scapy/layers/l2.py:174-175]. *(Inferred from the code, not separately exercised: the Q4a no-route
path returns the broadcast MAC via the loopback short-circuit rather than `None`, so
`DestMACField`'s `raise` branch [scapy/layers/l2.py:173-175] is never reached — the no-route case
would not raise even under `raise_no_dst_mac=True`.)*
