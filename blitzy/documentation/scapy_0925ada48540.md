error message is a response to a request that was previously sent. Every
behavioral claim below was produced by **executing the actual Scapy code paths**
(not by reading the source alone), each experiment was run **at least twice** and
confirmed byte‑identical, and the concrete observed output is pasted directly
beneath the command that produced it. Observed facts are kept distinct from any

## Mechanism overview — the two‑stage `SndRcvHandler` match

Scapy's send/receive engine matches replies to requests in **two stages**, and
every protocol layer participates through a uniform `hashret()`/`answers()`
contract defined on the base `Packet` class.

- **Base contract.** `Packet.hashret()` "returns a string that has the same value
  for a request and its answer" and by default recurses into the payload
  (`scapy/packet.py:1215`). `Packet.answers()` is "true if self is an answer from
  other" (`scapy/packet.py:1221`). Each protocol layer overrides these to add its
  own field comparisons.

- **Stage 1 — bucket the sent packets by `hashret()`.** As packets are sent, the
  engine files each one into a hash table keyed by its return hash:
  `self.hsent.setdefault(p.hashret(), []).append(p)` (`scapy/sendrecv.py:244`).
  Because `hsent` is a Python `dict`, this gives **expected/amortized O(1)**
  candidate lookup later (average‑case dict hashing; not a worst‑case guarantee).

- **Stage 2 — for each received packet, hash then confirm.** For every received
  packet `r`, the engine computes `h = r.hashret()` (`scapy/sendrecv.py:276`),
  checks `if h in self.hsent` (`scapy/sendrecv.py:277`) to select the candidate
  bucket, and then confirms each candidate with `if r.answers(sentpkt)`
  (`scapy/sendrecv.py:280`). Only a packet that both lands in the right bucket
  **and** passes `answers()` is recorded as the answer.

The `SndRcvHandler` class that implements this is at `scapy/sendrecv.py:100`. The
crucial consequence for ICMP errors: the received error must produce **the same
`hashret()` as the original request** (so it lands in the request's bucket — this
is Q2), and it must then pass `answers()` (so it is confirmed — this is Q1, Q3, Q4,
Q5). Q6 asks whether loading RFC 4884 extension support disturbs either stage.

**Security caveat — what this matching is, and what it is not.** The `hashret()`/`answers()`
machinery performs **correlation**, not authentication. `hashret()` is only a
**bucket key** for correlating a reply with an outstanding request; it is a plain
(non‑cryptographic) concatenation of header fields and provides no integrity or
authenticity guarantee. Crucially, **the matching path validates no checksum at all.**
Neither `hashret()` nor `answers()` (nor the embedded `IPerror.answers()` and its
recursion) recomputes or compares the **outer IP header checksum**, the **outer ICMP
checksum**, or the **quoted (embedded) IP checksum**: a received error whose every one
of those checksum fields is wrong still buckets and still `answers()` the request
(demonstrated immediately below). Scapy does *retain and dissect* those checksum
fields as ordinary packet data, but it never gates matching on them. The **only**
checksum that gates anything anywhere in this investigation is the **RFC 4884
extension‑structure checksum** inside the Q6 contrib `post_dissection` hook
(`checksum(ieh.build())` at `scapy/contrib/icmp_extensions.py:94`) — and even that
gates only whether the trailing `ICMPExtensionHeader` layer is *attached*, never
whether the error *matches* (Q6). Because ordinary 16‑bit ones'‑complement checksums
are trivially forgeable, they would provide **no authentication** even if they were
checked here. Nothing in this path verifies that the ICMP error genuinely originated
from an on‑path router: an off‑path attacker who can guess the correlated fields can
craft an error that both buckets and `answers()`. That is precisely why the
configuration flags in Q4 (`conf.checkIPsrc`, `conf.check_TCPerror_seqack`) exist —
they *narrow* the acceptance window against forged errors, but they are heuristics,
not authentication.

That the matching path ignores every checksum is **observed**, not merely asserted.
The command below mutates the outer IP, outer ICMP, and quoted‑IP checksums —
individually and all at once — and reparses; `answers()` stays `1` in every case (the
`wrong_embedded_ip` and `all_wrong` rows show the reparsed **outer** ICMP checksum
recomputed by the build step, but the deliberately‑wrong values that survive dissection

### Baseline harness (reused across Q1–Q3 and Q5)

The canonical offline harness builds an ICMP echo request, wraps a **reparsed**
copy of it inside an ICMP destination‑unreachable error, and reparses the whole
error. The reparse `IP(bytes(...))` is mandatory: it forces the embedded copy to be
**dissected** into the `IPerror`/`ICMPerror` classes (rather than staying as raw
build bytes), which is exactly what happens on the live receive path.

```python
from scapy.layers.inet import IP, ICMP, IPerror
req = IP(src="198.51.100.5", dst="192.0.2.1", id=0x1234)/ICMP(id=0xabcd, seq=1)
err = IP(bytes(IP(src="192.0.2.254", dst="198.51.100.5")/ICMP(type=3, code=1)/IPerror(bytes(req))))
```

The addresses are documentation‑range ([RFC 5737](https://www.rfc-editor.org/rfc/rfc5737):
`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`), so nothing here can touch a real
host even if it were run online.

## Q1 — Matching strategy: embedded‑packet field comparison, not re‑hashing

**Direct answer.** Scapy **extracts the embedded copy of the original packet** that
the ICMP error carries inside its payload and **field‑compares** it against the
outstanding request. It does **not** re‑hash arbitrary fields of the error to make
the accept/reject decision. But delegation to the embedded comparator is **not** the
whole story: before it delegates, the outer `IP.answers()` first applies its **own
guards** — most importantly an **outer‑destination check** (active whenever
`conf.checkIPaddr` is `True`, the default) that requires the error's outer `dst` to
equal the request's `src`. Only if that guard passes does `IP.answers()` recognize
the ICMP‑error type set and **delegate** the field comparison to the embedded
packet's own `answers()`.

**Cause → effect mechanism.** When the received packet is reparsed, its layer stack
becomes `IP / ICMP / IPerror / ICMPerror`: the `IPerror` layer is the dissected copy
of the original IP header, and `ICMPerror` is the dissected copy of the original
transport (here, the echo request). `IP.answers()` then runs **in order**: (1) an
IP‑in‑IP short‑circuit governed by `conf.checkIPinIP` (`:584‑592`); (2) a type guard
`if not isinstance(other, IP): return 0` (`:593‑594`); (3) the **outer‑destination
gate** — `if conf.checkIPaddr:` (`:595`) then, for the non‑mDNS case,
`elif (self.dst != other.src): return 0` (`:598‑599`) — which rejects the error
outright if its outer `dst` does not match the request's `src`; and only then (4) the
ICMP‑error detection `self.proto == IPPROTO_ICMP and isinstance(self.payload, ICMP)
and self.payload.type in [3, 4, 5, 11, 12]` (`:600‑602`) that returns
`self.payload.payload.answers(other)` (`:604`) — handing the decision to the embedded
`IPerror` layer (`self.payload` is the `ICMP`, `self.payload.payload` is the
`IPerror`). `IPerror.answers()` then compares the fields of the embedded original
against the request and recurses into the embedded transport. This is why the reparse
`IP(bytes(...))` is mandatory: without it the embedded bytes would not be dissected
into the `IPerror`/`ICMPerror` classes and the delegation target would not exist.

Source excerpt — `IP.answers()` from the outer‑destination gate through the ICMP‑error
delegation (`scapy/layers/inet.py:595‑604`); the gate at `:595‑599` runs **before**
the delegation at `:604`:

```python
        if conf.checkIPaddr:
            if other.dst == "224.0.0.251" and self.dst == "224.0.0.251":  # mDNS  # noqa: E501
                return self.payload.answers(other.payload)
            elif (self.dst != other.src):
                return 0
        if ((self.proto == socket.IPPROTO_ICMP) and
            (isinstance(self.payload, ICMP)) and
                (self.payload.type in [3, 4, 5, 11, 12])):
            # ICMP error message
            return self.payload.payload.answers(other)
```

the top‑level decision ultimately rests on once the delegation is reached.

`bad` error carries a **byte‑identical embedded copy** of the request (its
`IPerror` `src/dst/id/proto` are still `198.51.100.5 / 192.0.2.1 / 0x1234 / 1`, and

pre‑delegation outer‑destination gate at `scapy/layers/inet.py:598‑599` rejects the
error **before** `IP.answers()` ever reaches the delegation at `:604`. So the correct
characterization is: the match is the **embedded field comparison delegated to by
`IPerror.answers()`, but only after `IP.answers()`'s own guards (chiefly the
`conf.checkIPaddr` outer‑destination check) have passed** — not delegation alone.

## Q2 — Hashing (`hashret`): the error hashes identically to the request

**Direct answer.** For an ICMP error, `IP.hashret()` returns
`self.payload.payload.hashret()` — it **strips the outer IP + ICMP headers** and
hashes the **embedded** original instead. Because the embedded original carries the
same `src`/`dst`/`proto` (and the embedded ICMP the same `id`/`seq`) as the request,
the error's `hashret()` is **byte‑identical** to the request's. For the baseline the
observed value is **`0633660401cdab0100`** for both.

**Cause → effect mechanism.** The **request** is not an ICMP error, so its
`IP.hashret()` falls through to the "both checks" branch and returns
`strxor(inet_pton(src), inet_pton(dst)) + struct.pack("B", proto) + payload.hashret()`.
The **error** *is* an ICMP error, so its `IP.hashret()` takes the first branch and
returns the embedded `IPerror.hashret()`, which — being an `IP` subclass — recomputes
that *same* both‑checks expression over the embedded original. Since the embedded
`src`/`dst`/`proto` equal the request's, and the embedded echo `ICMP.hashret()` tail
`struct.pack("HH", id, seq)` equals the request's, the two hashes are equal. That
equality is precisely what lets stage 1 of `SndRcvHandler` drop the received error
into the sent request's bucket.

Byte decomposition of `0633660401cdab0100`:

- `06336604` = `strxor(inet_aton("198.51.100.5"), inet_aton("192.0.2.1"))`
- `01` = `struct.pack("B", proto)` where `proto = IPPROTO_ICMP = 1`
- `cdab0100` = `struct.pack("HH", id=0xabcd, seq=1)` — little‑endian, so `0xabcd`
  serializes as `cdab` and `seq=1` as `0100`

Source excerpt — `IP.hashret()` (`scapy/layers/inet.py:568‑581`); the ICMP‑error
branch is at `:572`, the both‑checks branch at `:577‑580`:

```python
    def hashret(self):
        if ((self.proto == socket.IPPROTO_ICMP) and
            (isinstance(self.payload, ICMP)) and
                (self.payload.type in [3, 4, 5, 11, 12])):
            return self.payload.payload.hashret()
        if not conf.checkIPinIP and self.proto in [4, 41]:  # IP, IPv6
            return self.payload.hashret()
        if self.dst == "224.0.0.251":  # mDNS
            return struct.pack("B", self.proto) + self.payload.hashret()

                           inet_pton(socket.AF_INET, self.dst)) +
                    struct.pack("B", self.proto) + self.payload.hashret())

```

## Q3 — Modified embedded packet: a changed TTL or checksum still matches

**Direct answer.** **Yes, it still matches.** A subtly modified embedded copy — for
example a changed **TTL** or a changed **IP checksum** — does **not** break the match,
because `IPerror.answers()` compares **only** `src`, `dst`, `id`, and `proto`. It
never inspects `ttl` or `chksum`, so mutating those fields cannot flip the decision.

**Cause → effect mechanism.** `IPerror.answers()` computes exactly four boolean tests
— `test_IPsrc`, `test_IPdst`, `test_IPid`, `test_IPproto` — combines them with a
single `and`, and if they all hold, recurses into the embedded transport. `ttl` and
`chksum` are simply not among the compared fields, so any value they carry is
irrelevant to matching.

Source excerpt — the **complete** `IPerror.answers()` (`scapy/layers/inet.py:1016‑1034`):

```python
    def answers(self, other):
        if not isinstance(other, IP):
            return 0

        # Check if IP addresses match
        test_IPsrc = not conf.checkIPsrc or self.src == other.src
        test_IPdst = self.dst == other.dst

        # Check if IP ids match
        test_IPid = not conf.checkIPID or self.id == other.id
        test_IPid |= conf.checkIPID and self.id == socket.htons(other.id)

        # Check if IP protocols match
        test_IPproto = self.proto == other.proto

        if not (test_IPsrc and test_IPdst and test_IPid and test_IPproto):
            return 0

        return self.payload.answers(other.payload)
```

**Exact `file:line` grounding.** `IPerror.answers` `scapy/layers/inet.py:1016`;
`test_IPsrc` `:1021`; `test_IPdst` `:1022`; `test_IPid` `:1025‑1026`; the comment
`# Check if IP protocols match` `:1028`; `test_IPproto` `:1029`; the combined guard
`:1031`; the recurse into the embedded transport `:1034`. The established regression
pattern deliberately builds the embedded original with `ttl=0` (a value different
from the request's) and still asserts a match: `test/scapy/layers/inet.uts:505‑506`
(with the `TCPerror` and `ICMPerror` siblings at `:509`/`:511` and `:514`/`:515`).

*(Contextual, not observed here.)* The practical value of this tolerance is a
**contextual rationale**, not something measured by the experiment above: in
real deployments the fields Scapy ignores are exactly the ones most likely to differ
between the datagram a host sent and the copy quoted back inside an error — a router
that generates the error will have decremented the datagram's TTL, and the quoted
checksum need not match a freshly recomputed one. Because Scapy compares neither
field, such benign variation does not defeat the match. This paragraph is offered as
**inferred/contextual** explanation of *why* the comparison surface is narrow; the
experiment itself only demonstrates that changing `ttl`/`chksum` does not change the
`answers()` result.

**Isolating each field, and the negative controls (run ≥2×).** The experiment above
changes `ttl` and `chksum` together, so on its own it cannot say whether *either* field
individually matters. The next experiment mutates **one field at a time**. The two
isolated cases hold every *other* compared field equal to the request — the TTL‑only case
even pins the embedded `chksum` to the request's own value, so `ttl` is the sole
difference, and the checksum‑only case keeps `ttl=64` so `chksum` is the sole difference.

`proto`, and — under `conf.checkIPID=True` — `id`), and a final control repeats the wrong

## Q4 — Configuration toggles: `conf.checkIPsrc` and `conf.check_TCPerror_seqack`

**Direct answer.** **Yes, both toggles change which packets are accepted.**
`conf.checkIPsrc` (default **`True`**) gates the embedded **source‑address** check in
`IPerror.answers()` and the **port** checks in `TCPerror.answers()` and
`UDPerror.answers()`. `conf.check_TCPerror_seqack` (default **`False`**) controls
whether the embedded TCP **sequence/acknowledgement** numbers are verified — by
default they are **not**. Relaxing these flags widens acceptance (tolerates
real‑world NAT/stack mangling); tightening them narrows the acceptance window against
forged / off‑path ICMP errors (the threat model of
[RFC 5927](https://www.rfc-editor.org/rfc/rfc5927), *ICMP Attacks against TCP*).

**Cause → effect mechanism.** In `IPerror.answers()` the source test is
`test_IPsrc = not conf.checkIPsrc or self.src == other.src` — when `checkIPsrc` is
`False`, `not conf.checkIPsrc` short‑circuits the whole test to `True`, so a wrong
embedded source is tolerated. In `TCPerror.answers()` and `UDPerror.answers()` the
`sport`/`dport` comparison is wrapped in `if conf.checkIPsrc:`, and in
`TCPerror.answers()` the `seq`/`ack` comparison is separately wrapped in
`if conf.check_TCPerror_seqack:`.

Source excerpt — the **complete** `TCPerror.answers()` (`scapy/layers/inet.py:1043‑1057`):

```python
class TCPerror(TCP):
    name = "TCP in ICMP"

    def answers(self, other):
        if not isinstance(other, TCP):
            return 0
        if conf.checkIPsrc:
            if not ((self.sport == other.sport) and
                    (self.dport == other.dport)):
                return 0
        if conf.check_TCPerror_seqack:
            if self.seq is not None:
                if self.seq != other.seq:
                    return 0
            if self.ack is not None:
                if self.ack != other.ack:
                    return 0
        return 1
```

Source excerpt — the **complete** `UDPerror.answers()` (`scapy/layers/inet.py:1066‑1073`):

```python
class UDPerror(UDP):
    name = "UDP in ICMP"

            return 0

                    (self.dport == other.dport)):
```

For completeness, the third sibling `ICMPerror.answers()`
(`scapy/layers/inet.py:1082‑1095`) is **not** gated by these flags at all: it always
compares `type` and `code` (`scapy/layers/inet.py:1085‑1086`), and then — only when the
literal condition `self.code in [0, 8, 13, 14, 17, 18]` holds
(`scapy/layers/inet.py:1088`) — additionally compares `id` and `seq`. That list is a
literal test of the **`code`** field; it must **not** be conflated with the separate
module‑level constant `icmp_id_seq_types = [0, 8, 13, 14, 15, 16, 17, 18, 37, 38]`
(`scapy/layers/inet.py:949`), which is a *different* set of values tested against the
**`type`** field inside `ICMP.hashret()` (`scapy/layers/inet.py:987`). In other words,
one list gates the id/seq *comparison* in `ICMPerror.answers()` (over `code`), the other
gates the id/seq *hash contribution* in `ICMP.hashret()` (over `type`). (The `ICMPerror`
comparator is the one exercised by the Q1/Q2 echo baseline, whose embedded `ICMPerror`
carries `code == 0` and therefore takes the `id`/`seq` branch.)

The relevant configuration defaults and their motivating comments are in the
network‑defaults block of `scapy/config.py`:

```python

    #: equals (bug in some IP stacks)

    #: if 1, checks IP src in IP and ICMP IP citation match
    #: (bug in some NAT stacks)

    #: not check IP layers that encapsulates another IP layer
```

"bug in some NAT stacks" that rewrites the embedded source, and
`check_TCPerror_seqack` optionally adds the stricter "also check that TCP seq and ack
match the ones in ICMP citation".

- **(a)** A wrong embedded source is **rejected** under the default `checkIPsrc=True`
  (`0`) but **accepted** once `checkIPsrc=False` (`1`).
- **(b)** A `TCPerror` whose embedded `seq`/`ack` differ is **accepted** under the
  default `check_TCPerror_seqack=False` (`1`) but **rejected** once it is set `True`
  (`0`). Separately, a wrong `TCPerror` **port** is rejected under `checkIPsrc=True`
  (`0`) and accepted under `checkIPsrc=False` (`1`); the reparsed layer stack
  confirms this went through the `TCPerror` sibling (`et.layers()` ends in
  `TCPerror`).
- **(c)** The `UDPerror` sibling behaves the same for ports: rejected under
  `checkIPsrc=True` (`0`), accepted under `checkIPsrc=False` (`1`);
  `eu.layers()` ends in `UDPerror`.

**Trade‑off.** The default posture (`checkIPsrc=True`, `check_TCPerror_seqack=False`)
is a deliberate middle ground: validate the embedded source address and ports (which
defeats trivially off‑target forgeries) while tolerating `seq`/`ack` variation (which
avoids dropping a legitimate error if a middlebox rewrote TCP state). Loosening with
`checkIPsrc=False` deliberately tolerates NAT source rewriting at the cost of accepting
more forgeries.

Tightening with `check_TCPerror_seqack=True` narrows the acceptance window in a way that
is **directionally related** to the threat model of RFC 5927 (*ICMP Attacks against
TCP*), whose §4.1 observes that validating the quoted TCP sequence number shrinks the
window an off‑path attacker has to land a forged ICMP error. The relationship must be
stated precisely, however: RFC 5927 §4.1 describes an **in‑window** check — accept the
quoted segment only if its sequence number falls inside the send window
(`SND.UNA =< SEG.SEQ < SND.NXT`), i.e. a *range* test — whereas Scapy's
`check_TCPerror_seqack=True` performs an **exact‑equality** test on both `seq` **and**
`ack` (`self.seq != other.seq` / `self.ack != other.ack`, `scapy/layers/inet.py:1052`,
`scapy/layers/inet.py:1055`). Scapy's exact‑equality behavior is therefore an
*implementation‑specific tightening* that is stricter than, and distinct from, the
algorithm RFC 5927 recommends; it is **not** the RFC's recommended check, and this
document makes no claim of RFC 5927 conformance. (Inferred, from comparing the RFC's
stated in‑window algorithm against Scapy's observed exact‑equality code: the two share
the goal of narrowing the off‑path forgery window but do not implement the same test.)

**Isolating destination port, and sequence vs acknowledgement (run ≥2×).** Experiment

## Q5 — Byte‑swapped IP ID tolerance: `conf.checkIPID` and `socket.htons`

**Direct answer.** The alternative accepted ID equals **`socket.htons(other.id)`** —
a **16‑bit byte swap** of the request's ID — and that alternative is **only consulted
when `conf.checkIPID` is truthy**. With the **default `conf.checkIPID = False`, the
ID is not checked at all** (any ID matches). This is exactly why a byte‑swapped ID is
"sometimes still a match": under the default it matches because the ID is **ignored**,
and under `checkIPID=True` it matches specifically via the **`htons` byte‑swap**
branch. For `id=0x1234` the accepted swapped value is `socket.htons(0x1234) == 0x3412`.

**Cause → effect mechanism.** The ID test in `IPerror.answers()` is exactly two lines
(`scapy/layers/inet.py:1025‑1026`):

```python
        test_IPid = not conf.checkIPID or self.id == other.id
        test_IPid |= conf.checkIPID and self.id == socket.htons(other.id)
```

- When `checkIPID=False`: line `:1025` is `not False or …` → `True`, so `test_IPid`
  is `True` regardless of the ID. Line `:1026` adds `False and …` → `False`, leaving
  `test_IPid` `True`. **The ID is effectively ignored.**
- When `checkIPID=True`: line `:1025` reduces to `self.id == other.id`; line `:1026`
  ORs in `self.id == socket.htons(other.id)`. So the ID matches **iff** it is equal
  **or** byte‑swapped.

The configuration comment (`scapy/config.py:745‑747`) documents this as tolerating a
"byte swapped equals (bug in some IP stacks)".

**Observed edge finding (report precisely).** The comment at `scapy/config.py:747`
says "if 2, strictly checks that they are equals", but the code does **not**
implement a strict‑only mode. With `conf.checkIPID = 2`, the expression
`conf.checkIPID and self.id == socket.htons(other.id)` evaluates as
`2 and X` → `X`, so the byte‑swap branch is **still active**. Consequently
`checkIPID=2` behaves **identically to `checkIPID=True`**, not more strictly. This is
an **observed discrepancy** between the config comment and the runtime behavior
(demonstrated by the `checkIPID=2` column in the output below).

**Endianness caveat (labeled inferred).** The test host is little‑endian
(`sys.byteorder == 'little'`), so `socket.htons(0x1234) == 0x3412` is a genuine byte
swap — this is **observed**. On a **big‑endian** host `socket.htons()` is the
**identity** function, so the "byte‑swap" branch would collapse into a plain equality
check and add nothing. That big‑endian behavior is **inferred** (a portability
caveat); it was **not** observed on this host because no big‑endian host was
available.

**Exact `file:line` grounding.** `test_IPid` `scapy/layers/inet.py:1025‑1026` (the
`socket.htons` branch specifically at `:1026`); `conf.checkIPID = False`
`scapy/config.py:748` (three‑line semantics comment `:745‑747`).

**Verbatim command (run ≥2×)** — feeds the **same** three inputs (a byte‑swapped ID,
an unrelated ID, and the exact ID) under **all three** `checkIPID` settings, and

## Q6 — RFC 4884 extension parsing: does loading it change the match?

**Direct answer.** Loading Scapy's [RFC 4884](https://www.rfc-editor.org/rfc/rfc4884)
support **does change the dissected
packet structure** — when the ICMP type is in `[3, 11, 12]` and the IP length is
`> 144`, `ICMPExtension_post_dissection()` **keeps the trailing `Padding` layer but
shortens its `.load`** (removing the extension bytes) and **attaches the parsed
`ICMPExtensionHeader` as that `Padding` layer's payload**. **For a well‑formed (or
absent) extension candidate it does NOT change whether the error matches the original.**
When the trailing region is a valid, checksum‑complete extension — or is empty — the
restructuring only rewrites the **trailing padding of the last layer** (its `load` and
its payload), never the **embedded original IP header/transport** that `IPerror.answers()`
(and its recursion) compares, so `err.answers(req) == 1` both **before** and **after** the
parser is loaded (**observed, not assumed**). **There is, however, one edge case where
loading the parser *does* change the outcome:** if the candidate region is **malformed —
present, of an eligible ICMP type, and `pkt.len > 144`, but too short to dissect as an
`ICMPExtensionHeader`** — then loading the parser makes **dissection itself raise**
(`struct.error: unpack requires a buffer of 2 bytes`), so the received error never finishes
dissecting and can therefore no longer be matched at all. The unqualified reading — that
"loading the parser can never affect matching" — is thus **false in general**; the precise
statement is that it never affects matching for **well‑formed or absent** extensions, and
the only way it can matter is by **aborting dissection** of a **malformed** one. Experiment
**(8)** below reproduces this counter‑case and traces its cause.

**Cause → effect mechanism.** The contrib module installs `ICMPExtension_post_dissection`
as the `post_dissection` hook on the embedded‑error classes `ICMPerror`, `TCPerror`,
and `UDPerror` (and on the IPv6 error layers). During dissection the hook: (1) returns
immediately unless the last layer is padding; (2) requires `IP in pkt`, an `ICMP`
whose `type` is in `[3, 11, 12]`, and `pkt.len > 144`; (3) reads the candidate
extension bytes as `pkt[ICMP].build()[136:]`; (4) validates the extension checksum;
and (5) only if valid, **shortens** the trailing padding layer's `load` (via
`lastlayer.load = lastlayer.load[:-len(ieh)]`, `scapy/contrib/icmp_extensions.py:97`)
and **attaches** the parsed `ICMPExtensionHeader` as that same, retained padding
layer's payload (via `lastlayer.add_payload(ieh)`, `:98`). The padding layer itself is
**not removed** — only its `load` shrinks and it gains a payload. The embedded original
(already dissected earlier into `IPerror`/`UDPerror`/…) is left completely untouched,
so `answers()` sees the same fields as before.

Source excerpt — the **complete** `ICMPExtension_post_dissection()`
(`scapy/contrib/icmp_extensions.py:67‑98`):

```python
def ICMPExtension_post_dissection(self, pkt):
    # RFC4884 section 5.2 says if the ICMP packet length
    # is >144 then ICMP extensions start at byte 137.

    lastlayer = pkt.lastlayer()
    if not isinstance(lastlayer, conf.padding_layer):
        return

    if IP in pkt:
        if (ICMP in pkt and
            pkt[ICMP].type in [3, 11, 12] and
                pkt.len > 144):
            bytes = pkt[ICMP].build()[136:]
        else:
            return
    elif scapy.layers.inet6.IPv6 in pkt:
        if ((scapy.layers.inet6.ICMPv6TimeExceeded in pkt or
             scapy.layers.inet6.ICMPv6DestUnreach in pkt) and
                pkt.plen > 144):
            bytes = pkt[scapy.layers.inet6.ICMPv6TimeExceeded].build()[136:]
        else:
            return
    else:
        return

    # validate checksum
    ieh = ICMPExtensionHeader(bytes)
    if checksum(ieh.build()):
        return  # failed

    lastlayer.load = lastlayer.load[:-len(ieh)]
    lastlayer.add_payload(ieh)
```

**Precise‑wording note (offset vs threshold — two distinct numbers).**

*Offset (accurate as written).* The comment at `scapy/contrib/icmp_extensions.py:68‑69`
says extensions "start at byte 137", and the actual slice at `:79` is `[136:]`
(0‑indexed) — i.e. the 137th octet counting from 1. Offset 136 = 8‑byte ICMP header +
128‑byte quoted "original datagram", which matches RFC 4884's 128‑octet minimum for
that quoted datagram. This offset is correct and consistent with the RFC.

*Threshold (Scapy is looser than the RFC — do not equate them).* RFC 4884's own
"no‑extensions" rule is stated over the **ICMP payload**: if the ICMP payload is
**144 octets or more**, the 137th octet must be examined for a valid Extension Header.
That 144 decomposes as **8** (the first two words of the ICMPv4 message) **+ 128** (the
"original datagram" field) **+ 4** (the 4‑byte ICMP Extension Header) **+ 4** (the
4‑byte minimum ICMP Object header) **= 144** — it does **not** double‑count the leading
words. Because the RFC measures the **ICMP payload**, a 20‑byte IPv4 header puts the
corresponding **total IP length at ≈ 164**. Scapy, however, tests `pkt.len > 144` at
`:78`, and `pkt.len` is the **total IP length** (it *includes* the 20‑byte IP header),
**not** the ICMP‑payload length. Scapy's guard is therefore a **looser, simpler**
approximation that trips roughly 20 octets *earlier* than the RFC's ICMP‑payload
threshold; the two thresholds must **not** be equated. (Scapy's own comment at `:68‑69`
loosely says "the ICMP packet length is >144", but the code compares total IP length.)

**Observed finding — a naive extension header is rejected (shown through dissection).**
A naively built `ICMPExtensionHeader()/ICMPExtensionMPLS()` is **not** accepted, because
`ICMPExtensionHeader.post_build` (`scapy/contrib/icmp_extensions.py:44‑48`) computes
its checksum over only its own 4‑byte header, whereas the `post_dissection` hook
validates the checksum over the **whole** extension structure (`checksum(ieh.build())`
at `:94`, returning early at `:94‑95` on a nonzero result). So
`checksum(bytes(ICMPExtensionHeader(version=2)/ICMPExtensionMPLS(classnum=1,classtype=1)))`
is nonzero (`0xfefa`) and the hook returns early without attaching anything. To
construct a **valid** RFC 4884 error, the header `chksum` must be set so the
whole‑structure checksum is zero (`0xdefa` here → extension bytes `2000defa00040101`).
This is **not merely asserted** from the build‑time checksum: experiment **(4)** below
feeds **both** the valid and the naive error **through `post_dissection`** with the
contrib loaded and observes that the naive one is left unparsed
(`ICMPExtensionHeader present = False`, last layer `Padding`) while the valid one is
parsed (`present = True`, last layer `ICMPExtensionMPLS`) — and, crucially,
`answers()` is `1` for **both**.

**Exact `file:line` grounding.** `ICMPExtensionHeader`
`scapy/contrib/icmp_extensions.py:36`; `ICMPExtensionHeader.post_build` `:44‑48`;
`ICMPExtension_post_dissection` `:67` (guard `pkt.len > 144` `:78`, offset `[136:]`
`:79`, restructure `:97‑98`); the `post_dissection` monkey‑patch onto
`ICMPerror`/`TCPerror`/`UDPerror` at `:176‑178` (and onto the IPv6
`ICMPv6DestUnreach`/`ICMPv6TimeExceeded` at `:180‑181`); `bind_layers` `:186‑187`.
The comparator that is left unaffected is `IPerror.answers`
`scapy/layers/inet.py:1016‑1034`. The established build pattern for the extension
header is `test/contrib/icmp_extensions.uts:3‑8`.

**Cause and effect (the counter‑case).** Before the contrib is loaded there is no
`post_dissection` hook, so the truncated trailing bytes stay as `Raw`/`Padding`, the packet
dissects cleanly, and `answers()` returns `1` (the BEFORE rows). After the contrib is
imported the hook runs *during* dissection: `pkt.len > 144` and the type is eligible, so it
slices `pkt[ICMP].build()[136:]` (`scapy/contrib/icmp_extensions.py:79`) — here only 1 or 3
bytes — and calls `ICMPExtensionHeader(bytes)` (`:93`). That constructor's `BitField`
unpack (`scapy/fields.py:2332`, `struct.unpack('!%dB', ...)`) needs more bytes than are
present and raises `struct.error: unpack requires a buffer of 2 bytes`. The exception
propagates out of dissection, so `IP(...)` never returns a packet and `answers()` is never
even called. This is the precise, **observed** sense in which loading the parser **can**
change matching: not by altering a comparison, but by **aborting the dissection** of a
malformed error so that a would‑be match (seen in the BEFORE rows) can no longer occur.

**Interpretation.** After the extension parser is loaded, the dissected layer list
gains `ICMPExtensionHeader` / `ICMPExtensionMPLS`; the trailing `Padding` layer is
**retained** (its `load` shrinks from 8 bytes to 0 and it gains the
`ICMPExtensionHeader` as its payload — experiment (5)), whereas before loading it ends
in `Raw`/`Padding` with an 8‑byte `load` and no payload. Yet `err6.answers(req6)` is
`1` in **both** cases, and `1` for the **naive** (rejected‑extension) error in
experiment (4) as well. The conclusion — **observed, not assumed** — is that RFC 4884
restructuring is **orthogonal** to request/response matching: the hook only rewrites
the trailing padding layer of the packet (shortening its `load` and giving it a
payload) and never touches the embedded original (`IPerror`/`UDPerror`) that
`IPerror.answers()` and its recursion compare. For a **well‑formed or absent** extension,
loading the extension parser therefore cannot change whether an error is recognized as the
answer. The **sole exception** is a **malformed** candidate (`pkt.len > 144`, eligible ICMP
type, but too short to dissect) whose presence makes the `post_dissection` hook **raise**,
aborting dissection so the received error can no longer be matched at all — reproduced in
experiment (8). Together, the boundary experiment (6), the eligible‑type sweep (7), and the
malformed counter‑case (8) delimit exactly when loading the parser is (well‑formed/absent)
and is not (malformed) orthogonal to matching.
