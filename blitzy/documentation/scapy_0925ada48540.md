# How Scapy Decides Where to Send Packets — An Evidence-Backed Investigation

## Overview

This document onboards to the [Scapy](https://github.com/secdev/scapy) packet-manipulation
library directly from the in-repo checkout and empirically answers five questions about **how
Scapy decides where to send a packet** — which interface it picks, which MAC address it targets,
what happens on a repeated send, and where/how a send fails when there is no route.

Every behavioural claim is backed by output captured by **running the real code path on the
canonical host runtime** — Scapy imported directly from this in-repo checkout — together with the
exact command that produced it. The document is organised as one section per question (Q0–Q4) and
closes with a coverage pass.

### Task

Answer, with observed runtime evidence, the following:

- **Q0** — Set up and run Scapy from the repository and start the interactive session.
- **Q1** — When no interface is specified, how does Scapy choose the outgoing interface?
- **Q2** — Once an interface is chosen, how does Scapy know which MAC address to send to in order
  to reach an **external (off-link)** destination?
- **Q3** — If the **same packet is sent twice** in quick succession, is an ARP request emitted on
  both sends, or only once (a cache hit)?
- **Q4** — For a destination with **no route**, at what point does the send fail, and what is the
  exact error message?

## Q1 — How Scapy chooses the outgoing interface

**Question.** When you call `send(pkt)` without naming an interface, how does Scapy figure out which
interface to use?

### Mechanism: the interface is *derived from the route to the destination*

`send()` [scapy/sendrecv.py:422] does **not** fall back to a fixed default interface. When the caller
does not pass `iface`, it delegates the choice to the helper `_interface_selection(iface, packet)`
[scapy/sendrecv.py:616], whose logic is:

- If the caller *did* pass an interface, it is used verbatim — `return iface` [scapy/sendrecv.py:631].
- Otherwise (`iface is None` [scapy/sendrecv.py:624]) the interface is computed from the **packet's own
  route**: `iff = next(packet.__iter__()).route()[0]` [scapy/sendrecv.py:626], returning
  `iff or conf.iface` [scapy/sendrecv.py:629] — i.e. the route's interface, falling back to
  `conf.iface` *only* if the packet cannot supply one.

`next(packet.__iter__())` yields the concrete packet and `.route()` is `IP.route()`
[scapy/layers/inet.py:559], which delegates to the routing table — `return conf.route.route(dst)`
[scapy/layers/inet.py:566]. `Route.route()` [scapy/route.py:146] performs a **longest-prefix match**
over `conf.route.routes` and returns the 3-tuple `(interface, outgoing_ip, gateway)`; element `[0]` of
that tuple is exactly the interface `_interface_selection` hands back. (Scapy's own manual describes this
routing table as the basis for interface selection — `doc/scapy/routing.rst:54`.)

So the answer is: **the interface is not a fixed default — it is a derived value, the interface of the
longest-prefix route to the destination**, and `conf.iface` is only the last-resort fallback.

- `conf.route.route("8.8.8.8")` returns `('eth0', '10.236.7.5', '10.236.7.1')` — the longest-prefix match
  for `8.8.8.8` is this host's default route, whose interface is `eth0`, whose chosen source IP is
  `10.236.7.5`, and whose next hop (gateway) is `10.236.7.1`. **Effect:** the *route* — not a hard-coded
  default — names the interface.
- `pkt.route()` returns the identical tuple, confirming `IP.route()` → `conf.route.route(dst)` is the
  same lookup `_interface_selection` uses. **Effect:** the packet and the helper agree on `eth0`.
- `_interface_selection(None, pkt)` returns `'eth0'` — element `[0]` of that route tuple. Because it is
  non-empty, the `iff or conf.iface` fallback [scapy/sendrecv.py:629] never needs `conf.iface`.
  **Effect:** the interface used for an unspecified-interface `send()` to `8.8.8.8` is `eth0`.
- `send(pkt)` prints `.` (one packet queued) then `Sent 1 packets.` — the packet is transmitted on the
  derived interface without the caller ever naming it.


## Q2 — How Scapy determines the MAC to send to (external destination)

**Question.** Once the interface is chosen, how does Scapy know *which MAC address* to put in the
Ethernet frame to reach an **external / off-link** destination such as `8.8.8.8`?

### Mechanism: resolve the *next hop* (the gateway), not the final destination

To transmit an IP packet the Linux L3 socket must build an Ethernet header. `L3PacketSocket.send()`
[scapy/arch/linux.py:598] selects the interface from the route [scapy/arch/linux.py:600] and prepends
the link-layer header via `conf.l2types.num2layer[...]() / x` [scapy/arch/linux.py:611]. Building that
`Ether` header asks the registered **L3 resolver** for the destination MAC: `inet_register_l3(l2, l3)`
returns `getmacbyip(l3.dst)` [scapy/layers/inet.py:1125-1126], wired for `Ether`/`Dot3` over `IP` at
[scapy/layers/inet.py:1129-1130]. (`conf.L3socket` is `L3PacketSocket` on Linux
[scapy/config.py:647].)

`getmacbyip(ip)` [scapy/layers/l2.py:122] performs the resolution:

1. Look up the route — `iff, _, gw = conf.route.route(ip)` [scapy/layers/l2.py:131].
2. Short-circuit loopback / on-link broadcast to `ff:ff:ff:ff:ff:ff` [scapy/layers/l2.py:132-133].
3. **If the route has a non-zero gateway, substitute the gateway IP for the destination:**
   `if gw != "0.0.0.0": ip = gw` [scapy/layers/l2.py:134-135]. This is the decisive step for an external
   destination — everything after this ARPs for the *gateway*, not for `8.8.8.8`.
4. Consult the ARP cache [scapy/layers/l2.py:137-139]; on a miss, issue
   `srp1(Ether(dst=ETHER_BROADCAST)/ARP(op="who-has", pdst=ip), iface=iff, …)`
   [scapy/layers/l2.py:141-148] and store the reply's `hwsrc` under that (gateway) IP
   [scapy/layers/l2.py:152-155].

So an off-link host is **never** ARPed directly (it is not on the local segment and could not answer);
Scapy resolves the **next hop** and addresses the frame to the gateway's MAC, while the IP header still
carries the final destination `8.8.8.8`.

### Observed (self-contained, writes no files)

The block flushes the ARP cache (so a real `who-has` is emitted), sniffs ARP with a **Python-level**
predicate (`lfilter=lambda p: ARP in p` — no BPF string, hence no `libpcap` filter error), then calls
`getmacbyip("8.8.8.8")` inside a `try/finally` that always stops the sniffer:

## Q3 — Sending the same packet twice: is ARP re-issued, or is it a cache hit?

**Question.** If the *same* packet is sent twice in quick succession, is an ARP request emitted on both
sends, or only once because of a cache hit?

### Mechanism: a 120-second ARP cache short-circuits the second resolution

The gateway MAC that Q2 resolved is stored in `_arp_cache`, created with a **120-second TTL**:
`# cache entries expire after 120s` [scapy/layers/l2.py:117] / `_arp_cache =
conf.netcache.new_cache("arp_cache", 120)` [scapy/layers/l2.py:118] (a `CacheInstance`
[scapy/config.py:347]). Inside `getmacbyip`, before any ARP is sent, the cache is consulted:
`mac = _arp_cache.get(ip); if mac: return mac` [scapy/layers/l2.py:137-139]. Only on a miss is the
`who-has` issued [scapy/layers/l2.py:141-148] and the reply stored `_arp_cache[ip] = mac`
[scapy/layers/l2.py:152-155]. So the **first** send resolves-and-caches the gateway MAC and the
**second** send (within the 120 s TTL) takes the cache-hit path and emits **no** ARP.

### Observed (self-contained, writes no files)

The block flushes the cache, sniffs gateway `who-has` requests with a Python-level predicate, and sends
`IP(dst="8.8.8.8")/ICMP()` N times (`verbose=0` to keep the output focused on ARP counts). It runs the
`N=2` case in detail, repeats `N=2` five times to report the distribution, and finishes with one `N=10`
run:

```
PYTHONPATH=. python3 -u - <<'PY' 2>&1 | sed 's/\x1b\[[0-9;]*m//g; s/[[:space:]]*$//'

            print("  after send#%d: who-has(gw) so far=%d ; cache.get(gw)=%r"
                  % (i + 1, len(frames), _arp_cache.get(GW)))

print("=== N=2 stability: 5 runs, distribution of total who-has(gw) ===")

### Reasoning (cause → effect) — confirmed at runtime

`CacheInstance` splits *where it stores* an entry from *where it enumerates* entries:

- **Store / retrieve use the base `dict`.** `__setitem__` writes through `super().__setitem__(item, v)`
  and records a timestamp in `_timetable` [scapy/config.py:384-389]; `get()`/`__getitem__` read back
  through `super().__getitem__` with a TTL check [scapy/config.py:364-382]; membership (`in`) uses the
  inherited `dict.__contains__`. All three therefore *see* the entry — the storage-split evidence proves
  it: `dict.__len__(_arp_cache) = 1`, `dict.keys(...) = ['10.236.7.1']`, and
  `_arp_cache._timetable = ['10.236.7.1']`.
- **Enumeration reads `self.__dict__` instead.** `keys()` [scapy/config.py:446-451], `items()`
  [scapy/config.py:436-444], `iterkeys()` [scapy/config.py:413-420] and `__iter__()`
  [scapy/config.py:422-424] all iterate `self.__dict__`, which is `{}` (the entry was never written
  there). `dict(_arp_cache)` calls `keys()`, so it is `{}` too.
- **`len()` follows the enumeration path.** With a non-`None` timeout, `__len__` returns
  `len(self.keys())` [scapy/config.py:463-467] — hence `len(_arp_cache) = 0` even though
  `dict.__len__(...) = 1`.

**Effect:** the cache genuinely holds the gateway MAC (which is exactly why Q3's second send is a cache
hit), but the human-facing enumeration API under-reports it. State must therefore be inspected with
`.get(key)` or `key in cache`, never with `len()`/`dict()`/`keys()`. (The Agent Action Plan flagged this
as *inferred* from reading `CacheInstance`; the storage-split block above **confirms it at runtime**.)


## Q4 — What happens when there is no route to the destination?

**Question.** At what point does a send to a destination with **no route** fail, and what is the exact
error message? This has two distinct sub-cases, both answered below: (Q4a) no route matches at all, and
(Q4b) a route exists but the destination MAC cannot be resolved.

The headline answer: **with Scapy's defaults, a no-route send does not raise at all** — it emits a
*warning* and degrades to a fallback (loopback for routing, broadcast for the L2 address), and `send()`
still reports `Sent 1 packets.`. An actual exception (`ScapyNoDstMacException`) is only raised when the
non-default `conf.raise_no_dst_mac = True` is set (Q4b).

> **Both experiments mutate `conf.route` only in memory and restore it in a `finally` block** (with an
> assertion that the table returns to 5 routes). Scapy builds `conf.route.routes` from the OS table at
> import via `read_routes()`; these scripts never touch `/proc/net/route` or run `ip route`, so the OS
> table is untouched and any fresh process re-reads the real 5-route table regardless.

### Q4a — No route at all: a soft fallback to loopback, not an exception

**Mechanism.** `Route.route()` [scapy/route.py:146] collects candidate paths by longest-prefix match. If
none match, it does **not** raise — it warns and returns loopback:
`if not paths: if verbose: warning("No route found (no default route?)")` then
`return conf.loopback_name, "0.0.0.0", "0.0.0.0"` [scapy/route.py:187-190]. So the "failure" surfaces as
a warning plus a loopback 3-tuple, and the send proceeds from there.

**Observed (self-contained, writes no files).** The block snapshots the routing table, removes the
default route through Scapy's own API so `8.8.8.8` has no match, calls `route()` and `send()`, and always
restores the table in `finally`:

```

### Q4b — A route exists but the MAC is unresolvable: broadcast vs `ScapyNoDstMacException`

**Mechanism.** When a next hop is on-link but never answers ARP, `getmacbyip` returns `None`, and the
Ethernet `DestMACField.i2h` [scapy/layers/l2.py:166] hits its unresolved branch: after
`conf.neighbor.resolve(...)` yields `None` [scapy/layers/l2.py:170], `if x is None:`
[scapy/layers/l2.py:173] chooses between two behaviours —
`if conf.raise_no_dst_mac: raise ScapyNoDstMacException()` [scapy/layers/l2.py:174-175] **else**
`x = "ff:ff:ff:ff:ff:ff"; warning("Mac address to reach destination not found. Using broadcast.")`
[scapy/layers/l2.py:176-178]. The gate `conf.raise_no_dst_mac` defaults to `False`
[scapy/config.py:908-910]; `ScapyNoDstMacException` is defined at [scapy/error.py:38].

**Reasoning (cause → effect).**

- After the added route, `route('192.0.2.254')` is `('eth0', '10.236.7.5', '0.0.0.0')` — a **route exists**
  and it is **on-link** (gateway `0.0.0.0`), so `getmacbyip` ARPs `192.0.2.254` *directly* (no gateway
  substitution). Because TEST-NET-3 has no host, the ARP goes unanswered and `getmacbyip` returns
  `None`.
- With the **default** `conf.raise_no_dst_mac = False`, the unresolved branch takes the `else`:
  `DestMACField` substitutes the broadcast MAC and emits the **exact message**
  `WARNING: Mac address to reach destination not found. Using broadcast.` [scapy/layers/l2.py:176-178];
  `send()` then reports `Sent 1 packets.` and **does not raise** (`send raised? = None`).
- With `conf.raise_no_dst_mac = True`, the same unresolved branch instead executes
  `raise ScapyNoDstMacException()` [scapy/layers/l2.py:174-175]; the send raises
  `ScapyNoDstMacException` (`isinstance … = True`). **This is the only configuration in which a
  send actually fails with an exception.**
- The `finally` block restored the table to 5 routes and the flag to `False`, and
  `route('8.8.8.8')` returns `('eth0', '10.236.7.5', '10.236.7.1')` again — identical to the Q1 baseline,
  proving the experiment is fully reversible.
